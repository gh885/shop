# cart — 选购暂存

> 暂存 · schema `cart` · 购物车（加购/整车/勾选/删改/游标并入/下单清车）+ 收藏夹（收藏/列表/批量查）已落

```yaml
module: cart
layer: 暂存
schema: cart
status: in-progress
depends_on: ["catalog :: api", "seller :: api", "trade :: events"]
emits: []
consumes: ["OrderGroupPlaced"]
```

## 职责

买家侧的「选购意图」暂存：购物车是「现在就想买」，收藏夹是「以后再买」。

**为什么这两件事在一个模块里。** 它们形状相同（`(buyer_id, 商品指针, 时间)`）、失效处理相同
（读时经 `catalog :: api` 判、失效置灰不删）、删除口径相同（硬删无软删列）、
对外依赖相同（只有 `catalog :: api`）。拆成两个模块只换来两份要同步维护的边界注释，
换不来任何独立性——谁也不会只发布其中一个。判据见
[module-map §0](../../../../../../../../../docs/domain/module-map.md)。

**为什么不叫「购物车」以外的名字。** 改名要动 schema、包名、全部 import，而收益只是一个更准的词。
等第三个暂存类需求（浏览历史）真的来了，再一次性改名，那时才知道该叫什么。

## 模块契约

### 输入

| 来源             | 拿什么                                                           | 用在哪                       | 拿不到会怎样                                               |
| ---------------- | ---------------------------------------------------------------- | ---------------------------- | ---------------------------------------------------------- |
| `catalog :: api` | `findSellable(skuId)` / `findSellableByIds(...)` → `SellableSku` | 加购闸门、整车拼装与置灰判定 | 加购折成 400 `CART_SKU_NOT_SELLABLE`；置灰不报错           |
| `catalog :: api` | `findSellableSpusByIds(...)` → `SellableSpu`                     | 收藏存在性校验、收藏列表拼装 | 收藏 404；列表置灰                                         |
| `seller :: api`  | `namesByIds(...)` → 店名 Map                                     | 购物车按店分组的展示字段     | 店名缺了给 null，前端兜底，不拦列表                        |
| 事件             | `OrderGroupPlaced`（buyerId + skuIds 全集）                      | 下单即清被买下的条目         | 收不到则已购条目留在车里 selected=true，下次结算会原样带上 |

### 输出

无。cart 没有对外 `api/` 包，不发事件，没有任何模块依赖它——纯叶子。
（消费 `trade :: events` 不破坏这个声明：叶子指的是「没人依赖我」，不是「我不依赖任何人」。）

### 边界

- **只存选购意图，不锁价不锁库存。** 一锁就变成第二份库存；库存不足照样加购，闸门在下单
- **永不调 pricing。** 购物车页与收藏页展示的都是 catalog 的提示性现价（加购到下单之间的比价窗口）；
  报价单要 address 才能算运费、要落四张证据表，这两页两样都没有。真实价格锚点在结算页的报价单
- **不存商品快照。** 标题、图、价都不落库。落库就要处理「商家改了标题，我的收藏里那条要不要跟着变」——
  那是缓存失效问题，而这两页都不是热路径，读时拼一次更便宜也更准
- **失效判定是读时做的**：拼装时 catalog 批查不到的条目 `available=false` 置灰，
  不落失效列、不订事件——覆盖所有失效原因且永不出错

### 购物车与收藏的关键差别

| 维度                 | 购物车                            | 收藏夹                                            |
| -------------------- | --------------------------------- | ------------------------------------------------- |
| 粒度                 | SKU                               | **SPU**（买家点的是商品页的心形，他没选颜色）     |
| 加的时候拦不可售吗   | **拦**（拦的是「现在就想买」）    | **不拦**（「先收着等降价/等有货」正是收藏的理由） |
| 加的时候校验存在性吗 | 拦（catalog 查不到即 400）        | 拦（查不到即 404，但不拦「下架」）                |
| 重复操作             | `ON CONFLICT` 累加数量、封顶      | `ON CONFLICT DO NOTHING`，幂等不刷新时间          |
| 种类上限             | 120（`CartRules.ITEM_KINDS_MAX`） | 500（`FavoriteRules.ITEM_KINDS_MAX`）             |
| 时间戳               | `created_at` + `updated_at`       | 只有 `created_at`（行永不 UPDATE）                |

「收藏不拦不可售」是这两件事最本质的分界：拦了它，收藏就退化成半个购物车，
而「先收藏、等它降价或有货」正是收藏存在的唯一理由。代价是列表里会有失效行，所以读侧必须置灰。

## 拥有什么

`cart.items`（buyer_id, sku_id 唯一；数量/勾选/时间戳，无价格无快照）
`cart.favorite_item`（buyer_id, spu_id 唯一；只有 created_at）

表都建在 `cart` schema 里，跨 schema 不 JOIN、不建外键。条目谁也不引用（订单做快照），硬删无软删列。

## 键与写法

- **条目按自然键寻址**：`(buyer_id, sku_id)` / `(buyer_id, spu_id)` 是唯一键也是自然键，没有行 id——
  前端在商品详情页手里只有 skuId 或 spuId，按它寻址天然幂等、跨设备稳定；
  暴露行 id 只会多一个「这个 id 是不是我的」的越权面
- **加购是 `ON CONFLICT` 行锁累加封顶**，不靠 catch 唯一键冲突回退；改数量是独立条件更新，两条路不互相抹值
- **收藏是 `ON CONFLICT DO NOTHING`**：PostgreSQL 撞唯一键会中止整个事务，catch 之后发不出任何语句，
  所以并发这条路只能靠 `ON CONFLICT`，不能靠异常处理
- **收藏上限在真的插进去之后判**，超了抛异常让事务回滚——刚插的那行一起没。
  重复收藏不占新坑，所以幂等命中不查上限
- **勾选是声明式资源**：`PUT /api/buyer/cart/selection`——「当前勾选集合就是这批 skuId」，
  先整车清再置真，单选/全选/按店选同一入口，并发双标签页 last-write-wins
- **三个列表型入参（并入行集 / 勾选集合 / 批删集合）都封顶在种类上限**：要操作的不可能比车里的还多，
  这条上限也是 foreach IN 子句有界的保证
- 所有 SQL 绑 `buyer_id`（DataScopeTest 白名单管辖），`buyerId` 一律从令牌来

## 闭环断点

- 凑单未做。
- 账号注销的整车清理（`CartService.deleteByBuyer` / `FavoriteService.deleteAllOf` 已备）等注销闭环发事件时接上。
- **收藏夹分组 / 收藏店铺 / 降价提醒**都没有。前两个是运营需求；降价提醒不是这个模块的事——
  它要的是 `catalog` 发 `PriceChanged` + 价格历史，再加一个 `notification` 投递通道，
  订阅关系只是其中最小的一块，放进这里等于让暂存模块承担定时比价与消息推送。
- **浏览历史**未做。它和收藏形状相同，真要做时加一张 `cart.view_history` 即可；
  但它是唯一的写热点（被动记录、每次浏览一条 upsert），真做时要把表按时间分区，别和收藏挤在一个维护节奏里。
