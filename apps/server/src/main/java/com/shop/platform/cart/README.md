## 模块契约

### 输入

| 来源             | 拿什么                                                           | 用在哪                       | 拿不到会怎样                                               |
| ---------------- | ---------------------------------------------------------------- | ---------------------------- | ---------------------------------------------------------- |
| `catalog :: api` | `findSellable(skuId)` / `findSellableByIds(...)` → `SellableSku` | 加购闸门、整车拼装与置灰判定 | 加购折成 400 `CART_SKU_NOT_SELLABLE`；置灰不报错           |
| `seller :: api`  | `namesByIds(...)` → 店名 Map                                     | 整车按店分组的展示字段       | 店名缺了给 null，前端兜底，不拦列表                        |
| 事件             | `OrderGroupPlaced`（buyerId + skuIds 全集）                      | 下单即清被买下的条目         | 收不到则已购条目留在车里 selected=true，下次结算会原样带上 |

### 输出

无。cart 没有对外 `api/` 包，不发事件，没有任何模块依赖它——纯叶子。
（消费 `trade :: events` 不破坏这个声明：叶子指的是「没人依赖我」，不是「我不依赖任何人」。）

### 边界

- **只存选购意图，不锁价不锁库存。** 一锁就变成第二份库存；库存不足照样加购，闸门在下单
- **永不调 pricing。** 购物车页展示的是 catalog 的提示性现价（加购到下单之间的比价窗口）；
  报价单要 address 才能算运费、要落四张证据表，购物车页两样都没有。真实价格锚点在结算页的报价单
- **失效判定是读时做的**：整车拼装时 catalog 批查不到的条目 `available=false` 置灰，
  不落失效列、不订事件——覆盖所有失效原因且永不出错
- **三道闸门分工**：加购拦不可售（拦「现在就想买」）+ 拦种类超限（400）；游标并入两样都不拦——
  不拦在售（搬「曾经想买」，失效照收置灰）、种类超限静默丢弃（「尽力搬」语义，丢弃比 400 更符合姿态）。
  但**种类上限本身对并入同样生效**，没有它登录一次 POST 就能越过防刷线把车灌成任意大
- **清车时机是「落单」不是「支付」**：下单成功货就是这单的了，等支付再清，支付失败的窗口里车被误清。
  事件处理走 `EventInbox` 去重，删的是事件 buyerId 名下的 skuIds，别人的车里同款照留

## 拥有什么

`items`（buyer_id, sku_id 唯一；数量/勾选/时间戳，无价格无快照）

表都建在 `cart` schema 里，跨 schema 不 JOIN、不建外键。条目谁也不引用（订单做快照），硬删无软删列。

## 键与写法

- **条目按 skuId 寻址**：`(buyer_id, sku_id)` 是唯一键也是自然键，没有行 id——前端在商品详情页
  手里只有 skuId，按它寻址天然幂等、跨设备稳定
- **加购是 `ON CONFLICT` 行锁累加封顶**，不靠 catch 唯一键冲突回退；改数量是独立条件更新，两条路不互相抹值
- **勾选是声明式资源**：`PUT /api/buyer/cart/selection`——「当前勾选集合就是这批 skuId」，
  先整车清再置真，单选/全选/按店选同一入口，并发双标签页 last-write-wins
- **三个列表型入参（并入行集 / 勾选集合 / 批删集合）都封顶在种类上限**：要操作的不可能比车里的还多，
  这条上限也是 foreach IN 子句有界的保证
- 所有 SQL 绑 `buyer_id`（DataScopeTest 白名单管辖），`buyerId` 一律从令牌来
