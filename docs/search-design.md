# 搜索与首页分类导航设计

> 状态：阶段 A 部分落地；阶段 B/C 仍为设计提案。
> 目标是成熟电商搜索的基本完成度，不代表对淘宝内部架构的还原，也不代表已具备淘宝规模的能力。
> 与现有决策的关系：[商品搜索方案决策](reference/search-decision.md) 记录当前已落地的 pg_trgm 包含匹配；本文补充首页入口、结果页及增强搜索的目标设计，不宣布已切换引擎。
> 与历史规划的关系：[CMS FUT-05](business-rules/cms.md#八已定案未实现设计稿内容禁止当作生效规则) 曾撤回独立搜索页。本文重新提出“统一搜索结果页”作为后续方案，而不是每类目独立频道；这是新提案，不改变当前 Feed 行为或宣称页面已上线。
> **引擎决策（2026-10-01）**：增强检索阶段确定采用 Elasticsearch 单引擎。阶段 A 继续用 PostgreSQL + pg_trgm 过渡；阶段 B 切到 ES，PostgreSQL 仍是事实源，pg_trgm 保留为显式降级路径。

## 0. 实现进度

阶段 A 部分落地：搜索框（首页大框 + 内页）提交到 `/search`，空关键词只提示；`/search` 支持 `q/categoryId/sort/page` URL 状态；首页分类叶子词条进搜索，显式 `SEARCH`/`CATEGORY` 目标按目标跳转、不伪造；搜索词里的 `%` `_` `\` 按 LIKE 字面量转义；公开列表按可售 SKU 重算展示价，无可售 SKU 时暂回退价格区间。

仍未落地：筛选 / 聚合 / 分词 / 相关性 / 联想 / 容错 / 拼音 / 历史；ES 索引与可靠同步；`published_at` 与结果窗口、仅看有货；独立搜索契约 `GET /api/search/products`。价格排序暂不展示，等增强接口统一匹配 SKU 定价、展示价与排序。

## 1. 核心决策

**先做一个可靠的搜索结果页，再让搜索框和首页分类词条共用它；不为每个分类另建一套页面。**

1. 统一入口为 `/search`，支持关键词搜索、指定类目浏览、类目内搜索。
2. 首页具体商品词条默认是预设搜索关键词，不要求每个词条绑定后台类目。
3. 搜索结果页负责找货；首页推荐 Feed 负责闲逛。两者可以复用商品卡，但不共用排序、分页和缓存语义。
4. 先复用现有 PostgreSQL + pg_trgm 接通入口，不把安装搜索引擎变成首页能用的前提。进入中文分词、相关性和复杂筛选阶段时，采用 Elasticsearch 单引擎方案，PostgreSQL 仍是事实源。
5. 价格、规格、库存必须在同一个 SKU 上联合满足；不能用商品级最低价冒充匹配规格的价格。
6. 先保证任务闭环与正确性，再做联想、容错和相关性优化。不以增加组件、模型或服务数量衡量“淘宝级”。

首期不做独立分类频道体系、个性化排序、广告竞价、向量检索、模型重排、复杂活动编排，也不实现店铺搜索。搜索框不展示尚未支持的搜索类型。

## 2. 起点：不是没有查询，是首页没接

本文补充的是「首页入口 + 统一结果页 + 增强检索」这一段；引擎与查询能力本身见 [reference/search-decision.md](reference/search-decision.md)。要点三条：

- 现有 `GET /api/products` 已支持 `keyword/categoryId/shopId/sort` 与分页，关键词是名称或副标题的 `ILIKE` 包含匹配，已有 pg_trgm GIN 索引；现有 `price_asc/price_desc` 按商品 minPrice/maxPrice，不是下文的相关性 / 上架时间 / 匹配 SKU 定价排序。
- 首页尚未接入：搜索框只给占位提示、左侧分类部分按钮无行为、Banner 点击回首页。阶段 A 接的就是这一层。
- 现有 CMS 契约里 `NavGroup.items` 是字符串数组、`NavEntryResponse` 已有 `targetType/target`；首期叶子词条直接用字符串作关键词，不为接通点击而把整个 CMS 改造成通用跳转配置系统。

## 3. 首页入口如何进入搜索

| 入口                           | 行为                           | 示例                             |
| ------------------------------ | ------------------------------ | -------------------------------- |
| 搜索框                         | 提交用户输入                   | `/search?q=跑步鞋`               |
| 分类中的具体商品词条           | 词条文字作为关键词             | 点击“跑步鞋”得到同样的 URL       |
| “女装 / 男装 / 内衣”等组合标题 | 展开菜单，不搜索整串标题       | 用户再选择具体词条               |
| 明确配置了 SEARCH 目标的入口   | 使用目标关键词，而非装饰性标题 | 展示“通勤装备”，目标为“通勤背包” |
| 明确配置了 CATEGORY 目标的入口 | 限定后台类目                   | `/search?categoryId=xxx`         |
| 类目内继续找货                 | 类目条件与关键词共同生效       | `/search?q=轻便&categoryId=xxx`  |

关键区别：

- **关键词是相关性条件**。“手机”可能召回配件，但真正的手机应优先。
- **categoryId 是硬范围**。只返回指定类目及其后代类目中的商品；未知类目不能静默退成全站搜索。
- 有明确目标时尊重目标；没有目标且是具体商品词条时，才按文字搜索。空词条、无效配置不伪造首页跳转。
- 组名只有在能表达明确商品需求或配置了真实目标时才作为链接，否则只是分组标题。
- 首页推荐条不是左侧分类导航。其 SEARCH 型词条当前仍走全站 Feed，不在本设计中顺手改为跳页；如需改变，必须另行同步 CMS 规则与测试。

“热销榜”“新品首发”“领券优惠”不是普通商品关键词。它们需要真实榜单、上架时间排序或优惠商品集合承接；未实现前，不用搜索文案本身冒充活动链路。

## 4. 结果页与交互

### 4.1 URL 是已提交搜索状态的来源

`q`、`categoryId`、筛选条件、排序、页码进入 URL；输入框尚未提交的草稿保留在组件内。分享 URL 表示相同搜索条件，不承诺不同时间看到完全相同的商品。

- 提交新关键词、改变筛选或排序：重置第一页；清空全部条件的范围在按钮文案中说清楚。
- 刷新保留条件；浏览器前进、后退恢复条件及可恢复的滚动位置。
- 从搜索框发起新搜索默认不限类目；结果页若保留类目范围，必须以可移除条件明确展示。
- 空关键词且没有类目：提示输入，不自动请求无限制的全站列表；只有类目时允许浏览。
- 参数只接受约定字段和排序枚举；URL 编码交给路由工具，不手工拼接用户文字。
- 商品详情默认沿用现有新标签页打开习惯；同标签页访问后返回也应能恢复搜索上下文。

### 4.2 页面结构

从上到下为：搜索框 → 查询与范围说明 → 可用筛选项及已选条件 → 排序/结果数量 → 商品网格 → 分页。

目标提供相关性、价格升序、价格降序、新品排序；“新品”按明确的上架时间定义，不用编辑时间冒充。接通现有接口阶段，先保留其已有排序语义并准确命名，不把创建时间排序标成“最新上架”，也不把默认排序标成“相关性”。匹配 SKU 定价与排序尚未统一前，不声称已经满足目标价格语义；增强接口落地后再启用对应选项。销量排序等质量信号在数据口径可靠后再加。

采用有上限的分页，不复制首页无限 Feed。后端设定分页与结果窗口上限，前端据契约限制翻页并提示缩小范围。同分结果以稳定商品 ID 排序；索引更新时不承诺跨请求快照一致。首期不提供任意深翻页，后续有实际需要再设计快照游标。

### 4.3 状态与反馈

| 状态       | 要求                                                         |
| ---------- | ------------------------------------------------------------ |
| 输入/提交  | Enter 和按钮均可提交；空输入有明确反馈                       |
| 首次加载   | 结构稳定的占位，不把加载当作无结果                           |
| 改条件加载 | 显示加载反馈；保留旧结果时标明正在更新，不能冒充新条件的结果 |
| 无结果     | 回显关键词与条件，提供修改关键词、移除筛选的真实操作         |
| 请求失败   | 独立错误态与重试；不能伪装成“没有商品”                       |
| 分页失败   | 明确本页没有成功加载，不把旧页标成新页                       |
| 商品已变化 | 缺货/失效可识别；进入详情及交易操作时重新校验                |

后续加入搜索建议时，支持方向键、Enter、Escape、可见焦点与读屏标签；建议失败不能阻断直接提交。短防抖及请求取消只改善体验，结果正确性仍由查询身份保证，旧请求不能覆盖新词的建议。

## 5. 增强检索流程

第 5–8 节描述增强阶段的目标，不把现有 ILIKE 包含匹配说成已经具备这些能力。分词/相关性需求已触发现有搜索决策中的重评条件，但评估不等于立即替换生产路径。

一次查询依次执行：**规范化 → 识别可确定的条件 → 召回候选 → 硬过滤 → 排序 → 返回商品与筛选信息**。

### 5.1 关键词与意图

首期建立适合中文商品的分析字段：标题、品牌/别名、型号、类目名称、规范化属性。型号同时保留精确匹配字段，避免分词破坏字母、数字组合。

- 统一首尾空白、大小写和全半角等表示差异，但保留影响型号含义的字符。
- 中文分词与少量人工维护的行业别名从首期验证，例如 USB-C / Type-C。
- 不把“手机壳”扩展成“手机”，不把“苹果”无条件锁定为品牌。
- “300 以内”这样的结构化意图识别不作为首期前提；先用显式筛选。后续解析时展示为可撤销条件，不确定的推断只能作为建议。
- 拼音、错别字、复杂同义词扩展依据查询回归集逐步增加，不默认做宽泛模糊匹配。

### 5.2 排序原则

以 BM25 等关键词相关性为基础，结合字段权重、完整短语和精确型号匹配。

1. 精确型号查询优先返回该型号，不能被热销的相似商品挤下去。
2. 泛类目查询先满足相关性，再考虑有可靠口径的质量、销量、新鲜度信号。
3. 品牌、型号、标题等字段的权重通过标注查询集校准，不把任意一组权重称为行业标准。
4. 用户明确选择价格或新品排序时，尊重该排序；不得暗中混入另一套综合排序。
5. 排序信号通过后台业务数据派生，不信任商家填写的“销量”“热销”等标题词。

查询与排序由服务端构造，客户端不能提交搜索引擎 DSL、脚本、任意字段排序或通配表达式。

## 6. 商品、SKU、价格与筛选

### 6.1 检索投影

首期以商品为结果去重单位：一件商品一张卡。搜索文档包含商品/店铺标识、公开状态、标题、品牌、型号、类目祖先路径、展示素材、上架时间，以及 SKU 集合。

每个 SKU 至少包含 SKU ID、有效状态、规范化规格、价格、可售库存信息。规格以属性 ID/规范值匹配，不靠展示字符串猜测。“库存”沿用库存域的可售口径，不直接把数据库某个数量字段当作可售库存。

推荐用 nested SKU 表达同一记录的联合条件。一个商品的 SKU 过多或库存更新导致整文档更新成本过高时，再根据压测决定是否拆分，不首期同时维护两套索引模型。

### 6.2 同一 SKU 联合匹配

| SKU  | 价格   | 库存 |
| ---- | ------ | ---- |
| 黑色 | 399 元 | 有货 |
| 白色 | 199 元 | 有货 |

用户筛选“黑色、300 元以下、有货”时，该商品不能命中。不能分别从不同 SKU 取得颜色、最低价、库存来拼出一个不存在的可购买组合。

- 同一属性的多个选项为 OR，不同属性/价格/库存之间为 AND，并在同一 SKU 上判断。
- 只返回公开上架、店铺可见且存在有效匹配 SKU 的商品。未开启“仅看有货”时可展示暂时缺货项，但必须明确缺货；开启后要求匹配 SKU 的可售库存大于零。
- 商品卡展示价和价格排序使用同一组匹配 SKU 的最低价；若该范围内既有有货又有缺货 SKU，优先以有货 SKU 定价，避免用不可购买低价引流。
- 如展示价仅为缺货规格的参考价，明确标识不可购买；选择条件改变后重算价格。
- 返回匹配规格信息，详情页能定位对应 SKU；SKU 变化后提示失效，不能悄悄换成另一规格。
- 金额契约沿用 `Money { amount, currency }`，amount 为分；展示复用共享 Money 工具与 Price 组件。首期不自行计算复杂券后价或向用户承诺未经结算验证的到手价。

### 6.3 筛选项与数量

品牌、类目、属性筛选项来自当前查询范围，而不是写死列表或只统计当前一页。类目属性不适用于当前范围时不展示。

计数按去重后的商品数，不按 nested SKU 数。计算某个维度的候选值时保留其他条件、放开该维度自己的选择，便于多选；SKU 维度仍须遵守同一 SKU 联合匹配。总命中数则包含全部已选条件。

首期不追求大型结果集的无限精确计数；如引擎返回下界，接口与 UI 必须表达“至少/以上”，不能伪装成精确总数。

## 7. 接口与前后端边界

接通阶段直接使用已有 `GET /api/products`，前端 URL 的 `q` 映射到既有 `keyword`，不新增同功能的中转接口。无搜索条件时的前端提示仅限制搜索页，不改变现有商品列表接口“无条件返回全站上架商品”的行为。

增强阶段建议新增 `GET /api/search/products`，承载相关性、匹配 SKU 和聚合等不同契约；既有列表接口继续保持兼容。以下是语义契约草案，不表示增强端点或类型已存在：

| 输入       | 语义                                               |
| ---------- | -------------------------------------------------- |
| q          | 可选关键词；无关键词时必须存在有效类目范围         |
| categoryId | 可选硬类目范围，含其后代类目                       |
| filters    | 品牌、属性值、Money 价格边界、仅看有货等已支持条件 |
| sort       | 有限枚举，默认相关性                               |
| 分页参数   | 沿用项目统一分页契约，并限制结果窗口               |

返回现有分页结构可承载的商品结果与计数，补充必要的匹配 SKU/展示价、聚合筛选项、计数是否精确的信息。字段名、GET 参数序列化和校验在 OpenAPI 中统一定义，再生成 SDK，不手改生成文件或建立第二套 Money 类型。

- 前端使用 TanStack Router 管理 URL、TanStack Query 管理服务端状态；query key 包含规范化后的全部查询条件。
- 参数等价的请求具有相同 key；取消信号传到请求层。SSR 与客户端共用查询定义，不裸 fetch、不复制第二套请求逻辑。
- 搜索结果使用有限时效缓存，不照搬首页 Feed 的 Infinity；返回页面可以先恢复缓存，但不把旧价格当作交易依据。
- 搜索后端是业务模块内的读能力，遵守 `api/events` 边界。需要跨域数据时由领域 API 或事件提供，不跨 schema JOIN，不访问别的模块内部 Mapper。
- 前端不直连搜索引擎。商品管理写接口也不因为索引暂时不可用而直接双写失败。

## 8. 索引同步与运行边界

链路为：**业务事务提交 → 可靠变更事件 → 构建搜索投影 → Elasticsearch → 搜索接口**。PostgreSQL 仍是事实源，索引只是可重建的读取副本。

- 项目已登记 Modulith 事件发布表，但现有跨模块监听以同步同事务为主，不能把“有表”视为搜索异步同步已就绪。启用索引前需补齐可靠异步监听、失败重投、启动补偿及测试；复用既有机制，不默认引入 Kafka 或再造一套 outbox。
- 标题、品牌、类目、SKU、价格、可售库存、上下架、店铺状态的变化都纳入更新范围；父类目变化还要处理后代商品的路径。
- 消费允许重复，写入幂等；同一商品投影更新通过串行化或版本保护避免倒退。不同领域各自的版本号不能直接互相比较。
- 下架/删除需保留防旧事件复活的机制；不能先删文档，再让迟到的旧事件将其重新加入。
- 全量重建写入新索引，补齐构建期间的增量，核对后切换别名；禁止清空线上索引再逐条灌入。切换失败应可回滚。
- 保留现有决策要求的 ILIKE 开关/回退路径，但禁止静默改变搜索语义。显式降级时标明基础搜索，清楚移除或拒绝不支持的条件和排序，并重置分页；不能保留筛选标签却忽略筛选。无法保证公开状态或用户条件时，返回暂不可用与重试，不伪造空结果。

价格与库存允许受控的短暂延迟，详情、加购、下单仍由业务系统校验。下架及店铺封禁不能仅靠交易时兜底：同步故障期间应有来自权威公开状态的查询侧屏蔽，并监控撤下时效。

引擎版本、中文分析器兼容性、部署资源和许可需在落地时验证；本提案不声明现有环境已部署 Elasticsearch。初期先一个检索引擎，不先拆独立微服务。

## 9. 分阶段落地

| 阶段                | 交付                                                                                        | 完成条件                                                         |
| ------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| A：接通现有查询     | 复用 pg_trgm 商品列表、结果页、现有有限排序与分页、搜索框及叶子词条接入；已有类目能力可复用 | 能从首页找货、进详情、返回；明确仍是包含匹配，不声称有相关性排序 |
| B：增强搜索与正确性 | 评估并引入检索引擎、可靠索引同步、中文分析与相关性、匹配 SKU、品牌/规格/价格/库存筛选及聚合 | 联合筛选、展示价和排序一致；发布/撤下、同步故障与重建均可验收    |
| C：提高搜索质量     | 建议、可清除历史、容错、同义词及排序校准                                                    | 查询回归集证明质量改善，且没有破坏型号匹配、价格真实性与延迟目标 |

基础正确性不能延期：即使阶段 A 尚无规格筛选，展示价也不能引用不可购买的低价 SKU 来误导。各阶段只暴露已经可用的筛选、入口和排序选项。

阶段 C 的搜索历史优先本地保存并支持清除，不默认做跨设备历史系统。查询统计复用现有遥测出口，不把原始关键词放进高基数指标标签；诊断样本需限制采集、访问与保留时间。

## 10. 验收与评估

### 10.1 必须自动验证的场景

| 场景                                    | 预期                                       |
| --------------------------------------- | ------------------------------------------ |
| 输入“跑步鞋”与点击同名首页词条          | URL 条件与检索语义一致                     |
| 点击组合分类标题                        | 展开菜单，不发起无意义的拼接词搜索         |
| 关键词含空格、中文或特殊字符            | 正确编码与回显，不改变字符含义             |
| 快速从词 A 改到词 B                     | A 的迟到响应不覆盖 B                       |
| 修改条件、翻页、刷新、前进后退          | 状态一致，条件变化重置第一页               |
| 黑色 399 / 白色 199，筛选黑色且低于 300 | 不命中；不存在跨 SKU 拼接条件              |
| 匹配规格与另一规格价格不同              | 卡片及价格排序使用匹配范围，不展示无关低价 |
| 多 SKU 命中                             | 一件商品只计一次，筛选数量不重复累加       |
| 商品下架、店铺封禁、SKU 失效            | 按公开状态及时屏蔽；详情与交易再次校验     |
| 事件重复、乱序、删除后旧更新            | 不重复、不倒退、不复活                     |
| 索引重建期间仍有商品更新                | 切换后无漏更新，可回滚                     |
| 无结果与搜索引擎故障                    | 显示不同状态，失败不是“没有商品”           |

测试分层：检索与同步规则测试使用真实引擎兼容环境；前端以 MSW mock 网络响应，不 mock 业务模块；E2E 覆盖首页入口到搜索、详情和返回的真实链路。

### 10.2 “足够好”的证据

先整理 100–300 条有代表性的中文查询，覆盖型号、类目、属性、简称、错字、空结果及 SKU 边界，人工标注前排商品的相关性。它是早期回归集，不是统计上证明已追平淘宝的样本量。

- 离线：前 10 条相关性、NDCG@10、精确型号与 SKU 正确性。
- 在线：无结果率、改词率、搜索后点击/加购/购买，并结合误导价格、失败和退出情况解释。
- 运行：接口延迟分位数、错误率、索引积压/更新延迟、公开状态撤下时效。

无结果率低不等于找得准，点击率高也可能来自误导。上线前必须在约定商品量、SKU 分布、并发量及设备网络下确定验收阈值；这些是项目目标，不引用为淘宝实测成绩。
