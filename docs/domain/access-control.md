# 权限

> 定位：**谁能做什么、能碰哪些数据、什么条件下不行**的唯一约定。
> 声明文件 `contracts/permissions.yaml` 是权限码的唯一真相源；表形状见迁移；这份说为什么这么分层。
>
> **状态：设计定稿，分批落地中。**
> 已落：权限码（yaml 唯一真相源 + 生成枚举/契约类型）、`AccessScope` 三个签发方法、seller/admin 两侧 controller 走工厂、`DataScopeTest` 的两层归属强制、`authz` 四张表的 DDL、解析器切到 `authz.*`（商家侧读 `authz.role_grant`；平台岗位集合从 yaml `staff_roles` 推导，不查库）、退款上限求值（`role.max_refund_amount` → `CurrentOperator.refundCap` → `AccessScope.Seller` → `RmaService` 动钱口比较）。
> 未落：买家侧 controller 接 `buyer()` 工厂（现在仍走 `current()`）、八条约束、两张审计表。
> 老模型（`common.permission` 目录表 + `staff.role` 文本列 + `seller.role` 两套形状）**整块拆掉**，不做兼容、不做数据迁移。

## 0. 一句话

**表示可以异构，判定链必须同构。**

一条判定链在全项目只有一个，顺序固定，任何端点都走它：

```
① 身份    你是谁、哪一类主体、属于哪个租户
② 功能权限 这类主体能不能做这个动作        ← 权限点（RBAC）
③ 范围    作用到哪些资源实例              ← 授权行上的符号化范围
④ 属性    金额上限等少量定点比较           ← 普通列，不是条件引擎
⑤ 决策    取交集，任一环不过即拒
⑥ 审计    拒绝留痕 + 权限变更留痕
```

约束（§6）**不在这条链上**——它在写入侧，是"这组授权能不能存在"。

## 1. 为什么不是"一个模型包打天下"

三个候选模型各自推到极限，崩在同一处：

| 只用…           | 崩在哪                                                                                                                           |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 纯 RBAC（五表） | "范围"无处安放。塞进角色 → 角色数 = 岗位 × 店数；塞进 `user_roles` → 它已经不是关联表了                                          |
| 纯 ABAC / PBAC  | "约束（SoD）"无处安放——它的求值签名里没有"一组授权是否合法"这个问句。列表查询还要把策略反向编译成 SQL，而越权事故 90% 发生在列表 |
| 纯 ReBAC        | 本项目的层级是一棵树（店 → 商品/订单 → 子单 → 包裹），树用归属列比 tuple 便宜一个数量级；而且约束层同样无处安放                  |

**所以分层是被迫的，不是偏好。** 而"分层"不等于"按模块挑模型"——按模块分片会让"这张单能不能看"在不同模块里有不同答案，那是权限系统最典型的自毁方式。

## 2. 身份层

### 2.1 三张主体表，不是一张

| 主体     | 表                      | 登录标识                                          | 归属                          |
| -------- | ----------------------- | ------------------------------------------------- | ----------------------------- |
| 买家     | `account.buyer`         | 手机号                                            | 自己                          |
| 商家员工 | `seller.merchant_staff` | 登录名（主账号 = 手机号，子账号 = `手机号:后缀`） | `merchant_id`（创建后不可改） |
| 平台员工 | `staff.platform_staff`  | 邮箱 / 工号                                       | 无（全平台）                  |

**为什么不是一张宽表 + `type` 列**：那样每一列都得 nullable，每个查询都要 `if (type == ...)`。买家三百万行里塞着 `merchant_id` 空列，商家员工行里塞着 `nickname` 空列。

**为什么不建一张薄基表 + 三张扩展表**：类型检查会退化成运行期比较（读到 `kind` 再比一次，漏写就放行）。三张独立表的类型检查是**结构性**的——令牌带 `typ`，`typ` 决定用哪个解析器，买家的令牌根本走不到商家解析器，不是"比了之后拒绝"。

统一的不是表，是三条约定：

1. id 都是 uuid v7，全局唯一（审计、会话、授权都能安全地 `(类型, id)` 引用）
2. 令牌必带 `typ`，`typ → 解析器` 是唯一路由，不认识的 `typ` 一律拒
3. 任何表引用主体都用 `(subject_type, subject_id)` 两列

### 2.2 不做账号合并

同一手机号可以开买家号，也可以开商家主账号——那是两个主体、两套凭据、互不感知。合并要回答"哪个是主身份、历史数据归谁、怎么解绑"，而 marketplace 的核心隔离假设是买家池与商家池不通。

### 2.3 主账号登录名 = 手机号

唯一性交给一个已经在别处被保证的东西：

- 主账号登录名 = 手机号 → 唯一性免费
- 子账号登录名 = `手机号:kefu01` → 前缀天然唯一，不会出现"第一个商家占了 `kefu01`，第二个商家的客服永远叫不了这个名字"
- **不需要"主账号登录名不可改"这条规则**——换个唯一源，三条补丁规则一起消失

### 2.4 认证与授权分离

| 事件           | 认证                                                                          | 授权                           |
| -------------- | ----------------------------------------------------------------------------- | ------------------------------ |
| 商家被暂停经营 | **仍能登录**                                                                  | 店铺范围解析为空，只给申诉入口 |
| 主体被禁用     | 拒绝                                                                          | —                              |
| 买家注销       | `status='deleted'`，手机号换成哨兵值 `deleted:<uuid>`，真号进冷却表保留 90 天 | —                              |

手机号必须换掉而不是软删占位：不释放则用户换号后永远无法注册；直接释放则号码被回收后新主人可能继承旧账号的历史订单。

### 2.5 会话

> **现状**：会话住 Redis（`infra.security.RefreshTokenStore`），已实现一次一换、重放检测、
> 同设备置换、禁用即吊销。下面的"落库"是目标形态——落库的价值是可查询（"这个人现在有哪些会话"），
> 而 Redis 只放得下摘要。这一步排在授权模型之后。

会话必须持久化，不能只靠 JWT。需要它才能做到：禁用主体后立即下线、refresh 一次一换、重放检测、"改密全端下线"。

同设备只留一条活跃会话（部分唯一索引）：不做这一步，登出/改密/重放兜底都只按索引吊销最新的那个，旧 refresh 全数存活到 TTL——"改密全端下线"就是假的。

## 3. 权限码

### 3.1 资源是 24 个，动作是 41 个

**资源判据**：使用者直接操作、且需要单独授权的东西。两条必要条件是**独立归属列**（否则范围无法表达）和**独立爆炸半径**（否则不需要单独授权）；有独立状态机是加强条件。

> 由此一条能挡住膨胀：**模块数 ≠ 资源数。** `media` 上传不是资源（是 `product:write` 的一部分），`search` 不是资源，`notification` 不是资源。

**资源名必须是可数名词**——能指着一条记录说"这个 ___ 是谁的"。领域名（售后）、流程名（治理、运维、审计）都通不过。据此：

| 不是                           | 是                                      | 原因                         |
| ------------------------------ | --------------------------------------- | ---------------------------- |
| `after_sale`                   | `after_sale_case`                       | "售后"是领域，"售后单"是实例 |
| `governance`                   | `governance_clue`                       | "治理"是流程                 |
| `audit`                        | `audit_log`                             | "审计"是流程                 |
| `ops`（job + event 合并）      | `job` / `event_record`                  | 合并不出名词 → 说明不该合并  |
| `funds`（suspense + 对账合并） | `suspense` / `reconciliation_statement` | 同上                         |

**动作是资源局部的**，不是一张全局动词表（否则会写出 `after_sale_case:execute` 这种没人懂的东西）。每个资源声明 1~5 个动作，动作名在资源内唯一、跨资源可重复。

**每个资源最多 5 个动作。** 超过就说明它该拆——这条比"一页纸"更好用，因为它能在设计时立刻报警。

### 3.2 格式 `resource:action`，但格式不是风险点

冒号还是点是无关紧要的，判权时它是不透明的原子。真正的风险在两个地方：

1. **资源怎么切**（见 3.1）
2. **动作不许复合**。`after_sale_case:refund` ✅；`after_sale_case:approve_refund` ❌——宾语重复说明你要的其实是 `approve`，或者你要操作的东西本身就是资源

### 3.3 声明文件是唯一真相源

`contracts/permissions.yaml` 是源，生成三样：后端枚举、前端/契约联合类型、清单文档。

**为什么不是数据库**：一次改名/重构时，DB 为真相源意味着代码里 41 个检查点全是字符串字面量，编译器一个都不提示，只能靠 grep；而 DB 侧一行 UPDATE 就完事。**必须被写下来的不是"有哪些码"，是"在哪里检查这个码"**——检查点不可替代，库里那张表可以由检查点完整重建。让投影当源，等于让可重建的东西指挥不可重建的东西。

**为什么要有一层 type**：代码里的检查点必须是 `check(Permission.AFTER_SALE_CASE_REFUND)` 而不是 `check("after_sale_case:refund")`。后者拼错只在运行期静默拒绝。

**前端不需要清单**。它需要的是 ① 当前用户的有效权限集（接口返回）② 契约上的联合类型（防拼错）。给前端生成一份"系统里有哪些权限"的常量是错的方向。

### 3.4 三个标记

| 标记          | 语义                                                               | 谁决定                         |
| ------------- | ------------------------------------------------------------------ | ------------------------------ |
| `risk = high` | 一次操作能改变别人的钱 / 改变全平台可见状态 / 封停账号 / 管钥匙    | 平台                           |
| `assignable`  | 商家能不能把这个码授给子账号                                       | 平台（保护商家自己或保护平台） |
| `pool`        | 这个码在哪个主体池里**有意义**（`merchant` / `platform` / `both`） | 平台                           |

**`risk` 和 `assignable` 不是同一个东西**，这是自助制逼出来的区分。`after_sale_case:refund` 动的是**商家自己的钱**，所以它是 `high` 但可转授（配退款上限，见 §5.2）。**永不可转授的只有两类**：管钥匙（`merchant_staff:write`）和不可逆（`shop:close`）。

**`pool` 是集合，不是排他域。** `order:read` 是 `both`——商家读自己的单、平台读全平台的单，**同一个码**。若给它标成排他域，就得新增 `ORDER_READ_ADMIN`，同一件事两个码必然漂。

`pool` 只有一个用途：**推导主账号的权限集合**（owner = `pool` 含 `merchant` 的全部码）。它不限制谁可以持有——`shop:review` 挂在 `scope: merchant` 的资源上，但它的 `pool` 是 `platform`（平台审别人的店），这个区分只能显式标，推不出来。

## 4. 角色与授权

### 4.1 角色：商家可自助编辑

`role` 带 `owner_kind`（platform / merchant）+ `owner_id`。平台角色是内置的（岗位），商家角色可以自建、自拼权限。

自助制的代价是一条硬约束：**商家角色的权限集合必须 ⊆ `assignable` 集合**。这道门在写角色时校验，不在判权时。

### 4.2 范围挂在授权行上，不挂在角色或主体上

- 挂角色上 → 角色数 = 岗位数 × 店数爆炸
- 挂主体上 → 一个人只能有一个范围，"在店 A 是客服、在店 B 是运营"表达不了

**所以范围唯一可行的位置是 `role_grant`。**

### 4.3 范围只有两种形态

| 形态             | 取值               | 出现在                                              |
| ---------------- | ------------------ | --------------------------------------------------- |
| 租户集合         | 商家集合 或 店集合 | 两侧都有                                            |
| 属性切面（类目） | 类目集合           | 只在平台侧，只作用于 `product` 和 `governance_clue` |

两者是 **AND**。都是集合，不是谓词、不是表达式、不是 JSON——因为范围的来源只有"归属关系"和"显式列举"两种，产出的都是集合。

**消掉的三个伪范围**：

- **关系传递**不是独立范围：以店为唯一租户根时，它是"店集合 + 资源树"的副产品。通用 ReBAC 在这里没有可表达的对象。
- **转交/交接**不是范围，是资源归属列的变更。"谁能管"和"这单归谁处理"是两件事，混在一起是 ReBAC 被滥用的第一大来源。
- **deny 黑名单**不是范围，是状态的伪装（店关了、账号禁用了）。做成规则会得到一张每次求值都要扫的表，而它本来在解析那一刻就能算完。

### 4.4 `ALL` 必须符号化，并且要分层级

主账号的范围是"本商家所有店"，平台小二是"全平台"。这两个**都不能枚举**（前者会在新开店时漏掉，后者是几万个店）。

求值结果不是 UUID 集合，是三种符号值：

```
Scope = All | Shops(Set<UUID>)
```

`All` → 生成 SQL 时**不加 shop 谓词**；`Shops` → `shop_id IN (...)`。没有 `Own` 这种授权范围——买家不持码，"资源行 buyer_id = 我"是列绑定不是授权，见 §2。

**一个简化**：商家侧不展开店集合。因为归属谓词里本来就有 `merchant_id = ?`：

```
商家 All      → WHERE merchant_id = ?                    （天然含已关店、含新开的店）
商家 Shops(S) → WHERE merchant_id = ? AND shop_id IN (S)
平台          → 不加任何谓词
```

这条同时消灭了"开店时要给主账号补授权"和"每请求查一次 shop 表"。

**`ALL` 不分层级是越权的经典最短路径**：平台的全部商家 vs 商家的全部店，同一个值撞车 → 某个店主看到全平台。

### 4.5 `scope_kind` 是显式的

不采用"无子行 = 不限"。后者的危险是"忘了写范围"和"故意不限"长得一样，求值时静默全放开。

**唯一能致命的细节**：没有任何授权时必须解析成**空集**，不能解析成 `All`。

### 4.6 一行一个范围，不是一行带一个集合

"客服调岗，把他从店 B 摘掉"是高频操作。一行一个范围时撤销 = 标记一行；一行带集合要读-改-写，并发下互相覆盖。而且唯一约束让重复授权天然幂等。

代价是"一次授权 3 个店 = 3 行"。这个代价由审计吸收：**授权表存结果，审计日志存事件。**

### 4.7 有效期与撤销不删行

`valid_to` 过期忽略、`revoked_at` 标记撤销，都不 DELETE。这三条一起保证：任何时刻问"某个历史时间点这个人有什么权限"都能算出来。DELETE 会让这个问题永远无解——审计最常问的就是它。

## 5. 求值与阈值

### 5.1 每请求回库，不缓存

| 选项              | 延迟                              | 结论                                        |
| ----------------- | --------------------------------- | ------------------------------------------- |
| 权限塞 JWT claims | 改权/禁用要等令牌过期（≤15 分钟） | **不成立**：自助制下角色是商家天天改的东西  |
| 每请求一次查询    | 下一请求即生效                    | **采用**                                    |
| 加缓存            | 几乎立即                          | 性能优化，不是正确性问题；等有 QPS 数据再说 |

每请求两次查询：① 主体状态（禁用即拒，不信令牌）② `role_grant ⋈ role_permission`。

解析产物：`codes`、`scope`（符号）、`refundCap`（各退款角色上限取 max；任一不限则不限）。

**先不缓存。** 缓存的正确形态是 `(subject_id, permission_version)` 做键、变更时 bump；但那是性能优化，现在做只会引入"失效漏了"这个新故障。

### 5.2 阈值只有一处，且不是条件引擎

退款上限是 `role.max_refund_amount` 一列。放在角色上是讲得通的，不是"为某个权限码开的洞"——角色的本质是岗位描述，"客服能批 500 以内"本来就是岗位描述的一部分。

```
authorizer.seller(AFTER_SALE_CASE_REFUND)  // 能不能退（凭据发出来才继续）
amount <= scope.refundCap()                // 能退多少（在 service 里比）
```

- `Authorizer` 只提供**取值**（凭据上带着上限），比较是业务规则（`RmaService.startRefund`），不是权限判定
- 多角色的上限取 **max**（权限是并集，上限跟着取并集）
- `NULL` = 不限，**只有内置店长角色是这种**；商家建的含退款角色必须 > 0

**不写 `role_permission.params jsonb`。** 那是会无限膨胀的 JSON 口袋。如果第二个阈值出现，它拿自己的列；出现五个时再回头看要不要抽象——不为一个取值抽象一个维度。

### 5.3 为什么不用 ABAC / PBAC

- **列表查询是分水岭。** ABAC 在点查上优雅，在列表上要么全查后过滤（分页错、性能崩），要么把策略 partial-eval 成 SQL（自己实现最容易出错的地方）。而越权事故 90% 在列表上。
- **多租户隔离会被降级。** RBAC 里"角色属于商家"是结构性事实；ABAC 里它变成"每条策略都记得写 `resource.merchant_id == subject.merchant_id`"的纪律。对"绝不能错"的规则，这是降级。
- **它一个表都省不掉。** 策略引用的 `subject.shop_scope`、`role.max_refund_amount`、`grant.valid_until` 还是得有人存、有人写。
- **PBAC 解决的是治理，不是建模。** 单服务、策略几个月不动一次、策略作者就是工程师——三条收益前提现在一条都不成立。

## 6. 约束层

**全部在写入侧，判权侧一条都没有。** 这是它和 ABAC 最根本的区别：ABAC 求值发生在请求时，而约束描述的是"这组授权能不能存在"。

### 6.1 两条写入链

| 写入点                                   | 管什么                       |
| ---------------------------------------- | ---------------------------- |
| **写角色**（`role` / `role_permission`） | 角色的权限集合是否合法       |
| **写授权**（`role_grant`）               | 谁能把什么授予谁、在什么范围 |

### 6.2 不变式

| #   | 约束                                                           | 写入点 | 失败 |
| --- | -------------------------------------------------------------- | ------ | ---- |
| 1   | 商家角色 ⊆ `assignable` 集合                                   | 写角色 | 400  |
| 2   | 含 `after_sale_case:refund` 的商家角色必须设 cap（非空且 > 0） | 写角色 | 400  |
| 3   | `role_grant.subject_type` 必须与 `role.owner_kind` 一致        | 写授权 | 400  |
| 4   | 授权里的 `scope_shop_id` 必须属于该商家                        | 写授权 | 400  |
| 5   | 主体不能给自己写授权                                           | 写授权 | 400  |
| 6   | 被授予的权限集合 ⊆ 授予者的有效权限集合                        | 写授权 | 400  |
| 7   | 不能撤销/降级到"在岗超管数 = 0"                                | 写授权 | 409  |
| 8   | 内置店长角色不可归档、不可删权限点                             | 写角色 | 400  |

**3、4、5 是水平越权的入口。** **6 现在恒成立**（只有主账号能写授权，主账号拥有一切），但必须写成不变量——将来若允许"子账号管家授权"，这条就是唯一的闸。**恒成立的约束现在不写，将来加功能时一定漏。**

### 6.3 三条要特别处理

**聚合类必须防并发（#7）。** 两个超管在同一刻互相降级，两个请求都读到"在岗超管 = 2"，都放行 → 0 个超管，平台锁死。解法是先取串行闸（哨兵行 `FOR UPDATE` 或 advisory lock），**再数人**。顺序不能反。

**存量数据靠启动扫描。** 每个写入侧校验都配一条启动扫描：违规行列出来，应用起不来。这就是"配置即测试"——它让策略变更不可能悄悄留下脏数据。

**不建约束表。** 八条不变式硬编码 + 单测。做成配置需要的是 `type + 参数 JSON`，那就是一直在反对的万能表达式表。八条硬编码的成本是八个方法。

## 7. 审计

### 7.1 两类，别混一张表

|                          | 记什么                               | 量           |
| ------------------------ | ------------------------------------ | ------------ |
| `audit_log`（变更）      | 数据从什么变成什么（含权限变更本身） | 与写操作同阶 |
| `audit_decision`（拒绝） | 被拒绝的尝试：谁想动什么、为什么拒   | 同阶或更低   |

### 7.2 记录后果，不记录判断

- 判权**通过**没有后果 → 不记。它导致的那次写才有后果，那次写已经在 `audit_log` 里
- 判权**拒绝**有后果 → 记
- **权限变更本身**后果最重 → 逐条全量

**全量记录 allow 不可承受**：每个请求 N 次 `check`，一次页面加载就能写几十行。

### 7.3 拒绝要按 reason 分级

| reason               | 含义                           | 处置                                           |
| -------------------- | ------------------------------ | ---------------------------------------------- |
| `out_of_scope`       | **有这类权限，但对象不是他的** | 逐条明细 + 告警（同一主体 5 分钟内 ≥N 次）     |
| `not_owner`          | 归属不符（买家侧）             | 同上                                           |
| `missing_permission` | 没有这个权限点                 | 聚合计数，**大概率是 UI 没藏好按钮**，不是攻击 |
| `subject_disabled`   | 身份已禁用                     | 聚合计数                                       |

`out_of_scope` 是唯一真正值得逐条留痕的——它意味着这个人正在试着碰别人的数据。没有 `reason` 这一列，拒绝日志就是一堆"403"，没人会看。

### 7.4 两个不同的事务语义

|                  | 语义               | 为什么                                                |
| ---------------- | ------------------ | ----------------------------------------------------- |
| `audit_log`      | **与业务同事务**   | 权限加了但审计丢了 = 无法追溯。宁可操作失败，不留黑账 |
| `audit_decision` | **尽力而为，可丢** | 请求本来就要被拒，审计写失败不影响结论                |

### 7.5 不存属性快照

排查的关键是"谁在什么时候想动哪个 id"，属性可以按那一刻的参数复算。快照会腐烂、会长成没人维护的 JSON 口袋，且它让"为什么拒"从一个可推理的事实变成一个需要解释的副本。

**两张表都 append-only**，靠数据库授权（应用角色没有 UPDATE / DELETE），不靠代码纪律。

## 8. 代码里的入口

业务代码只碰三个工厂——判权和"能碰哪些数据"一次拿全：

```java
AccessScope.Buyer    buyer    = authorizer.buyer();                            // 买家：无权限点，边界是 buyer_id 列绑定
AccessScope.Seller   seller   = authorizer.seller(Permission.ORDER_READ);      // 商家：判权 + merchantId + shopIds
AccessScope.Platform platform = authorizer.platform(Permission.JOB_TRIGGER);   // 平台员工：判权，无店铺范围
```

- **拿不到凭据，带范围的查询写不出来**——归属与店铺范围从凭据里取，往下传给 service/mapper 进 SQL
- `seller.coversShop(id)` / `seller.coversNoShop()` 是范围判断的唯一 vocabulary；空集 = 一个店都碰不了，**不是全部**
- `seller.refundCap()` 是角色退款上限（分），null = 不限——能不能退是判权，能退多少是它；比较在 service
- 买家侧 controller 接 `buyer()` 是未落项（现在仍走 `current()`），见文件头状态

**身份只有一份来源：Spring Security 的 `SecurityContextHolder`。** 不另建 ThreadLocal——两套上下文一定会漂移，且只在并发下复现。

**异步上下文会丢。** `@Async`、线程池、`CompletableFuture` 里拿不到操作人。定时任务、消息消费必须显式 `Authorizer.runAs(...)`。**没有隐式兜底身份**：拿不到操作人就抛——给匿名兜底是权限系统最典型的自毁方式。

---

## 9. 数据归属进 SQL

按 `shopId` / `merchant_id` 查改的每一处，归属条件必须写进 SQL 谓词，不允许"先查出来再在 Java 里比对"——每新增一条读就多一个忘比对的机会。

**不存在和不是你的，都折 404。** 403 等于告诉对方"这个 id 真实存在"，拿它当枚举器就能确认哪些订单号有效。

**强制机制是 `DataScopeTest`**（源码扫描，不连库）：范围表上的 SELECT 必须在谓词位置出现归属列，绑了 `merchant_id` 还必须绑 `shop_id`——归属对了不等于范围对了。缺了红灯，精确到文件和方法。豁免只有一个——方法名以 `Internal` 结尾（调用方自行完成归属校验），而 `ArchitectureTest` 拦死 controller 调 `Internal`。两套规则配对，缺一不可。

## 10. 落地顺序

每一步都能独立验收：

1. **身份层 + 会话**——地基，其他层都要引用 `(类型, id)`
2. **声明文件 + 三份生成物 + 启动校验**——把"两份清单"问题一次性消灭
3. **`role` / `role_permission` / `role_grant` + 求值 + 范围谓词生成**——判权链跑通
4. **八条约束 + 启动扫描**——写入侧收紧
5. **两张审计表**——先接变更，再接拒绝

第 2 步做完就能验证一件事：**41 个码每个都能指到检查点，且没有死码。** 那是整套设计唯一的正确性证据，建议在那一步就把覆盖面测试写死。
