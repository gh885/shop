# 平台基线

> 重写分支的第 0 份文档。这里只放**与业务无关或弱相关**的能力，业务模块开工前必须先在 G0 里打勾。
>
> 用法：每做完一项把 `[ ]` 改成 `[x]`，验收标准当场能验，验不过的不算完成。

## 0. 三档划分

| 档            | 判据                             | 处置                       |
| ------------- | -------------------------------- | -------------------------- |
| G0 纯技术底座 | 与电商业务零相关，所有模块都依赖 | 自建或托管，**先做**       |
| G1 弱业务     | 有电商味道，但规则由国家或行业定 | 全部外采，只留接口         |
| G2 看似底座   | 优化的是"已经跑起来的东西"       | **明确不做**，等有流量再说 |

## 1. G0：纯技术底座

| #   | 能力         | 干什么                             | 来源                   | 验收标准                                           | 状态  |
| --- | ------------ | ---------------------------------- | ---------------------- | -------------------------------------------------- | ----- |
| 1   | 标识策略     | 主键、对外单号、凭证号             | 自建（无需独立服务）   | 一张订单同时有不可枚举的对外单号和连续无洞的凭证号 | `[ ]` |
| 2   | 配置中心     | 费率、阈值、开关热更新             | 托管（Nacos / Apollo） | 改一个费率不发版，5 秒内生效，可回滚               | `[ ]` |
| 3   | 开关与灰度   | 按商家/城市/百分比放量             | 托管                   | 能只对 1% 商家开启新流程                           | `[ ]` |
| 4   | 事件 outbox  | 事件与业务同事务落库再投递         | 自建                   | 停掉消费者再重启，事件不丢；重复投递不产生重复扣款 | `[ ]` |
| 5   | 幂等与防重   | 请求令牌 + 业务键唯一索引          | 自建                   | 同一令牌提交两次，只落一条记录                     | `[ ]` |
| 6   | 分布式锁     | 清分、打款、调账的临界区           | 托管（Redis）          | 两个并发清分请求，只有一笔成功                     | `[ ]` |
| 7   | 网关         | 路由、鉴权、限流、熔断             | 托管 + 少量策略        | 限流触发返回可识别的 429，不是 500                 | `[ ]` |
| 8   | 结构化日志   | 固定字段 + `traceId` 跨异步        | 托管（SLS 一类）       | 用一个 `traceId` 串起 HTTP → 事务 → 消费端         | `[ ]` |
| 9   | 指标与告警   | RED + 业务指标                     | 托管                   | 三条告警各触发过一次并被人处理过                   | `[ ]` |
| 10  | 审计留痕     | 框架层强制记录，不靠业务代码       | 自建                   | 改费率、冻结商家，能查到谁、何时、改前改后         | `[ ]` |
| 11  | 权限         | 三套主体：买家 / 商家子账号 / 运营 | 自建                   | 商家子账号查别家数据返回 404 而非 403              | `[ ]` |
| 12  | 调度         | 定时扫描 + 逐笔失败隔离            | 托管 + 自建扫描规约    | 一条数据失败不影响同批其他数据                     | `[ ]` |
| 13  | 测试数据工厂 | 一套 fixture 代替手工造数          | 自建                   | 新增一个集成测试不需要手写造数代码                 | `[ ]` |

第 13 项是给自己补的账：测试代码量接近主代码量，根因是每个集成测试都在手工搭数据。

**第 6 项的锁不覆盖库存扣减。** 库存走 `UPDATE ... WHERE available >= n` 的条件更新，不加分布式锁；锁只用于清分、打款、调账这类跨行临界区。

## 2. G1：弱业务，全部外采

| 能力               | 边界                                 |
| ------------------ | ------------------------------------ |
| 地址库与行政区划   | 只存 `adcode` 与快照，不自己维护层级 |
| 图片视频与 CDN     | 只存 `key` 与处理参数                |
| 短信 / 推送 / 邮件 | 自建模板与频控，通道外采             |
| 搜索**引擎**       | 只买检索能力，排序与召回规则自己定   |
| 支付渠道对接       | 渠道 SDK 与签名在适配层，不渗进交易  |
| 物流轨迹查询       | 只订阅轨迹事件，不解析承运商内部状态 |
| 电子面单           | 取号是外部调用，包裹状态归自己       |
| 企业实名核验       | 委托持牌机构，不自建 KYC             |
| 电子发票           | 税务口径归外部服务，账本口径归自己   |

共同点：**规则是国家或行业定的，不是你定的。** 自建等于替别人维护标准。

## 3. G2：明确不做

数据仓库、AB 实验平台、全链路压测、流量回放、服务网格、多活容灾。

它们优化的是"已经跑起来的东西"。没流量时建数仓，建出来的是没人查的表；没故障时搞多活，搞出来的是没人验证的配置。

## 4. 排序

两条判据：

1. **扇入**——几个模块依赖它。全员依赖的先做。
2. **不可逆**——定错了要全量迁移。先做且一次做对。

按这两条，头五件是：**标识 → 配置 → outbox → 审计 → 权限**。其余跟着业务模块走。

## 5. 预算红线

**G0 的投入，不超过第一个业务纵切跑通之前总工作量的三分之一。**

三个月不写业务代码只搭平台，最后一定发现平台是按想象设计的。底座够用就停，托管服务顶住，等第一条真实链路跑起来再回头补。

## 6. 附：关于发号器

**不自建独立发号服务。** 三样东西够用：

- **主键**：`uuidv7`（PostgreSQL 18 原生函数）。时间有序、索引友好、全局唯一、无中心节点。
- **对外单号**：类型前缀 + 日期 + 随机段，加唯一索引。不连续，防爬虫枚举。
- **凭证号**：按业务日期分段取号（一行 `daily_seq` + 行锁），**连续无洞**，只有清结算需要。

真正需要集中发号的只有"严格递增且无洞"这一类场景，电商里只有会计凭证。其余用 UUIDv7 就够，省一个服务、省一个单点。
