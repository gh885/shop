# Coupon 优惠券设计笔记

## 0. 出发点：三处已经留好的钩子

这个领域不是凭空接的，仓库里已经有三处明写的接口位：

| 位置                                  | 留的话                                                                                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `V17__order_orders.sql`               | `ck_orders_pay_amount CHECK (pay_amount = item_amount + shipping_fee)`——「将来上优惠券加 discount 列时同步换 CHECK」 |
| `shop/mapper/ShippingTemplate.freeAt` | 满额包邮基数是**商品总额**——「将来接优惠券时，这里的基数要跟『优惠后金额』对齐」                                     |
| `apps/seller/.../SidebarMenu.tsx`     | 已有「优惠券」菜单项，指向 `/marketing/coupon` 死链                                                                  |

第一条是**金额口径**的钩子，第二条是**运费与优惠的计算顺序**的钩子——后者是真耦合，不是待办清单，见 §5.5。第三条说明卖家侧的产品入口已经想好了。

## 1. 开工前必须拍死的三个板

### 决策一：券与自动促销共用一套优惠引擎

满减/打折（自动生效）与券（领取后选用）本质相同：`条件 + 优惠计算`，区别只在**触发方式**。做成两套的代价是订单金额计算链出现两个叠加点，之后每加一种玩法都要在两处改，且"券和满减能不能叠加"会变成两套代码之间的暗契约。

**定案：一套规则模型，`auto`（满足即生效）与 `coupon`（需领取+指定）只是触发方式的两个取值。**

模块名仍叫 `coupon`——一期只有券，就不起一个叫 `promotion` 的壳（符合项目「不预创建空目录 / YAGNI」的一贯做法），引擎放在模块内部。

### 决策二：券的价值锚点只有"减金额"

折扣券封顶之后也是减金额，运费券是"减运费"这一项的减金额。**兑换券/赠品券（换商品）不做**——它是 SKU 级的履约变更，会把订单行项目模型撕成两半（行可能是"买的"也可能是"送的"，价格、退款、库存全要分叉）。

### 决策三：一期只做店铺券，平台券的跨店分摊推迟

一笔订单只属一个店（`OrderService.create` 按店拆单），店铺券天然落在单笔订单内，**零分摊逻辑**。平台券跨店会同时引爆"优惠额按比例分摊 + 分/尾差处理 + 平台与卖家成本归属"三个问题，而成本归属要结算/分账模块来接——那还没开始。先做店铺券不是缩水，是把一条真正独立的依赖排在后面。

## 2. 领域模型：模板与实例必须分离

### 2.1 两类对象

- **券模板（`coupon_templates`）**：运营配置的规则。可编辑、可下架。
- **用户券（`user_coupons`）**：用户领取后持有的一张券。**创建后规则字段不再变，只有状态流转**。

分开的根本理由：运营改一次配置不能让历史数据跟着变。混成一张表的典型事故是"发放时是满 100 减 20，运营改成满 200 减 20 之后，用户券包里已领的券也变了"。

### 2.2 领取即固化

**有效期规则、面额、门槛在领取（或发放批次）时固化成绝对时间与绝对值**，读券时不再回查模板。模板此后被改或被删都不影响已发出的券。

代价是每张券多几个冗余列；收益是"券包"这个高频读路径完全不碰模板，且账可追。

### 2.3 规则维度清单（模板上要定的字段）

| 维度     | 取值                                                          | 备注                                              |
| -------- | ------------------------------------------------------------- | ------------------------------------------------- |
| 券类型   | 满减 / 折扣 / 无门槛 / 运费券                                 | 折扣**必须带封顶**，否则高客单直接打穿            |
| 适用范围 | 指定店铺 / 指定品类（含子类目）/ 指定 SPU / 指定 SKU / 排除项 | 一期只有店铺券，范围 = 本店；其余维度留字段留接口 |
| 有效期   | 绝对区间 / 领取后 N 天 / 固定周期                             | 领取时统一换算成绝对时间（§3）                    |
| 门槛     | 满 X 元                                                       | 基数定义见 §5.1，**这是客诉重灾区**               |
| 发放约束 | 总量 / 每人限领 / 单人总量                                    | 限量扣减与限领的并发口径见 §8                     |
| 叠加性   | 能否与其他券叠加                                              | 一期单券，字段留空（§5.3）                        |
| 承担方   | 平台承担 / 卖家承担                                           | 店铺券 = 卖家承担，直接进将来的结算扣款           |

范围的多值表达不要做成"N 行关联表 + 运行时 JOIN 匹配"——写放大且改一次配置锁很久。范围是**读多写极少**的数据，用"维度 + ID 集合"存一行，匹配在内存做。

## 3. 有效期模型（被低估的复杂度）

四种口径都会遇到：绝对区间、领取后 N 天、固定周期（每周一）、长期有效。

- **相对有效期必须在领取时换算成绝对 `effective_at` / `expire_at` 落库**，不在运行时用模板算。理由同 §2.2：模板会变。
- **正确性以绝对时间为准（被动过期）**：任何判定都用 `now > expire_at`，而不是"状态字段是不是 EXPIRED"。
- **定时任务只做状态收敛**，把到期的券刷成 `EXPIRED`，用途是券包分组、统计、清理索引。
    - 反模式：把"券能不能用"押在定时任务上。任务一停（或漏扫），过期券就能直接用——正确性挂在调度器的可用性上。
    - 与 `OrderTimeout` 的关系要说准：**可复用的是同一条原则——扫描依据是绝对时间列（`pay_expire_at` / `expire_at`），任务不自算窗口**；`OrderTimeout` 的到期判定也完全落在列上（它只声明三件事：什么状态、过哪个截止列、到期落成什么）。
      差别在**券比订单多一层**：订单状态必须由任务或用户动作推进，读时不会"自己变"；而"券此刻能不能用"是每次读券都要判的问题，所以券必须**读时被动判定**（`now > expire_at` 即不可用），任务只负责让展示与统计跟上。不能照抄"订单靠任务"这一面。

## 4. 状态机：锁定态不可省

```
UNUSED ──下单占用──> LOCKED ──支付成功──> USED
   │                    │
   │                    └──取消/超时关单/支付失败──> UNUSED（释放）
   └──时间到──> EXPIRED
UNUSED / LOCKED ──运营作废──> VOID
```

- **`LOCKED` 是必需的**。下单到支付完成之间有一个待付款超时窗口（`pay_expire_at`），不锁的话同一张券能被两个未支付订单同时用掉，等其中一个取消再释放就晚了。
- 锁定要绑**结算幂等键**（`checkoutKey`）或订单 ID，释放要按同一把钥匙**幂等**。触发释放的路径至少三条：买家取消、`pay_expire_at` 超时关单、支付失败——三条都必须释放，漏一条就产生"券永久锁死"的客诉。
- **`USED` 不可逆**。退款走"发一张新券"或"把原券恢复为可用"，不是把 `USED` 改回 `UNUSED`——否则核销流水断链，也算不清"这张券到底被用过几次"。

## 5. 算钱：优惠计算链（最容易出客诉的地方）

### 5.1 门槛基数必须写清并落在券详情页

"满 100 减 20"，这个 100 是什么？以下每一条都有人理解错：

- 商品**销售价**（不是划线价 `original_price`，不是原价）
- **不含运费**
- **不含其他优惠**（平行口径，见 5.2）
- 适用范围限定后，基数是**该券适用商品的小计**，不是整单商品额

### 5.2 平行优惠（定案），不是递进优惠

- **递进**：满减基于"上一轮优惠后的金额"算，计算顺序影响结果。
- **平行**：所有优惠都基于原始适用金额算，互不影响，可并行判定、可解释。

**定案：平行优惠。** 用户能自己算清楚，后端可并行判定，规则之间不产生隐式顺序依赖。选定就要用测试钉死：门槛判定用的基数和优惠额计算用的基数是同一个，不随其他优惠变化。

### 5.3 叠加与选券

- **一期：一笔订单只允许一张券**，叠加字段留但不实现。叠加规则用"互斥组 + 优先级"模型，不要写嵌套 `if`。
- **同一订单有多张可用券时用哪张**：用户想"省得最多"，平台想"先用快过期的"。这是业务决策，必须显式选一个，不能让它从代码里自然涌现。
    - 定案：**默认按优惠金额降序，同额按到期时间升序**，并允许用户手动切换。

### 5.4 金额明细必须拆解落库

`商品额 + 运费 − 优惠额 = 实付`，并且在订单上落全：`item_amount` / `shipping_fee` / **`discount_amount`（新增）** / `pay_amount` / `currency`，外加券 ID 与承担方快照。

同时按 V17 留的注释**换掉那条 CHECK**：`pay_amount = item_amount + shipping_fee - discount_amount`。

券的规则会变、券会被删，订单必须能自证"当时减了多少、凭什么减的"——所以券面额、券 ID、承担方都是订单快照的一部分，不是外键引用。

### 5.5 运费与优惠的顺序（现有钩子，必须显式选）

`ShippingTemplate.freeAt` 现在的满额包邮基数是**商品总额**，且注释里留了"要与优惠后金额对齐"。引入券之后用户一定会问："我用了券是不是就不包邮了？"

- **定案：包邮门槛按优惠前商品总额判定**（与现状一致，`ShippingFeeReadQuery` 的入参口径不变）。
- 配套：券详情页与结算页的文案要写明"包邮门槛按优惠前金额计算"，否则这是一条必然的客诉。

选另一个方向（按优惠后金额）也成立，但它会让"包邮门槛"和"券的门槛"两个基数不一致，更难讲清楚。

## 6. 多店铺：本期不涉分摊，但范围与拆单要对齐

- 店铺券 + 按店拆单 = 天然对齐，一笔订单最多一张本店券。
- 将来做平台券时，跨店结算会拆成 N 笔订单，优惠额要**按各店适用金额比例分摊**，且**除不尽的尾差必须有规则**（分给金额最大的那单，或最后一单兜底），否则 Σ分摊 ≠ 券面额，对账永远差几分钱。
- 平台券的"可用性判定按跨店合计"，但"核销与减免落在各店订单"——这是两次调用，必须保证两处口径一致（同一条计算链，见 §11）。
- 承担方决定结算：店铺券扣卖家货款，平台券平台自担。

以上全部推迟，写在这里是为了让一期的表结构不把路堵死（模板上预留 `scope`、`bearer` 字段）。

## 7. 逆向流程（最常被漏掉的一块）

退款必须回答四个问题，且要**在写代码前定死**：

| 问题                 | 定案                                                             |
| -------------------- | ---------------------------------------------------------------- |
| 整单退款，券退不退？ | 券未过期 → 退（发新券）；已过期 → 不退。券是限时权益，不是资产   |
| 部分退款，券怎么办？ | 一期**券不退**，只退实付差额。按比例退券留到有部分退场景之后再谈 |
| 退款金额口径？       | 退**实付**，绝不退券面额——否则等于给用户套现                     |
| 退的是原券还是新券？ | **发新券**（新的到期时间），原券保留 `USED` 记录，核销流水不断链 |

配套硬要求：

- **核销要有流水表**（谁、何时、因哪笔订单、用了哪张券、减了多少），退款回退也记一条。只靠状态字段回放不出历史。
- **退券不恢复"每人限领"额度**，否则能被反复薅。
- 退款链路在本仓库是 `aftersale` 发起（已有 `AfterSaleRefundedEvent`）。券的回退见 §11 的依赖取向。

## 8. 并发、幂等、过期

- **核销必须条件更新**：`UPDATE ... SET status='USED' WHERE id=? AND status='LOCKED'`，看影响行数，不做读-改-写。这与本仓库既有口径一致（条件更新 + 影响行数 = 并发闸门，见 `apps/server/AGENTS.md`「实体行为约定」）。
- **限量领取防超发**：总量扣减用条件更新（`WHERE issued < total`）或 Redis 预扣 + DB 兜底；**每人限领靠唯一索引兜底**，不靠应用层判重。
- **发券幂等**：事件驱动的发券（新人礼包、支付返券）必须能安全重放，用"业务键 + 唯一索引"去重。
- **下单核销与订单落库必须同事务**：券被用掉和订单成立要么都成要么都不成。这是强一致单体的红利，不要退化成事件最终一致。
- **过期以时间为准**，定时任务只收敛状态（§3）。

## 9. 发放渠道

主动领取（券中心）/ 注册礼包 / 支付返券 / 分享拉新 / 运营定向人群包 / 兑换码 / 积分兑换。

设计点：**所有渠道收敛到同一个 `grant(批次, 用户, 数量)` 入口**，量控、幂等、限领、审计都在这一处做。否则每加一个渠道就复制一遍限领逻辑。

兑换码要单独防两件事：一码多发（单次核销 + 唯一索引）与暴力枚举（码足够长 + 有效期）。

## 10. 展示与运营（会反向驱动后端设计）

- **"我的券包"必须能给出"不可用原因"**（未达门槛 / 不适用商品 / 已过期 / 不可与已选优惠叠加）。这一条会倒逼后端把可用性判定做成**可解释的**（返回原因码），而不是一个 boolean。
    - 与 aftersale 的取向一致：前端不复刻规则，但后端要给得出"为什么不行"。
- 券详情要有"去使用"导流（点到适用商品列表），这要求适用范围能**反查**成商品列表。
- 数据指标：领取率、使用率、带动 GMV、ROI。从事件流出，不靠事后扫表。
- 风控：刷券、套现、羊毛党；预算上限（平台/卖家可设）是运营的刹车。
- 币种：券面额必须带币种，与订单同币种，**不支持跨币种券**（`Money` 类型贯穿，同全库约定）。

## 11. 架构归属与依赖取向

### 决策：券是独立模块，不塞进 order

判据来自 `apps/server/AGENTS.md`：**模块切在流程中间 = 一个状态机横跨两个 schema**，是坏味道。券有自己完整的生命周期（领取 → 锁定 → 核销 → 过期/回退），塞进 `orders` schema 会让它和订单状态机纠缠。

```
一期：
coupon   → shop::api                     （券包/券中心展示店铺名；店铺归属本身不靠 api）
order    → coupon::api                    （预览算券 + 下单核销同事务）
aftersale → coupon::api                   （退款回退发券，同事务）

二期（范围扩到品类/SPU/SKU）：
coupon   → product::api                   （适用范围反查商品列表，"去使用"导流）
```

两点说明：

- **店铺归属校验不需要 `shop::api`**：卖家建券时 shopId 从 `common.ShopIdHolder` 取（`ShopMembershipFilter` 校验 `X-Shop-Id` 成员身份后设值），`common/` 是共享纯包，不需要登记依赖——`product` 有整套卖家端点却只登记 `inventory :: api`，就是这个道理。
- 编译期无环：coupon 不依赖 order/aftersale，核销记录里的 `order_id` 是**裸引用不加 FK**（同全库跨 schema 约定）。

### 决策：算钱有一条明确的归属链

- **coupon 只回答**："给定这批行和这个用户，有哪些可用券、每张能减多少、不可用的原因是什么"——纯函数式的可用性 + 优惠额计算，入参是**结算行事实**（shopId / productId / skuId / 单价 / 件数），不需要反过来读订单。
- **order 负责**编排、选券、落库、核销。
- 关键：**优惠计算必须插在 `CheckoutResolver.groupByShop` 这条现存链路上**，让**结算预览（`OrderService.preview`）与真实下单（`OrderService.create`）走同一条计算链**。现在这两条路已经共用 `groupByShop`，券接在同一个位置即可天然同源。
    - "预览一个价、下单另一个价"是最经典的客诉来源，本仓库已经用同源计算避免了运费上的这个问题，券不能破这个例。
- **核销走 api 命令同事务**，**发放 / 过期提醒走事件**。这与 `apps/server/AGENTS.md`「api 命令只用于同事务原子」的判据一致。

## 12. 分期

| 期   | 范围                                                                                                                               |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 一期 | 店铺券 + 满减 + 绝对有效期 + 单券不叠加 + 下单锁定/核销 + 取消释放 + 退款退券 + 买家券包（含不可用原因）——**后端已实现，前端待做** |
| 二期 | 折扣券与封顶、运费券、范围扩到品类/SPU/SKU、自动促销共引擎、叠加规则、选券策略可配、券中心与发放渠道                               |
| 三期 | 平台券与跨店分摊（依赖结算/分账）、定向人群、预算控制、兑换码、积分打通、风控、ROI 看板                                            |

一期验收的最小闭环：**领 → 预览看到可用与不可用 → 下单核销 → 取消释放 → 整单退款退券**，五段全通才算完
（已由 `CouponFlowIT` 逐段覆盖，含限领/防超发/占用闸门/封顶/有效性兜底）。

## 15. 实现记录：落地时的取舍与踩到的坑

一期后端按上面的定案实现（迁移 `V56`/`V57`，模块 `platform/coupon`，测试 `CouponFlowIT` 19 个用例覆盖五段闭环）。
以下是**写代码时才暴露出来、设计稿没写到**的部分——比上面的原则更值得回看。

### 15.1 与设计稿的偏离（都是有意为之）

| 设计稿                          | 落地                                                                                   | 为什么                                                                                                                       |
| ------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 券类型含满减/折扣/无门槛/运费券 | **没有 `type` 判别列**，只有 `threshold_amount` + `discount_amount`（前者 0 即无门槛） | 一期四种玩法实际只有一种；折扣券要 rate + 封顶、运费券是另一套履约口径，二期 `ALTER TABLE ADD COLUMN` 即可（加列比删列容易） |
| 每人限领（可多张）              | **固定 1 张**，靠唯一索引兜底                                                          | 限领多张无法用唯一索引表达；一期店铺券每人 1 张是常态，多张等有真实需求再上「计数 + 行锁」                                   |
| 有效期「领取时换算成绝对时间」  | 一期只有绝对区间，领取即复制                                                           | 相对有效期（领取后 N 天）是二期；但**复制到绝对列**的机制一期就建好了，二期只改换算函数                                      |
| 「退券不恢复每人限领额度」      | 唯一索引做成**部分索引**（`WHERE source = 'CLAIM'`）                                   | 全量唯一索引会让退款补偿券直接插不进去（原券还在手上）。补偿不占名额，正好落实「不恢复额度」                                 |
| 券上不记减免额                  | 加 `applied_discount_amount`（本单**实际**减免额）                                     | 面额 ≠ 实减：面额 100 的券用在 50 元单上封顶减 50。流水与对账要的是 50（见 §5.5 封顶）                                       |
| 承担方只在订单上落快照          | `coupon_templates` 与 `user_coupons` 也各有一列                                        | 否则 order 只能硬编码 `SELLER`——「谁承担」是券的属性，不该由 order 猜                                                        |

### 15.2 踩到的坑（都不是业务逻辑，而是本仓库的机制）

1. **命名接口是字节码级校验，不是包级**。`order` 只是调用 `coupon.model.CouponUnavailableReason.name()`，`ModularityTests` 照样报违规——只要 order 的常量池里出现 `coupon.model.*` 就不行。
   处置：`CouponUnavailableReason` 与 `CouponBearer` **移到 `coupon.api`**。它们本来就是对前端的码值与要进订单表的承担方，是名副其实的跨模块词汇；真正的内部状态词表（`UserCouponStatus` / `CouponSource` / `CouponUsageAction`）留在 `model`。

    > 参考先例：`OrderPaymentView`（order.api）把 `OrderStatus` 藏在 `pendingPayment()` 谓词后面，payment 因此从不 import 它。

2. **可空枚举会让前端 zod 拒绝 null**。springdoc 把 `nullable = true` 的枚举内联成 `{"type":["string","null"],"enum":[…]}`，openapi-ts 生成的 zod 不认这个形态（`contract-audit` 的 ERROR 闸门抓到）。
   处置：给枚举加 `@Schema(enumAsRef = true)`，让它输出成 `$ref` 组件 + `anyOf[{...},{type:null}]`，生成器就认了（同 `OrderTimeout` 的处理）。

3. **同一个业务情形不能有两条出参不同的路径**。领券「已领过」有两条：友好判重（先查一次）与撞唯一索引（并发兜底）。前者原本不带 `code`，于是前端时而有码时而没有。
   处置：两条都带 `COUPON_ALREADY_CLAIMED`。附带发现 `Validate.isTrue(cond, code, detail)` 的重载是 **400**，要 409+code 得显式 `BusinessException.conflict(code, detail)`。

4. **`Validate.isTrue(cond, msg)` 的文案参数会被即时求值**。`Validate.isTrue(usable, "…" + reason().message())` 在券可用时 `reason()` 为 null → NPE。改为 `if (!usable) throw …`。这类"看起来更简洁"的写法在带副作用/可空取值时有陷阱。

5. **金额值对象缺减法**。`Money` 只有 `plus`/`times`，而应付 = 商品 + 运费 − 券。补了 `Money.minus`，并让它**拒绝负结果**（金额类型语义是交易金额，负值无意义；需要"差额为负"的场景应先判方向）。

### 15.3 一期实际覆盖的边界（写下来免得被当成漏洞）

- **`NOT_EFFECTIVE` 是一期的兜底分支**：领券本身就有时间窗（未开始/已结束都拒），领券页也只列已开始的券，所以"领到手但还没生效"在一期没有用户可达路径。评估器仍然判它——真出现这种数据（相对有效期、运营预热券、直接改库）也不能被用掉。单测覆盖，IT 用直接改库的方式造出来验了一次。
- **券的占用闸门只在真并发下才会走到**：串行地拿同一张券下第二单，会在"候选里没有它"这一步就以 400 拒绝（券已不在 `UNUSED` 候选集里），到不了条件更新的 409。两条都是对的失败方式，409 是防御性的最后一道。
- **锁定的券不会被过期收敛**：`CouponExpiryJob` 只扫 `UNUSED`。下单时优惠已定格在订单上，不能因为券过期就让已下单的支付失败。
- **券包的状态是算出来的**（`MyCoupon.displayStatus`）：库里可能还是 `UNUSED` 而事实已过期（收敛任务没跑到），出参加工成 `EXPIRED`；券包按状态筛选也按这个口径（见 `UserCouponMapper.selectPageMine`）。
- **「未使用」页签连 `LOCKED` 一起收**（前端接入时补的）：`LOCKED` 对用户就是「还没用掉的券，只是暂时不可选」。若严格按库里的 `UNUSED` 过滤，这些券在三个页签里都查不到，用户会以为券丢了。展示状态仍如实出 `LOCKED`（前端显示「结算中」）——**页签收进来不等于状态改口径**。

### 15.4 端点与鉴权划分

| 端点                                                        | 鉴权                   | 说明                                                                                                                         |
| ----------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/shops/{shopId}/coupons`                           | **匿名**               | 店铺可领券（浏览和持有是两件事；`/api/*` 在 `JwtProperties.skipPaths` 里）。刻意不返「我领过没领过」——匿名通道拿不到当前用户 |
| `GET /coupons/mine`                                         | 登录                   | 我的券包（状态页签 + 店名 + 展示状态）                                                                                       |
| `POST /coupons/{templateId}/claim`                          | 登录                   | 领券（409 `COUPON_ALREADY_CLAIMED` / 409 已领完 / 400 不在发放期）                                                           |
| `GET/POST /seller/coupons`、`PUT /seller/coupons/{id}/stop` | 登录 + `COUPON_MANAGE` | 卖家建券/列表/停券；shopId 走 `X-Shop-Id`。列表带**已发放数**与**已核销数**（`usedQuantity`，只算 `USED`，占用中的不算）     |
| `POST /orders/preview`、`/orders/create`                    | 登录                   | 新增入参 `userCouponIds`（可空 = 不用券），出参带 `discountAmount` 与 `coupons`（含原因码）                                  |

前端接入注意：`/coupons/` 已加进 `apps/web/vite.config.ts` 的代理白名单（此前不在，会直接 404）；券包页面路由建议放 `/account/coupons`，避免与 API 前缀抢 `/coupons`。卖家菜单里那个 `/marketing/coupon` 死链现在有对应端点了。

### 15.5 一期范围内的边界

- **券的编辑**：只有建与停。已发出的券是快照，改模板只影响后来人，容易被误解成"改了就是全都改了"——要调整就停旧建新。卖家页面上有一句明说，避免卖家去找那个不存在的编辑按钮。
- **`coupon → product::api` 仍未引入**：一期券范围 = 本店全部商品，不需要反查商品；二期扩到品类/SPU/SKU 时才加（见 §11）。
- **默认选券由前端定**：后端不会替你选券（`appliedCouponId` 只是回显请求里的 id），结算页取候选里的第一张可用券作为默认；预览会因此多发一次（不重算就没有券后价）。
- **抢券的表达**：限量（`issued_quantity >= total_quantity` → `soldOut`）就是"先到先得"，领完的券仍出现在列表里置灰而不是消失；`validFrom` 同时是可领时段起点。**「仅剩 N 张」做不了**——匿名可领券出参只有 `soldOut` 一个布尔，没有 total/issued。不为一句紧迫感文案给匿名接口加库存口径（详见 reference §6.2）。
- **「已领取」标记不持久**：可领券端点是匿名的，出参刻意不含"我领过没"（见 §15.4），所以浮层里的已领取状态是局部态，刷新即丢；重复点由 409 + `COUPON_ALREADY_CLAIMED` 兜底成「已领取」。要根治得给匿名端点补标记或另开一个登录态端点——一期不做。
- **券卡片只出三行**（面额 / 一句话规则 / 店名+有效期）：模板名、承担方这类字段不上卡面。判据见 §16.1 与 reference §6.1——每一行都在逼用户做交叉判定。第三行在窄屏会被截断，所以它是可聚焦的 Tooltip 触发器（全值拿得到），不是一段纯文本。
- **选券行的整行不可点**：只有 16px 的单选圆点可点，行样式（边框 + 选中底色）却暗示整行可点。这是 `Item` + `RadioGroupItem` 这套组合的既有形态（结算页的地址选择同款），修它要动 `packages/ui-web` 的 `Item`，不该只改选券这一处——已记进 `TODO.md`。
- **券的演示状态徽章用了品牌橙**：`variant="default"` 是实色 primary，按 `packages/ui-web/DESIGN.md` §0.3 品牌橙只留给转化引导；`product`/`order` 的常量表同款，属既有约定问题，整改应一次覆盖三处（已记进 `TODO.md`）。

## 16. 平台对照与二期候选

一期的规则模型不是凭空定的，摊开淘系/京东的做法逐条对过一遍，**方向基本都对**（门槛平行、一商品一券、取最优、不找零、承担方、快照）。
对照原始资料与逐条映射见 [`docs/reference/coupon-platform-practices.md`](../reference/coupon-platform-practices.md)，这里只留结论。

### 16.1 关键认知：券种是维度组合，不是枚举清单

平台自己就把券拆成正交维度在讲（京东官方原文：使用限额／商品品类／销售主体／存在形式）。
**"支持几种券"是个错问题，该问的是每个维度支持到第几个取值**——按枚举做设计会得到一堆同义同构的券种，
每加一种都要在金额计算链上开一个分支。

### 16.2 最小业务闭环只需要一种券

闭环是「**卖家建券 → 用户看得到 → 领得到 → 下单用上 → 金额对得上 → 取消/退款有交代 → 卖家看到效果**」。
这条链上，**满减券（含 `threshold = 0` 的无门槛）一种就够**——平台那些其它券种解决的是别的问题，不是闭环缺环：

| 券种                     | 真实解决的问题                 | 属不属于闭环       |
| ------------------------ | ------------------------------ | ------------------ |
| 满减 / 无门槛            | 促销降价、提升客单             | ✅ 闭环本体        |
| 折扣券                   | 同上（另一种报价表达）         | 变体，非缺环       |
| 运费券 / 包邮券          | 运费敏感品类的转化             | 独立成本项，非缺环 |
| 品类券 / 商品券          | 精准圈品、控成本               | 精细化，非缺环     |
| 跨店满减 / 平台券        | **平台方**贴钱做大促、多店凑单 | 平台化，需结算分账 |
| 裂变券 / 口令券 / 直播券 | 拉新与拉流量                   | 增长，非交易闭环   |
| 有价券 / 兑换码          | 券本身当商品卖、线下核销       | 独立业务形态       |

结论：**一期已实现的这一种券，业务闭环在"券种"这一维上不缺东西**。真正缺的是两处，都不在券种上（**都已在"前端接入"这一批里补掉**）：

1. **前端页面**（§15.5）——功能对用户不可见，闭环等于没通。买入侧券包/领券/结算选券与卖出侧建券页同批实现。
2. **卖家看不到效果**——原 `CouponTemplateResponse` 只有 `totalQuantity` / `issuedQuantity`，没有**已核销数**。
   已补 `usedQuantity`（`GET /seller/coupons`，只算 `USED`）：卖家建完券不只知道"发了多少"，
   还知道"用掉多少"，两者的差额就是**领了没用掉**的那批——券是带来了订单，还是只在券包里养僵尸券。

### 16.3 二期候选（按"变体 / 机制"分级）

| 候选                      | 类型 | 成本 | 说明                                                                                      |
| ------------------------- | ---- | ---- | ----------------------------------------------------------------------------------------- |
| ~~卖家侧已核销统计~~      | 已做 | —    | `ShopCoupon` + `countUsedByTemplateIds`，一次批量查询，不做成核销率（比率还原不回绝对数） |
| 折扣券（N 折 + 必须封顶） | 变体 | 低   | 评估器加分支；`ALTER TABLE ADD COLUMN`（加 rate/封顶列），不加 `type` 判别列              |
| 相对有效期（领取后 N 天） | 变体 | 低   | §15.1 已把"领取即固化成绝对时间"的机制建好，二期只改换算函数                              |
| 定向发放 / 后台发券       | 入口 | 中   | 扩展 `user_coupons.source`；先做"给指定用户发一张"，不做人群包                            |
| 运费券                    | 机制 | 中   | 要抵 `shippingFee`，与商品券口径不同且需可叠加（叠加=互斥组模型）                         |
| 品类券 / 商品券           | 机制 | 高   | 引入"券的适用商品集合"，要 `coupon → product::api` 与圈品存储设计                         |
| 跨店满减 + 优惠分摊       | 机制 | 很高 | 会同时引爆分摊、尾差、承担方分账、部分退款，且反向改订单金额口径——**单独出设计文档再做**  |

排序建议：**折扣券 + 相对有效期（纯变体、用户感知强）→ 其余按业务需要逐个立项**。
跨店满减不要顺手做，它把结算/分账模块一起拖下水，而那个模块还没开始。
