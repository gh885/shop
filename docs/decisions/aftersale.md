# Aftersale 售后前端闭环设计笔记

> 目的：逆向环（申请 → 卖家处理 → 回寄 → 确认收货退款）后端早已做完，前端却停在
> 「点按钮弹一句即将上线」。这篇记下补齐时定下的边界与取舍，避免下次有人重新发明一遍。
> 代码位置以 `apps/` 为根；`web/` = 买家端，`seller/` = 卖家工作台，`server/` = 后端。
>
> **状态：买家端全链路 + 卖家端决策上下文已实现**（2026-09）。卖家「退款售后」工作台页仍缺一个列表端点，见 §4。

---

## 0. 出发点：断点在哪

| 环节         | 断点前                                                         | 现在                                                     |
| ------------ | -------------------------------------------------------------- | -------------------------------------------------------- |
| 买家申请     | `orders/$orderId.tsx` 里 `notify.info("「申请售后」即将上线")` | 申请弹窗（类型 + 理由）→ `POST /orders/{id}/after-sales` |
| 买家看进度   | 订单详情只有 `afterSaleStatus` 投影列，没有售后单本体          | 售后卡：类型/状态/金额/理由/回寄单 + 撤销/回寄入口       |
| 买家回寄     | 无入口（后端 `returnGoods` 早已并入 logistics 的 RETURN 包裹） | 回寄弹窗；已填单可查看退货物流（复用物流详情页）         |
| 卖家处理     | 订单列表行内「同意/拒绝」**但看不到类型与理由**                | 决策弹窗先摊开售后单（类型/理由/金额/退货运单号）        |
| 卖家确认收货 | 需求同上                                                       | 同上（带退货运单号供核对）                               |
| 卖家待办视图 | `/trade/refund` 是占位页，处理入口散在订单列表里               | 退款售后工作台：按状态分页 + 行内动作（见 §8）           |

## 1. 决策一：前端不复刻售后状态机

后端的状态机唯一真相是 `server/.../aftersale/model/TicketAction`（转移表 + 每行的 409 文案）。
前端**不写第二份**转移表，只回答两个它能独立回答的问题：

1. **能不能发起申请**（`canApplyAfterSale`）：三项都在订单契约里 —— 已完成 + 申请窗口未过 + 没有进行中的单；
2. **这张售后单此刻露出哪些操作**（`buyerAfterSaleActions`）：由售后单自身状态直接读出。

转账合法性一律不在前端判定：点了发请求，被 409 拒了就按后端 detail 提示（`notify.fromError`）。
好处是后端加一个终态或改一处转移，前端不会因为「忘了改副本」而露出一个必然 409 的按钮。

## 2. 决策二：404 = 没有售后单，不是错误

`GET /orders/{id}/after-sales` 在「从未申请过」时 404。这是「没有」而不是「失败」，
与 logistics「未发货 404」同一套判据：query 层把 404 归零为 `null`，其余错误照实抛。

相应的测试代价（踩过，写在这免得再踩）：**测试期必须装配 SDK client**
（`apps/*/src/test/setup.ts` 的 `configureSdkClient("http://localhost:8080")`）。
不装配时非 2xx 走 ky 自己的抛错路径（它会预读 body），hey-api 解析时报
"Body is unusable"，调用方拿到的是 `{status: 0}` 的网络错误 —— 于是「404 → 没有售后」
这类按 status 分支的逻辑**测不到**，测试还会带上一个 unhandled rejection。
baseUrl 必须是绝对地址：jsdom 的 `new Request()` 来自 undici，相对 URL 直接抛错。

## 3. 决策三：卖家点「同意」之前必须看得见售后单

列表上一个「售后申请中」徽章不足以支撑决策：仅退款点头就退钱，退货退款点头才开始等货，
两者对资金与货物的走向完全不同，而按钮是同一颗。所以决策弹窗拉 `GET /seller/orders/{id}/after-sales`
把类型、买家理由、退款金额（确认收货时再带退货运单号）摆出来，并按类型给出「同意之后会发生什么」。

配套两条：

- **没拿到售后单也照常可确认**（404/请求失败降级成一句说明）：列表徽章已经说明有售后在，卖家可能有别的上下文，不该被锁在门外；
- **没拿到类型就不断言走向**：加载中/读取失败时那句「同意后会怎样」不渲染成默认口径，否则会在退货退款的单上写着「商品不寄回」。

顺带修正了一处与代码不符的文案：拒绝后**可以**重新申请（后端只挡「进行中」的单），
原文案写的是「拒绝后买家不可再次申请」。

## 4. 决策四：展示文案两端各自维护

同一个 `TicketStatus`，买家看到「待寄回商品」（他要做的事），卖家看到「退货中」（他要判断的状态）。
强行合并成一份共享文案只会逼一方读另一方的话。所以买家文案在 `web/src/order/after-sale.ts`，
卖家文案在 `seller/src/order/constants.ts`，**契约类型**仍然共用 SDK 生成的 `TicketType / TicketStatus`。

## 5. 决策五：门槛不成立时整条不渲染

`OrderShopSection` 的「申请售后」用 `canApplyAfterSale` 控制**渲染与否**，不是渲染成禁用灰按钮：
买家问的是「这单还能不能申请」，一个永远点不动的按钮只会逼他猜原因。

已退款不给入口（`REFUNDED` 一律 false）：后端 V1 没有拦「退款后二次申请」，
前端不主动把用户送到重复退款那条路上。已拒绝/已撤销在窗口内允许重新申请 —— 那是买家的正当权利。

## 6. 代码地图

```
web/src/order/
├── after-sale.ts                 领域层：类型 + 文案 + buyerAfterSaleActions / canApplyAfterSale（纯规则）
├── after-sale-queries.ts         数据层：queryOptions（404→null）+ 申请/撤销/回寄 3 个 mutation 与统一失效
├── AfterSaleCard.tsx             订单详情里的售后卡（纯展示 + 回调）
├── AfterSaleApplyDialog.tsx      申请弹窗（类型单选 + 理由）
└── AfterSaleReturnDialog.tsx     回寄填单弹窗（快递公司 + 运单号，可改单重交）
seller/src/order/
├── data.ts                       getShopAfterSale（404→null）、listAfterSaleTickets（工作台分页）
├── queries.ts                    售后单详情 / 工作台列表的 key 与 options
├── after-sale-decision-dialog.tsx  同意/拒绝/确认收货三态决策弹窗（订单列表与工作台共用）
└── refund/                       退款售后工作台（路由 /trade/refund）
    ├── model.ts                  页签定义 + 一行可执行的动作（纯规则）
    ├── use-refund-list.ts        URL 同步的分页/页签 + 列表 + 三个处理动作
    ├── refund-tabs.tsx           页签栏
    └── refund-table.tsx          表格（纯展示 + 事件上抛）
```

失效口径：三个写操作都同时失效 **售后单 + 订单详情 + 订单列表**。
订单上的 `afterSaleStatus` 是 aftersale 写回的投影列，少失效一棵就会出现
「售后卡已更新、订单徽章还是旧值」这种自相矛盾的界面。工作台同理，还要连带失效它自己的列表与三类 key。

## 7. 卖家工作台列表端点（GET /seller/after-sales）

`PageResult<SellerTicketItem>`：售后单本体 + **订单摘要**（订单号/买家/行数/首个商品名），status 可选筛选，时间倒序。

三处值得记的取舍：

1. **订单摘要经 `order::api` 批查后内存拼装**，不是本模块的列。新增的
   `OrderReadQuery.summariesByIds` 仍是按主键 IN 的点查（`infra.db.IdBatchReader`，与 shop/product 的批查同一条管道），
   行数/首行名是同 schema 子查询 —— 跨 schema 不 JOIN 这条线没动。
2. **不做「进行中优先」的排序**：待办与历史是同一张表的两种看法，交给 status 筛选分流
   （前端默认停在「待处理」页签），比在 SQL 里编一个状态优先级更好讲清楚。
3. **拼不出订单摘要就 500，不降级**：订单行没有删除路径，缺摘要说明数据被外力改坏。
   宁可让它响，也不要给出一行"订单号空着"的售后单让卖家去猜。
   索引配套：`V55` 补 `(shop_id, created_at DESC)`；带状态的页签走原有的 `(shop_id, status)`。

前端 `/trade/refund` 默认页签 = 待处理（售后有时效，进来先看待办），页签与页码进 URL；
行内动作由售后单状态推出（待处理 → 同意/拒绝，退货中 → 确认收货，终态 → 无），
点开的是同一个决策弹窗 —— 同一个不可逆决定不该有两套说法。

## 8. 已知边界（刻意留白）

- **买家订单列表没有售后徽章**：`OrderListItemResponse` 没带 `afterSaleStatus`（只有详情契约有）。
  加它要动列表契约，故未做；买家目前从订单详情进售后。
- **没有售后时间线**：`aftersale.ticket_events` 没有出参接口，前端只展示当前状态与关键时刻
  （申请/退款/回寄），不凭当前状态编造一条看似权威的轨迹。
- **V1 是整单售后**：`Ticket.orderItemId` 已预留行项售后，退款口径 = 整单实付；
  前端按钮挂在商品行上，但语义仍是整单（与后端一致）。
- **后端未拦「已退款后再次申请」**：`AfterSaleService.apply` 只挡「进行中」的单，
  理论上同一订单可被重复退款。前端已用入口门槛规避，但 API 层面仍然敞着 ——
  建议后端补一条「存在 REFUNDED 单则拒绝」（属后端待办，不是前端能兜住的）。
- **工作台没有计数角标**：菜单项上不显示「待处理 N」，每页都要点进去才知道有没有活儿。
  要做得再加一个 count 端点（或让列表返回 statusCounts），暂按 YAGNI 留白。
