# Auth 模块设计笔记

> 目的：把登录相关的每个安全决策记下来——为什么这么做、不做什么、踩过什么坑。
> 叙述方式统一为「攻击者想干什么 → 我怎么断他的路」，既是设计依据也是面试素材。
> 代码位置以 `apps/server/src/main/java/com/shop/platform/` 为根，下称 `platform/`。

---

## 0. 总览：登录其实是两个问题

| 阶段         | 回答的问题                                   | 关键词               |
| ------------ | -------------------------------------------- | -------------------- |
| **身份认证** | 你是谁？（验证手机号/密码真的是本人）        | 对抗、限流、防猜测   |
| **凭证管理** | 怎么记住你？（发什么凭证、放哪、丢了怎么办） | 双 token、轮换、吊销 |

分开谈很重要：身份认证的核心矛盾是「人和攻击者」，凭证管理的核心矛盾是「安全和体验」。混在一起讲容易两边都说不清。

---

## 1. 背景：这个领域大家都怎么做

### 凭证的两大门派

**Session 派**：登录后服务端记一本账（谁在哪个 session），发给客户端一个编号。优点是控制权全在服务端——想踢人随时删账。缺点是每次请求都要翻账本，服务器多了还得共享账本。

**JWT 派**：服务端不记账，签一张防伪名片给客户端，名片上写明身份和有效期，签名防篡改。每次请求验个签名就行，不用查任何存储，加机器随便加。代价是**名片发出去了就收不回**——有效期之内它永远是通行证。

一句话总结取舍：**Session 把状态留给服务端，JWT 把状态换成时间来兜底**。小系统选 Session 完全够；只有当「查存储」成为瓶颈或微服务需要跨服务验身时，JWT 才真正划算。

### 业界的主流混合做法

纯 JWT 有收不回的问题，所以现在事实上的标准是**双 token**：

- **access token**：有效期很短（几分钟），每次请求都带着；
- **refresh token**：有效期长（几天），只在 access 过期时用来换新的，而且服务端留底、可以吊销。

这样「有状态的负担」被压缩到了一个低频接口上，平时请求依然无状态。

## 2. 身份认证阶段：这是一个对抗场景

出发点就一句话：**每个环节先想攻击者的算法——他能观察到什么信号，我就切断什么信号。**

下面按攻击目的分四组。

### 攻击一：账号枚举——「哪些手机号注册过？」

攻击者的打法：拿一批手机号挨个调接口，通过返回的差异筛出「已注册」名单（精确营销、定向撞库都用得上）。他能观察的信号只有两个：**响应内容**和**响应时间**。

对应的防御就是把这两个信号都做成常量：

1. **响应内容恒定**：登录失败永远返回同一句「手机号或密码错误」，不管错的是手机号、密码，还是「账号存在但从未设密码」——「未设密码」这一态不通过登录失败响应暴露（早期用 `PASSWORD_NOT_SET` 区分，被短信自动注册的大量活跃号放大了枚举面，已移除）。忘记密码同样静默：不存在的手机号也走完整流程并返回成功（静默成功），让攻击者无法凭响应/时序区分。代价是会给请求方自报的号码真实发出短信——因此该端点尤其吃频控，除 IP/每号冷却/每日限外，还额外做了「单 IP 每日不同手机号数」上限，防止一个 IP 横扫大量号码轰炸。
2. **响应时间对齐**：这是最容易被漏掉的。「手机号不存在」天然比「密码不对」快——后者要算一次 BCrypt。于是查无此人时也要对着一个假哈希（dummy hash）白算一次，把那约 200ms 补齐。攻击者掐秒表测不出任何东西。

一个容易误解的点：**代码内部是有分支的**——日志会精确记录这次失败是「无此用户」「没设过密码」还是「密码错误」。运营抓撞库者靠的就是这些日志。所以准确的说法是「对外统一、对内精确」：给攻击者看的是常量，给自己留的是情报。

> 代码落点：`AuthService.authenticate()`（dummy hash + 统一文案 + MDC 日志，无 `PASSWORD_NOT_SET` 分支）、`SmsCodeService`（三层频控 + 单 IP 去重号码上限 + 静默发送）。

### 攻击二：撞库——「拿别的网站泄露的密码来碰运气」

三层防线：

1. **限流**：IP 维度（10 次/分钟）+ 手机号维度（5 次/10 分钟），双管齐下。计数用 Redis 的 INCR，且 INCR 和设置过期时间包在同一个 Lua 脚本里原子执行——这两步如果分开，进程恰好在中间崩溃就会留下一个永不过期的计数键，等于把某个 IP 永久误伤到人工清理为止。
2. **抬高单价**：BCrypt cost 12 让每次尝试消耗约 200ms CPU。撞库百万次就是五十多个核时的纯烧钱，经济学上不划算。
3. **压缩字典**：密码策略（最少 8 位、不超过 BCrypt 的 72 字节硬限制、不能等于手机号、常见弱密码黑名单），把「123456」这类必中答案提前挡掉。

### 攻击三：猜短信验证码

6 位数字，总共 100 万种可能。防御的关键不是「限制请求次数」，而是**把猜测空间从数学上封顶**：

- **尝试计数器**：每个验证码最多容错 4 次（错满 5 次即作废，要求重发）。也就是说一个验证码从生到死最多被猜 5 次，命中率上限是十万分之五——所以**校验接口根本不需要再做限流**，数学已经封死了。
- **错满作废、成功即焚**：前几次输错只计数、码保留（人都会手滑，一次就烧码的产品没人敢用）；第 5 次错或首次成功时删除。
- **存储即 HMAC 摘要 + 服务端 pepper**：Redis 里存的是 `HMAC-SHA256(phone:code, pepper)` 而不是明文。这里踩过一个坑：最初用裸 SHA-256，但手机号就在 key 里，全量拖库后枚举 10⁶ 个组合毫秒级就能还原 6 位码——裸哈希对低熵输入形同虚设。换成 HMAC 后 pepper 在应用配置而非 Redis，「拖库」必须升级为「拖库 + 攻陷应用配置」才能开始猜解。refresh token 同理走这套摘要。
- **开发便利不变成后门**：本地联调有固定码 666666，但它所在的 Bean 用 `matchIfMissing=false` 显式装配——生产环境忘了配置真实短信通道时直接启动失败，而不是静默开着万能码上线。

### 攻击四：短信轰炸——「烧你的钱，骚扰你的用户」

短信按条计费，这是唯一能直接换算成钱的攻击。三层频控：

```
IP 维度      10 条/分钟   ← 挡脚本
手机号冷却   60 秒/条     ← 挡连点
日限额       20 条/天     ← 兜底止损
```

### 设计细节：限流要让用户看见吗？

分场景，而且两个方向都是故意的：

- **密码登录被限流** → 返回和普通登录失败一模一样的响应（还照常执行一次 dummy hash 保持耗时一致）。连「你被限流了」这个信息都不给攻击者。
- **短信发送被限流** → 明示 429 和倒计时。因为「发短信」这个动作本身不涉及账号是否存在，藏起来没有安全收益，明示反而让正常用户知道该等多久。

判断标准：**隐藏信息的前提是信息本身有泄露价值。**

### 收尾：自己复盘出的洞（已修复）

这部分面试时主动讲，比声称无洞更有说服力：

1. **IP 提取曾盲信 X-Forwarded-For**：直连部署下这个头是客户端随便填的，伪造它就能让整个 IP 维度限流失效。修复后默认只信 TCP 对端地址（remoteAddr），只有显式配置 `shop.web.trust-forwarded-for=true`（部署在会覆写此头的可信反代之后）才解析。（`infra/web/ClientIp.java`）
2. **短信登录漏了账号状态检查**：密码登录会校验账号是否被禁用，短信路径漏了——禁用账号换个通道就能登进来。一行修复补齐。（`AuthService.loginBySms`）
3. **并发首登的竞态**：两个合法验证码同时注册同一手机号，靠数据库唯一索引兜底，应用层捕获冲突后回读对方插入的账号即可幂等。过程中发现一个 PG 特性：事务内 insert 撞索引后整个事务中止，catch 了也没法再查——所以该方法本来就不该开事务。
4. **重置密码曾发 64 位长串**：用户根本没法人工抄写，改为复用 6 位验证码体系（同一套频控、哈希存储、尝试上限）。
5. **吊销全设备时用了 Redis KEYS 命令**：O(全键空间) 的阻塞命令，生产环境会卡住所有请求。改为维护每用户的设备集合（Set），吊销就是遍历一个小集合。
6. **OTP/凭证存储用裸 SHA-256**：低熵输入（6 位码）在全量拖库下可离线秒破（key 里就有手机号）。修复为 HMAC-SHA256 + 服务端 pepper（`SecretHasher`），并把哈希计算从调用方下沉到 `RefreshTokenStore` 内部——调用方只传原文，摘要细节不再外泄到业务层。
7. **refresh 链路漏了账号状态检查**：登录两条路都查 status，刷新链路却没查——被封禁的账号只要握着未过期的 refresh 就能一直续命。补上后「封号」自动等于「吊销全部会话」（旧码已消费、新码不签发）。admin 员工侧同款问题一并修。
8. **重放检测会误伤多标签页**：两个标签页同时启动、拿同一个旧 refresh 并发刷新，后到者会被判成盗用、触发全端吊销——用户莫名其妙全线掉线。修复：消费记录带时间戳，15 秒内的重复按并发竞争静默拒绝，超出宽限期才升级为全端下线。
9. **响应体里夹带 refreshToken**：httpOnly cookie 的意义是 XSS 读不到 refresh，但登录/刷新响应体又把它明文返回了——防护被自己拆台。所有客户端实际都走 cookie，`TokenPair` 序列化时已剔除该字段。

## 3. 凭证管理阶段：发出去的东西要能收回来

### 这套方案是怎么选出来的

先立两条必须同时满足的约束，方案就是被它们逼出来的，而不是抄某家的模板：

1. **凭证要能收回**。登录是一次性的，之后几个月用户都带着凭证到处走。一旦被封、被盗、被发现泄漏，系统必须「说收回就收回」，不能眼睁睁等它自然过期。
2. **凭证要尽量让 JS 摸不到**。电商前端是复杂 SPA，XSS 面大；凭证存放位置的最高优先级是「即便有 XSS，攻击者也拿不到长期有效的东西」。

规则一淘汰了「纯 JWT/纯无状态」——它发出就收不回；规则二淘汰了「把长凭证放浏览器可读位置」。剩下的可行域，就是**无状态短凭证（access）+ 服务端留底的长凭证（refresh）**这一组合。

#### 关键决策点总表

| 决策点       | 选了什么                                   | 为什么                                                   |
| ------------ | ------------------------------------------ | -------------------------------------------------------- |
| 凭证形态     | 双 token（无状态 access + 有状态 refresh） | 状态负担压到低频接口，日常请求零查库（见下表）           |
| access 算法  | JWT，ES256，10 分钟寿命                    | 免查库；非对称签名防私钥外泄；短寿命限住黑名单缺失的窗口 |
| refresh 形态 | 不透明随机串（32 字节），7 天              | 要支撑吊销/轮换，JWT 优势用不上；随机串推不出信息        |
| refresh 存储 | 只存 HMAC-SHA256 摘要，不落明文            | 拖库拿到的不是凭证本身（见下）                           |
| 客户端条目   | access 内存 / refresh httpOnly cookie      | JS 摸不到长期凭证（见下）                                |
| 有效期权威   | 服务端存储 TTL，cookie maxAge 只是展示层   | 吊销靠服务端删，不靠浏览器自觉                           |
| 吊销粒度     | 按设备、按主体两级                         | 登录态是「某设备上的某账号」，登出不该误伤别的设备       |
| 收回时机     | 一次一换（rotation）+ 重放裁决             | 让「被盗的旧凭证」复用本身成为告警信号                   |

### 为什么是两种不同的 token

- **access token 选 JWT**：每个请求都要验它，必须做到零查库——签名本地一验就过。
- **refresh token 反而选不透明随机串**：它本来就要查库（要支持吊销、要轮换），既然都要查库，JWT「免查库」的优势就用不上；而随机串泄漏后推不出任何信息，吊销也只是删一个 key。

一句话：**双 token 不是「多一层」，而是把「有状态的负担」从每个请求挪到只有一个低频接口（=refresh）上**。平时请求依然无状态、可随便加机器；需要收回时，只有那个低频接口查一次库、删一个 key——负担和收益都是在这里换的。

**为什么是这两档寿命（10 分钟 vs 7 天）**：access 越短，被偷走后的可用窗口越小，但用户越容易撞上过期需要刷新；refresh 越长，用户越无感，但一旦泄露危害越大。10 分钟 / 7 天的比例是把「刷新是低频、可静默」和「泄露窗口要小」折出来的日常惯例，不是拍脑袋——原则是**寿命跟着凭证的「可收回性与危害」走，而不是统一定长**。

各取所长，而不是「既然用了 JWT 就全套 JWT」。

签名算法选 **ES256**（椭圆曲线）而不是最常见的 HS256：HS256 是对称的，谁能验签谁就能签发——将来加了网关或多服务，私钥就得到处发。ES256 私钥只留在签发方，公钥随便分发。单体阶段不为微服务过度设计，但**不可逆的技术选型做在前面**。

另外 JWT 里带 `kind=user/staff` claim：买家 token 和平台员工 token 是两套 UUID，claim 层一刀切，员工 token 拿到 C 端链路直接拒绝——防止两套随机 ID 混淆。

### 放在哪里：一场 XSS 与 CSRF 的权衡

| 凭证    | 位置                                     | 理由                                                                                                  |
| ------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| access  | 浏览器内存变量                           | JS 读不到（localStorage 一旦有 XSS 就是全部送人）；刷新丢失由启动时静默刷新补偿                       |
| refresh | httpOnly cookie，且 `path=/auth/refresh` | JS 读不到；SameSite=Lax 挡住跨站携带；path 限定让它只在换新这一个接口出现——即使别处出了漏洞也够不着它 |

cookie 同时支持 body 传参兜底，脚本测试等非浏览器客户端走 body。注意方向是单向的：**入站**接受双来源，**出站**响应体绝不携带 refreshToken——曾经夹带过，等于把 httpOnly 的防护自己拆掉（`TokenPair` 序列化时已剔除该字段）。

每一个安全收益都配了一个工程补偿：内存态刷新即失 → 启动时 `bootstrapAuth()` 单例静默刷新；SSR 首屏裁决不了登录态 → 路由守卫 + 客户端守卫双保险。

**买/卖家共享会话（轻量单点登录，淘宝千牛式）**：买家端(web)与卖家端(seller)共用同一个 `account.users` 统一账号（无角色字段，手机号即身份）。要让「登录一处另一处自动登录」，只靠共享账号还不够——必须共享**会话**。做法是给 refresh cookie 配共享父域 `Domain=.example.com`（`shop.auth.refresh-cookie-domain`，生产环境变量注入，本地留空）。两个前端站都走 `/auth/refresh`，拿同一个 refresh cookie 静默换 access，于是天然单点登录。三个受控决策：

1. **身份 vs 权限**：共享会话只解决身份，不解决权限。卖家端能操作哪些店铺完全由 `X-Shop-Id` + 店铺成员关系在服务端校验决定——单纯「登录了买家账号」绝不等于拥有卖方权限，这是安全边界，必须写在产品规则里。
2. **admin 不纳入共享**：平台员工走独立 staff 账号体系（`/admin/auth/refresh`，JWT 带 `kind=staff`），与 C 端隔离，避免员工身份混入普通用户会话。
3. **同名**：共享会话意味着买家会话被窃取也同时暴露卖家工作台入口，属于刻意接受的权衡——风险由店铺成员关系这一鉴权层兜底，而非靠「两端各自登录」来隔离。

**为什么 refresh 只存摘要、不存明文**：落库/落 Redis 的凭证一旦被拖，等于把「能直接拿去换 access」的东西直接送给攻击者。存摘要（HMAC-SHA256 + 服务端 pepper）后，攻击者拿到的是「猜不出原值的指纹」——而 refresh 本身是 32 字节高熵随机串，裸哈希其实已不可枚举；之所以仍上 HMAC，是让它与验证码共用同一套 `SecretHasher`、并把「哈希细节收敛到存储层内部」这件事统一起来，避免业务层引入第二套裸哈希（见第 2 节 OTP 的教训）。

**为什么按设备维度管理，以及 TTL 的权威是谁**：真实用户往往多设备同时在线（手机+电脑+多标签页），「登录态」准确说是「某账号在某设备上的会话」。因此吊销分两级——登出只踢当前设备（`deviceId`），改密/被盗才全端下线；这依赖每个 refresh 落库时附带 `subjectId + deviceId` 索引。至于有效期，**权威是 Redis 里 `refresh:<hmac>` 的 TTL，cookie 的 maxAge 只是给浏览器一个展示层提示**——真正说「过期」的是服务端存储，而不是调一个 `expire` 让浏览器自觉。这样吊销「删 key」与过期「key 自然消失」是同一套机制，不需要两套时钟。

### 续期与吊销：rotation + 重放检测

- **轮换（rotation）**：每次用 refresh 换新 token，旧的立即作废（Redis GET+DEL 一步完成，两个并发请求不可能同时消费同一个）。
- **重放裁决（带宽限期）**：作废过的 refresh 再次出现就是被盗信号——但一刀切会误伤：多标签页同时启动会拿同一个旧码并发刷新，后到者被判成攻击就把用户全线踢下线。所以消费记录带时间戳：15 秒内的重复按并发竞争静默拒绝，超出宽限期才升级为「吊销所有设备 + 告警」。假设最坏情况，但给善意竞争留缓冲。
- **封号即下线**：刷新链路同样校验账号状态——旧码已消费、新码不签发，禁用动作自动等效于吊销全部会话。
- **改密/重置密码** → 全设备吊销；**普通登出** → 只吊销当前设备（别的不打扰）。吊销粒度跟着威胁等级走。

已知取舍：access 没有黑名单，改密后旧 access 还能飘最多 10 分钟（它的自然寿命）。引入黑名单=每次请求查库=白瞎了 JWT，10 分钟窗口在当前规模下可接受。**能讲清为什么忍比做了更显功力。**

## 4. 面试追问预判

**Q：为什么不用常量时间比较函数比对验证码哈希？**
SHA-256 摘要比对能泄露的信息可以忽略；真正有时序风险的密码路径由 BCrypt 慢哈希天然均衡。比较高价值的 MAC/token 时才需要 constant-time equals——工具箱里有这个工具，但这里不需要。

**Q：错了为什么不立刻烧码？**
手滑友好是产品刚需，且猜测上限已被计数器封顶——除以 10⁶ 之后，「1 次」和「5 次」是同一个量级的零。

**Q：读哈希、比对、删除不是原子的，有并发问题吗？**
并发同码双过的窗口存在，但收益极小，接受；真要收敛就把比对+删除包进同一个 Lua 脚本。

**Q：BCrypt cost 12 会不会太贵？**
会，这是有意为之的安全预算。登录 QPS 高到撑不住时，正确动作是降 cost 并把强度转移到前置风控，而不是默默忍受。

**Q：验证码存了哈希，拖库是不是就安全了？**
裸 SHA-256 不是——手机号在 key 里，6 位码可离线秒破。已改为 HMAC + 服务端 pepper：pepper 不在 Redis，反推需先攻陷应用配置；短 TTL + 尝试封顶仍是第二道兖底。

**Q：如果要封号立即生效呢？**
补 access 黑名单（Redis 存 jti，TTL=剩余寿命），或缩短 access 寿命。当前 10 分钟窗口不值得付这个成本。

**Q：重放宽限期为什是 15 秒？攻击者卡在宽限期内重放呢？**
15 秒覆盖多标签页启动错峰与网络重试的量级；真实攻击者从旧码得手到使用的时间分布远比这宽。且宽限期内重放只换来一个 401——拿不到任何凭证，损失的只是「响应不升级」，access 本来就只有 10 分钟寿命。

**Q：多标签页里输家那个标签页显示未登录怎么办？**
服务端职责止于「不误杀会话」；跨标签页状态同步是前端课题（BroadcastChannel/Web Locks 单飞刷新），属于已知边界。

**Q：演进到微服务怎么办？**
公钥发布成 JWKS 端点，网关统一验签后向内网透传 userId，业务代码里的 `UserIdHolder` 抽象不变——钥匙的形状已经为此预留。

## 5. 知道但故意不做的（边界声明）

| 不做的事                       | 为什么不做                                                                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 图形验证码/滑块                | 需接入第三方风控或自建设备指纹，超出单体范围。它该插在「发送验证码」之前，作为第四层频控                                                  |
| 泄露密码库比对                 | 黑名单应对接 HIBP 等真实数据源，硬编码 14 条只是占位                                                                                      |
| 短信异步化 + 双通道            | 需要 MQ 基建；同步发送在线程池抖动时会阻塞请求                                                                                            |
| 登录风控（异地提醒、设备指纹） | 属于风控工程而非认证本身，成熟电商一半的登录代码在这里                                                                                    |
| access 过期后无法主动登出      | /auth/logout 挂在 access 校验之后，过期时点登出会 401，refresh cookie 要等自然过期。前端清内存态可接受；改进方向是允许凭 refresh 直接登出 |
| Redis 故障降级                 | 故障表现为要求重新登录，单机阶段可接受；降级策略等 Redis 可靠性成为真实诉求时再设计                                                       |
| 密码哈希升级检测               | BCrypt 自描述格式已预留升级路径，「登录时检测旧 cost 并重写哈希」未实现；第一次调 cost 时补上                                             |
| CSRF Token                     | 当前同站点 SameSite=Lax 够用；接入 OAuth 第三方登录时切 Lax + CSRF Token（原裁决 #4 预留）                                                |
| 容量规划 / 多实例              | 未压测；单机假设（订单号进程内序列、超时关单不加锁）都在代码注释标了出处，多实例化时逐一重评                                              |

> 面试说法：「我知道它们该插在哪一层，只是当前阶段的投入产出比不划算。」
