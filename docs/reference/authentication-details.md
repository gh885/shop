# 认证细节清单

> 版本：v1.1（2026-07-26）。对照实现文档引用本清单时注明此版本号。

从用户感知划分，登录方式只有三种：**账号 + 密码**、**验证码登录**、**第三方 / 生物识别**。

三种方式只在"验证身份"这一步不同，验证通过后的凭证体系（签发、请求验证、维护、注销）完全共用。

## 使用说明

**编号**：每条有稳定 ID（如 `LOGIN-03`），用于代码评审、交付文档中精确引用，不因增删条目而变动。

**优先级**（安全是底线，优先级表达的是"缺了会怎样"，不是"做不做"）：

- `P0` 底线：缺了就是直接可被利用的漏洞或必现 bug，第一天上线的最低要求
- `P1` 短期：特定攻击面或事故高发区，上线后短期内必须补齐
- `P2` 演进：与规模/业务强绑定，实现可延后，但架构必须预留升级路径

**冲突裁决**：部分条目之间存在张力（如无状态 vs 可吊销），统一在文末「冲突项的裁决」说明，实现时以裁决为准。

**AI 交付要求**：见文末「给 AI 的使用要求」，编码前后各读一次。

## 一、身份验证

每种方式只描述"我如何确认你是你"，验证通过后统一走凭证管理。

### 1.1 账号 + 密码

#### 注册阶段

注册时的决策决定了登录时的安全上限，后续很难回头补救。

**密码策略**

- [ ] [P0][REG-01] 长度 > 组合复杂度，`correct-horse-battery-staple` 比 `P@ss1!` 安全得多
- [ ] [P0][REG-02] 不强制大小写/特殊字符组合（强制组合会导致模式化，如 `Password1!`）
- [ ] [P0][REG-03] 对常见密码黑名单（`123456`、`password`、`qwerty123` 等）
- [ ] [P1][REG-04] 泄露密码检测（k-anonymity）：本地算 `SHA1(password)`，只发哈希前 5 位给 HaveIBeenPwned API，本地比对返回的后缀列表；命中即拒绝。防"看起来不弱但已在攻击者字典里"的密码（NIST 800-63B 推荐）
- [ ] [P0][REG-05] 不与用户名/邮箱相同
- [ ] [P0][REG-06] 限制密码最大长度（64–128 字符），防超长密码打满哈希 CPU；BCrypt 会在 72 字节处**静默截断**，超限必须显式拒绝，不得截断后照常哈希

**所有权验证**

- [ ] [P1][REG-07] 注册时验证邮箱/手机号所有权（验证链接或验证码）；未验证所有权的账号不得被第三方登录按邮箱自动关联（OIDC-07 的前置）

**哈希参数选择**

- [ ] [P0][HASH-01] 当前推荐：Argon2id 优先（m ≥ 19 MiB, t ≥ 2, p = 1）；BCrypt cost ≥ 12；scrypt N ≥ 32768（r=8, p=1）
- [ ] [P0][HASH-02] 每个用户使用唯一随机 salt（16+ 字节）
- [ ] [P0][HASH-03] 自描述哈希格式，包含算法、参数、salt，为未来升级留空间（REHASH-01 的前置）

自描述哈希的事实标准是 PHC 字符串格式：`$算法$版本$参数$salt$hash`，Argon2 官方输出即此格式；BCrypt 的 modular crypt 格式思想相同。scrypt 没有统一标准格式，各库自定义。

```
$argon2id$v=19$m=19456,t=2,p=1$base64salt$base64hash
$2b$12$22字符salt+31字符hash            （BCrypt）
```

#### 登录验证

验证过程每一步都可能泄露信息，攻击者不需要真正登录成功就能拿到东西。

- [ ] [P1][LOGIN-01] 用户不存在时使用 Dummy Hash（真实哈希运算），防止响应时间差异暴露用户存在
- [ ] [P0][LOGIN-02] 查用户与比密码之间不做任何分支处理，流程走到底

```typescript
const user = db.findByEmail(email)
const storedHash = user ? user.hash : dummyPasswordHash // 用户不存在也继续走
const salt = user ? user.salt : dummySalt // dummy hash 需配套固定的 dummy salt，否则此处产生分支
const ok = timingSafeEqual(hash(password, salt), storedHash)
if (!ok) return { error: "账号或密码错误" } // 统一提示
```

- [ ] [P0][LOGIN-03] 使用常量时间比较函数（`crypto.timingSafeEqual` / `hash_equals`）
- [ ] [P0][LOGIN-04] 统一错误提示："账号或密码错误"，不区分用户不存在还是密码错（UX-05 的日志侧除外）
- [ ] [P0][LOGIN-05] 双维度限流：IP + 账号/邮箱（推荐阈值：IP 维度 10 次/60s，账号维度 5 次/600s（按场景调整））
- [ ] [P1][LOGIN-06] 连续失败 N 次（3–5 次）后触发人机验证（CAPTCHA / Turnstile 打分制）：限流防"快"，但防不住多 IP + 多账号的分布式慢速撞库，CAPTCHA 提高单次尝试的自动化成本
- [ ] [P1][LOGIN-07] 限流触发时返回与正常失败相同的错误信息，不暴露限流状态
- [ ] [P1][LOGIN-08] 登录成功后清除该账号的失败计数
- [ ] [P1][LOGIN-09] 记录审计日志：时间、IP、User-Agent、设备标识

#### 渐进式重哈希

- [ ] [P2][REHASH-01] 登录时检测哈希参数陈旧度，如果当前标准参数已升级，自动用新参数重算哈希并存储（前置：HASH-03 自描述格式）
- [ ] [P2][REHASH-02] 用户完全无感知，利用"登录"这个既有动作完成升级

```typescript
// 登录成功后
if (hash.params !== currentParams) {
    const newHash = await hash(password, currentParams) // 用新参数重哈希
    await db.updateHash(user.id, newHash) // 静默更新
}
```

#### 密码重置与修改

重置流程是攻击重灾区：它绕过密码直接拿到登录能力。

- [ ] [P0][RESET-01] 无论账号是否存在都返回相同提示（"如该邮箱已注册，重置邮件已发送"），不暴露账号存在性
- [ ] [P0][RESET-02] 重置 token 高熵随机、一次性、短有效期（15–30 分钟），服务端存哈希而非明文
- [ ] [P0][RESET-03] 重置成功后吊销该用户所有 token/session（见 REVOKE-02）
- [ ] [P1][RESET-04] 重置成功后邮件/短信通知用户
- [ ] [P0][RESET-05] 登录态下修改密码必须验证当前密码（或等价的重新认证 / sudo mode），防止被窃取的短寿命凭证直接换掉密码、永久接管账号

### 1.2 验证码登录（短信 / 邮箱）

把密码换成一次性验证码，本质上是"证明你能收消息"。

- [ ] [P0][OTP-01] 纯随机数字/字母，不可预测
- [ ] [P0][OTP-02] 短有效期（通常 5 分钟）
- [ ] [P0][OTP-03] 一次使用即作废，不可重复使用
- [ ] [P0][OTP-04] 服务端存哈希（`hash(手机号 + code)`）而非明文码，防止存储泄露后验证码被直接利用；绑定目标账号/手机号，独立计数尝试次数
- [ ] [P0][OTP-05] 发送频率限制（同一手机号/邮箱 N 分钟一次）
- [ ] [P0][OTP-06] IP 维度限流，防止批量轰炸
- [ ] [P1][OTP-07] 验证尝试输入错误 N 次后要求重新发送
- [ ] [P1][OTP-08] 限流触发时返回相同响应，不暴露限流状态
- [ ] [P1][OTP-09] 短信渠道认知：存在 SIM swap、SS7 劫持风险，选型时知悉
- [ ] [P1][OTP-10] 邮箱渠道认知：存在邮箱账号被黑的场景，选型时知悉
- [ ] [P1][OTP-11] 高风险操作（转账、改密）建议叠加其他验证方式（见 1.4 MFA）

---

### 1.3 第三方 / 生物识别

用户不需要输入任何字符，操作降到了"点一下"或"扫一下"。

#### OAuth / OIDC（第三方登录）

- [ ] [P0][OIDC-01] 使用 OIDC（OpenID Connect）而非纯 OAuth 2.0，确保拿到 `id_token` 做身份验证
- [ ] [P0][OIDC-02] 验证 `id_token` 的签名、`iss`、`aud`、`exp`
- [ ] [P0][OIDC-03] `state` 参数防 CSRF
- [ ] [P0][OIDC-04] `nonce` 参数防重放
- [ ] [P1][OIDC-05] 不要信任第三方返回的 `email_verified`，如果重要业务需要自己验证
- [ ] [P0][OIDC-06] 所有客户端启用 PKCE（S256），防授权码拦截；OAuth 2.1 已对全部客户端强制，不再限于移动端等公共客户端
- [ ] [P0][OIDC-07] 账号关联：第三方登录按 email 匹配到已有本地账号时，必须先验证该邮箱所有权（重新验证或要求输入密码）再关联，防 pre-account takeover——攻击者可抢先用受害者邮箱注册第三方账号，等自动合并接管本地账号（前置：REG-07）

#### WebAuthn / Passkeys（生物识别）

- [ ] [P0][WAN-01] 公私钥对，私钥锁在设备安全区（TPM / Secure Enclave），服务器只存公钥
- [ ] [P0][WAN-02] 服务器发送 challenge → 设备用私钥签名 → 服务器用公钥验签
- [ ] [P0][WAN-03] 验证 origin 与 RP ID，防止钓鱼站点中继签名请求
- [ ] [P1][WAN-04] Passkeys 跨设备同步（iCloud Keychain / Google Password Manager）意味着私钥可被云同步，对"设备绑定"有强要求的场景需知悉
- [ ] [P1][WAN-05] 作为二阶段加固时绑定到已有账号；作为主登录方式时允许注册时直接创建 Passkey

---

### 1.4 二次验证（MFA）

第一因素（密码/验证码）之上叠加第二因素，防"密码泄露即账号沦陷"。

- [ ] [P1][MFA-01] TOTP（基于时间的一次性密码，如 Google Authenticator）：服务端存共享密钥，30 秒窗口动态码；密钥需加密存储
- [ ] [P1][MFA-02] 校验时容忍 ±1 个时间窗口（时钟漂移），但每个码只能用一次（防重放）
- [ ] [P1][MFA-03] 发放一次性恢复码（10 个左右，存哈希），用于设备丢失后的自救，用完重新生成
- [ ] [P1][MFA-04] 触发时机：登录（可选/强制）、高风险操作（转账、改密、换绑）时强制
- [ ] [P1][MFA-05] MFA 也有失败限流：6 位数字码 100 万种组合，不限流就是暴力破解的活靶子
- [ ] [P1][MFA-06] 强度排序：Passkey/硬件密钥 > TOTP > 短信验证码（SIM swap 风险），别让弱的第二因素覆盖强的
- [ ] [P1][MFA-07] 启用流程：TOTP 绑定时必须先成功校验一次动态码才正式生效，防止用户扫码/保存密钥失败即被锁在门外

## 二、凭证管理（所有登录方式共用）

验证身份通过后，后续流程完全统一，与用户用了哪种方式登录无关。

### 2.1 凭证签发

验证通过后，需要给客户端一个"后续证明身份"的凭证。主流的两个选择是 Session 和 JWT。

#### Session vs JWT

| 维度     | Session                | JWT                            |
| -------- | ---------------------- | ------------------------------ |
| 存储位置 | 服务器（DB/Redis）     | 客户端（token 本身）           |
| 可吊销   | ✅ 直接删 session 即可 | ❌ 需要黑名单/版本号机制       |
| 验签成本 | 查一次 store           | 本地验签，无 I/O               |
| 跨端     | 需共享 store（Redis）  | 天生无状态，跨端方便           |
| 容量     | 存多少都行             | Payload 不宜大（每次请求都带） |

- [ ] [P0][GRANT-01] C 端 API 首选 JWT 双 Token（Access + Refresh）
- [ ] [P0][GRANT-02] 服务端渲染的传统 Web 应用用 Session 更简单
- [ ] [P0][GRANT-03] Session 方案：登录成功后必须重新生成 Session ID，防 Session Fixation（攻击者先给用户种一个已知 Session ID，用户登录后攻击者直接拿它接管会话）

#### JWT 双 Token 模型

- [ ] [P0][JWT-01] Access Token 短寿命（5–15 分钟）
- [ ] [P0][JWT-02] Refresh Token 长寿命（7–30 天）
- [ ] [P0][JWT-03] Claims 最小化：`sub`、`iat`、`exp`、`jti`、`iss`、`aud`
- [ ] [P0][JWT-04] Payload 不放敏感数据（密码、手机号、身份证等）
- [ ] [P0][JWT-05] 签名算法默认 ES256：代码复杂度与 HS256 相同（库 API 一致，仅传入密钥对而非字符串），签名仅 64 字节使 token 更小，私钥只用于签发、公钥可随意分发，避免架构演进时的算法切换（理由见「冲突裁决 #6」）
- [ ] [P1][JWT-06] Token 带 `kid`，支持密钥多版本并存与轮转（从第一天预留，是 MAINT-09 密钥轮换的前置）
- [ ] [P1][JWT-07] 时钟偏移容忍（clock skew 30–60 秒）

#### 存储位置

- [ ] [P0][STORE-01] Web：Access Token 放内存（变量/状态管理），不放 localStorage（防 XSS）。代价：页面刷新后内存丢失，需用 Refresh Cookie 静默换新（见「冲突裁决 #3」）
- [ ] [P0][STORE-02] Web：Refresh Token 放 HttpOnly + Secure + SameSite Cookie，Path 限定刷新接口
- [ ] [P1][STORE-03] Refresh Token 走 Cookie 后需防 CSRF：SameSite 至少 Lax（优先 Strict），刷新接口额外校验 CSRF Token 或自定义请求头（SameSite 档次选择见「冲突裁决 #4」）
- [ ] [P0][STORE-04] App：Token 存系统安全区（Keychain / Keystore）
- [ ] [P0][STORE-05] 全程 HTTPS，确保传输层安全
- [ ] [P0][STORE-06] Session 方案（GRANT-02）：session cookie 同样 HttpOnly + Secure + SameSite，要求与 STORE-02/03 一致，不因走 Session 路线而豁免

---

### 2.2 请求验证

每次请求都需要验证凭证的有效性。

- [ ] [P0][VERIFY-01] JWT：验证签名、`exp`、`iss`、`aud`
- [ ] [P0][VERIFY-02] JWT：算法白名单校验，拒绝 `alg: none` 与算法降级攻击
- [ ] [P1][VERIFY-03] JWT：可选检查 `jti` 黑名单（快速失效场景）、`nbf`
- [ ] [P0][VERIFY-04] Session：查询 store，确认 session 存在且未过期
- [ ] [P1][VERIFY-05] 双过期模型检查：空闲过期（Sliding Window）+ 绝对过期（Hard Cap），Sliding 不突破绝对上限
- [ ] [P1][VERIFY-06] 记录 token/session 的使用环境（IP、UA），环境突变时触发告警或要求重新登录

---

### 2.3 凭证维护

登录后凭证的持续管理，覆盖安全加固和体验优化。

- [ ] [P0][MAINT-01] Refresh Token 用 opaque token（高熵随机字符串，非 JWT）：Refresh Token 寿命 7–30 天，登出/改密/封号都要求立即失效，且 Rotation 和重放检测都依赖服务端记录，因此必须存库（与 JWT 无状态的矛盾见「冲突裁决 #1」）
- [ ] [P0][MAINT-02] 服务端存 Refresh Token 的 SHA-256 哈希（格式 `sha256:xxxxx`），不落明文
- [ ] [P0][MAINT-03] 一次一换（Rotation）：刷新即签发新 Refresh Token，旧 token 立即作废
- [ ] [P0][MAINT-04] 重放检测：已作废的 Refresh Token 被再次使用，判定盗用并吊销整条 token 链
- [ ] [P1][MAINT-05] 存储于 Redis，TTL 与 token 过期时间一致
- [ ] [P1][MAINT-06] 并发 Refresh Token / Session 数限制，超限自动吊销最旧的会话
- [ ] [P1][MAINT-07] 按设备/会话维度管理，支持查看登录设备、踢下线
- [ ] [P1][MAINT-08] 密钥存 KMS / Vault 或等价的密钥管理服务，不进代码库（低配版：环境变量 + 部署平台密钥管理也算达标）
- [ ] [P2][MAINT-09] 密钥轮换流程：新 `kid` 上线 → 新旧密钥并存验签 → 旧密钥签发的 token 全部过期后下线（JWKS 天然支持多 `kid` 并存）
- [ ] [P2][MAINT-10] JWKS 端点下发公钥，多实例无状态验签

---

### 2.4 注销与吊销

凭证的结束阶段，目标是让已签发的凭证尽快失效。

- [ ] [P0][REVOKE-01] 登出后 Refresh Token / Session 立即作废，清除 Cookie
- [ ] [P0][REVOKE-02] 修改密码、密码重置后该用户所有 token/session 失效，强制重新登录
- [ ] [P1][REVOKE-03] 账号封禁后全部活跃 token/session 立即吊销
- [ ] [P1][REVOKE-04] Access Token 快速失效机制（user tokenVersion 版本号比对，或 jti 黑名单）
- [ ] [P1][REVOKE-05] 黑名单 TTL 不超过 Access Token 剩余寿命
- [ ] [P1][REVOKE-06] 一键全局吊销能力（版本号 + 1、全局黑名单等）
- [ ] [P1][REVOKE-07] 审计日志贯穿所有操作，记录谁在什么时候做了什么

## 三、工程实践（非安全维度）

安全之外的常见线上问题，按踩坑频率排列。

### 3.1 可用性 / 体验

- [ ] [P0][UX-01] **刷新竞态**：页面并发 N 个请求时 Access Token 过期，N 个请求同时触发 refresh —— 必须单飞（single-flight）或请求队列，否则 Rotation 会把后续请求误判为"旧 token 重放"而吊销整条链。这不是加固项：双 Token + Rotation 方案不做这个就是必现 bug
- [ ] [P1][UX-02] **过期时刻的体验**：用户填了 20 分钟长表单，提交时 401 → 数据丢失。对策：活跃时静默续期（滑动）、提交前先 refresh、或本地暂存草稿
- [ ] [P1][UX-03] **验证码重发语义**：重发后旧码应作废（或仅最后一条有效），否则用户卡在"两条短信谁先谁后"
- [ ] [P1][UX-04] **第三方登录的中途取消**：OAuth 跳转后用户返回、扫码超时，都要有明确的状态收口
- [ ] [P1][UX-05] **错误提示分级**：给用户统一模糊提示（LOGIN-04 防枚举），但日志里精确区分"用户不存在 / 密码错 / 限流 / 验证码过期"，否则客服和排查抓瞎

### 3.2 可靠性 / 性能

- [ ] [P2][REL-01] **认证是关键路径**：Redis 挂了 = 全站掉线。Session/Refresh Token 存储要有降级策略（如 Redis 故障时临时降级为纯 JWT 验签 + 缩短 Access Token 寿命）
- [ ] [P2][REL-02] **哈希耗时是刻意的，但要纳入容量规划**：BCrypt cost 12 ≈ 单次 250ms CPU，登录接口天然 CPU 密集且易被放大攻击，考虑单独部署/排队/独立限流（与 LOGIN-01 的张力见「冲突裁决 #2」）
- [ ] [P1][REL-03] **客户端时钟**：不影响 JWT 验签（在服务端），但影响 TOTP 和"记住我"等本地判断，别拿客户端时间做安全决策

### 3.3 可运维性

- [ ] [P2][OPS-01] **会话可观测**：在线人数、token 签发/刷新/吊销速率进 metrics，否则"大面积掉线"无法定位是密钥轮换还是 Redis 的问题
- [ ] [P2][OPS-02] **密钥轮换要演练**：流程不能只存在于文档，要真的跑过——很多团队第一次轮换密钥就是事故现场（MAINT-09 的配套）
- [ ] [P2][OPS-03] **审计日志的留存与检索**：合规（等保/GDPR）有明确保留期要求；GDPR 下用户可要求删除数据，账号注销后日志如何匿名化要提前设计

### 3.4 业务 / 合规

- [ ] [P2][BIZ-01] **注销账号**：不只是吊销 token，还有数据删除义务和冷静期设计（防误删、防盗号者恶意注销）
- [ ] [P2][BIZ-02] **多端登录策略是业务决策**：视频网站"同时在线设备数"、金融 App"单端互踢"，技术上都用 MAINT-06 实现，但阈值由产品定，要留配置口
- [ ] [P2][BIZ-03] **实名制 / 未成年人**（国内场景）：可能需接实名核验，影响注册流程设计

## 冲突项的裁决

以下条目之间存在张力，实现时以本节裁决为准，不要自行"二选一"。

**#1 JWT 无状态 vs 可吊销**（MAINT-01 × REVOKE-04）
分工解决，不是取舍：Access Token 无状态、短寿命（5–15 分钟），到期前被窃的损失可接受；Refresh Token 有状态（opaque + 存库），承担吊销、Rotation、重放检测。两者各管一段，不要把 Refresh Token 也做成无状态 JWT。

**#2 Dummy Hash 的恒定成本 vs 登录接口容量**（LOGIN-01 × REL-02）
安全不让步：保留 Dummy Hash，每次登录（无论用户是否存在）都付出一次哈希成本。CPU 压力靠容量规划消化（登录接口独立限流/排队/部署），不靠"省掉 Dummy Hash"来省 CPU。

**#3 Access Token 放内存 vs 页面刷新丢失**（STORE-01）
内存存储的代价是页面刷新后 token 丢失，标准做法：页面加载时先用 Refresh Cookie 静默调刷新接口换新 Access Token，再进入应用。禁止因为"刷新麻烦"退回 localStorage——那是用 XSS 攻击面换便利。

**#4 SameSite Strict vs OAuth 跨站回跳**（STORE-03 × OIDC-01）
SameSite=Strict 会阻断第三方登录回跳时携带 Cookie，导致 OAuth 流程断掉。裁决：接入了第三方登录的站点用 Lax + CSRF Token 双保险；纯第一方登录的站点可用 Strict。

**#5 对用户模糊 vs 对排障精确**（LOGIN-04 × UX-05）
不冲突，分层处理：HTTP 响应统一模糊（防枚举），服务端日志精确到失败原因。两层各管各的受众。

**#6 HS256 vs ES256**（JWT-05）
曾有"单体用 HS256 就够"的说法，本清单不采纳：两者代码复杂度相同（库 API 一致，仅传入的密钥类型不同），ES256 的额外成本只是一次性生成密钥对；而 HS256 的隐患是长期的——secret 每分发到一个验签方，就多一个能伪造 token 的点，服务拆分之日就是切换之时。裁决：默认 ES256 并带 `kid`（JWT-06），HS256 仅限一次性原型/玩具项目。

你正在或即将为某个项目实现认证相关代码，本清单是你的设计依据和验收标准。要求如下：

**编码前**

1. 通读全文，包括「冲突项的裁决」，不要只看你正在写的那一节。
2. `P0` 条目必须全部实现，没有例外；`P1` 默认实现，不做必须在交付文档中写明理由；`P2` 可不实现，但架构上必须预留（如 `kid`、自描述哈希格式），不得堵死演进路径。
3. 条目间出现表面冲突时，以「冲突项的裁决」为准；裁决未覆盖的冲突，停下来问人，不要自行取舍。

**编码后**

4. 在项目内（建议 `docs/auth-implementation.md`，或项目约定的文档位置）写一份**对照实现文档**，逐条引用本清单的 ID，标注三种状态之一：

```markdown
# 认证实现对照（基于认证细节清单 vX）
```
