# 可观测性细节清单（单体版）

> 版本：v1.0（2026-07-29）。对照实现文档引用本清单时注明此版本号。

本清单的适用范围是**单体应用**（一个进程、一个数据库、可能有少量外部依赖）。分布式追踪、日志管道、成本分摊、多团队语义对齐等微服务/企业级条目**刻意不收**——它们解决的问题在单体里不存在，等架构演进到时再补，届时本清单需要升级版本。

可观测性一句话定义：不修改代码、不登录机器，仅通过系统向外输出的数据，就能回答"系统内部正在发生什么、为什么"。

## 使用说明

**编号**：每条有稳定 ID（如 `LOG-03`），用于代码评审、交付文档中精确引用，不因增删条目而变动。

**优先级**（优先级表达的是"缺了会怎样"，不是"做不做"）：

- `P0` 底线：缺了系统就是瞎的——出问题只能登录机器翻文本、猜、加日志重新发版
- `P1` 短期：事故高发区或排查效率的质变点，上线后短期内必须补齐
- `P2` 演进：与规模/业务强绑定，实现可延后，但不得堵死演进路径

**冲突裁决**：部分条目之间存在张力，统一在文末「冲突项的裁决」说明，实现时以裁决为准。

**AI 交付要求**：见文末「给 AI 的使用要求」，编码前后各读一次。

## 一、请求标识（请求 ID）

一次请求在进程内会过中间件、打多条日志、可能进异步任务。请求 ID 是让"这一次请求的所有日志"可以被一键筛出的唯一手段。

命名约定：日志字段叫 `trace_id`（蛇形，日志惯例），响应头叫 `X-Request-ID`，响应体字段叫 `requestId`（camelCase，JSON 惯例）——**三者是同一个值**，只是各自世界的命名风格。

- [ ] [P0][REQ-01] 入口中间件为每个请求生成请求 ID：检查 `X-Request-ID` 请求头中有无合法 ID，有则采纳，无则生成
- [ ] [P0][REQ-02] ID 格式：UUID v4（32 位 hex）。校验只做格式检查（长度 + 字符集），格式不合法则丢弃并自行生成——不信任客户端传来的值
- [ ] [P0][REQ-03] ID 存入请求上下文（按语言惯例：Node 的 AsyncLocalStorage、Java 的 MDC、Go 的 context），进程内任何位置可取
- [ ] [P0][REQ-04] 日志框架自动将 ID 注入每条日志（见 LOG-02），不靠业务代码手写
- [ ] [P0][REQ-05] 出站调用自动携带：HTTP client 统一在拦截器中把 ID 写进出站 `X-Request-ID` 请求头；发 MQ 消息时写入消息元数据，消费端恢复进上下文
- [ ] [P1][REQ-06] 跨线程/异步任务不断链：线程池或异步调度要做上下文传递，定时任务、消息消费等"无上游"入口自行生成 ID 作为链路起点
- [ ] [P0][REQ-07] 所有响应的响应头回带 `X-Request-ID`（值与日志 `trace_id` 相同），在**序列化之前**的层面设置（Filter / 最外层中间件）：String 响应、void/204、异常响应都经过这一层，不存在序列化盲区。跨域部署必须同时返回 `Access-Control-Expose-Headers: X-Request-ID`，否则浏览器 JS 读不到该头
- [ ] [P1][REQ-08] 错误响应体额外带 `requestId` 扩展字段（RFC 9457 Problem Details 的扩展成员用法）：报障截图里 body 的 ID 比 header 好找。成功响应体**不带**——成功侧的 ID 由响应头统一承载（REQ-07），body 里放一份是冗余
- [ ] [P2][REQ-09] 请求传播的头部标准演进到 `traceparent`（W3C Trace Context）：接入 OpenTelemetry 或标准网关时切换，入站同时认 `traceparent` 与 `X-Request-ID`（取第一个格式合法的），出站发 `traceparent`。注意 `traceparent` 是**请求**传播标准，响应头回带仍是 `X-Request-ID`（社区惯例），不回带 `traceparent`。切换点集中在入口中间件与公共 client 拦截器，当前方案不得把头部名称散落硬编码到业务代码中

## 二、结构化日志

### 2.1 总体格式

- [ ] [P0][LOG-01] 每条日志是一行 JSON（JSON Lines）。异常堆栈换行转义后塞进字段，一条日志绝不跨行
- [ ] [P0][LOG-02] 信封字段由日志框架自动注入每条日志，业务代码一行不允许手写：

| 字段       | 类型   | 说明                                                  |
| ---------- | ------ | ----------------------------------------------------- |
| `ts`       | string | ISO 8601 UTC，毫秒精度，如 `2026-07-29T10:00:01.123Z` |
| `level`    | string | `debug`/`info`/`warn`/`error`，小写                   |
| `service`  | string | 服务名。单体也必填，为演进留位置                      |
| `version`  | string | 版本号或 commit hash，见 REL-01                       |
| `env`      | string | `dev`/`staging`/`prod`                                |
| `trace_id` | string | 请求 ID，见 REQ-01                                    |

- [ ] [P0][LOG-03] 每条日志必有 `event` 字段：短标识，点分命名，是检索/聚合/告警的唯一依据。给人读的描述放 `msg`（可选），检索不靠 `msg`
- [ ] [P0][LOG-04] 场景字段**顶层平铺**，不包进嵌套对象。命名蛇形。`ts`/`level`/`service`/`version`/`env`/`trace_id`/`event`/`msg` 为保留字，场景字段禁止使用；错误字段统一 `error.*` 前缀
- [ ] [P0][LOG-05] 数字就是数字（`"latency_ms":203` 而非 `"203ms"`），布尔就是布尔，可聚合的字段不得字符串化
- [ ] [P0][LOG-06] 敏感信息不进日志：密码、token、密钥、身份证号、银行卡不打；手机号、邮箱如需出现必须脱敏（`138****1234`）。红线，无例外
- [ ] [P0][LOG-07] 输出到 stdout。落盘、滚动、清理、采集是运行环境（PM2 / systemd / Docker / PaaS）的职责，应用不管，日志库不配置任何文件输出

### 2.2 日志级别语义

级别本身没有争议，**语义统一**才是重点：

- [ ] [P0][LVL-01] `debug`：排查细节，生产默认关闭
- [ ] [P0][LVL-02] `info`：正常业务事件与请求日志
- [ ] [P0][LVL-03] `warn`：出问题了但系统自己兜住了（重试成功、降级生效、限流触发）
- [ ] [P0][LVL-04] `error`：**意味着"有人应该被叫醒"**。请求 500、依赖调用失败、未捕获异常。不满足此语义的不许打 error（与 ALM-01 的张力见「冲突裁决 #1」）

### 2.3 固定事件目录

以下事件的值与字段**定死**，是验收标准。全部由框架/公共库自动打，业务零接入（见 INS-01）。

**HTTP 服务端**（中间件，每请求一条）

- [ ] [P0][EVT-01] `http.request`：`method`、`path`、`status`、`latency_ms`、`client_ip`；`user_id` 可选
- [ ] [P0][EVT-02] `path` 必须是**路由模板**（`/orders/:id`），不是实际 URL——路径里的实体 ID 会让聚合查询报废（与排查需求的张力见「冲突裁决 #2」）

**数据库**（DB client 自动）

- [ ] [P0][EVT-03] `db.query`：`query_type`（select/insert/update/delete）、`table`、`latency_ms`
- [ ] [P0][EVT-04] `db.query.failed`：上述字段 + `error.type`、`error.message`
- [ ] [P0][EVT-05] 不打 SQL 原文与参数——参数可能含敏感数据，大 SQL 会撑爆日志。慢 SQL 排查交给数据库自身的 slow log（见「冲突裁决 #3」）

**出站 HTTP**（client 自动）

- [ ] [P0][EVT-06] `http.client.call`：`target`、`method`、`path`、`status`、`latency_ms`
- [ ] [P0][EVT-07] `http.client.call.failed`：上述字段（status 可为空）+ `error.type`、`error.message`

**消息队列**（如有，client 自动）

- [ ] [P1][EVT-08] `mq.publish` / `mq.consume`：`topic`、`latency_ms`
- [ ] [P1][EVT-09] `mq.consume.failed`：`topic` + `error.type`、`error.message`

**应用生命周期**（框架自动）

- [ ] [P0][EVT-10] `app.started` / `app.shutdown`：信封中的 `version`、`env` 即关键信息
- [ ] [P0][EVT-11] `app.unhandled_error`：`error.type`、`error.message`、`error.stack`——未捕获异常必须有出口，不能进程静默死掉

**认证**（如有登录）

- [ ] [P1][EVT-12] `auth.login.succeeded`：`user_id`
- [ ] [P1][EVT-13] `auth.login.failed`：`reason`（枚举值，非自由文本）、`client_ip`——对外响应模糊（防枚举），日志内精确（防排查抓瞎），两层各管各的受众
- [ ] [P1][EVT-14] 目录是最小集：调缓存、发邮件、调第三方支付等，按同模式补条目进目录（如 `cache.get`、`email.send.failed`），字段一并定死

### 2.4 业务事件语法

业务事件（`order.created` 等）的值取决于业务，清单不穷举，但语法定死：

- [ ] [P0][BEV-01] 命名：`名词.动词过去式`（成功/中性），`名词.动词.failed`（失败）。名词用领域实体，动词用业务动作，不发明缩写
- [ ] [P0][BEV-02] 失败是**独立事件**（`payment.charge.failed`），不是 `success:false` 字段。失败事件必有 `error.type`、`error.message`
- [ ] [P0][BEV-03] 成功事件必带该实体的 ID（`order_id`），业务字段平铺、蛇形、禁保留字（LOG-04）
- [ ] [P0][BEV-04] `event` 永远是短标识，禁止以下形态：

```
❌ event: "用户下单成功"        （msg 当 event）
❌ event: "createOrder"        （函数名不是业务事件）
❌ event: "order_created"      （风格不统一）
✅ event: "order.created"
```

## 三、框架级埋点

埋点 = 在代码特定位置主动留下记录。埋点收敛为框架能力的检验标准只有一句话：**一个新写的接口，开发者什么都不做，就自动有日志和指标。**

- [ ] [P0][INS-01] 2.3 固定事件目录全部由中间件/公共 client/框架生命周期钩子自动产生，业务代码不可见、不可绕过
- [ ] [P0][INS-02] 出站调用必须走公共 client（HTTP client、DB client、MQ client），禁止业务代码自行 new 客户端绕过埋点与 ID 传播
- [ ] [P0][INS-03] 信封注入（LOG-02）、ID 上下文（REQ-03）与埋点共用同一套请求上下文设施
- [ ] [P1][INS-04] 业务手动埋点只需一行：日志框架从上下文自动补齐信封字段，业务只写 `event` + 业务字段
- [ ] [P2][INS-05] 新增一类公共依赖（接入缓存、搜索引擎等）时，同步在公共 client 层补埋点并进固定事件目录（EVT-14），不允许先上线后补

## 四、指标与告警

### 4.1 核心指标

单体不需要指标平台全家桶，但以下四组必须能实时看到（用什么工具不限，一个最小面板即可）：

- [ ] [P0][MET-01] 请求量与错误率：按路由模板的 QPS、5xx 比例（数据即来自 `http.request`，指标可以是日志的聚合视图）
- [ ] [P0][MET-02] 延迟：核心接口的 P50/P99，按路由模板分组
- [ ] [P0][MET-03] 依赖健康：DB 查询耗时、出站调用耗时与失败率（来自 `db.query` / `http.client.call`）
- [ ] [P1][MET-04] 资源饱和度：CPU、内存、磁盘、连接池占用——单体挂了最常见的原因就是资源耗尽

### 4.2 告警

- [ ] [P0][ALM-01] 每条告警必须对应"有人要采取的动作"。无动作的告警删除或降级为面板指标——告警疲劳是告警体系最常见的死因
- [ ] [P0][ALM-02] 告警能触达人（邮件/IM/Webhook 均可），只写进日志的告警等于没有告警
- [ ] [P0][ALM-03] 最小告警集：5xx 错误率超阈值、P99 延迟超阈值、进程退出/重启、磁盘将满
- [ ] [P1][ALM-04] 告警基于固定事件目录书写（如 `event=http.request AND status>=500`），与日志格式同生命周期演进
- [ ] [P1][ALM-05] 为核心接口定义粗糙的"正常水位"（日常错误率、延迟范围），告警阈值从水位出发而非拍脑袋——这是 SLO 的单体简化版，不引入错误预算等完整仪式
- [ ] [P2][ALM-06] 定期告警审计：回顾哪些告警没人理（删/降级）、哪些故障没有告警（补），双向修剪

## 五、变更与版本

- [ ] [P0][REL-01] 每条日志/指标带 `version`（版本号或 commit hash），指标异常时能对齐"是不是刚发版"——定位时间从小时级降到分钟级
- [ ] [P1][REL-02] 发布动作本身有记录可查（部署流水线的历史、或至少 `app.started` 事件的时间线），"什么时候开始慢的"能回答

## 冲突项的裁决

以下条目之间存在张力，实现时以本节裁决为准，不要自行"二选一"。

**#1 error 语义纯洁 vs 第三方不可控错误**（LVL-04 × ALM-01）
外部依赖的正常失败（如下游限流返回 429）不该打 error——否则 error 满天飞、告警失效。裁决：依赖失败但系统有兜底的打 warn（LVL-03）；最终传导为对用户的失败（请求 5xx）由 HTTP 层统一打 error。同一个失败在不同层级别不同，各层只对自己"是否兜住"负责。

**#2 路由模板 vs 想看原始 URL**（EVT-02）
聚合查询和原始 URL 都要，分层解决：`path` 永远填路由模板保证可聚合；确有排查需求时把原始 URL 放 `msg` 或独立字段 `raw_path`，但该字段**不得用于聚合与告警**，仅人肉查看。

**#3 不打 SQL 原文 vs 排查慢查询**（EVT-05）
日志里的 SQL 原文是敏感数据泄露和日志膨胀的双重风险，不让步。慢查询走数据库自身的 slow log（MySQL/PostgreSQL 都有），应用日志只负责告诉你"哪张表、多慢、哪个请求 ID"——拿请求 ID 和时间去 slow log 里对。

**#4 采纳客户端 ID vs 信任边界**（REQ-01 × REQ-02）
不矛盾，是同一条规则的两面：格式合法则采纳（链路连续性有价值），格式不合法则重造（不信任客户端）。格式校验防注入与存储污染；恶意方拿合法 UUID 重复刷不在本条防御范围内，那是限流的职责。

## 给 AI 的使用要求

你正在或即将为某个单体项目实现可观测性相关代码，本清单是你的设计依据和验收标准。要求如下：

**编码前**

1. 通读全文，包括「冲突项的裁决」，不要只看你正在写的那一节。
2. `P0` 条目必须全部实现，没有例外；`P1` 默认实现，不做必须在交付文档中写明理由；`P2` 可不实现，但不得堵死演进路径。
3. 条目间出现表面冲突时，以「冲突项的裁决」为准；裁决未覆盖的冲突，停下来问人，不要自行取舍。
4. 本清单是单体版：发现项目实际是微服务/多实例架构时，停下来告知——清单的取舍前提已失效，不要自行外推。

**编码后**

5. 在项目内（建议 `docs/observability-implementation.md`，或项目约定的文档位置）写一份**对照实现文档**，逐条引用本清单的 ID，标注三种状态之一：

```markdown
# 可观测性实现对照（基于可观测性细节清单 vX）

| ID     | 优先级 | 状态      | 说明                                 |
| ------ | ------ | --------- | ------------------------------------ |
| REQ-01 | P0     | ✅ 已实现 | 见 src/middleware/requestId.ts:18    |
| EVT-08 | P1     | ⏳ 延后   | 项目暂无 MQ，接入时按目录补          |
| MET-04 | P1     | 🚫 不做   | 托管平台自带资源监控面板，不重复建设 |
```

- `✅ 已实现`：注明实现位置和方式（文件:行 / 配置项）
- `⏳ 延后`：注明触发条件（"接入 MQ 时""多实例化时"）
- `🚫 不做`：注明理由和兜底措施；**P0 不允许出现此状态**

6. 对照文档完成后自查：P0 全 ✅，P1 的 🚫 每条都有理由，P2 的 ⏳ 每条都有触发条件。不满足则回去改代码或改文档，直到满足。

7. 验收测试：任选一个贯穿"入口 → DB → 出站调用"的请求，拿其请求 ID 检索日志，每一跳都应能用同一个 ID 串出；中间任何一段搜不到即为断点，不算完成。

## 总览：三层结构

```
框架自动（业务零感知，追求 100% 覆盖）
├── 请求 ID：入口生成 → 上下文 → 出站携带（REQ-*）
├── 信封注入：ts/level/service/version/env/trace_id（LOG-02）
└── 固定事件：http.request / db.query / http.client.call / app.*（2.3）

业务手动（一行埋点，框架补信封）
└── 业务事件：order.created / payment.charge.failed（2.4 语法）

消费层
├── 核心指标：错误率 / 延迟 / 依赖健康 / 资源（4.1）
└── 告警：每条对应一个动作，能触达人（4.2）
```
