# 权限细节清单

> 版本：v1.0（2026-07-27）。对照实现文档引用本清单时注明此版本号。
> 姊妹篇：《认证细节清单》（authentication-details.md）。认证回答"你是谁"，本清单回答"你能干什么"——两者以 token 交付为界，互不重叠。

权限系统只回答一个问题：**谁（主体）在什么条件下，能对什么资源，做什么动作**。

判权只是最后一厘米。前面还有主体的生命周期、资源建模的粒度、规则的叠加、授权的治理流程——
复杂度是组织规模的影子：淘宝/京东级的权限系统服务几万员工 × 千万级商家子账号 × 上万内部系统，
其一半代码根本不在判权，在工单流、盘点引擎、审计存储。

## 使用说明

**编号**：每条有稳定 ID（如 `ENF-02`），用于代码评审、交付文档中精确引用，不因增删条目而变动。

**优先级**（安全是底线，优先级表达的是"缺了会怎样"，不是"做不做"）：

- `P0` 底线：缺了就是直接可被利用的漏洞（越权、自提权、收权不生效）或必现 bug，第一天上线的最低要求
- `P1` 短期：特定攻击面或事故高发区，上线后短期内必须补齐
- `P2` 演进：与规模/业务强绑定，实现可延后，但架构必须预留升级路径

**复杂度光谱**（理解 P2 条目的存在方式——留缝不施工）：

```
1. if 判断 → 2. 固定两级角色 → 3. 静态 RBAC → 4. 可配置角色
→ 5. 功能权限点化 → 6. 行级数据权限 → 7. 工单审批流+临时授权
→ 8. 盘点合规 → 9. 权限中台 → 10. ReBAC/ABAC（Zanzibar 层级）
```

挪格判据只有一条：**上一格开始频繁出现「绕不过去的业务诉求」或「审计追责压力」**，才挪一格。
本清单 P0 ≈ 第 1～3 格的底线，P1 ≈ 第 3～5 格，P2 ≈ 第 6 格以后。提前挪格 = 为不存在的组织复杂度预付架构税。

**冲突裁决**：部分条目之间存在张力（如实时性 vs 性能），统一在文末「冲突项的裁决」说明，实现时以裁决为准。

**AI 交付要求**：见文末「给 AI 的使用要求」，编码前后各读一次。

## 一、主体（谁）

### 1.1 账号体系划分

主体先分类，不同类的主体不共享信任域。最小起点是人机分离 + 角色域隔离，ISV/机器账号是规模产物。

- [ ] [P0][SUBJ-01] 人与系统分开：人的账号和程序调用（API Key、服务账号）不是一种东西，不共用鉴权链路
- [ ] [P0][SUBJ-02] 多身份域必须隔离：同一系统内存在两套主体（如平台员工与商家用户）时，凭证必须携带 subject kind，A 域的 token 到 B 域一律无效——结构上杜绝"A 冒充 B"，这是所有越权防护的地基
- [ ] [P1][SUBJ-03] 企业场景用主账号/子账号模型：子账号由主账号创建或邀请，**子账号可获得的权限上限 ≤ 授予者的权限**（防权限自我繁殖：客服邀个朋友给自己提权）
- [ ] [P1][SUBJ-04] 子账号数量设上限（每主账号 N 个），防滥用与成本失控
- [ ] [P2][SUBJ-05] ISV/第三方应用作为独立主体类型（应用身份，client credentials 授权），授权粒度到"只能读订单"级别，与人的身份严格分离
- [ ] [P2][SUBJ-06] 机器账号/服务账号：服务间调用同样要判权，不因"在内网"豁免

### 1.2 岗位与角色挂载

权限挂载点是"岗位/角色"，不是人。这一条决定了后面所有生命周期操作的成本。

- [ ] [P0][ROLE-01] 权限挂角色/岗位，不直接挂个人：人走权限留在岗位上、人来权限随岗位到——直接挂人的每一次人员变动都是一次人工排雷
- [ ] [P0][ROLE-02] 无角色的主体默认无任何权限（默认拒绝在主体层的体现）；不存在"隐含的基础角色"
- [ ] [P1][SUBJ-07]/[ROLE-03] 兼岗（一人多角色）二选一：要么明确不支持（单角色列），要么支持但向主体展示**合并后的有效权限集**——禁止隐式叠加出没人预期的组合
- [ ] [P2][ROLE-04] 角色层级/继承（RBAC1）：真实需求极少，选型时知悉即可，不要预先引入
- [ ] [P2][ROLE-05] 可配置角色（角色入库、界面编辑映射）：触发条件 = "改一次映射要发一版代码"成为真实痛点。升级路径必须预留：静态映射收敛在单个枚举/常量类，届时搬表而判权接口不变

### 1.3 生命周期联动

主体的生老病死必须驱动权限变化，靠纪律不如靠联动。

- [ ] [P0][LIFE-01] 离职/移除成员**当天**全量回收权限；收权动作是系统行为（禁用账号、删成员记录即全局生效），不是"记得去后台删一下"
- [ ] [P0][LIFE-02] 转岗/换岗 = 显式权限变更：旧岗位权限回收、新岗位权限授予，不做增量累积（累积三年后没人说得清他为什么有财务权限）
- [ ] [P1][LIFE-03] 入职基础包：新主体开通即可完成基本工作，但不包含任何 L3 高危权限（见 RISK-01）
- [ ] [P1][LIFE-04] 休眠账号处理：长期未登录（如 90 天）降权或锁定，激活需重新验证
- [ ] [P2][LIFE-05] 对接 HR 中台离职事件自动回收；无 HR 系统时，以定期对账（活跃账号清单 vs 在职名单）替代

## 二、资源与动作（对什么、做什么）

### 2.1 判权模型

- [ ] [P0][RES-01] 判权语义统一为四元组 `check(subject, resource, action, condition)`——哪怕 v1 的 condition 恒空也保留参数位，避免日后推翻全部判权签名
- [ ] [P0][RES-02] 权限码是前后端共同契约：SCREAMING_SNAKE_CASE，唯一真相源是一份文档，TS/客户端侧显式同步；码表改动 = 契约改动，过评审
- [ ] [P0][RES-03] 资源类型命名化（SHOP_REVIEW / PRODUCT / ORDER…），权限码 = 资源 × 动作的编码或独立语义码，全站二选一并保持一致

### 2.2 粒度

粒度的裁判不是工程师的洁癖，是审计问题的可答性。

- [ ] [P0][GRAN-01] 粒度跟着审计问题走：「谁能导出买家手机号？」「谁能改价格？」这类问题必须答得出来——答不出来就是粒度不够，答出来但答案是"所有人"就是分配不对
- [ ] [P0][GRAN-02] 合并码起步（`*_MANAGE` 型），出现第一个真实的"能看不能改"岗位再拆 `READ/WRITE/APPROVE/EXPORT`；不为假想岗位预拆
- [ ] [P1][GRAN-03] 敏感字段列级脱敏（手机号/证件号/资金）：多数角色看掩码，全文可见需专项权限且**逐次留痕**
- [ ] [P1][GRAN-04] 数据导出是独立权限点，不是查询权限的附属品——导出 = 数据离开系统边界，风险等级不同（与 RISK-01 联动）
- [ ] [P2][GRAN-05] 行级数据权限（按类目/组织/地域圈定数据范围）：判权返回 dataScope，由查询层拼装范围条件，不在业务代码里手写
- [ ] [P2][GRAN-06] 功能权限点化（按钮/字段级）：前端消费与服务端同一份权限码，前端显隐是体验优化而非安全边界（ENF-01）

## 三、判权执行（怎么判）

### 3.1 执行点

- [ ] [P0][ENF-01] **服务端强制是唯一真相**：前端隐藏按钮不构成任何安全边界，绕过前端直打 API 必须被拒
- [ ] [P0][ENF-02] **默认拒绝（deny by default）**：没有显式声明 = 拒绝。新增接口忘加权限声明的后果必须是开发期失败（启动自检/ArchUnit 扫描），绝不能是生产期静默放行
- [ ] [P0][ENF-03] 判权集中在统一入口层执行（拦截器/AOP/中间件 + 声明式注解），不在业务方法里散落 if——散落的判断必然漏标
- [ ] [P0][ENF-04] 权限与业务规则分层：「谁有权管理成员」是权限（入口判权），「不能移除店主」是领域不变式（service 校验）；两层各自拒绝，错误语义不混用
- [ ] [P1][ENF-05] 启动期扫描全部 handler：受保护路由缺失权限声明 → 启动失败；与运行时默认拒绝构成双保险
- [ ] [P1][ENF-06] 通配符只在解析层展开（超管的 `*` 在 Resolver 内变成具体集合），注解层永远写具体权限码——保持"看注解即知所需权限"的可读性

### 3.2 时效性

收权不生效等于没收权。这一组是权限系统区别于"配置读取"的本质特征。

- [ ] [P0][TIME-01] 权限变更**即时生效**：判权依据不放进长寿命凭证（JWT claims）；收权、降级、禁用之后，该主体的下一个请求必须被拒
- [ ] [P0][TIME-02] 权限确实进了 token 的场景（历史包袱/极端性能需求）：access token 寿命必须短到"被收权后的残余窗口"损失可接受，且必须有强制下线手段兜底
- [ ] [P1][TIME-03] 缓存判权结果必须配套失效机制：失效传播时间 = 可接受的越权窗口，这个数字要显式写出并被接受，不许"反正很快"地模糊过去
- [ ] [P2][TIME-04] 分布式判权一致性（new enemy problem）：收权瞬间，主体手里的旧引用（分享链接、已签发的委托凭证）立即失效——需要版本号/快照机制，Zanzibar 用万亿级实践证明了这个问题的分量

## 四、规则叠加（RBAC 之上）

RBAC（主体→角色→权限）只是地基，以下是叠在上面的规则层。按优先级排序，前两组是 P0。

### 4.1 职责分离（SoD）

- [ ] [P0][SOD-01] **自指禁令**：任何人不得变更自己的角色/权限、不得禁用自己——防自提权，这是一切内部防线里最便宜的一条
- [ ] [P0][SOD-02] **末位保护**：不允许降级/禁用最后一个超级管理员，防止系统锁死无人可救
- [ ] [P0][SOD-03] 关键互斥：强业务含义的互斥权限不可授予同一人（典型："配置收款账户" × "执行付款"）；至少做到「申请人 ≠ 审批人」硬校验
- [ ] [P1][SOD-04] 发布 ≠ 审核：内容审核、入驻审核场景，提交者与审核者不得同人；若两类主体天然隔离（不同身份域），补测试钉死即可

### 4.2 高危操作分级

- [ ] [P0][RISK-01] 高危操作单列分级，判定标准一句话：**出了事要向平台外交代的，就是最高级**（删类目、封店、改他人角色、批量导出）；高级别操作要求：审计日志 + 强二次确认
- [ ] [P1][RISK-02] 最高级别操作预留二次认证升级位（重新输密码 / sudo mode），触发时机由事故驱动，不预先开启
- [ ] [P1][RISK-03] 高危清单是活文档：维护在唯一真相源文件里，新增条目过评审；清单长度本身是治理信号，超过 ~5 个就该考虑审计落表（GOV-08）

### 4.3 条件与其他

- [ ] [P1][COND-01] 条件判权（IP 白名单、时间窗、设备指纹）按需启用：每个条件都是新的攻击面 + 新的排障面 + 新的客诉来源（"在家连 VPN 就用不了"），没有真实事故驱动不加
- [ ] [P2][TEMP-01] 临时授权：带有效期，到期自动回收——大促借调权限的正确姿势，不用记得删
- [ ] [P2][TEMP-02] 委托代理：休假期间审批权暂交副手，期满自动收回

## 五、授权治理（权限怎么给出去）

- [ ] [P0][GOV-01] 最小权限是默认值：授予界面是白名单勾选（可选集 ⊆ 授予者权限），不是"全集去掉几个"；新建子账号默认零权限
- [ ] [P0][GOV-02] 授权动作本身可追溯：谁、何时、给谁、给了什么、依据是什么——最低限度落到结构化日志
- [ ] [P1][GOV-03] 审计记录 append-only 预期：不提供修改/删除审计记录的应用层入口
- [ ] [P1][GOV-04] **审计先行于复杂度**：审计完备度 ≥ 权限复杂度，是每一格光谱演化的前提——没有审计兜底的细粒度权限只是更难排查的混乱
- [ ] [P1][GOV-05] 权限变更即时反馈给在线主体：改完权限，对方下一次请求即按新权限执行（与 TIME-01 同源），必要时前端提示刷新
- [ ] [P2][GOV-06] 工单审批流：申请（理由+有效期）→ 直属主管 → 数据 Owner → 安全合规（高危才走）——权限从"管理员给的"变成"流程批的"
- [ ] [P2][GOV-07] 季度盘点（recertification）：数据 Owner 收清单逐条确认，不确认自动冻结——等保/SOX 硬要求
- [ ] [P2][GOV-08] 审计落表 + 查询界面：触发条件 = 出现第一次真实追责 / 高危操作数 > ~5 / 需要导出审计报告；此前结构化日志足够
- [ ] [P2][GOV-09] 审计留存期满足合规（等保/GDPR 有明确年限）；账号注销后审计记录的匿名化方案提前设计，别等监管问

## 六、架构与可靠性

- [ ] [P0][ARCH-01] 单体进程内判权起步：filter/interceptor + ThreadLocal 上下文 + 一次 indexed query，不上中台、不引依赖
- [ ] [P0][ARCH-02] 判权基础设施自身的故障模式显式选择：**默认 fail-close**（判不了 = 拒绝）；确需 fail-open 的纯浏览类读操作逐个白名单并写明理由
- [ ] [P1][ARCH-03] 判权路径性能预算：每请求 O(1) 次 indexed query，或零增量（复用认证/成员过滤链已查出的数据顺带装载权限）——超预算才谈缓存，先看是不是设计浪费
- [ ] [P1][ARCH-04] 测试基线与业务回归同权重：每个端点的权限矩阵用例（有权通过 / 无权 403 / 边界角色 / 已禁用 / 已过期），权限回归纳入 CI 门禁
- [ ] [P2][ARCH-05] 权限中台化：触发条件 = 判权 QPS 或依赖系统数压垮单体；形态 = SDK 内嵌 + 多级缓存 + 变更秒级广播失效；中台的降级开关（fail-open/close 分级）本身按高危管理
- [ ] [P2][ARCH-06] ReBAC/ABAC（Google Zanzibar 层级）：仅关系型共享场景（网盘/文档协作/社交图谱）考虑，交易型电商 RBAC+数据权限几乎总能覆盖

## 七、错误语义

- [ ] [P0][ERR-01] 判权失败返回 403，与 401（没登录/凭证无效）严格区分：401 该去登录，403 是"知道了也没用，你没有"
- [ ] [P0][ERR-02] 403 携带稳定错误码（如 `PERMISSION_DENIED`），与业务性拒绝（"你不是该店铺成员""店铺已封禁"）区分——前端要据此渲染不同页面（无权限页 vs 引导申请页 vs 提示换店）
- [ ] [P1][ERR-03] 对外模糊、对内精确的边界：403 可以明说"无权限"（这不是敏感信息），但**不暴露"谁有什么权限"的枚举接口**——权限配置查询本身就是敏感权限

## 冲突项的裁决

以下条目之间存在张力，实现时以本节裁决为准，不要自行"二选一"。

**#1 实时查库 vs 判权缓存/token 自包含**（TIME-01 × ARCH-03）
实时为准：收权即时生效是安全属性，不是可拿来交换性能的优化项。中小规模一次 indexed query 不是瓶颈；能复用既有查询（认证链、成员过滤链）就零增量。缓存的准入条件是失效机制已就绪且越权窗口数字被显式接受（TIME-03），准入前禁止"为了快"引入。

**#2 默认拒绝 vs 开发效率**（ENF-02 × ENF-05/ARCH-04）
漏标必须在开发期爆炸（启动失败），不能在生产期被发现。"先跑起来、权限以后补"是权限债的第一大来源——以后 = 永远不会。开发体验靠启动自检的清晰报错解决，不靠放宽默认拒绝。

**#3 合并码够用 vs 细粒度审计**（GRAN-01 × GRAN-02）
合并码起步，但命名必须让审计问题可答（`PRODUCT_MANAGE` 能回答"谁能改商品"）。拆分的触发器是第一个真实的"能看不能改"岗位出现——是业务事件触发的重构，不是架构预演。反方向同样成立：已经拆开的码不因为"看起来冗余"合回去。

**#4 fail-open vs fail-close**（ARCH-02）
权限基础设施自身故障时，写操作与资金相关一律 fail-close；纯浏览类读可评估 fail-open，但必须白名单化并写明业务理由。默认 close，开 open 是例外且要有 owner 签字——这个开关本身按最高危管理。

**#5 权限拒绝 vs 业务拒绝**（ENF-04 × ERR-02）
同一个请求可能同时踩两层：无权限（403 PERMISSION_DENIED）与业务不允许（400/422 业务码）。裁决：入口判权在前、service 业务校验在后，错误各归各层；前端拿 403 渲染权限页，拿业务码渲染操作提示。禁止把业务规则伪装成权限码（"不能移除店主"不是 OWNER 缺权限），也禁止在 service 里重查一遍权限。

**#6 静态映射 vs 角色入库**（ROLE-05 × GOV-06）
静态枚举起步，映射改动走发版。入库的触发条件是「改映射发版」的频率×紧急度成为真实痛点，届时把映射数据搬表、判权接口不动。不为"运营同学将来想自己配"的想象需求预建管理界面——那个界面本身就是一个高危权限面（RISK-01）。

## 给 AI 的使用要求

你正在或即将为某个项目实现权限相关代码，本清单是你的设计依据和验收标准。要求如下：

**编码前**

1. 通读全文，包括「冲突项的裁决」，不要只看你正在写的那一节。
2. `P0` 条目必须全部实现，没有例外；`P1` 默认实现，不做必须在交付文档中写明理由；`P2` 可不实现，但架构上必须预留升级路径（如四元组的 condition 位、静态映射的可搬表结构、Resolver 返回值的 dataScope 位），不得堵死演进路径。
3. 先问清楚项目站在光谱哪一格，按格子取条目——把第 9 格的中台塞进第 3 格的项目和把第 3 格的 if 散在第 9 格的系统里，是同等严重的错误。
4. 条目间出现表面冲突时，以「冲突项的裁决」为准；裁决未覆盖的冲突，停下来问人，不要自行取舍。

**编码后**

5. 在项目内（建议 `docs/permission-implementation.md`，或项目约定的文档位置）写一份**对照实现文档**，逐条引用本清单的 ID，标注三种状态之一：

```markdown
# 权限实现对照（基于权限细节清单 vX）

| ID      | 优先级 | 状态      | 说明                                                      |
| ------- | ------ | --------- | --------------------------------------------------------- |
| ENF-02  | P0     | ✅ 已实现 | PermissionInterceptor 对 /admin/** 无注解请求直接 403     |
| ROLE-05 | P2     | ⏳ 延后   | 静态枚举起步（StaffRole.kt），映射搬表的触发条件见文档 §6 |
| COND-01 | P1     | 🚫 不做   | 无 IP/时间窗约束的业务诉求，condition 参数位已保留        |
```

- `✅ 已实现`：注明实现位置和方式（文件:行 / 配置项）
- `⏳ 延后`：注明触发阶段或前置条件（"出现跨部门数据圈选需求时""接入 ISV 前"）
- `🚫 不做`：注明理由和兜底措施；**P0 不允许出现此状态**

6. 对照文档完成后自查：P0 全 ✅，P1 的 🚫 每条都有理由，P2 的 ⏳ 每条都有触发条件，且「高危操作分级清单」「权限码表」在项目内有唯一真相源。不满足则回去改代码或改文档，直到满足。
