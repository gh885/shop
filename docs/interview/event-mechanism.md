# 事件机制 — 面试梳理

> 面试准备材料，口语复述设计；设计口径以 [infra/README](../../apps/server/src/main/java/com/shop/platform/infra/README.md) 和代码注释为准。

## 范围

讲的是**支付成功之后、订单模块收到通知之间**那一段：事件怎么保证不丢、不重、卡住了怎么救。对应代码在 `infra/event`（outbox 登记、去重、补发、清理、管理端放行）。

前置问题：支付事务提交之后，怎么告诉订单模块「钱到了」？两个模块不能直接互调（会成环），用的是事件：支付模块发一个 `PaymentSucceeded`，订单模块订阅它。

## 电梯稿

事件不是发完就完。它在支付事务里和业务写一起落进登记表——提交了才存在，回滚了一起消失；提交后框架才把监听器叫醒（AFTER_COMMIT）。消费失败或进程挂掉，登记行留在表里，补发任务每 30 秒重投，直到成功——代价是可能重复投递，所以消费方自己按事件 ID 去重。反复失败超过上限就停投转人工，管理端能看清单位数、清零重放。

## 追问

### Q1 publishEvent 是在事务里调的，事务回滚了，事件会不会已经被消费方拿到了？

不会，因为调用和投递是两个时刻。事务内调 `publishEvent` 只做一件事：往登记表插一行——这行和业务写在同一个事务里。监听器标的是 AFTER_COMMIT，Spring 保证它只在事务提交成功之后被叫醒。回滚的话，登记行跟着业务写一起回滚，根本不存在「之后」，监听器一次都没跑。消费方不是自己去捞事件的，是被 Spring 叫醒的，而叫醒条件是 commit 成功。

_追问「裸 @EventListener 行不行」：不行，那是当场、同步、在事务内执行——消费方提交了、支付事务随后回滚，就出现订单推进了、支付单还 pending 的脏状态，还没有任何机制能修复。_

### Q2 事务提交了，但消费方处理时抛异常，或者进程直接挂了，事件丢不丢？

不丢，因为事件的真身不是那条内存通知，是登记表里那一行——它已经和支付状态一起落库了，进程被 kill 也抹不掉。消费失败或没跑起来，这行就停在「未完成」，补发任务每 30 秒扫一遍，把够老的、没超上限的重新投递。进程重启也一样，新进程起来接着扫。这套思路叫 at-least-once：宁可重复，不可丢失。

### Q3 至少一次就意味着可能重复，重复了怎么办？

消费方第一件事去抢占：往去重表插一行，`INSERT ... ON CONFLICT DO NOTHING`，同一条事件 ID 只有第一次能插进去，插不进去说明处理过，直接返回。关键细节是这个抢占和业务写在**同一个事务**——上次业务写回滚了，抢占也一起回滚，下次重投不会被误挡；上次提交了，抢占记录也在，重投会被挡住。两个动作要么都成要么都没成，才不会出现「处理了但没记账」的缝。

### Q4 反复失败超过重试上限，停投之后，这条事件怎么救回来？

先修根因——不修的话捞起来只会再失败一轮。然后管理端有个放行入口：把那条事件的重投计数清零，下一轮补发任务自动捡起来。注意不是去调大全局的重试上限：那是全局旋钮，一调等于把所有超限事件一次性全放出来，可能只想重放一条；而且改配置要走发布，救火变成部署。单条放行是运维动作，全局上限是系统参数，不该混在一个旋钮里。

_追问「重放会不会重复推进订单」：不会，Q3 的去重和业务侧的状态前置条件都在，同一条事件放多少遍只生效一次。_

### Q5 登记表会不会无限增长？清理策略怎么定的？

每天凌晨清一次，只删**已完成**的登记和过期的去重记录，保留期 7 天——盖住重投窗口和投诉回溯就够。未完成的**永不删**：那是补发任务的病人，删了等于销毁病历，「钱到了但订单没推进」这种事物理消失，谁也没法再救。所以这张表的未完成部分只会增不减，它的体量就是「当前悬而未决的事件数」。

### Q6 这么多环节，日常怎么知道它活着？

盯两个指标：最老未完成事件的年龄（持续上涨说明有消费者在失败，归零说明系统是通的），和超限未处理的事件数（大于 0 就是在喊需要人）。卡住的事件不会自己喊救命，唯一的迹象就是指标上一条永远平的线——所以这两个数要进监控，光靠翻日志发现不了。

```
支付事务: [改支付单状态 + 插登记行]  ←──── 同一个事务，要么都成要么都不成
              │ 提交
              ▼
        AFTER_COMMIT 唤醒监听器 ──抛异常──▶ 登记行停在未完成
              │ 成功                              │
              ▼                                  ▼
        消费方: 先抢占(去重)               补发任务每30秒重投
        再业务写(同事务)                   超上限→停投→管理端放行
```
