# 订单链路 — 面试梳理

> 面试准备材料，口语复述设计；设计口径以 [order-model.md](../domain/order-model.md) 为准。

## 范围

讲 **trade 模块的订单生命周期**：从算价报价到交易完成（含退款怎么改订单）。支付回调怎么推进状态在 [payment-flow.md](payment-flow.md)，退款的钱怎么从渠道退回在支付篇，这里只讲订单侧的数字怎么动。

三层先立住：**订单组**（order_group）= 买家一次结算，支付单位；**子单**（seller_order）= 按商家拆，发货/结算/判责单位；**订单行**（order_line）= 具体到 SKU 的明细，价格和计数器单位。付款看组，发货看子单，算钱看行。

## 电梯稿

用户去结算，系统先算价出一张报价单。提交时拿报价单号落单：一个事务里烧掉报价单、建三层订单（组、按商家的子单、商品行）、预占库存，行上把价格优惠地址拍成快照。然后 30 分钟付款窗口，延时消息和兜底扫表两条腿盯着，超时关单。付款后商家发货，发货数记在行的计数器上，子单状态和买家看到的展示态都是从计数器现场算的。全部签收订单完成，结算才能分钱。已付款的订单关闭只有一条路：退款。

## 流程展开（追问的锚点全在这里）

```
阶段① 算价报价
  点「去结算」→ pricing 算价 → 报价单：SKU/数量/行金额/优惠分摊
  ↳ 此刻三层订单都还不存在

阶段② 落单（一个事务，四件事）
  前置校验：报价单可用、未过期、指纹一致（地址参与指纹）
    ↳ 对不上 → PRICE_CHANGED，重新确认，不拿旧价硬落单
  同一事务：
    ├─ 烧报价单（issued→used CAS；订单组上 quote_id 唯一索引再兜一层）
    │    ↳ 烧单和插单必须同事务：先烧后插=白烧好报价；先插后烧=两单抢一报价
    ├─ 建订单组 → 按商家拆子单 → 铺订单行（快照列一次写死）
    ├─ 预占库存（同步；异步会超卖）
    └─ 发 SellerOrderPlaced（outbox）
    ↳ 库存不足 → INSUFFICIENT_STOCK，整单回滚（报价单恢复可用）

阶段③ 等付款 30 分钟（挂在订单组上）
  主腿：落单时投延时消息，准点关
  备腿：每 5 分钟扫「未付且未关」的部分索引，绝不漏
    ↳ 两条腿走同一个 handler，消息是提醒、数据库才是事实
  CAS：WHERE payment_status='unpaid' AND closed_at IS NULL（和回调赛跑）
    ↳ 回调赢 → 关单 0 行，无事
    ↳ 关单赢 → 迟到回调挂账 order_closed，人工退
  ↳ 未付款部分取消会改应付金额：支付单没发起→作废重下；
    已到渠道→不许取消；付了没回调→等回调，金额不符整单退

阶段④ 已付款（消费 PaymentSucceeded，见支付篇）
  markPaid CAS → 发 OrderPaid（按子单各带一份金额）
    ↳ 预占被提前释放：commit 0 行时看预占状态，released/expired 要重新预占，
      失败发退款请求 + 告警——已付款订单必须有货

阶段⑤ 发货（商家，必须带运单号）
  履约建包裹 → 回写订单（api 命令，不是事件）→ 行上 shipped_qty 递增
  → 子单履约状态从行计数器重算（未发/部分发/全发）
  → 买家看到的展示态再从子单算，不落库
  改地址（已付款未发货）：改子单上的「当前生效地址」，组上快照只读；
    运费差额走独立退补款，原订单金额不动

阶段⑥ 签收与完成
  物流轨迹回调，或 10 天自动确认 → received_qty 递增
  → 全部行签收 → 子单 received → 全部子单收完 → 发 OrderCompleted
  → 结算开工：收货是货的终点，也是分钱的闸门

阶段⑦ 退款（已付款订单唯一的关闭方式）
  RefundSucceeded → 行上 refunded_qty / refunded_amount 递增
    （按 refundId 幂等，事件键挡重复）
  → 组上 refunded_amount 累加：满额转 refunded 并关单，否则 partially_refunded
    ↳ 快照列永不改，全是计数器叠加，历史可追溯
```

## 追问

### Q1 为什么必须先报价，不能前端传价格明细直接落单？

后端不能信前端，尤其钱。但更准的说法是：算价只允许发生在一个地方。接受前端传明细，后端就得写一套「校验价格」的逻辑，那本质上是在第二个地方算价，规则一变两边漂移。报价单的含义是价格在报价那一刻定死，订单只是引用结论。它同时是幂等键：报价单号在订单表上唯一索引，加 issued→used 的 CAS，同一张报价只能落一单——烧单和插单必须在同一事务，先烧后插会白烧好报价，先插后烧会被并发抢用。报价单还是变更隔离墙：地址参与价格指纹，改了地址回来指纹对不上，让用户重新确认而不是拿旧价硬落。

### Q2 订单行为什么抄一份商品信息，引用 SKU 不行吗？

引用是「现在是什么」，快照是「当时是什么」，订单要的是后者：商品改价、改名、下架甚至删档，订单页还得显示当初买了什么。佣金费率也在快照里——商家费率会调，老订单必须按下单时的费率结算。地址特殊，有两份：组上是下单快照只读（历史事实），子单上是当前生效地址（发货读它），因为改地址是单个商家的事。

### Q3 订单组为什么不存发货状态？

因为「部分发货」这个状态天生不是单值：三个子单一个签收一个发了一半一个没发，订单组该显示什么？说不清。所以不存，现场算——行上有精确计数器，子单状态从计数器重算，展示态再从子单算。存了就有两处真相，五条写路径迟早有一条漏更新，必然漂移。多写路径并发冲突是症状，表达不了才是病根。

### Q4 「已关闭」为什么不是付款状态的一个值，是单独一列？

两个正交维度回答两个问题：payment_status 答「收没收过钱」，closed_at 答「还活着吗」。合成一个枚举，关闭时收没收钱的信息就被覆盖了——对账、退款、客服都还要问这个问题。拆开还有个实际好处：关单和回调赛跑的 CAS 前置条件刚好是两个维度各出一条（unpaid 且未关闭），闸门形状统一。

### Q5 有了延时消息，为什么还要每 5 分钟扫表？

消息是提醒，数据库才是事实，关单不能建立在「消息一定送达」上——broker 重启、队列重建、位点回退，任何一种发生订单就永远挂着、库存一直被占。兜底扫表和延时消息走同一个 handler、同一个 CAS，不是第二套逻辑，是同一次判决的第二次机会。分工：消息管准点，扫表管不漏。扫表只扫「未付且未关」的部分索引，分批跑。

## 追问的生长规律

同支付篇：happy path 没信息量，追问全长在边角——报价单为什么烧、快照为什么抄、状态为什么算不存、消息为什么还要兜底。准备方法不变：把流程里每句话当问题读。
