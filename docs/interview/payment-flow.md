# 支付流程 — 面试梳理

> 这是一份**面试准备材料**，用口语复述设计，不承载规范——设计口径以 [domain/](../domain/) 和模块 README 为准，两处不一致时以那边为准。

## 范围

讲的是 **支付模块（`platform/payment`）加上 trade 里的发起编排**，也就是「钱怎么进来、怎么确认、对不上怎么办」这一段。

覆盖：支付单生命周期、渠道回调处理、幂等、挂账、有效期、查单兜底。
不覆盖：退款重试、结算对账（`clearing`）、发货履约（`fulfillment`）；「通知订单模块」那一层的机制（outbox、去重、补发、放行）另见 [event-mechanism.md](event-mechanism.md)，面试里点到为止。

## 电梯稿（先背这段）

用户点支付，系统开一张支付单（pending），编好自己的单号，拿这个号加金额去渠道预下单，把收银台给用户。用户付完，渠道回调过来；系统先验签，再拿单号找到那张支付单，比对金额，都没问题就把支付单置成功，通知订单模块，订单进入待发货。任何一步不对劲：重复了就跳过（CAS），数目不对或来晚了就挂账等人，回调丢了就等用户点确认时主动查单兜底。

## 流程展开（追问的锚点全在这里）

```
阶段① 发起（买家点支付）
  trade 算好金额传给 payment（金额是参数，payment 不认识 trade）
  → 开支付单：生成 out_trade_no（PAY 前缀业务号），落库，状态 pending
    ↳ 已有未过期 pending 单直接复用，不堆一串；已过期未扫到的是死票，重开一张
  → 有效期 = min(自身 30 分钟，订单可付期 + 5 分钟宽限)
    ↳ min：不给「注定推进不了订单」的付款开门；+5：盖关单任务的扫描延迟
    ↳ 过期时间同步传渠道：我们关自己的门，渠道的门一起关
  → 拿 out_trade_no + 金额调渠道预下单 → 支付凭证给前端
    ↳ 渠道流水号此刻还不存在，回调回来时才补进支付单行

阶段② 回调路径（渠道主动，加速器）
  验签（渠道公钥，RSA）
    ↳ 失败 → 400 固定文案，真原因只进日志——细节是给攻击者的探测路线图
    ↳ 渠道只认报文里的 failure 回执，回 4xx/5xx 会被无限重投
  → 按 out_trade_no 查本地支付单（路由键：回调喊的号就是我们存的号）
    ↳ 查不到 → 404
    ↳ 已终态但报文说成功 → 挂账 late_callback，回 success 让渠道停止重投
  → 金额比对：报文实收 vs 库里应收（验签证明「渠道说的」，比对证明「说的是这单的事」）
    ↳ 不符 → 支付单照样置 success + matched=false + 挂账 amount_mismatch
  → CAS 推进：UPDATE … WHERE status = 'pending'
    ↳ 影响 0 行 = 重复或并发回调已被处理，跳过，无异常，应用层看行数
  → 置 success、渠道流水号落库，同事务登记 outbox 事件

阶段③ 查单路径（买家触发，回调丢了时的唯一出路）
  归属校验：查不到和不属于你返回同一个 404（可枚举的单号不做校验就是探测器）
  → 查渠道（远程调用放事务外，不占行锁）
    ↳ 渠道查不到 ≠ 出错 → paid=false 正常返回，用户可能还没付
  → 汇入和回调同一个处理函数，金额比对、CAS、挂账逻辑一字不差
    ↳ 多入口单出口：两条路各写一套必然漂移

阶段④ 事件投递（事务提交之后）
  AFTER_COMMIT 唤醒 → trade 消费（事件去重 + markPaid CAS）
    ↳ 不丢、不重、卡住怎么救，见 event-mechanism.md
```

术语速查：**支付单**=一次收款尝试的记录（订单一对多支付单）；**out_trade_no**=我们编的接头暗号；**渠道流水号**=渠道的收据编号，付款完成才产生；**挂账**=钱真到了但推进不了，记下来交人工；**CAS**=带条件更新，条件不满足=有人处理过了。

## 追问

### Q1 为什么单独开一张支付单？订单上加个状态不行吗？

订单和支付单生命周期不一样：订单活到发货售后结束，好几天；一次支付尝试只活 30 分钟。一个订单可能尝试好几次支付，每次尝试都是一个独立的东西。而且渠道那边一个号只能对应一次收款，用户第一次没付完，你想再发起，就得有个新号——新号总得有地方存。所以单独一张表，钱相关的字段（渠道流水号、实收、报文）也全挂在它身上，不污染订单表。

_追问「付两次钱吗？」：是尝试多次，成功只有一次。_

### Q2 为什么不用订单号当支付单号？

渠道要求一个号对应一次收款，订单号在整个订单周期不变，第二次尝试根本发不出去，这是硬约束。顺带内部 UUID 不出门，外面只流动我们自己编的业务号；这号虽然规律性强、容易被扫，但所有暴露它的接口都做了归属校验，「查不到」和「不是你的」返回同一个 404，枚举了也查不到别人的。

### Q3 验签都过了，为什么还要比对金额？

签名证明的是「这话确实是渠道说的」，不证明「说的就是我们这单的事」。金额比对是拿报文里渠道说的实收，和自己库里的应收对账——两边缺一不可：少了报文金额不知道实收多少，少了库里应收连该收多少都没依据。对不上多半是我们自己的 bug（分转元、算错应付），挂账清单反而是报警器。

### Q4 金额不符为什么不自动原路退款？

退款不是撤销，是一笔新的资金操作——它同样要选金额、选账户、过渠道。系统这时候只知道自己不知道：数目不对，但为什么不对、差在哪，一概不知，连该退多少都答不出来。所以把这笔有疑问的钱隔离在可审计、不流转的状态里，交给有上下文的人去查。晚几个小时处理，代价是用户等等；自动退错一次，代价是真金白银加对账烂摊子。

### Q5 两个回调同时到达，CAS 凭什么只成功一个？底层发生了什么？

UPDATE 是一条语句，判断和修改在数据库内部一步完成，没有留给别人的缝。两个请求真并发时，第二个会在行锁上排队，等第一个提交；醒来后按提交后的最新数据重新检查 WHERE，status 已经不是 pending 了，条件不成立，影响 0 行。注意不是报错——语句正常执行完，0 行受影响，应用层靠行数知道有人抢先了。

_追问「先 SELECT 再 UPDATE 行不行」：那是两个语句，中间有缝，两个请求能都查到 pending 然后都更新。_

### Q6 CAS 都保证只推进一次了，下游为什么还要按事件 ID 去重？

两道闸管的不是一个门口。CAS 在支付侧，管「这张支付单的状态只能变一次」；但通知本身会重发——补发机制保证至少送到一次，代价是可能到两遍。消费方不能赌上游的闸顺手替自己挡了，要在自己家门口再放一道「这条我处理过没有」。防御放在离风险最近的地方，不算重复建设。

### Q7 订单关了之后钱才到账，回调进来怎么处理？

直接挂账，交人工。这钱和金额不符的钱是同一类东西：真实到账但状态机推进不了。但有个别忘的细节：回给渠道的响应必须是 success——渠道对失败响应会无限重投，而重投救不了任何东西，让它停止敲门是止损第一步。挂账记录里要留全故事线：订单何时关的、钱何时到的，处理的人要看得懂全貌。

### Q8 回调和查单两条路，代码是分开写的吗？

必须汇合到同一个处理函数。分开写必然漂移：回调路径记得比对金额、查单路径忘了；回调路径有幂等、查单路径没有——两条路就是两份必须永远同步的代码，靠自觉守不住。原则是多入口、单出口：入口可以有回调、查单、以后的对账补单，状态机的心脏只能有一个。查单独有的东西只有两个：归属校验（用户可触发，不能让人拿别人的单号确认收款）和渠道调用放事务外（慢操作不占行锁）。

### Q9 支付单有效期为什么是 min(30 分钟，订单期限 + 5 分钟)？

min 是两条死线取早的：一次尝试不该挂超过半小时；更重要的是不能活得比订单可付窗口久，否则渠道还在收一笔注定进挂账的钱——用户在订单过期前 1 秒点支付，就是系统自己给自己制造挂账。+5 分钟盖的是关单任务的扫描延迟：订单到期不是那一秒就关，任务隔几秒才扫一轮，不留「支付单死了、订单还活着」的错位窗口。过期时间还同步传给渠道，两边门一起关。

## 追问的生长规律

面试官的追问几乎不长在主链路上——happy path 谁都会讲，没信息量。它们全长在边角：两条路赛跑谁赢、通知丢了怎么办、为什么不能自动退款、为什么这个号不复用。准备方法：把自己流程里的**每句话当问题读**——「开了支付单」→ 为什么开？「比对金额」→ 验签过了为什么还比？能经得起三层「为什么」的句子才算掌握。
