# mapper 层职责：怎么取，以及怎么在一条语句里原子地改

> 后端细则。速查结论见 `apps/server/AGENTS.md`「硬规则」。并发写偏斜/丢失更新的论证见 [../adr/0001-lost-update.md](../adr/0001-lost-update.md) 与 [../adr/0002-write-skew.md](../adr/0002-write-skew.md)。

**判据一句话：mapper 管「怎么取」和「怎么在一条语句里原子地改」，本模块 service 管「做什么、按什么规则、按什么顺序」。** 分界不看代码长短，看**放错层会不会有人在别处抄第二份**——条件抄第二份就有两个答案，流转抄第二份就有一条绕过闸门的路。

- **该放 mapper**：查询条件、排序、批量 `IN` 取值域、投影与聚合、常用查询的具名薄封装（`UserMapper.selectByPhone`）。聚合在 SQL 里闭合、交出结果形状，不把裸 row 抛回 service 再拼（`FavoriteItemMapper.collectCountByProductIds` 回 `Map<UUID,Long>`）
- **条件更新的守卫默认写死在 mapper，不由参数传入**：`UserCouponMapper.lockOne`（`UNUSED → LOCKED`，CPN-35）、`OrderMapper.markDelivered`（`SHIPPED` + `delivered_at IS NULL`）、`UserMapper.markDeletionRequested`（`ACTIVE` + 两个 `isNull`，ACC-75）、`ProductMapper.takedownPublished`（只碰 `PUBLISHED`）。方法名就是那条流转，守卫是它的**适用域**——把守卫做成参数等于把「注销只碰 ACTIVE」这类裁决交给调用方，传错一个值洞就开了。只有两种情况该传参：① 起点由实体状态机推导（`Order` 私有 TRANSITIONS 表那种），service 定从哪到哪、mapper 只保证「不是那一行就不改」；② 把上游已判、但两步间可能变掉的谓词在同一语句里重跑（`UserMapper.anonymize` 的 `requestedBefore`，防冷静期内被撤销）
- **mapper 交出「改到了没有」的信号，不决定后果**：条件更新回影响行数（`SkuStockMapper.freezeOne`/`captureOne`/`releaseOne` 用 PG18 `WHERE` 闸门 + `RETURNING OLD/NEW` 拿回前后两帧，无行 = 闸门没过）。409 还是重试、要不要记流水，一律在 service 判；「0 行即没发生，不报错也不重试」是 `anonymize` 头注释里的既定口径
- **一切「读到再写回」的量必须是一条语句**：禁 `selectById` 后接 `updateById`——两步之间的窗口只有并发来了才看得见，看不见不等于没有。原子手段按需挑：`WHERE` 闸门（`lockOne`）、`ON CONFLICT DO NOTHING`（`SkuStockMapper.insertIgnoreConflict`）、`ON CONFLICT ... DO UPDATE ... RETURNING`（`FavoriteItemMapper.upsertIdempotent`，PG 一报唯一索引错就把整个事务标成 aborted，catch 之后的回读根本执行不到，25P02）
    - **`updateById` 的坑源**：跳过 null 字段（「空串＝清空头像」落不进去）、靠 `AuditedEntity` 自动填 `updated_at`（wrapper 条件更新须自己 `.set(updatedAt, now)`）。整行回写的代价是「把别人的处置写回旧值」：登录/刷新手里的快照晚一步落库，就能撤销这期间管理端封的号、把已匿名化的号码复活。治理与账号写入一律收进条件更新族（`UserMapper.updateStatus`/`touchLastLogin`/`updatePasswordHash`/`updateProfile`、`StaffMapper.disable`/`enable`/`updateRole`、`ShopReviewMapper.decideIfPending` + `ShopMapper.applyReviewVerdict`）
    - **有第二个写者的列，实体必须标 `@TableField(updateStrategy = FieldStrategy.NEVER)`**：`updateById` 写的是「打开页面时读到的那一帧」，一列若还有别的事务经条件更新/原子写在改（`Product.soldCount` 由 `addSoldCount` 自增、`Product.status` 由停业级联 `takedownPublished` 与上下架条件更新改），整行回写就是把别人的处置写回旧值——卖家编辑商品撞上平台下架，商品会被静默「救活」。普通字段编辑仍允许走 `updateById`（JSONB 列的 typeHandler 只在实体路径生效，同一主体 last-writer-wins 可接受），判据只有一句：**这一列有没有第二个写者**。有就 NEVER；状态流转一律走 mapper 条件更新，不走「读整行、setStatus、updateById」（`ShopMemberMapper.activatePending`/`CouponTemplateMapper.stopIfActive` 就是从这种写法收回来的）。回归样本 `ProductStaleWritebackIT`；门禁 `SecondWriterColumnGateTest`：扫每个 `updateById` 调用点的实体，同一条 wrapper 语句里既做守卫又被 SET 的列（转移列）与本实体 Mapper SQL 里 `x = x ± n` 的列（累加列）必须 NEVER，`@Version` 实体豁免，同主体普通编辑的撞车不归它管——第二次审视抓到 `ShopMember.status`（店主调权限撞上对方确认）后立的，第一跑补标了 `Payment.status`、`Address.isDefault`、`MerchantAddress.defaultShip/defaultReturn`、`CartItem.quantity`，后三者顺带把置默认 / 改数量改成具名条件更新（`setDefaultFlag`/`setDefaultFlags`/`updateOne`）
    - **聚合量的末位保护不是一条行级语句能表达**：「不能禁用/降级最后一个在岗超管」（ACC-57）数的是跨行聚合，`WHERE status = ACTIVE` 挡得住同一行被抢两次，挡不住两个最后超管被同时禁用。用 `StaffMapper.lockSuperAdminGovernance()`（事务级咨询锁，提交即释放；行锁会各自先拿对方行的共享锁再抢主写锁凑成环 → PG deadlock）。这类动作一天没几次、全是人在管理端点的，串行化代价可忽略。锁与计数必须成对出现在同一私有出口（`StaffService.requireNotLastActiveSuperAdmin`），否则新增调用点会忘记取锁
    - **真并发只有真线程验得到**：`StockConcurrencyIT`（16 线程抢同一行、断言流水前帧互不重复）的形状已复用到 `StaffGovernanceIT`（末位超管竞争下是否还留一个）与 `ShopReviewConcurrencyIT`（双审批只落成一边）。串行用例跑不出这一格，mock 用例把失败面直接挡掉
- **「根据查询结果决定下一步」要拆开看，别误杀正当代码**：正当的是 `ProductMapper.requireShopOwned`/`OrderMapper.requireOwned`——「取行 + 判归属 + 交回这一行」一句写完的薄封装，只把 404 口径收在取数点（`OwnershipDoorTest` 背书）；不正当的是在 `default` 方法里连调两条语句、按第一条结果决定第二条（要不要补发、锁哪张券、跳到哪个状态），那是编排，住进 mapper 后本模块规则就没有一个读得到的地方了
- **有一条例外必须写出来，否则下一个人会去补 JOIN**：跨表聚合出来的排序键进不了 SQL。库存两档（PRD-79）不在 `products` 的列上，只能 service 把整店商品取回内存按聚合值排、再手动分页，mapper 只负责那一次批量取。不许为了「合规」写跨 schema JOIN，那条禁令更硬
- **复杂条件含业务口径时，口径要在名字或注释上现身**：`ShopReviewMapper.QUEUE_ORDER_BY` 把「待审记 0、已处置记 1」写成常量并注明排的不是列而是一句档位表达式（ACC-08）；`UserCouponMapper.selectPageMine` 的「UNUSED 那一档含 LOCKED、EXPIRED 那一档含库里还没收敛但已过 `expire_at` 的行」是券包页签的展示口径（CPN-51）。这类口径从注释丢了，下一个人就在 service 再判一次状态，两处答案从此漂移
- **方向：MyBatis-Plus 类型不外泄，`Page` 翻译只有一处**。出参：没有 service/api 交出 `Page<Entity>`，一律折成 `common.PageResult<T>`。入参：`new Page<>`、条件容器、裸 `.last(...)` 只出现在 mapper 包，service/api 递 `PageParams` + 筛选值、接回 `Page<T>` 局部变量。范本 `ShopReviewMapper.selectQueuePage(PageParams, filter)`
- **只碰本模块那张表**：mapper 不 import 他模块 service/api/mapper，不跨 schema JOIN（`NamingRulesTest` 的 `JdbcTemplate` 白名单、`MoneyTypeRulesTest` 的 `currency` 列白名单都假定这一条）；跨 schema 裸 SQL 只允许 `infra.db` 与各模块 api 包
- **编译期门禁**（都在 `NamingRulesTest`）：`mybatis_conditions_only_in_mapper`（ArchUnit 挡 `com.baomidou.mybatisplus.core.conditions..` 被非 mapper 包引用）；`分页构造与裸SQL尾巴只住在mapper包`（非 mapper 文件出现 `new Page<` 或 `.last(` 即红）
- **写审计账本的调用点必须在事务里**（`AuditTransactionGateTest`）：`RecordAuditCommand.record` 是 `@Transactional(MANDATORY)`，调用方漏注解就是「库已改、账本没写、接口回 500」。门禁按行认成员，认不出所属方法也算违规
- **钉不住的半边由 code review 维持**：「有没有副作用」「有没有按结果决定下一步」静态判不了。写新的语句型 mapper 方法前先答「这条能不能一条语句做完」，不能就搬 service 或改状态机，别在 mapper 里堆步骤
