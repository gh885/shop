# 国际化（i18n）约定与落地架构

> 当前只启用 zh-CN + en-US，但所有模型按「未来支持 N 个语言」设计。
> 本文是 i18n 的唯一入口；改用户可见文案、错误文案、日期/数字格式前先读。
> 相关文档：前端规范 [frontend.md](frontend.md)、错误码 [../error-codes.md](../error-codes.md)、架构总览 [../architecture.md](../architecture.md)。

## 1. 结论

| 项                        | 决定                                                                                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 源语言 sourceLocale       | zh-CN                                                                                                                                                                                             |
| 支持语言 supportedLocales | zh-CN、en-US                                                                                                                                                                                      |
| 默认语言 defaultLocale    | zh-CN                                                                                                                                                                                             |
| 回退链 fallback           | en-US → zh-CN                                                                                                                                                                                     |
| 一期范围                  | 三端 UI 文案、错误码文案、日期/数字格式、Locale 请求头透传                                                                                                                                        |
| 一期不做                  | RTL、多币种结算、动态内容翻译、TMS 深度集成、按地区数据驻留                                                                                                                                       |
| 包边界                    | 纯逻辑进 @shop/common；React Provider/hook 进 @shop/app-kit；业务文案按 app ownership 拆                                                                                                          |
| Web URL 策略              | 一期先用 cookie + Accept-Language；正式出海前再升级为路径前缀 /en-US/...                                                                                                                          |
| Locale 的载体             | **不允许跨请求共享的可变 locale**：随请求（SSR）或随启动（SPA）解析一次，显式流经 context 与 fetch 边界。要删的是进程级可变量，客户端把它存成 React state 不在此列（§3.5）                        |
| key 与参数                | **类型与生成期校验分工，不互相替代**：装配走 glob，tsc 不读 JSON，「en 不缺条目」也是生成期的事；类型真正接走的只有「调用侧拼错 key/传错参数」一条（§5.5）                                        |
| 消息语法                  | **ICU**，引擎是 `intl-messageformat`。不再有私有子集，也就不再有私有校验器（§4.4、§10.1）                                                                                                         |
| 错误文案归属              | **本项目 UI 错误：后端出 code，前端出文案**；`detail` 降级为日志字段。服务端本地化在公开 API 与通知场景仍是正解，范围限定见 §7.3                                                                  |
| 门禁的判据                | **覆盖完整 / 判定准确 / 自动执行 / 失败阻断**四条一起成立才算门禁。旧脚本要被删是因为它撑不住后三条（第一条覆盖已在 §9 P0′ 补上），不是因为「门禁不该是脚本」；codegen 那套四条已成立（§10.1 末） |

**一句话：架构上支持多语言，一期只交付中英；文案资源可替换，核心代码不感知当前支持几种语言。**

上面新增五行是**判据**，不是已经全部成立的事实：换引擎（消息语法）、资源清单收口（§4.2 那两处漏点）、门禁的自动执行与失败阻断（codegen 已接进 `i18n:drift` + lefthook + CI，§5.5、§10.1）、locale 不再跨请求共享（`getCurrentLocale`/`setCurrentLocale` 已删，§3.5）四件已随 §9 P0′ 落地；第五件——`MessageKey`/`ParamsOf` 真的约束到**三端**的调用点——随 P0′-4b 成立，落点是各端 `src/locales/use-t.ts`（机制与已知的口子见 §5.5 表末）。

locale 那条只算**半程**：进程级可变量没了，但 web 的 SSR 仍是「一份 scope 服务整个进程」，服务端按请求解析语言要等 §9 P3′-a（约束与后果见 §3.5 末）。

判据的反面是它容易被绕开：locale 存成全局、资源不进统一清单、错误文案回到服务端，任何一条发生都不会有东西自动报错。`scripts/i18n-check.mjs` 曾经整片查不到 app-kit 的文案（§10.1），就是「有门禁」和「门禁覆盖了目标」是两件事的实例。

## 3. Locale 模型

### 3.1 类型与常量

放在 packages/common/src/i18n/locale.ts（纯逻辑，不依赖 React）：

    export const SUPPORTED_LOCALES = ['zh-CN', 'en-US'] as const
    export type AppLocale = (typeof SUPPORTED_LOCALES)[number]

    export const DEFAULT_LOCALE: AppLocale = 'zh-CN'
    export const SOURCE_LOCALE: AppLocale = 'zh-CN'

    export const FALLBACKS: Record<AppLocale, AppLocale | null> = {
        'zh-CN': null,
        'en-US': 'zh-CN',
    }

### 3.2 归一化

外部输入可能来自：

- Cookie：locale=zh-CN
- Accept-Language：en-US,en;q=0.9,zh-CN;q=0.8
- 用户资料
- 未来 URL 前缀

统一入口：

    export function normalizeLocale(input: string | null | undefined): AppLocale | null
    export function resolveLocale(candidates: Array<string | null | undefined>): AppLocale

一期可把 zh、zh-Hans、en 分别归一到 zh-CN、en-US；以后加语言时只扩映射表。

### 3.3 解析优先级

| 场景               | 优先级                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 三端（今天的实现） | locale cookie（「用户显式设置」就落在这条 cookie 里）> navigator.language > DEFAULT_LOCALE |
| web SSR 首屏       | 同上，但挂载前恒为 DEFAULT_LOCALE：服务端还没参与解析（缺口记在 §5.3 与 §9 P3′-a）         |
| web 正式出海后     | URL 前缀 > locale cookie > Accept-Language > 默认                                          |

三行都交给同一个 `resolveLocale()`：归一（`zh_CN` / `zh-Hans-CN` → `zh-CN`）与「不支持就往下走一级」只在它那里判一遍，装配侧不各判一次。

### 3.4 回退

任何取文案的地方都遵守：

    请求 locale -> 当前 locale 资源 -> fallback locale 资源 -> key 本身

key 本身作为最后兜底，同时上报缺失监控。不允许回退成空字符串，也不允许因缺翻译白屏。

### 3.5 当前 Locale 的持有方式

**规则：不允许跨请求共享的可变 locale。** 注意这条禁的东西很窄，别顺手扩成「locale 不能是状态」：

- 客户端把当前语言存成 **React state** 完全正当（今天 `provider.tsx:38` 的 `useState` 就是这么做的，保留）。
- 请求上下文里**持有** locale 也是正当的——它是不是「数据」取决于是否跨请求共享，不取决于它存在哪里。
- 要删的是**进程级可变量**：`packages/common/src/i18n/locale.ts` 里那个 `let currentLocale` 配 `getCurrentLocale()` / `setCurrentLocale()`。**已删**（§9 P0′-5），下面这段留的是删它的理由，别再按现状读它。

理由不是风格：

- 它是进程级可变量，而 web 是 SSR。当时写它的是 `provider.tsx` 的 effect，读它的是 `app-kit/src/format.ts`、`translateAppKit`、以及三端拼请求头处。
- effect 在服务端不跑，所以**当时还没出错**。但 §9 P3′-a 要让服务端按请求解析 locale 时，这个全局就是跨请求串语言的通道：两个用户的请求在同一次进程存活里共用一个 `currentLocale`，其中一个的 `Accept-Language` 会带着另一个的语言出去。
- 修它的正确时机是在 P3′-a 之前，不是之中：那条「服务端解析 locale」如果落在保留全局的实现上，得到的功能是「按请求头切语言」，代价是并发下的错语言响应。
- **而且这种响应错在修之前就能被测出来**：两条不同 `Accept-Language` 的请求交错进 SSR，断言各自的 HTML 语言与请求头一致——保留全局时这条测试应当红。正确顺序是先写它、看它红、再删全局，不是删完再补。旧版这里写过「这类 bug 在测试里长不出来」，那是错的：写不出来的不是测试，是**懒得构造交错请求**的测试。

约束：

1. locale 由装配侧解析**一次**：SSR 每请求一次、SPA 每次切换一次；解析结果作为参数传进 `I18nProvider`、`formatMessage`、`format*`。
2. `format*` 纯函数的 locale 参数一律**必填**，不给默认值。有默认值就等于允许「不知道当前什么语言」这个状态存在。
3. 非组件上下文需要 locale（`notify.ts`、`translateAppKit`、请求头注入）→ 由**请求级/装配级作用域**提供。手段按可达性排序，不指定实现：能沿调用链传参就传参（首选，`translateAppKit` 与 `format*` 都属于此类）；传不动就用装配时注入的**持有者实例**（`configureSdkClient` 的 `contextHeaders` 钩子已是这个形状，见 §7.1）；两者都不成立的场景，才轮到服务端 `AsyncLocalStorage`——它是补漏的工具，不是这条规则的默认形态。
4. `document.documentElement.lang` 与 cookie 的写是**副作用**，留在 Provider 里；它们是 locale 的输出，不是 locale 的存储。
5. 语言隔离不止 locale：时区输入与缓存维度同样会让「没串状态」的实现输出错语言的内容，见 §5.6。

落地后的形状（三档各有一个指认得出的出口，别再造第四个）：

| 谁需要 locale                                 | 走哪一档            | 出口                                                                                                                                     |
| --------------------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 组件                                          | 传参（约束 3 首选） | `const { locale } = useI18n()`，显式传给 `format*` / 纯函数                                                                              |
| 纯函数与投影链（model / tracking / 表元代生） | 传参                | 签名里加 `locale: AppLocale`，由最近的组件喂                                                                                             |
| 模块级 `ColumnDef[]` 的 `cell`（不是组件）    | 换形状              | `@shop/app-kit` 的 `<TimeText iso shape>`；它是「渲染这一格的小组件」，因此既拿得到语言又能随切换重画                                    |
| 拿不到 hook 的全局回调（`MutationCache`）     | 装配注入的持有者    | `createAppQueryClient(scope, …)`；scope 由各 app `src/shared/lib/locale-scope.ts` 导出，同一实例交给 Provider、`contextHeaders` 与该工厂 |

**SSR 下那个 scope 仍是进程内的一个实例**，这不是回归而是有意留下的缺口：服务端没有组件挂载，没人写它，读到的恒是平台默认语言（`packages/app-kit/src/i18n/scope.ts` 头注释同此）。P3′-a 落地时它要么按请求创建、要么换成请求上下文——那时被改的是这一个文件与三处装配，不再是包在一个 `let` 里的隐式全局。

## 4. 资源 ownership 与格式

### 4.1 放哪

| 层                      | 职责                                                             | 不做什么                                                            |
| ----------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| @shop/common            | Locale 解析、回退、格式化纯函数                                  | 不依赖 React；**不承载任何用户可见文案**，含错误码文案（§7.3）      |

| apps/web/src/locales    | 买家端业务文案                                                   | 不复制 app-kit/ui-web 已有文案                                      |
| apps/seller/src/locales | 卖家端业务文案                                                   | 同上                                                                |
| apps/admin/src/locales  | 管理端业务文案                                                   | 同上                                                                |

### 4.2 命名空间

    apps/web/src/locales/
      zh-CN/
        app.json common.json footer.json header.json login.json nav.json security.json   # 今天的 7 个
        home.json product.json order.json                                                 # P2 铺业务页面时再加
      en-US/
        # 与 zh-CN 同名、同 key：文件级平齐由装配保证，key 级平齐由 codegen 保证（§5.5）

    packages/app-kit/src/locales/          # 共享那份，与 app 侧同一形状、同一装配、同一 codegen、同一约束
      zh-CN/appKit.json                    # 31 条：登录壳层 + 确认框/网络错误/搜索框
      en-US/appKit.json
      {zh-CN,en-US}/error.json             # 待 §7.3 把 error-messages.ts 收进来（§9 P0′）

共享组件文案走 appKit namespace，错误文案走 `error.<code>`（§7.3）：

    appKit.login.submit
    appKit.error.network
    error.SMS_CODE_EXPIRED

**所有资源必须被同一份清单覆盖。** 这是判据；「形状统一成 JSON」是达成它的手段，不是目的——TS 对象同样能被类型约束，别把这条读成「非 JSON 就必然失控」。真正的问题是 §5.5 的 codegen 从哪拿到资源清单：一条藏在 `src/i18n/messages.ts` 里的字典不会出现在 `**/locales/**/*.json` 的 glob 结果里，于是任何按清单跑的东西（解析、比对、生成类型、覆盖率统计）都静默漏掉它。仓库里有两处这种漏点，P0′ 都收了：

- `packages/app-kit/src/i18n/messages.ts` 曾把 `APP_KIT_MESSAGES` 内联在 TS 里（实测 31 条 × 2 语言）。而全仓库唯一真在用插值的两条消息（`appKit.topbar.searchLabel` 的 `{brand}`、`appKit.login.resend` 的 `{countdown}`）恰好全在那里面——旧校验器只扫三端的 `src/locales/`，一条都查不到，这就是「有门禁但门禁没覆盖目标」的实例。现已落成 `packages/app-kit/src/locales/<locale>/appKit.json`，逐条与内联那份比过，两种语言 31/31 一致。附带好处：JSON 是翻译工具直接读写的格式，§9 P4 少一层转换器。
- 三端原来各一个 `common.json` 装了全部 198 个 key（web 87 / seller 63 / admin 48；这一版文档先前写 298，与它自己给出的逐项拆分加起来对不上，是抄下来的数没核过——正是 §10.1 讲的「判定准确」问题）。按域拆完：web 7 个 namespace（app / common / footer / header / login / nav / security）、seller 7（account / app / common / layout / login / nav / topbar）、admin 7（account / app / common / layout / login / nav / page）。key 一条没改名，所以调用点零改动；合并结果与拆之前的 `common.json` 逐条相等（脚本比完即删，没留在仓库里当门禁）。`common.json` 现在只剩 6 条 `common.*`。拆的收益是**可维护性与按域 ownership**（一个 PR 只碰一个 namespace，review 面小），namespace 由文件名给而不靠 key 前缀约定。

两处收口用的是同一个装配：`import.meta.glob` 拿清单，`packages/app-kit/src/i18n/resources.ts` 的 `assembleLocaleResources` 合并。装配只负责把两种**静默失效**变成抛——语言目录名打错（那份文件等于不存在）与同一语言内跨文件撞 key（拆文件之后新出现的覆盖面，也是上一版内联字典根本不会有的失效）。清单本身仍然不校验 key 平齐与语法，那是 codegen 的活（§5.5），别把它记在装配头上。

第二条要说清一件事，别混着卖：**拆文件本身不会让联合类型变小。** 只要 `MessageKey` 还是一个全局联合，198 条拆成 21 个文件之后它仍是 198 个成员，报错信息一样不可读。想控制类型体量是另一个决定——按 namespace 出 key 类型（`OrderKey` / `CheckoutKey`，`t()` 用 `t<K extends MessageKey>(…)` 但各 app 只 import 自己那几个 namespace 的类型）。这条在 P0′ 做 codegen 时一并定，不要等到铺完 P2 才发现联合炸了。

### 4.3 key 规范

使用语义 key，禁止用中文/英文原句当 key：

    home.header.searchPlaceholder
    product.detail.addToCart
    order.status.pendingPayment
    common.action.confirm

命名建议：

    {domain}.{area}.{element}

### 4.4 文案写法

必须使用 ICU 参数，禁止拼接。**语法以 `intl-messageformat` 的解析器为准**，不是「ICU 风格」的私有子集——私有子集正是 `scripts/i18n-check.mjs` 存在的原因（它得为那套私有语法当校验器）。

    order.items: {count, plural, =0 {No items} =1 {1 item} other {# items}}
    order.greeting: Hello, {name}
    order.rank: 第 {index, selectordinal, one {#st} two {#nd} few {#rd} other {#th}} 位

覆盖范围：插值、plural、select、selectordinal、嵌套一期**全支持**，因为它们是现成 parser 的功能，不是我们的功能。旧版「一期先实现变量插值 + plural，select/selectordinal 后续补」作废——分阶段实现子集，就还是要维护一个子集校验器。

**金额是唯一例外。** ICU 的 `{n, number, currency: CNY}` 会在 `formatMoney` / 共享 `Price` 之外开出第二条金额格式化路径，直接撞 [AGENTS.md](../../AGENTS.md) 的「金额全链路只有一个形状、展示只走 `formatMoney`」。日期/数字照常允许走 ICU，只有钱不行。

但要说清这条护栏**靠什么成立**，它不是类型能自动给的：`总计：{amount}` 里的 `amount` 是不是金额，ICU 的 AST 里没有这个信息，从消息文本推不出来。所以护栏是两件事的合取，缺一都不成立：

1. **codegen 检查消息 AST**：任何带 `number` + `currency` 选项、或直接写 `¤`/币种符号的金额格式化，解析阶段就判失败。这一步类型系统完全帮不上——TS 看不见字符串内部。
2. **参数元数据显式声明**，codegen 据此把 `ParamsOf<K>` 里那个槽位收成 `formatMoney` 的返回类型（brand type），于是调用侧传裸 number / 裸 string 编译不过。元数据怎么给，二选一在 P0′ 定：约定参数名后缀（`{totalMoney}`、`{priceMoney}`），或资源侧带标注（`"@types": { "total": "money" }` 一类的旁表）。**没有元数据就没有 brand type**，旧版写「codegen 自动把它标成该类型」是把这一步跳过去了。

选第 1 条走 AST、而不是「约定不用 ICU 的 currency 就行」：约定不需要执行的东西都会漂，而这条漂了的后果是两种语言下金额长得不一样，属于最难被 review 看见的那类。

## 5. 运行时设计

### 5.1 纯核心

packages/common/src/i18n/ 提供（locale 参数一律必填，理由见 §3.5）：

    lookupMessage(catalog, key): string | undefined
    resolveMessage(resources, key, locale): string | undefined   // 走 §3.4 回退链
    isMessageValid(template, locale): boolean                   // 模板本身能不能编译（t() 用它降级成 key）
    formatMessage(template, params, locale): string
    formatNumber(value, locale, options?): string
    formatDate(value, locale, options?): string
    formatDateTime(value, locale, options?): string

`formatMessage` 是 `intl-messageformat` 的薄封装，不是引擎本体——`packages/common/src/i18n/message.ts` 现在就是这个形状（119 行的 `findBlockEnd` / `parseOptions` / `selectPlural` / `selectOption` / `replaceIcuBlocks` 已随 §9 P0′ 删除）。

封装必须保留的两条契约，都是 §10.3 的验收项：

1. **构造 `IntlMessageFormat` 对坏 ICU 抛 `SyntaxError`，而 `t()` 是同步返回字符串的**。所以 try/catch 必须在封装里面，不能指望调用点兜——这是「坏消息不白屏」的实现前提，不是防御性冗余。
2. 解析失败或缺消息 → 返回 **key 本身**（§3.4），不是空串。

日期格式不要在三端各写一套 yyyy-MM-dd，由 core 统一暴露应用层格式：

    formatDate(iso, locale)      // 中文：2025-06-01；英文：Jun 1, 2025
    formatDateTime(iso, locale)  // 两端的业务展示口径各写一条，不散落

### 5.2 React 胶水

packages/app-kit/src/i18n/ 提供：

    <I18nProvider initialLocale={initialLocale} resources={resources} scope={localeScope}>
        {children}
    </I18nProvider>

    const { locale, setLocale, formatDate } = useI18n()   // 只剩 locale 与 format*
    const t = useT()   // 各端 src/locales/use-t.ts 那份：key 与参数受生成物约束（§5.5）

各 app 传入自己的资源包：

    <I18nProvider initialLocale={initialLocale} resources={{ zh-CN: webZhCN, en-US: webEnUS }} scope={localeScope}>

`scope` **必填**，且必须是同一个实例交给 `configureSdkClient` 的 `contextHeaders` 与 `createAppQueryClient`（三端在 `src/shared/lib/locale-scope.ts` 各导出一个，§3.5）：漏传的表现是请求头与 toast 停在平台默认语言而不报错，所以这条路没有默认值。seller/admin 经 `mountSpa(router, { resources, scope })` 装配，参数同样必填。

seller/admin 是 SPA，在 mountSpa 外层包 Provider；web 是 SSR，在 RootDocument 的 shell 层包 Provider。

**web 今天没传 initialLocale**（`__root.tsx` 只传 `resources`）：Provider 首屏保持 `DEFAULT_LOCALE`，挂载后再读 cookie/浏览器语言切换——这样 SSR 与 hydration 的 HTML 一致，代价是海外用户首帧拿到中文。真正的解是服务端解析 locale 再传下来（见 §9 P3′-a），不是把 Provider 挪到客户端。另注意 §3.5：传下来的 locale 不许再写进模块级变量，否则「按请求解析」在并发下自己就不成立。

### 5.3 SSR

web 的 __root.tsx：

- lang 使用当前 Locale
- title、description 从 t() 取
- 不稳定/随机值不要参与 SSR 文案，避免 hydration 不一致。日期与时区是这条最容易踩的形态：`new Date().toLocaleString()` 在 Node 侧和浏览器侧读到的时区不同，输出就会不一致，所以时间类文案一律走 §5.6 的显式 `timeZone`，不在此处另立口径
- 一期不用 URL 前缀，但 Locale 仍应由服务端确定后下发，不能客户端渲染后才切

**今天最后这条不成立**：`apps/web/src/routes/__root.tsx:86` 只传 `resources`，不传 `initialLocale`，首帧恒为 `DEFAULT_LOCALE`，挂载后才按 cookie/浏览器语言换。换的后果只有一帧文案，不产生 hydration 报错（Provider 刻意这么设计），所以先记成缺口不拦提交；真出海要 SEO 时必须补上。

补这条时别把两件事搞混：**首屏语言是 Node SSR 那侧（TanStack Start 的服务端）读 cookie / `Accept-Language` 决定的，跟 Spring 的 LocaleFilter 无关**。旧版这里写「后端没有 LocaleFilter，所以服务端不参与」，把两个不同的服务端捆成了一条依赖——Java 侧的 LocaleFilter 服务于动态内容与日志（§7.2），它落地与否都不影响 web 首屏能不能出正确语言，反之也是。§9 P3′ 因此把它们拆成两条独立的事。

2. 更新 React context
3. 触发页面用新 Locale 重渲染

### 5.5 类型化 catalog 与 codegen（§10.1 那套门禁的实现处）

codegen 读全部语言的资源，产出每个资源 root 一份 `messages.gen.ts`，落在 `apps/*/src/locales/` 与 `packages/app-kit/src/locales/` 下（生成物，`.gen.ts` 后缀，不进 `vp fmt`/`vp lint`，与 `packages/api/src/sdk` 同一待遇）。实际形状（`pnpm gen:i18n` 的输出，不是设想）：

    export type AppKitMessageKey = "appKit.confirm.cancel" | "appKit.login.resend" | …
    type AppKitParamsByKey = {
        "appKit.login.resend": { countdown: string | number }
    }
    export type AppKitParamsOf<K extends AppKitMessageKey> = K extends keyof AppKitParamsByKey
        ? AppKitParamsByKey[K]
        : undefined
    export type AppKitCatalog = { [K in AppKitMessageKey]: string }   // 装配侧消费的那份
    export type AppKitTranslate = <K extends AppKitMessageKey>(       // 调用侧消费的那份
        key: K,
        params?: AppKitParamsOf<K>,
    ) => string

app 那份 `XTranslate` 的 key 位是本端 catalog ∪ `AppKitMessageKey`，参数位按各自的 `ParamsOf` 走嵌套条件——与运行时的解析链同一条（先查本端资源、再查共享资源）。

三处与上面这段最初的设想不同，都不是随手改的：

- **`ParamsOf` 是「映射类型 + 一条 `K extends keyof`」，不是逐条条件链。** 逐条链在「这个 root 一条带参消息都没有」时（三端今天就是这样）会让 `K` 成为未使用的类型参数，`tsc` 直接 TS6196 打红 typecheck。映射类型两种情形都写得下。
- **`MessageValue<K>` 没有实现，`Catalog` 的值就是 `string`。** 它原本是为「金额槽位」留的（需要 §4.4 的参数元数据），而全仓库现在零条金额消息。没有需求就不造这个抽象；金额那条由 codegen 在生成期直接拦（见下）。
- **无参消息的参数位是 `undefined`，不是 `Record<never, never>`。** 后者看着等价，实则对象字面量对它不做超额属性检查——`t("零参 key", { brand: "x" })` 会静静通过（探针实测）。`undefined` 才拦得住。

`AppKitCatalog` 的落点是各 root 的装配文件——它当 `import.meta.glob` 的类型参数（`apps/web/src/locales/index.ts`）。注意这只是「形状对得上」，**不是完整性证明**：glob 拿到的 JSON 里没有类型信息，tsc 看不见资源内容。

`XTranslate` 的落点是调用侧：三端各有一份 `src/locales/use-t.ts`，它把生成物那份形状盖到上下文里的 `t` 上（`useT(): WebTranslate`），组件因此拿到的是收在本端 key 联合上的 `t`。**「把上下文里那个 `t` 盖成本端形状」这一步的断言只有一处，在 `packages/app-kit/src/i18n/use-i18n.ts` 的 `useTypedT`**——运行时那个 `t` 先查本端资源再查 `APP_KIT_MESSAGES`，「一个 key 属于哪份 catalog」由装配时挂上来的 resources 决定，而 React context 的类型拿不到 root 的类型参数，所以这件事运行时成立、类型里只能断言一次。app-kit 自己的 `useT` 返回 `AppKitTranslate`（只认 `appKit.*`），三端漏切到本端 `use-t.ts` 的文件会直接编译不过——这就是为什么不需要再加一条 grep 式门禁。

三个已知的口子，都不是漏写而是量过的：

1. **带参消息整个漏传不拦**（`params` 是可选位）。改成必传元组 `...args: ParamsOf<K> extends undefined ? [] : [params: ParamsOf<K>]` 实测能拦住漏传，代价是拼错 key 时报的是「Expected 2 arguments」而不是 key 本身——把最值钱那条保证的报错质量换掉，不值。
2. **按规则现拼的导航 key 接不住**（`admin.nav.<key>`、`seller.nav.<to>`、web 的 `NAV_LABEL_KEYS[label]`）。三个 `nav-i18n`/`nav` 助手各保留一次「放宽到 `(key: string) => string`」的断言，拼不出来的 key 由 `formatMessage` 回退成 key 本身（菜单露出路径名，不白屏）。§10.1 把未使用 key 定成字面量常量表之后，这三处放宽即可取消。
3. **`useI18n().t` 仍是宽形状**（`(key: string, params?: MessageParams) => string`），绕得开类型化。生产代码里只剩一处这么用：app-kit 的 `LocaleSwitcher` 读宿主 app 的 `common.locale.switch`——共享组件依赖端内 key，这条同时是 §4.2 ownership 的一处欠账（那个 key 在三份 catalog 里各存了一份，组件却只在 admin 挂）。它该跟 §10.1 那条一起定：挪成 `appKit.locale.switch` 之后 `LocaleSwitcher` 直接用 `useT()`，宽形状就只剩测试与 Provider 自己在用。

这件事的责任分工有个很容易写错的地方：**类型系统看不见字符串内部**。下面这张表按「谁真的保证得了」划分，不按「听起来谁更硬」划分。

| 要保证的事                               | 谁保证                                                                                                                                                | 性质   |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| en-US 缺条目（zh 有、en 没有）           | **codegen**。装配走 glob 而不是 `Record<MessageKey, string>` 的对象字面量赋值，tsc 根本不读 JSON；「缺一条即编译不过」这条在换成 glob 时就没了        | 生成期 |
| en-US 多条目（en 有、zh 没有）           | **tsc 不报**——结构赋值允许多余属性（JSON 导入的不是 fresh literal）。只能由 codegen 比 key 集合                                                       | 生成期 |
| 消息是不是合法 ICU                       | **tsc 不报**——它只看到 `string`。由 codegen 用 `intl-messageformat` 的 parser 逐条解析                                                                | 生成期 |
| 两侧占位符集合一致                       | **tsc 不报**。`ParamsOf` 从 zh 反推只约束**调用方传什么**，不证明 en 那句写的是 `{count}` 而不是 `{wrongName}`。必须由 codegen 解析**全部语言**后比对 | 生成期 |
| 参数类型（number vs string vs 金额槽位） | codegen 从 AST 的槽位类型推；**金额槽位直接拒绝**（见契约 5）                                                                                         | 生成期 |
| key 拼错、参数名/形状不对                | tsc：`t<K extends MessageKey>(key: K, params?: ParamsOf<K>)`。三端与 app-kit 各自实例化到 `src/locales/use-t.ts` / app-kit 的 `useT`                  | 编译期 |

也就是说：类型化真正接走的**只有「调用侧」一条**，其余五条全靠 codegen。**旧版把「缺条目」也算在类型头上，是这份文档当时最大的技术错误**——它在装配换成 glob 之后连那半条都不成立了。

codegen 因此不是一个便利工具，而是门禁的本体。它的契约要写死，否则它和 `i18n-check.mjs` 犯的是同一个错（只是换了一副更体面的面孔）。`scripts/i18n-codegen.mjs` 按五条落，头注释里逐条对得上：

1. **资源清单唯一确定**：`MANIFEST`（`apps/*/src/locales`，一段通配）+ `EXTRA_ROOTS`（app-kit）一处定义，展开后断言非空，`--list` 能逐条列出（今天 44 个 JSON 文件）。清单外即不存在——§4.2 说「所有资源必须被同一份清单覆盖」，这条就是它的实现。语言清单不在脚本里抄第二份，从 `packages/common/src/i18n/locale.ts` 现读（Node ≥23.6 的类型剥离），所以 `SUPPORTED_LOCALES` 加一项，这里跟着加一项，没有第二处。
2. **任一条消息解析失败或各语言参数不符 → 收集完一次性报错、非零退出，且一个字节都不写**。半截生成物比没有生成物更糟（教训见 `scripts/check-sdk-drift.sh` 头注释：SDK 生成物被并发删改那次）。
3. **生成物必须被 `pnpm typecheck` 与 `pnpm build` 消费**，否则 codegen 跑不跑等于没门禁。指认得出「哪一步跑它」：script `gen:i18n`（写）与 `i18n:drift`（只比对、漂移退 1），lefthook pre-push 的作业 `i18n-drift`，CI frontend job 的步骤 `i18n`；消费点是各 root `locales/index.ts` 里 `import.meta.glob<XxxCatalog>` 的类型参数，加上各 root `locales/use-t.ts` 里那份 `XTranslate`（app-kit 侧是它自己的 `useT`）。
    - **这条要按 root 检查，不是按仓库检查。** 某个 root 产了类型却没有调用点消费，契约 3 对它就是在空转——而这种情况不会被静默放过：那个没人用的类型导出会被 `pnpm fallow` 报成死代码。P0′-4 时三端还没有消费点，靠清单条目上的 `typed: false` 显式记着这笔欠账；4b 接上 `use-t.ts` 之后四个 root 全有消费点，标记随之删掉（一个恒真的开关比没有开关更糟）。
4. **比对覆盖所有语言，不只是源语言**：逐语言读目录、逐语言编译，再与源语言比 namespace、比 key、比参数集合。只解析 zh 的实现等于把表里第 3、4 行那条保证删掉了。
5. **金额槽位在生成期拒绝**：AST 里 `number` 节点的 style 是 `currency`（`{x, number, currency}` 与 `{x, number, ::currency/CNY}` 两种写法都认）就报错。理由是 AGENTS.md 的 Money 硬规则——金额展示只走 `formatMoney`/共享 `Price`，符号跟币种，不该由 ICU 按运行 locale 渲染。§4.4 那套「金额槽位元数据」等第一条真需要金额槽位的消息出现时再建，现在没有需求就不造类型。

契约不是写着就算成立：拿 10 类变异验过（整份 en-US 文件缺失 / 缺一个 key / 多一个 key / ICU 语法非法 / 两侧参数名不一致 / 同语言跨文件 key 撞车 / 值不是字符串 / 金额槽位 / 整个语言目录不见了 / 手改生成物），每类都是**非零退出 + stderr 指到具体文件 + 4 份生成物字节不变**，还原后 `pnpm i18n:drift` 重跑转绿。

### 5.6 语言隔离的完整面：locale、时区、缓存

§3.5 只解决了「进程里不能有共享的可变 locale」。这一条补另外两面——它们和全局变量无关，删干净了照样会串语言。

**时区。** 服务端与浏览器即使 locale 相同，`formatDateTime` 各按自己的默认时区算，就会出两个不同的字符串，表现为 hydration 文本差异。所以：

- 一期口径：**平台单一展示时区 `Asia/Shanghai`**。`format*` 的 `timeZone` 由 core 显式传入，不依赖运行环境默认值——`process.env.TZ`、容器时区、用户系统时区三者都不是口径。仓库已有前例说明这件事不能留给偶然：`e2e` 的物流用例专门钉死了 `Asia/Shanghai`，UTC runner 上否则假红（commit 16989376）。
- 日期（date-only）与时点（instant）的展示语义分开定义，不用同一个 format 兜。前者一般恒按平台时区显示，后者才是「同一时刻不同人看到不同钟点」的东西。
- `X-Timezone`（§7.1 那条一直没发的头）不属于修 hydration 的工作，它属于多时区产品功能，与 §9 P4 那条「时区业务规则」一起进。

**缓存。** 语言是响应的一部分，不是纯客户端的渲染细节。P3′-a 落地时必须同时定这三条：

- 首屏 HTML 随 locale 变 → CDN / 边缘缓存的 key 必须含语言。一期不引 `/en-US/` 路径前缀（§1），所以只能走 `Vary`（`Accept-Language` 加那条 `locale` cookie），代价是命中率下降——这笔账要在 P4 决定要不要换前缀时摊开算，不能默认它不存在。
- **TanStack Query 的缓存 key 必须含 locale**，一旦后端按请求语言本地化过响应（P3′-b 之后）。英文用户命中中文用户留下的缓存，和「有没有全局变量」毫无关系，是独立的一条口子。这条要求 query key 工厂（各域 `queries.ts`）把 locale 放进去，与 [frontend.md](frontend.md) 的取数约定对齐后再改。
- 不翻译的动态内容（§8）继续共享缓存，不带语言维度——它本来就没有两种语言版本。

`Vary` 与 query key 是同一件事的两端（「语言进缓存维度」），口径只写在这里一处，装配侧不复述。

## 7. 请求头与后端

### 7.1 前端请求头

configureSdkClient 已有 contextHeaders 钩子，各 app 直接注入：

    configureSdkClient('', tokenStore, {
        contextHeaders: () => ({
            'Accept-Language': locale,
            'X-Locale': locale,
            'X-Timezone': timezone,
        }),
    })

一期 X-Timezone 可以先不启用；但 Header 名和上下文形状先定好。

今天的实际装配（三端 `configureSdkClient` 各一处）：三端都只发 `Accept-Language` + `X-Locale`，`X-Timezone` 一处都没发；seller 用同一个钩子多带 `X-Shop-Id`。这两个头目前**后端没人读**（§7.2 未落地），发出去只进访问日志，不改变响应语言。

**`contextHeaders` 的钩子不许读模块级 locale。** 这条曾经是收口项（三端都在钩子里调 `getCurrentLocale()`），现在成立：钩子读的是 app 装配时注入的 `localeScope`（§3.5 的落地形状），`createAppQueryClient` 与 `I18nProvider` 拿到的是**同一个实例**，所以切一次语言，界面、出站头、写操作兜底文案一起跟着换。

还欠的那半在 SSR：`localeScope` 目前是进程级一份，服务端没人写它，于是 `Accept-Language` 恒为平台默认值（`X-Timezone` 同理，仍未发）。P3′-a 把「按请求解析」补上时，改的是这个实例的创建时机，钩子本身的形状不动。

优先级由 `sdk-client` 实现保证而不是靠约定：**单次调用显式带的头压过 `contextHeaders`**（注入条件是 `!request.headers.has(name)`）。`apps/web/src/shared/api/client.locale.test.ts` 钉的就是这条——显式带语言的交错请求各说各话，没带的那条落到装配默认。

### 7.2 后端 LocaleContext（范围已收窄）

**整节未落地**（§9 P3′）。它存在的理由只有两条，都不涉及错误文案：

- **动态内容**按请求语言挑选（§8 的 `entity_translation` / JSONB 读取，以及未来的后端生成文本：邮件、短信模板）
- **日志**：HttpRequestLoggingInterceptor 的 http.request 事件带 locale，排查「这个用户为什么看到中文」时用得上

在 apps/server/src/main/java/com/shop/platform/infra/web 增加：

- LocaleContext / LocaleContextHolder（请求作用域，用完即清）
- LocaleFilter：解析 X-Locale > Accept-Language > 默认 zh-CN
- WebMvcConfig 注册 Filter
- 请求结束后清理 ThreadLocal
- http.request 日志带 locale

**本节不引入 `MessageSource` 去接管 UI 错误文案**（理由见 §7.3，那才是本仓库最容易走回去的一条岔路）。注意这条否得很窄：它只排除「用 Java `messages_*.properties` 承载前端能看到的错误句子」。上面两条职责里，邮件/短信模板真要做服务端本地化时，仍然需要一个服务端文案载体，`MessageSource` 是它的候选之一——那是那条线自己的决定，不由本节预判，也不与 §7.3 冲突（§7.3 末尾列了服务端本地化仍然成立的三类场景）。

### 7.3 错误文案：后端出 code，前端出文案

**决定。** 用户可见的错误句子归前端 catalog 拥有（namespace `error.`，key 直接用 code：`error.SMS_CODE_EXPIRED`）；后端 `BusinessException` 的 `detail` 降级为日志与调试字段，不进用户可见路径。

**为什么本项目的 UI 错误不放到服务端。** 本仓库刚刚把「一份 catalog、类型化、ICU、编译期平齐」定为文案的唯一架构（§5.5）。UI 错误文案若留在 Java `.properties`，就有了**两套本地化系统**：两种平齐机制、两个语感来源、两条加语言的流程，而 §11 那条「前后端各维护一份错误码文案且无门禁」正是它的必然结局——今天 `error-messages.ts`（115 行、覆盖 ErrorCodes、含单测）**没有任何生产调用方**，就是「两份」已经存在的一次证据：它写了，但没人接，因为另一份（后端 detail）正在被 `notify.ts` 优先读。方向反过来（服务端本地化 UI 错误）也能解决英文界面显示中文 detail，代价是删掉 `error-messages.ts` 并在 Java 侧新建一套要手工保持平齐的 properties——那等于把 §10.1 刚拆掉的校验脚本换个语言重装一遍。

**这不是一条普遍规律，别把它抄走。** 服务端本地化在下面这些场景是正解，而且本仓库已经需要它：

- **邮件、短信模板**——文案离开浏览器之后就再也没有第二次本地化机会，只能服务端出成品（§7.2 把这条列为 LocaleContext 存在的理由之一）
- **公开 API / 多种客户端**——同一份后端要喂 web、seller、未来的小程序或第三方，客户端不一定有自己的 catalog
- **动态内容**——商品名、CMS 词条按请求语言挑选（§8）

所以本条否掉的只有一件事：**把 UI 错误文案放进 Java `messages_*.properties`**，因为它与 §5.5 的 catalog 是同一职责的两份实现。上面三类是另外三条线，各有各的 owner，不与本条冲突。旧版 §11 把它写成「服务端建 MessageSource 是反模式」，说过头了。

**落地即接通，不是再写一份。** `error-messages.ts` 的内容进 catalog（共享那份走 app-kit 的 `error.json`，与 §4.2「所有资源必须被同一份清单覆盖」一致），TS 字典与 `getErrorMessage` 一起删除。这样 §2 基线里「apps/server 直接返回中文 detail」那行才算真被处理。

#### 最终行为（目标态，和迁移行为分开写，别让过渡逻辑长成永久架构）

    已知 code              -> error.<CODE> 的本地化文案
    未知 code / 非预期错误  -> 本地化通用提示（appKit.error.network）
    detail                -> 只进日志与诊断，不进任何用户可见路径

迁移期允许保留 `code 未命中 -> detail` 这条回退（`notify.ts` 今天是「detail 优先」，一步切到位不现实），但**退出条件写死**：① 上面那条反向门禁（每个 code 恰有一条 `error.<code>`）转绿；② 生产代码里 toast 渲染 detail 的分支清零。两个条件都满足后回退删除；未满足前，它是已知缺口而不是「设计如此」——旧版把这两件事写在同一句话里（一边说 detail 不进用户可见路径，一边说未命中回退 detail），是这个毛病。

#### 代价（三条，都得到 §9 P3′ 排队，不是免费）

1. **`docs/error-codes.md` 的定义原则要改写。** 它今天的第一句是「只有前端**无法仅通过 HTTP status 区分**时才定义 code，否则省略 code，让 `detail` 承载用户提示」——那是为「detail 当文案」设计的判据。前端要按 code 取文案，判据就得换成「**这句话用户可见 → 就要有 code**」。多数行已经带 code（`SHOP_NAME_TAKEN`、`CATEGORY_NOT_LEAF`、`ADDRESS_LIMIT_EXCEEDED` 那批「谁在读 = `—`」的是标签不是分支，正好是新判据下的主力），但要逐条扫出「有用户可见 detail 却没有 code」的漏网。连带 `ErrorCodeVocabularyTest` 的语义要更新：TS 侧那道核对从「`ErrorCodes` 键集合 ⇄ 本表 Code 列相等」升级为「每个 code 在 catalog 里**有且只有一条** `error.<code>`」——这条反向核对过去没有，是新增门禁，也是防止「加了码忘了加文案」的唯一手段。
2. **422 校验族要参数化。** `@Size` / `@Pattern` 那套数字**是 OpenAPI 契约的一部分**（对照 `apps/server/AGENTS.md`「入站校验词表」与 error-codes.md 的「code 不进契约」那条），后端现在交付的是成品中文句子。前端要本地化它，就得改成交参数 `{field, rule, min, max}` 由前端渲染——**这是契约改动，要 `pnpm gen:sdk`**。注意别把两件事混成一句：_code_ 不进契约所以补错误文案不触发生成；_校验参数_ 进契约，改它必须重生成。
3. **抛出点看不到最终句子。** 后端一个 `throw` 处不再有那句话，可读性靠 error-codes.md 的「前端行为 / 后端触发场景」两列加 catalog 里的 `error.<code>` 条目补回来。上面那条反向门禁就是这笔可读性损失的补偿，不是可选项。

#### 一期边界（在完成 P3′ 之前必须显式承认）

无 code 的 400/422 与未参数化的校验消息，在 P3′-b 完成前仍会显示后端中文 detail。§10.3 保留对应那条验收，别把它记成已解决。

## 10. 门禁与验收

### 10.1 门禁的四条判据，以及旧脚本为什么删

判据是这四条，**同时成立**才算一道门禁：

1. **覆盖完整**——清单上的每条资源都被检查，清单外的资源不允许存在（§5.5 契约 1）
2. **判定准确**——按目标格式的真实语法判，不按正则近似判
3. **自动执行**——在 `pnpm` 脚本、`lefthook.yml` 的某个 job、`ci.yml` 的某个步骤里能指认出它跑在哪一步
4. **失败阻断交付**——红了 typecheck/build/push 就过不去

`scripts/i18n-check.mjs` 与 `pnpm i18n:check` 按这四条判，立项时**一条都不满足**；第一条（覆盖完整）已在 §9 P0′ 合上，另外三条照旧：

| 判据     | 旧脚本的事实                                                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 覆盖完整 | 扫描面是 `apps/*` 那三份 `src/locales/`，看不见 `packages/app-kit/src/i18n/messages.ts`——而全仓库真在用的两条插值消息恰好全在那儿。漏掉全部，命中零 |
| 判定准确 | 花括号只配平不解析 ICU 规则；占位符靠正则 `\{(\w+)\}` 数，`{count, plural, …}` 里的嵌套参数抓不到                                                   |
| 自动执行 | `lefthook.yml` 的 pre-commit / pre-push 与 `.github/workflows/` 都没有它（旧版这条只承认了 CI，把话说小了）。只能靠人记得                           |
| 失败阻断 | 跟着上一条：不进任何流水线，红了也不拦任何东西                                                                                                      |

覆盖完整那条在 P0′ 已经合上（`i18n-check.mjs` 的 `RESOURCE_ROOTS` 加了 `packages/app-kit/src/locales`）。合上之后往 app-kit 的 en-US 里注入一个 `{oops}` 占位符，脚本报「占位符不一致」退出 1，撤掉注入又转绿——**这一步是必要的**：不这么测一遍，「我把目录加进清单了」和「清单真的扫到了」是两句话。剩下三条判据仍然不成立，所以它照旧是待删对象（§9 P0′）。

外加一条实测：三端 catalog 共 198 key（web 87 / seller 63 / admin 48），**含花括号的 0 条**——后两项检查对这些文件今天连输入都没有。

**codegen（§5.5）今天按这四条成立**：判据 1 = `MANIFEST` + `--list`；判据 2 = 用运行时那个 `IntlMessageFormat` 的 AST 判，不写正则近似；判据 3 = `gen:i18n` / `i18n:drift` 两个 script、lefthook 作业 `i18n-drift`、CI 步骤 `i18n`；判据 4 = 失败既不退 1 且不写盘，drift 模式专门用来拦「资源改了、生成物没跟着改」。§5.5 末那 10 类变异是逐条验过的，不是推的。

**但删它的理由是「它按这四条不成立」，不是「门禁不该是脚本」。** 这是本次改版最重要的措辞修正：旧版写过「脚本只会近似、会漏、会静默不跑；类型与构建期天然可靠」，那是一个伪对立。§5.5 的 codegen **本身也是脚本**，它同样可能漏扫 app-kit、可能没接进 CI、可能红了却照样写出半截生成物。它之所以算门禁，是因为 §5.5 那四条契约把上面这四条判据逐条钉住了，而不是因为它长得像生成器。同理，用官方 parser 精确解析各语言再比对参数的**独立校验脚本**，也完全可以满足这四条——本仓库选 codegen 是因为它顺手把类型产出了，不是因为脚本这条路被证明不成立。

于是旧脚本查的三件事的去向：

| 旧检查                    | 新承担者                                                                                                            | 性质   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------ |
| 两侧 key 集合相等         | 缺条目与多条目**都由 codegen 比 key 集合**（§5.5 表格第 1、2 行；装配走 glob，tsc 不读 JSON，这里没有编译期那半条） | 生成期 |
| 花括号配对                | codegen 用 parser 逐条解析（§5.5 表格第 3 行）                                                                      | 生成期 |
| 两侧 `{placeholder}` 一致 | codegen 解析**全部语言**后比对（§5.5 表格第 4 行）                                                                  | 生成期 |

**旧版「没查的」两条，一条有了着落、一条待定：**

- _对新增强制_：成立，但承担者不是类型。新增一个 key 只进源语言那份 JSON，「另一种语言立刻要求补齐」今天靠的是 codegen 的 namespace/key 比对（`--check` 与 pre-push 都会红），不是 `Record<MessageKey, …>` 的赋值检查——装配换成 glob 之后，那条检查不存在了（§5.5 表格第 1 行）。结论没变（不需要白名单机制），理由换了。
- _未使用 key_：旧版直接断言「`pnpm fallow` 会抓」，**没有依据**——通用死代码分析不认识 JSON 条目与 `t("order.items")` 之间的对应关系，也不处理动态 key。两种形状二选一，P0′ 必须定：
    - (a) codegen 另产一个常量对象（`M.order_items`），调用点写 `t(M.order_items)`。引用变成真标识符，fallow 的可达性分析就能看见，未使用条目等于死代码，**复用已有门禁**。代价是调用点啰嗦、字符串补全的手感变差。
    - (b) 保持字符串字面量调用。那么未使用 key 只能由 codegen 自己扫 AST 里的 `t(` 调用来判——动态 key 与模板串拼接会漏，需要显式白名单，等于再养一个 scanner。
    - 默认走 (a)：与「资源必须被同一份清单覆盖」同源，且不新写 scanner。
    - 这条决定要一并收的账已经在 §5.5 末记着：三端导航助手那三处「放宽到 `(key: string) => string`」（口子 2），和 app-kit `LocaleSwitcher` 读宿主 app key 那一处（口子 3）。定了 (a)，四处都能删；定了 (b)，它们就是白名单的头四条。

**新增一条必须自己盯的门禁**：`error.<code>` 与 ErrorCodes 的反向核对（§7.3 代价 1）——它是本次架构里唯一「加了码可能忘加文案」的口子，`ErrorCodeVocabularyTest` 不扩就没人管。

### 10.3 验收标准

- 中英切换可用，刷新后保持

## 11. 反模式与项目选择

这一节分成两半。**上一版把它们混在一起写了**，结果是把项目偏好当成普遍规律论证——那种写法会让人以为别处也该照抄，而真正的原因是「我们选了这个并且它能被验证」。

### 11.1 真反模式（做了就会出错，与项目偏好无关）

- 用中文/英文原句当 key
- 字符串拼接生成句子
- 组件内写死用户可见文案
- 跨请求共享的可变 locale（模块级 `let`，SSR 下串语言）——注意这禁的范围很窄：客户端 React state、请求上下文持有 locale 都**不是**反模式（§3.5）
- 资源不进 §5.5 那份统一清单：藏在组件旁边的字典、组件默认 props 里的中文。真正的判据是「清单覆盖不到」，**不是「它是 TS 而不是 JSON」**——TS 对象同样能被类型约束，旧版那句「内联 TS 必然逃过约束」说过头了
- 把 `detail` 直接当 UI 文案（§7.3）；前后端各维护一份错误码文案且无门禁
- 缺翻译时静默吞掉或回退为空串
- 用 ICU 的 `{n, number, currency: CNY}` 格式化金额（§4.4）：开出 `formatMoney` 之外的第二条金额路径，撞 AGENTS.md 的 Money 硬规则
- 直接改 `formatMoney` 的 CNY 假设来做多币种
- 动态内容未翻译却宣称国际化完成
- **让 `contextHeaders` 读模块级 locale**（§7.1）：后端接了 LocaleFilter 也白接，头本身就是错的
- **让 codegen 产出生成物却没人消费它**：`typecheck`/`build` 不引用 `.gen.ts`，等于门禁不存在（§5.5 契约 3）
- **用「它是脚本 / 它是类型」代替 §10.1 那四条判据来论证可靠性**：生成器也是脚本，也会漏扫、也会不跑

### 11.2 项目选择（合理但不是普遍规律，换项目可能反向）

- **UI 错误文案在前端、不在 Java properties**（§7.3）。反过来的情形是真实存在的：公开 API、多客户端、邮件短信都必须服务端本地化——本仓库那两类也已经划给 LocaleContext 了。所以「服务端建 MessageSource」**不是**普遍反模式，上一版那样写是错的。
- **资源用 JSON**。选它是因为翻译工具直接读写、glob 清单好定义、和 §9 P4 衔接；不是因为非 JSON 就失控。
- **语言标签内部统一用地区级**（`zh-CN` / `en-US`）。要修正的是旧版那条「用 zh/en 是反模式」——`en` 是合法标签，`normalizeLocale` 的职责本来就是收层级（`LOCALE_ALIASES` 里 `en → en-US` 已经写了）。真正要避免的是**同一链路里混用不同层级**，语言级、脚本级、地区级哪一层是「内部口径」由产品要不要区分 `pt-BR`/`pt-PT` 决定。
- **非组件上下文用参数/注入实例传递 locale，`AsyncLocalStorage` 只是兜底**（§3.5 约束 3）。上一条版本把它写成必选，那是不必要的隐式机制。
- **按 namespace 拆资源文件**（§4.2）。这是可维护性与 ownership 的选择，不解决联合类型体量——那是另一个决定。
- **一期不做 URL 前缀、走 `Vary`**（§5.6）。SEO 要求高的产品会反过来选路径前缀，那是 P4 的正常改道，不是纠错。
