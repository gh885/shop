# 国际化（i18n）约定与落地架构

> 当前只启用 zh-CN + en-US，但所有模型按「未来支持 N 个语言」设计。
> 本文是 i18n 的唯一入口；改用户可见文案、错误文案、日期/数字格式前先读。
> 相关文档：前端规范 [frontend.md](frontend.md)、错误码 [../error-codes.md](../error-codes.md)、架构总览 [../architecture.md](../architecture.md)。

## 1. 结论

| 项                        | 决定                                                                                                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 源语言 sourceLocale       | zh-CN                                                                                                                                                                |
| 支持语言 supportedLocales | zh-CN、en-US                                                                                                                                                         |
| 默认语言 defaultLocale    | zh-CN                                                                                                                                                                |
| 回退链 fallback           | en-US → zh-CN                                                                                                                                                        |
| 一期范围                  | 三端 UI 文案、错误码文案、日期/数字格式、Locale 请求头透传                                                                                                           |
| 一期不做                  | RTL、多币种结算、动态内容翻译、TMS 深度集成、按地区数据驻留                                                                                                          |
| 包边界                    | 纯逻辑进 @shop/common；React Provider/hook 进 @shop/app-kit；业务文案按 app ownership 拆                                                                             |
| Web URL 策略              | 一期先用 cookie + Accept-Language；正式出海前再升级为路径前缀 /en-US/...                                                                                             |
| Locale 的载体             | **不允许跨请求共享的可变 locale**：随请求（SSR）或随启动（SPA）解析一次，显式流经 context 与 fetch 边界。要删的是进程级可变量，当前语言交给请求/应用实例持有（§3.5） |
| key 与参数                | **类型与生成期校验分工，不互相替代**：装配走 glob，tsc 不读 JSON，「en 不缺条目」也是生成期的事；类型真正接走的只有「调用侧拼错 key/传错参数」一条（§5.5）           |
| 消息语法                  | **ICU**，运行时是 `i18next + i18next-icu`。不再有私有子集，也就不再有私有校验器（§4.4、§10.1）                                                                       |
| 错误文案归属              | **本项目 UI 错误：后端出 code，前端出文案**；`detail` 降级为日志字段。服务端本地化在公开 API 与通知场景仍是正解，范围限定见 §7.3                                     |
| 门禁的判据                | **覆盖完整 / 判定准确 / 自动执行 / 失败阻断**四条一起成立才算门禁。不要用「它是脚本 / 它是类型」代替这四条论证可靠性；codegen 本身就是脚本（§10.1）                  |

**一句话：架构上支持多语言，一期只交付中英；文案资源可替换，核心代码不感知当前支持几种语言。**

这五条都已各有落点（§4.2/§4.4/§5.5/§7.3），缺口见 §2。要留意的是它们容易被绕开——locale 存成全局、资源不进统一清单、错误文案回到服务端，任何一条发生都不会有东西自动报错：「有门禁」和「门禁覆盖了目标」是两件事。

## 2. 当前缺口

- ui-web 仍有待迁移的内嵌中文；完整 UI 覆盖见 TODO.md。
- 动态商品内容尚未按语言存储或返回；不能把英文 UI 宣称为完整英文商城。
- 语言 URL 与将来本地化查询的缓存维度仍需按内容能力补齐（§5.6）；当前 SSR 文档已禁止共享缓存并返回语言 Vary。
- 金额槽位的元数据形式未定；禁止 ICU 直接格式化金额的 AST 门禁保留。
- errors[].message 尚未彻底退役：已知 rule 取 catalog，未知 rule 仍有后端中文回退（§7.3）。

运行时实例、切换联动、SSR hydration 与必传 ICU 参数已迁移并有测试，不再列作缺口。

## 3. Locale 模型

### 3.1 类型与常量

放在 packages/common/src/i18n/locale.ts（纯逻辑，不依赖 React）：

    export const SUPPORTED_LOCALES = ['zh-CN', 'en-US'] as const
    export type AppLocale = (typeof SUPPORTED_LOCALES)[number]

    export const DEFAULT_LOCALE: AppLocale = 'zh-CN'
    export const SOURCE_LOCALE: AppLocale = 'zh-CN'

    export const FALLBACKS: Record<AppLocale, AppLocale | null> = {
        'zh-CN': null,
        'en-US': 'zh-CN',
    }

### 3.2 归一化

外部输入可能来自：

- Cookie：locale=zh-CN
- Accept-Language：en-US,en;q=0.9,zh-CN;q=0.8
- 用户资料
- 未来 URL 前缀

统一入口：

    export function normalizeLocale(input: string | null | undefined): AppLocale | null
    export function resolveLocale(candidates: Array<string | null | undefined>): AppLocale

一期可把 zh、zh-Hans、en 分别归一到 zh-CN、en-US；以后加语言时只扩映射表。

### 3.3 解析优先级

| 场景               | 优先级                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 三端（今天的实现） | locale cookie（「用户显式设置」就落在这条 cookie 里）> navigator.language > DEFAULT_LOCALE |
| web SSR 首屏       | 同一套优先级，服务端按请求解析后作为 `initialLocale` 传下来（§5.2）                        |
| web 正式出海后     | URL 前缀 > locale cookie > Accept-Language > 默认                                          |

三行都交给同一个 `resolveLocale()`：归一（`zh_CN` / `zh-Hans-CN` → `zh-CN`）与「不支持就往下走一级」只在它那里判一遍，装配侧不各判一次。

### 3.4 回退

任何取文案的地方都遵守：

    请求 locale -> 当前 locale 资源 -> fallback locale 资源 -> key 本身

key 本身作为最后兜底，同时上报缺失监控。不允许回退成空字符串，也不允许因缺翻译白屏。

### 3.5 当前 Locale 的持有方式

**当前语言只存在原生 i18next 实例中。** 不再维护 React state、LocaleScope 和 HTML 三份可变状态。

- 浏览器每个应用一个实例，在 React 渲染和 SDK 请求之前初始化；cookie 和 html.lang 只是输出。
- web SSR 每个请求调用 createAppI18n，实例进入 Router context，并交给 I18nProvider 与 QueryClient。禁止服务端复用会 changeLanguage 的模块单例。
- React 通过 react-i18next 订阅；非组件代码读取同一实例的 localeOf(i18n)，或给纯翻译显式传 locale。
- 纯翻译实例可以共享，但必须使用 t 的 lng 选项，不调用 changeLanguage。
- 浏览器持久化在 languageChanged 事件中同步执行；Router context 快照由同一事件更新并 invalidate。监听器必须提供清理函数，HMR 时释放。

入口：common/i18n 的 createI18n；app-kit/i18n 的 createAppI18n、bindBrowserI18n；web/app/i18n-router.ts 的 bindRouterI18n。

## 4. 资源 ownership 与格式

### 4.1 放哪

| 层                      | 职责                                                             | 不做什么                                                            |
| ----------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------- |
| @shop/common            | Locale 解析、回退、格式化纯函数                                  | 不依赖 React；**不承载任何用户可见文案**，含错误码文案（§7.3）      |
| @shop/app-kit           | I18nProvider、useT、跨三端共享的登录/通用/错误文案、日期展示适配 | 不承载 web/seller/admin 各自业务文案；共享文案也不内联在 TS（§4.2） |
| @shop/ui-web            | 纯 UI；组件文案通过 labels / i18n / locale prop 注入             | 不在组件内部写死中文或英文业务文案                                  |
| apps/web/src/locales    | 买家端业务文案                                                   | 不复制 app-kit/ui-web 已有文案                                      |
| apps/seller/src/locales | 卖家端业务文案                                                   | 同上                                                                |
| apps/admin/src/locales  | 管理端业务文案                                                   | 同上                                                                |

### 4.2 命名空间

    apps/web/src/locales/
      zh-CN/
        app.json common.json footer.json header.json login.json nav.json security.json   # 今天的 7 个
        home.json product.json order.json                                                 # P2 铺业务页面时再加
      en-US/
        # 与 zh-CN 同名、同 key：文件级平齐由装配保证，key 级平齐由 codegen 保证（§5.5）

    packages/app-kit/src/locales/          # 共享那份，与 app 侧同一形状、同一装配、同一 codegen、同一约束
      zh-CN/appKit.json                    # 31 条：登录壳层 + 确认框/网络错误/搜索框
      en-US/appKit.json
      zh-CN/error.json                     # 每个 code 一句（§7.3）
      en-US/error.json                     # 与 zh-CN 同 key；平齐归 codegen，覆盖归 ErrorCodeVocabularyTest

共享组件文案走 appKit namespace，错误文案走 `error.<code>`（§7.3）：

    appKit.login.submit
    appKit.error.network
    error.SMS_CODE_EXPIRED

**所有资源必须被同一份清单覆盖。** 判据是「清单覆盖得到」；「形状统一成 JSON」只是手段之一——TS 对象同样能被类型约束。要留意的是 §5.5 的 codegen 从哪拿清单：一条藏在 `src/i18n/messages.ts` 里的字典不会出现在 `**/locales/**/*.json` 的 glob 结果里，于是任何按清单跑的东西（解析、比对、生成类型、覆盖率统计）都静默漏掉它。这就是「有门禁但门禁没覆盖目标」。今天资源只有 JSON 一种形状，正是为了让这条成立。

装配是统一的：`import.meta.glob` 拿清单，`packages/app-kit/src/i18n/resources.ts` 的 `assembleLocaleResources` 合并。装配只负责把两种**静默失效**变成抛——语言目录名打错（那份文件等于不存在）与同一语言内跨文件撞 key。清单本身仍然不校验 key 平齐与语法，那是 codegen 的活（§5.5），别把它记在装配头上。

**拆文件的收益是可维护性与按域 ownership**——一个 PR 只碰一个 namespace，review 面小；namespace 由文件名给，不靠 key 前缀约定。

**拆文件不会让联合类型变小。** 只要 `MessageKey` 还是全局联合，198 条拆成 21 个文件后仍是 198 个成员，报错一样不可读；控制类型体量是另一个决定，落在 §5.5 的收窄形态上（`useT("nav")` → `XScopedT<"nav">`）。

### 4.3 key 规范

使用语义 key，禁止用中文/英文原句当 key：

    home.header.searchPlaceholder
    product.detail.addToCart
    order.status.pendingPayment
    common.action.confirm

命名建议：

    {domain}.{area}.{element}

### 4.4 文案写法

必须使用 ICU 参数，禁止拼接。**语法以 `intl-messageformat` 的解析器为准**，不是「ICU 风格」的私有子集（那需要自建一个子集校验器）。

    order.items: {count, plural, =0 {No items} =1 {1 item} other {# items}}
    order.greeting: Hello, {name}
    order.rank: 第 {index, selectordinal, one {#st} two {#nd} few {#rd} other {#th}} 位

覆盖范围：插值、plural、select、selectordinal、嵌套**全支持**，因为它们是现成 parser 的功能，不是我们的功能。分阶段实现子集，就还是要维护一个子集校验器。

**金额是唯一例外。** ICU 的 `{n, number, currency: CNY}` 会在 `formatMoney` / 共享 `Price` 之外开出第二条金额格式化路径，直接撞 [AGENTS.md](../../AGENTS.md) 的「金额全链路只有一个形状、展示只走 `formatMoney`」。日期/数字照常允许走 ICU，只有钱不行。**注意这与「`formatMoney` 内部调 `Intl.NumberFormat`」不矛盾**（它是这么实现的）：禁的是**绕过 `formatMoney` 这一个出口**去让消息自己按 locale 渲染货币，库在出口内部用是收敛而不是分叉——口径见 [frontend.md「金额（Money）」](frontend.md)。

这条护栏不是类型能自动给的：`总计：{amount}` 里的 `amount` 是不是金额，ICU 的 AST 里没有这个信息。所以现在是 codegen 检查消息 AST——任何带 `number` + `currency`、或直接写币种符号的格式化，解析阶段就判失败（走 AST 而不是「约定别用 currency」，因为约定不需要执行的东西都会漂，而这条漂了的后果是两种语言下金额长得不一样，最难被 review 看见）。「参数元数据 → 金额槽位收成 brand type」那半等第一条真需要金额槽位的消息出现时再建，现在全仓零条。

## 5. 运行时设计

### 5.1 纯核心

运行时用 **i18next + i18next-icu**，接线位于 packages/common/src/i18n/message.ts；不再自写查找、fallback 循环、ICU 编译缓存。

- createI18n(resources, locale, shared) 创建独立实例。当前字典 eager 加载，initAsync: false，初始化不等待网络。
- app/shared 是资源所有权 namespace。文件名 namespace 仍用于维护和类型收窄；key 保持完整扁平字面量，keySeparator 与 nsSeparator 都关闭。
- i18next 按 app → shared 查找，每个 namespace 内按语言 fallback。en-US → zh-CN 的配置仍来自公共词表。
- translate(instance, key, params, locale?) 仅适配参数和字符串返回；查找和格式化由库执行。显式 locale 不改变实例状态。
- 缺 key、缺 ICU 参数、坏模板都返回 key，不返回裸模板，不抛到页面。分别上报 i18n_missing_key、i18n_missing_param、i18n_invalid_message，同实例内去重；日志不包含插值数据。

依赖兼容：i18next-icu 2.4.4 的 peer 范围为 intl-messageformat >=10.3.3 <12.0.0，workspace catalog 固定统一使用 ^11.2.15；codegen 与运行时使用同一 ICU 主版本。不通过忽略 peer 警告强装 12。

### 5.2 React 胶水

I18nProvider 只接收 { i18n, children }：原生 I18nextProvider 加上 UI 文案适配器，不再接收 resources / scope / initialLocale。

useI18n 返回 locale / availableLocales / setLocale / t，内部通过 react-i18next 的 useTranslation 订阅。setLocale 归一化后调用 changeLanguage，不另存 React state。

各端 useT 保留生成类型；app-kit useT 只认识共享 key。UI labels、表格、字段错误仍通过 ui-web 的 props/context 注入，ui-web 不依赖翻译库。

### 5.3 SSR

web 的 getContext 为每个服务端请求创建 i18next 与 QueryClient；初始语言按 cookie → Accept-Language → 默认语言解析。SDK 出站头从 Start 的请求上下文读取同一请求的语言，不读浏览器实例。

客户端 getBrowserI18n 只在浏览器初始化：继承服务端 html.lang；没有有效 SSR 语言才读浏览器偏好。之后 HTML 只是输出，SDK 不再反过来从 HTML 读取当前语言。

不要把 i18next 实例作为 loader data 或服务端函数返回值序列化。当前实例与 QueryClient 一样在各环境本地创建，只传递语言选择。

并发请求隔离、真实 renderToString → hydrateRoot 的文本一致性由 common/message.test.ts 与 app-kit/ssr.test.tsx 验证。

**发布约束：**web 停用预渲染，同一路径不能生成单语言 HTML。src/server.ts 为 HTML 响应添加 Cache-Control: private, no-store，以及 Vary: Accept-Language, Cookie（保留已有 Vary）；带哈希的静态资源继续由静态服务器缓存。部署必须整体替换 dist/client，避免旧 welcome/index.html、sell/index.html 残留；CDN/代理不得强行覆盖文档缓存策略。仓库没有生产 CDN/反向代理配置，本地验收走真实生产构建 + preview HTTP 入口。

浏览器验收命令 pnpm test:e2e:i18n 自动构建并启动三端，不需要后端。它覆盖真正的语言入口、输入保留、SDK 请求、cookie、标题、SSR 响应头和旧静态路径；CI 独立运行。

### 5.3.1 文档标题：统一由 Router head 输出

根路由 head 提供站点级默认 title/description；具体路由 head 覆盖页面标题，全部由 HeadContent 去重输出。RootDocument 不再手写第二份 title/meta，避免刷新时站点标题盖掉页面标题。translateWeb 与组件走同一 i18next + ICU 引擎，包含共享 catalog；它只接受无参数 key，防止把未格式化消息当标题。

语言变化时，web/app/i18n-router.ts 同步更新 router.options.context.locale，再调用 router.invalidate() 重新计算当前 head。不能只改 React 文案而保留旧路由快照。

### 5.4 语言切换

调用 useI18n().setLocale 或实例 changeLanguage；同一个实例的 languageChanged 驱动 React 订阅、浏览器 cookie/html 输出、web 路由 head 更新。

买家站点头部及登录弹窗都提供 LocaleSwitcher，模态弹窗打开时也能切换而不丢输入。

seller/admin 首次挂载前就解析 cookie/浏览器偏好，不再先渲染中文再在 effect 中切换。页面不整页刷新；web 集成测试同时验证未保存输入不丢失。

当前 API 数据没有按语言返回不同内容，不因切语言清空全部 Query 缓存。将来某个查询返回本地化内容时，只给该查询加入 locale 维度（§5.6）。

### 5.5 类型化 catalog 与 codegen（§10.1 那套门禁的实现处）

**必传参数已经启用：**生成的 Translate / ScopedT 使用参数元组。带 ICU 槽位必须传完整参数，无参 key 不收参数；动态配置若只能使用无参文案，应收窄为 Exclude<MessageKey, keyof ParamsByKey>。反例编译测试在 web/locales/types.test.ts。

codegen 读全部语言的资源，产出每个资源 root 一份 `messages.gen.ts`，落在 `apps/*/src/locales/` 与 `packages/app-kit/src/locales/` 下（生成物，`.gen.ts` 后缀，不进 `vp fmt`/`vp lint`，与 `packages/api/src/sdk` 同一待遇）。实际形状（`pnpm i18n:gen` 的输出，不是设想）：

    export type AppKitMessageKey = "appKit.confirm.cancel" | "appKit.login.resend" | …
    type AppKitParamsByKey = {
        "appKit.login.resend": { countdown: string | number }
    }
    export type AppKitParamsOf<K extends AppKitMessageKey> = K extends keyof AppKitParamsByKey
        ? AppKitParamsByKey[K]
        : undefined
    export type AppKitCatalog = { [K in AppKitMessageKey]: string }   // 装配侧消费的那份
    export type AppKitTranslate = <K extends AppKitMessageKey>(       // 调用侧消费的那份
        key: K,
        ...args: AppKitParamsOf<K> extends undefined ? [] : [params: AppKitParamsOf<K>]
    ) => string

app 那份 `XTranslate` 的 key 位是本端 catalog ∪ `AppKitMessageKey`，参数位按各自的 `ParamsOf` 走嵌套条件——与运行时的解析链同一条（先查本端资源、再查共享资源）。

生成细节三处易踩：`ParamsOf` 用映射类型而非逐条条件链（否则无参 root 上 `K` 成了未使用的类型参数，TS6196）；`Catalog` 的值就是 `string`，没造为金额槽位预留的 `MessageValue`（零条金额消息时不造抽象）；无参消息的参数位是 `undefined` 而非 `Record<never, never>`（后者对对象字面量不做超额属性检查，拦不住多传的参数）。

`AppKitCatalog` 的落点是各 root 的装配文件——它当 `import.meta.glob` 的类型参数（`apps/web/src/locales/index.ts`）。注意这只是「形状对得上」，**不是完整性证明**：glob 拿到的 JSON 里没有类型信息，tsc 看不见资源内容。

`XTranslate` 的落点是调用侧：三端各有一份 `src/locales/use-t.ts`，把生成物那份形状盖到上下文里的 `t` 上（`useT(): WebTranslate`），组件拿到的是收在本端 key 联合上的 `t`。「把上下文里那个 `t` 盖成本端形状」只需**一处断言**（app-kit 的 `useTypedT`）——运行时那个 `t` 先查本端再查共享资源，「一个 key 属于哪份 catalog」由装配时挂上来的 resources 决定，而 React context 的类型拿不到 root 的类型参数，所以类型里只能这么断言一次。app-kit 自己的 `useT` 只认 `appKit.*`，三端漏切到本端 `use-t.ts` 的文件会直接编译不过——所以不需要再加一条 grep 式门禁。

#### 收窄形态：`useT("nav")` 与 `{P}ScopedT`

`{P}MessageKey` 是一个全局联合，而它注定会长大（铺完 P2 是几千条）。所以 codegen 除了整份那份，还按 namespace 出一套窄的：

    export type NavKeys = "web.nav.home" | "web.nav.orders" | …        // 每个资源文件一份
    export type WebNamespace = { "nav": NavKeys, "header": HeaderKeys, … }
    export type WebMessageKey = WebNamespace[keyof WebNamespace]        // 全局联合由它派生，不再手抄
    export type WebScopedT<N extends keyof WebNamespace> = <K extends WebNamespace[N]>(
        key: K,
        ...args: WebParamsOf<K> extends undefined ? [] : [params: WebParamsOf<K>]
    ) => string

`useT` 是重载：不传参数返回整份 `XTranslate`（key 位 = 本端 ∪ app-kit 共享），传一个 namespace 返回 `XScopedT<N>`（**只有**本端那一个文件）。参数位一律走整份的 `XParamsOf<K>`——key 在一个 root 内全局唯一，按 key 查就是准的；per-namespace 再切一层只会多出一批没人用的导出，而那按契约 3 是要报出来的。

四条形状上的取舍，都是量过或实测过的：

- **key 仍是带前缀的完整字面量**（`t("web.nav.home")`）：契约 6 的扫描与菜单表的 `labelKey` 都认完整串，砍前缀会让两条判据同时失效。
- **收窄形态不并入共享 key**（`appKit.*` / `error.*` / `validation.*`）：并进去等于没收窄；要共享文案就用不传 namespace 的整份那份。
- **整份那份也保留**：菜单表一张 `labelKey` 跨 `nav` 与 `page` 两个 namespace，`translateSidebarItems` 收的就是整份 `t` 的形状（实测 `TS2345`）。
- **收益是「误用被拦」，不是「报错变短」**：本仓库这版 tsc 不展开联合成员，收窄换来的是 `not assignable to parameter of type 'HeaderKeys'`，在 footer 里写 header 的 key 从此编译不过。

`useT` 是重载但实现只有一个、参数运行时没用（key 始终是完整字面量），所以实现里 `void namespace` 读掉。**一个已知代价**：`ReturnType<typeof useT>` 取最后一个签名（收窄那份），需要整份形状的函数签名要显式写 `XTranslate`（`BasicStep.tsx` 的 `toLocalizedUploadError`）。

带参消息使用必需参数元组；拼错 key 时可能先提示实参数量，但不会再放过整个参数对象缺失。

这件事的责任分工有个很容易写错的地方：**类型系统看不见字符串内部**。下面这张表按「谁真的保证得了」划分，不按「听起来谁更硬」划分。

| 要保证的事                               | 谁保证                                                                                                                                                | 性质   |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| en-US 缺条目（zh 有、en 没有）           | **codegen**。装配走 glob 而不是 `Record<MessageKey, string>` 的对象字面量赋值，tsc 根本不读 JSON；「缺一条即编译不过」这条在换成 glob 时就没了        | 生成期 |
| en-US 多条目（en 有、zh 没有）           | **tsc 不报**——结构赋值允许多余属性（JSON 导入的不是 fresh literal）。只能由 codegen 比 key 集合                                                       | 生成期 |
| 消息是不是合法 ICU                       | **tsc 不报**——它只看到 `string`。由 codegen 用 `intl-messageformat` 的 parser 逐条解析                                                                | 生成期 |
| 两侧占位符集合一致                       | **tsc 不报**。`ParamsOf` 从 zh 反推只约束**调用方传什么**，不证明 en 那句写的是 `{count}` 而不是 `{wrongName}`。必须由 codegen 解析**全部语言**后比对 | 生成期 |
| 参数类型（number vs string vs 金额槽位） | codegen 从 AST 的槽位类型推；**金额槽位直接拒绝**（见契约 5）                                                                                         | 生成期 |
| key 拼错、参数名/形状不对                | tsc：生成的 Translate / ScopedT 必需参数元组。三端与 app-kit 各自实例化到 `src/locales/use-t.ts` / app-kit 的 `useT`                                  | 编译期 |

也就是说：类型化真正接走的**只有「调用侧」一条**，其余五条全靠 codegen。注意「en-US 缺条目」也在生成期那侧——装配走 `import.meta.glob`，`Record<MessageKey, string>` 那种赋值检查在换成 glob 时就没了，把「缺条目」算在类型头上是错的。

codegen 因此不是一个便利工具，而是门禁的本体。它的契约要写死，否则它和 `i18n-check.mjs` 犯的是同一个错（只是换了一副更体面的面孔）。`scripts/i18n-codegen.mjs` 按六条落，头注释里逐条对得上：

1. **资源清单唯一确定**：`MANIFEST`（`apps/*/src/locales`）+ `EXTRA_ROOTS`（app-kit）一处定义，展开后断言非空，`--list` 可逐条列出。清单外即不存在——这是 §4.2 那条的实现。语言清单不在脚本里抄第二份，从 `locale.ts` 现读，所以 `SUPPORTED_LOCALES` 加一项这里跟着加一项。
2. **任一条解析失败或各语言参数不符 → 收集完一次性报错、非零退出，且一个字节都不写**。半截生成物比没有生成物更糟。
3. **生成物必须被 `pnpm typecheck` 与 `pnpm build` 消费**，否则它跑不跑等于没门禁。跑在哪一步指认得出：script `i18n:gen`（写）与 `i18n:drift`（只比对），lefthook pre-push 作业 `i18n-drift`，CI frontend job 步骤 `i18n`。**按 root 检查消费，不是按仓库**——某个 root 产了类型却没人消费时，那个死导出会被 `pnpm fallow` 报出来。
4. **比对覆盖所有语言**，不只源语言：逐语言读目录、逐语言编译，再与源语言比 namespace、key、参数集合。
5. **金额槽位在生成期拒绝**：AST 里 `number` 节点的 style 是 `currency`（两种写法都认）就报错（§4.4）。
6. **未使用的 key 非零退出**（取舍见 §10.1 末）。这条只在 1–5 都过了之后跑——一份坏掉的 catalog 会顺带把一堆 key 报成「没人用」，那不是真问题。

契约不是写着就算成立：拿 11 类变异逐个验过（en-US 缺文件 / 缺 key / 多 key / 非法 ICU / 两侧参数名不一致 / 跨文件撞 key / 值非字符串 / 金额槽位 / 语言目录消失 / 手改生成物 / 未使用的 key），每类都是**非零退出 + stderr 指到具体文件 + 生成物字节不变**。

### 5.6 语言隔离的完整面：locale、时区、缓存

§3.5 只解决了「进程里不能有共享的可变 locale」。这一条补另外两面——它们和全局变量无关，删干净了照样会串语言。

**时区。** 服务端与浏览器即使 locale 相同，`formatDateTime` 各按自己的默认时区算，就会出两个不同的字符串，表现为 hydration 文本差异。所以：

- 一期口径：**平台单一展示时区 `Asia/Shanghai`**。常量在 `packages/common/src/i18n/timezone.ts` 的 `PLATFORM_TIME_ZONE`——这是全仓唯一的时区出处，展示层不写时区字符串。展示层（`@shop/app-kit/display/format.ts`）用 `TZDate`（`@date-fns/tz`）把 instant 投到该时区再排版，所以 `date-fns` 的图案与 locale 一行未改，只多出「按哪个时区读」这一维。`TZDate` 需要完整 ICU，Node 13+ 与现代浏览器都有，仓库本来就依赖 `Intl`。不依赖 `process.env.TZ`、容器时区、用户系统时区三者中的任何一个。
    - **按天/按年分支也要走同一个时区**，否则会出现「按 +08 跨年、却按 UTC 判是否同年」这种自相矛盾：`isSamePlatformYear` 是为此存在的（`getFullYear()` 读环境时区），物流轨迹的跨年补年份是它的第一个调用点。实测 `2025-12-31T17:30:00Z` 在 UTC 下还是 2025 年、在 +08 下已是 2026 年，两边对同一条节点会得出相反的展示形态。
    - **测试写成「让环境时区变」而不是「把环境时区钉住」**：`format.test.ts` / `timezone.test.ts` 让 `TZ` 在 UTC / America_New_York / Pacific_Kiritimati 之间切换、断言输出逐条相同。反过来（旧写法 `vi.stubEnv("TZ","Asia/Shanghai")` 再断言字面量）等于把实现的环境依赖钉死、恰好绕过要防的那件事；这两条用例在去掉 `TZDate` 后当场变红，是它们的判据。
    - **顺带删掉的两条第二出口**：`@shop/common/i18n` 的 `formatDate`/`formatDateTime`/`formatNumber`（零调用方，日期那两个还吃环境时区），以及 `I18nContextValue` 上挂的 `formatDate`/`formatDateTime`/`formatNumber`（同样零调用方，且日期那两个吃环境时区）。上下文本就只给语言与翻译。
    - **已知例外**：`ui-web` 的 `calendar.tsx` 里两处 `toLocaleString`/`toLocaleDateString` 仍吃环境时区——它的 `Date` 由调用方（react-day-picker）构造，且 `data-day` 的生产与消费两侧用同一个调用、相对自洽，改它要连调用方一起动，留在「时区业务规则」那条（P4）一起做。
- 日期（date-only）与时点（instant）的展示语义分开定义，不用同一个 format 兜。前者一般恒按平台时区显示，后者才是「同一时刻不同人看到不同钟点」的东西。
- `X-Timezone` 头**已发**（§7.2），但它发的是平台时区、**不属于修 hydration 的工作**——「按用户所在时区展示」是多时区产品功能，与「时区业务规则」那条一起进。

**缓存。** 语言是响应的一部分，不是纯客户端的渲染细节。这三条要一起定：

- 首屏 HTML 随 locale 变 → CDN / 边缘缓存的 key 必须含语言。一期不引 `/en-US/` 路径前缀（§1），所以只能走 `Vary`（`Accept-Language` 加那条 `locale` cookie），代价是命中率下降——这笔账要在 P4 决定要不要换前缀时摊开算，不能默认它不存在。
- **TanStack Query 的缓存 key 必须含 locale**，一旦后端按请求语言本地化过响应。英文用户命中中文用户留下的缓存，和「有没有全局变量」毫无关系，是独立的一条口子。这条要求 query key 工厂（各域 `queries.ts`）把 locale 放进去，与 [frontend.md](frontend.md) 的取数约定对齐后再改。
- 不翻译的动态内容（§8）继续共享缓存，不带语言维度——它本来就没有两种语言版本。

`Vary` 与 query key 是同一件事的两端（「语言进缓存维度」），口径只写在这里一处，装配侧不复述。

新增 UI 组件的硬规则：组件内不出现用户可见的自然语言字符串；需要文案就通过 props 注入。

**壳层通用文案的唯一机制是 `UiLabelsProvider`**：`packages/ui-web/src/components/ui-labels.tsx` 声明九类壳层组件（确认框/搜索框/错误态/图片上传/区划/手机号/下拉/日期时间/脱敏查看）需要哪些槽位，app-kit 的 `I18nProvider` 把当前语言装配成 value 传进去，组件在**渲染期** `useUiLabels()` 取（显式 prop 仍可覆盖）。它与 §6.1 的 `FormErrorTranslateProvider`、DataTable 的 i18n 同属「渲染期按当前语言取」这一条道，没有第二条路径——尤其不要换成 `useEffect` 里 `Object.assign` 改模块级单例那套：effect 不在服务端跑（SSR 首屏文字与 aria 空）、切语言时子树先渲染再改（同一页有的组件立刻换、有的等下一次交互）、并发 SSR 下所有请求写同一个模块对象。

**「一个文件里 `t()` 很多，要不要收成一处」——判据是「形状是否重复」，不是「次数是否多」。** 形状重复（菜单项、顶栏入口、状态枚举按数据渲染）→ 收成一张表，表里存 `labelKey` 字面量并标注成 `XMessageKey` 兜住写错（三端菜单表 `SidebarSourceItem<K>`、seller `AppTopBar.tsx` 的 `TOPBAR_ACTIONS`）。次数多但形状各异（一个设置页 23 句）→ **不要收**：那是 23 个不同 UI 元素的真实文案，集中只是离使用点远了一步，该问的是组件是不是太大。两张表并存的老形态（中文 label + `NAV_LABEL_KEYS` 对照表）会各自漂——新增项忘了登记就静默露出中文；收成一张后这个失效模式不存在了。

ui-web 那几行（尤其「其他内嵌中文」）**要先做完再铺业务文案**：壳层文案一旦从组件默认值里自己长出来，§4.2「所有资源走同一份清单」就又被破一次。

### 6.1 表单校验错误：schema 抛结构化事实，渲染边界换句子

**规则**：Zod 里的每一条用户可见消息，只写「事实」不写「句子」——`message` 放 catalog key，需要进句子的数放 `params`：

```ts
// apps/seller/src/coupon/form.ts
type CouponErrKey = Extract<SellerMessageKey, `seller.coupon.form.err.${string}`>
const err = (key: CouponErrKey) => ({ message: key })
const errWith = (key: CouponErrKey, params: Record<string, string | number>) => ({
    message: key,
    params,
})

name: withMaxLength(
    z.string().trim().min(1, err("seller.coupon.form.err.nameRequired")),
    COUPON_NAME_MAX,
    err("seller.coupon.form.err.nameMax"),
)
```

**带数字的条款一律 `refine` / `ctx.addIssue`，不许 `.min(N, …)` / `.max(N, …)`**（Zod 4.6）：
check 那两条通道接受 `{ message, params }` 这个形状，但会**静默丢掉 `params`**——issue 里只剩 `message` 与
`maximum`/`minimum`，而渲染层的翻译器只读 `message` 与 `params`。槽位填不上时 `translate` 原样给回模板，
用户当场看见裸的 `{max}`。`refine` 通道把 `params` 原样带上，所以长度上下限统一走
`@shop/common/domain` 的 `withMaxLength` / `withMinLength`（判据与槽位同源，调用方只换句子、换不掉槽位）。

另一种写法是 **schema 工厂**（`regionCodeSchema(issue)`）：形状与位数仍由 `@shop/common` 持有，句子交给调用方，
用于「通用句说不清、这句要指出该去点哪个控件」的情形（区划码的「请选择所在地区」）。它与 `validation.*`
的取舍判据是：**这句话与后端某条注解是同一个条件吗**——是就复用 `validation.*`（一个条件两句话比一句话两个来源更糟），
不是才进本 app 的 catalog。

句子在渲染边界换：`packages/ui-web/src/components/form-error-translate-context.tsx` 提供 `FormErrorTranslateProvider`（由 `FieldFrame` 消费，与 §5.5 那份表格文案同一条道），app-kit 的 `I18nProvider` 按当前语言灌进实现。ui-web 仍然不读任何 app catalog——§4.2、§6 那条边界一寸没让。

**为什么不选另外两种常见写法**（`zod-i18n-map` / `makeSchema(t)` 工厂是它们的代表）：`makeSchema(t)` 把 schema 从模块级常量变成 locale 的函数——切语言要重新校验才换掉已显示的错，`LoaderData` 与测试里的模块级引用全要改带参调用，而它换来的「schema 里直接是句子」正是本条要拆掉的。`zod-i18n-map` 那类外挂要求 i18next 作运行时，与本项目零依赖纯函数的核心（§5.1）冲突，且跨字段自定义错误在它那儿仍是裸 message。服务端成品句已由 §7.3 降级，本条把同一判据推到本地校验那半边。

**服务端那一半也归这条**：`serverFieldErrors` 交进表单的是 `{ message: "validation.MAX_LENGTH", params: { max } }` 而不是提前翻好的句子，形状与 Zod issue 逐字相同，所以 `FieldFrame` / 裸 `<FieldError>` 认两种来源。它必须交事实而不是句子——提交那一刻按当时 locale 翻成字符串存进表单状态的话，切语言后本地错误跟着变、**已显示的服务端错误不变**，同一页两种行为。连带后果：`serverFieldErrors(error, map)` 不收 `locale`（每个调用点少传一个参数），而边界缺失时「不给事实、由调用方降级」的判据原样保留（不给的仍是那格，不是印裸 `{max}`）。回归用例在 `form-error-translate.test.tsx` 的「服务端字段级错误：与本地校验走同一条道」那条：中文界面出 catalog 那句，切语言后同一格变英文、且没有第二次提交。

**事实的出口是 `messageFactFactory`**：本条写的是「key + params」，怎么把两者绑在一起只有一个办法。`packages/common/src/i18n/message-fact.ts` 的 `messageFactFactory<XErrKey, XParamsByKey>()` 收这两个类型实参，产出的函数签名是 `<T extends XErrKey>(key: T, ...args: T extends keyof XParamsByKey ? [params: XParamsByKey[T]] : [])`。业务域的写法因此是一行：

```ts
type CouponErrKey = Extract<SellerMessageKey, `seller.coupon.form.err.${string}`>
const err = messageFactFactory<CouponErrKey, SellerParamsByKey>()
```

`XParamsByKey` 是 codegen 顺带导出的（`ParamsOf` 一直是），所以**参数位跟着每条消息自己在 catalog 里声明的槽位走**：带参的 key 少传参数、参数名写错（`{ maximum: 365 }` 配 `{ max }` 那条句子）、无参的 key 多传参数，三种都编译不过。

事实工厂与 t 现在都约束必传参数；工厂仍要求 key 与参数保持关联。反例编译测试分别在 common/i18n/message-fact.test.ts 与 web/locales/types.test.ts，由 pnpm typecheck 执行。

**输入边界：**裸字符串表示已经成句的兼容文本，原样返回；结构化 { message, params } 表示 catalog key，统一走 i18next 翻译与诊断。缺 key 返回 key 并去重上报，缺参数不显示裸 ICU。旧 schema 若把自然语言包装成结构化 message，需要逐步改成类型化事实；其显示内容保留，但会产生缺 key 诊断。

**数组里的字段：`name` 必须写成方括号**。实测事实（`@tanstack/form-core/dist/esm/standardSchemaValidator.js:13`）：Zod issue 的 `path: ["rules", 0, "region"]` 被拼成 `rules[0].region` 作为键，而 field 是按自己的 `name` 字符串精确取键——写成 `rules.0.region` 就**一条都取不到**（错误静默隐身，页面一句红字都没有）。所以 `superRefine` 里给数组行报 `path` 时，渲染点必须是 `form.AppField name={`rules[${i}].region`}`，且**那一格得是真的 field**：受控子组件（自己收 `value`/`onChange` 的那四格输入）不在 field 表里，它的错同样隐身。这一条也是运费模板页「拆成逐格 field」的理由，两种情形各钉了一条用例在 `packages/app-kit/src/i18n/nested-field-path.test.tsx`（A 方括号命中自己那格且不漏到别行；B 没有 field 时提交被拦住而页面一个字都不显示）。

承重链的用例在 `packages/app-kit/src/i18n/form-error-translate.test.tsx`，钉三条：key 命中并插值、**切语言不重新校验**已显示的错当场变（这条是工厂那版做不到的，也是选它的决定性理由）、结构化 key 查不到时返回 key 并上报。

进度记在 `TODO.md` 的 i18n 段（不散抄在这里）。

### 6.2 写操作与复制反馈：构造时校验，显示时翻译

通知使用同一套消息事实工厂，不另定义宽泛的 `{ key: string, params?: … }`。应用侧的 `locales/message.ts` 用本端与 app-kit 生成的 key / ParamsByKey 绑定 `messageFactFactory`：

```ts
import { message } from "#/locales/message"

notify.info(message("web.cart.toast.maxStock", { stock: 3 }))
// meta.success / meta.error 与 notify 的参数相同
```

- `CheckedMessageFact` 是只能经工厂构造的类型；运行时仍是普通 `{ message, params? }`，没有额外对象层或语言状态。
- 拼错 key、漏参数、参数名不符、给无参消息塞参数，均由 TypeScript 拦截；codegen 只管资源与生成物，不代替调用处检查。
- `notify` 与 MutationCache 到完成时才翻译，避免等待期间切语言后显示旧文案。
- `copyWithNotify(value)` 只复制原值，成功统一显示通用复制提示；不收已经翻译的字段标签，失败仍提供手动复制提示。

## 7. 请求头与后端

### 7.1 前端请求头

三个应用均发送 Accept-Language、X-Locale 与平台 X-Timezone。

seller/admin 请求钩子读取入口装配的 appI18n；web 浏览器读取 getBrowserI18n，SSR 从 Start 请求上下文解析。请求钩子执行时现读，禁止在 SDK 初始化时拍语言快照。

QueryClient 的 MutationCache 接收与 Provider 相同的 i18next 实例：Toast 的 key/params 在成功或失败时翻译，不提前冻结成品句。

### 7.2 后端 LocaleContext（范围只有那两条）

它存在的理由只有两条，都不涉及错误文案：

- **动态内容**按请求语言挑选（§8 的 `entity_translation` / JSONB 读取，以及未来的后端生成文本：邮件、短信模板）
- **日志**：HttpRequestLoggingInterceptor 的 http.request 事件带 locale，排查「这个用户为什么看到中文」时用得上

**落点**（`apps/server/src/main/java/com/shop/platform/infra/web`）：

- `SupportedLocales`：支持语言清单（`zh-CN` / `en-US`）+ `normalize()`（与前端 `normalizeLocale` 同一条规则）
    - `PLATFORM_TIME_ZONE`。**与前端 `packages/common/src/i18n/locale.ts` 的 `SUPPORTED_LOCALES` 双向核对**
      （`LocaleVocabularyTest`）——前后端各有一份「支持哪几种语言」时，唯一能自动发现漂移的办法就是这条等式。
      少改一侧的后果是静默的语言不一致（后端把 `de-DE` 归成 zh-CN、或前端加了语言后端不认，都不报错）。
- `LocaleContextHolder`：ThreadLocal 装请求语言 + 时区，读时永不返回 null（缺失给平台默认）。
- `LocaleFilter`（`OncePerRequestFilter`，`HIGHEST_PRECEDENCE + 10`，在 RequestIdFilter 之后）：解析
  `X-Locale` > `Accept-Language`（按 q 权重降序取第一个能归一的）> 默认 `zh-CN`；`finally` 里必清。
- `http.request` 事件加 `locale` + `timezone` 两字段（`BusinessEventCatalogTest` 核目录）。

**为什么 `X-Locale` 排在 `Accept-Language` 前面**：前者是前端已归一过的应用语言，后者是浏览器原样带过来的
（可能一长串、也可能被网关改写）。两个都认，前端换机制时后端不用跟着改。

**解析失败一律落默认、不抛**（`LocaleFilterTest.畸形AcceptLanguage不抛_落默认` 钉住）：请求头是外部输入，
`";;, zh-CN;q=abc"` 这类畸形值必须落回可用的默认语言，而不是 500。这条测试当初抓到过一个真实 bug——
Java 的 `";;".split(";")` 丢弃尾部空串后返回**长度 0 的数组**，取 `parts[0]` 直接 `ArrayIndexOutOfBounds`。

**它不接管任何错误文案**：不引入 `MessageSource`，`LocaleContextHolder` 也不提供「按语言取文案」的方法——留着那个能力它就会长成第二套文案系统（理由见 §7.3）。这条否得很窄，只排除「用 Java `messages_*.properties` 承载前端能看到的错误句子」；邮件/短信模板真要做服务端本地化时仍需要一个服务端文案载体，那是那条线自己的决定。

### 7.3 错误文案：后端出 code，前端出文案

**决定。** 用户可见的错误句子归前端 catalog 拥有（namespace `error.`，key 直接用 code：`error.SMS_CODE_EXPIRED`）；后端 `BusinessException` 的 `detail` 降级为日志与调试字段。「降级」要说准：它**在中文界面仍是兜底文案**（那里后端那句是同语言且更具体的），在其它语种才是纯日志字段——不进任何非中文界面。判据的完整形状与被否掉的那版判据，见 [docs/error-codes.md](../error-codes.md) 头部。

**为什么 UI 错误不放到服务端。** 本仓库把「一份 catalog、类型化、ICU、编译期平齐」定为文案的唯一架构（§5.5）。UI 错误文案若留在 Java `.properties`，就有了**两套本地化系统**：两种平齐机制、两个语感来源、两条加语言的流程，而 §11 那条反模式正是它的必然结局——仓库里那份 115 行的 `error-messages.ts` 曾是一个零调用方的孤儿（它写了，但没人接，因为另一份正被 `notify.ts` 优先读），就是「两份」已经存在的一次证据。反方向（服务端出成品句）也能解决英文界面显示中文 detail，代价是在 Java 侧新建一套要手工保持平齐的 properties，等于把 §10.1 拆掉的校验脚本换个语言重装一遍。

**这不是一条普遍规律，别把它抄走。** 服务端本地化在下面这些场景是正解，而且本仓库已经需要它：

- **邮件、短信模板**——文案离开浏览器之后就再也没有第二次本地化机会，只能服务端出成品（§7.2 把这条列为 LocaleContext 存在的理由之一）
- **公开 API / 多种客户端**——同一份后端要喂 web、seller、未来的小程序或第三方，客户端不一定有自己的 catalog
- **动态内容**——商品名、CMS 词条按请求语言挑选（§8）

所以本条否掉的只有一件事：**把 UI 错误文案放进 Java `messages_*.properties`**，因为它与 §5.5 的 catalog 是同一职责的两份实现。上面三类是另外三条线，各有各的 owner，不与本条冲突。

**落地即接通，不是再写一份。** 文案走 app-kit 的 `locales/{zh-CN,en-US}/error.json`，与 §4.2「所有资源必须被同一份清单覆盖」一致——glob 清单零改动就把它收进了 `MessageKey`，`i18n:drift` 一起管；码到 key 的映射由 `packages/app-kit/src/i18n/error-keys.ts` 承担，那张表带 `satisfies Record<code, AppKitMessageKey>`，**漏一个码是编译不过**，不是靠人记。

#### 最终行为

已知 code 走 catalog（数字由 params/errors 参数化）；未知 code 或非预期错误走本地化通用提示（非中文界面按状态码那支，中文界面按 `detail`）；`detail` 只进日志与诊断——中文界面那一格是设计，不是漏网。

未命中 code 的兜底**还在**，但优先级已经反过来了：链收成一处纯函数 `errorText(err, locale, fallback?)`（`packages/app-kit/src/i18n/error-keys.ts` 的 `errorTextPlan`，五支逐条写着），先查 code、命中就用 catalog；查不到才按 locale 分岔——中文界面拿 `detail`，其它语种拿场景文案或**按状态码**的那句（`appKit.error.{badRequest,unauthorized,forbidden,notFound,conflict,validation,rateLimited,serverError,network}`，两份语言九条齐）。**客户端本地失败（断网 / 超时 / 取消 / 响应不合契约）也在第 1 支**——它们有码（`packages/common/src/contract/client-failure.ts`）也有 catalog 文案，与其它三族区分得开，用户分得出「超时该重试」与「断网该检查连接」。**用它的有两类出口**：全局 toast（`notify.fromError`）与表单里内联渲染的那几处（`login-form.tsx`、web 注销弹窗、web 改密表单、seller 发品横幅）——同一屏上不该出现「toast 说 catalog、横幅说 detail」两种语感。

两条退出条件，一条成立、一条换了判据：

**① 反向门禁（每个 code 恰有一条 error.<CODE>）已成立**，两个方向都查：TS 侧 `satisfies` 编译期拦，Java 侧 `ErrorCodeVocabularyTest` 拦两份语言的键集合与空值。

**② 生产代码里渲染 detail 的分支拆成了两笔：**

- _三个码全部退出 detail 优先。_ FORBIDDEN_WORD_HIT 走扩展属性 `errors`（`[{field, message, value?}]`，字段级）：前端按 field 定位输入框、把 value 嵌进当前语种的那句。ADDRESS_LIMIT_EXCEEDED / MERCHANT_ADDRESS_LIMIT_EXCEEDED 走扩展属性 `params`（`{limit}`，错误级——没有字段可定位）：上限数字从后端常量作为数据出一次，catalog 句子写 `最多保存 {limit} 条收货地址` / `You can save up to {limit} shipping addresses.`，后端把 20 改成 30 时前端零改动。**句子装不下关键值时的答案不是「让 detail 优先」，是「把那个值从句子拆出来」。** 门禁换了个方向钉：`error-keys.test.ts` 核「带 {槽位} 的句子都在 `CODE_SLOTS` 登记着」且「登记的槽位在句子里真的存在」——两向都红，`DETAIL_FIRST` 集合本身已删除。
- _未命中 code 的兜底**不再承诺清零**。_ 普查（数字与口径在 [docs/error-codes.md](../error-codes.md) 头部）数出报错出口 304 处，带 code 的 37 处，不带的 267 处，内联中文句子去重 204 句——补齐 = 204 个新码，而 404 那 78 处全是「XX 不存在」、状态码那条通道本就覆盖它。所以这一笔换成了闭环：中文界面按 `detail`、其它语种按状态码那句兜住，`notify.fromError` 把走过这两支的错误报成 `error_fallback source=… status=… code=…`，**哪句值得升成 code 由真实频次定**。这不是一笔待平的欠账，而是一个要被频次逐步收拢的面。

口径一句话：**已登记的码走 catalog，其它语种拿状态码那句，中文界面拿 `detail`——而「未登记」靠上报频次逐条升上来，不靠人工扫平。**

#### 代价（三条，都已付）

1. **`docs/error-codes.md` 的定义原则定稿为「用户看到的句子由 catalog 或状态码通道给；`detail` 只在中文界面当文案；升不升成 code 由上报频次定」**（定稿过程与普查数字见上一节②）。价值不是少写码，是把「哪个码重要」从一次性的 204 个猜测换成可观测的频次。`ErrorCodeVocabularyTest` 四边核对的第四边是「每个 code 在两份语言的 `error.json` 里**有且只有一条**非空 `error.<CODE>`」——它防「加了码忘了加文案」；防不到的另一侧（有句子没码）按定稿判据**不设门禁**。
2. **422 校验族参数化的代价比预估小。** `@Size` / `@Pattern` 的数字**是 OpenAPI 契约的一部分**，所以前端本地化它就得把数字拉出句子自己渲染；已落地的形状避开了新增契约字段——`errors` 是 ProblemDetail 的**扩展属性**，`errors[].field` 又正是 DTO 的属性名，而那些数字前端已有一份对边（`packages/common/product-fields.ts`），按 field 定位 + 用前端自己那份上限渲染句子就够了。要 `sdk:gen` 的只有一种选择：把数字**再**进一次契约。**别把两件事混成一句**：_code_ 取值不在契约里，补文案不触发生成；_契约里那格上限_ 改了要重生成。
3. **抛出点看不到最终句子。** 后端一个 `throw` 处不再有那句话，可读性靠注册表那张卡的 `behavior` / `trigger`（它们同时进 Java 与 TS 两份生成物的注释）加 catalog 里的 `error.<code>` 条目补回来。上面那条反向门禁就是这笔可读性损失的补偿，不是可选项。注意它的边界：**门禁能保证每个码有文案，保证不了那句文案说对了事**，后者仍然靠人读。

#### 新增一个命名空间（`locales/<locale>/<ns>.json`）时的坑：**已由 codegen 自动处置**

装配是 `import.meta.glob`，glob 的展开结果**在构建期被烤进装配文件的编译产物**；而
`--fs-module-cache`（全部 test script 都带着）按**那个文件的内容哈希**复用那份产物。新增一个
`.json` 并不改装配文件的内容，于是缓存命中、产物里还是没有新文件的那一份——症状是「新 key 取出来
等于 key 自己」（`t()` 拿不到模板时降级成 key），而 glob 在测试文件里当场展开又是全的，
极易误判成「装配代码坏了」。

**现在的处置是自动的**：`scripts/i18n-codegen.mjs` 写完生成物后会删掉 `node_modules/.vitest-cache`
（整个目录，它是可再生的）。理由是**该失效的权威时刻就是这里**——资源文件刚被读过、刚判过平齐，
改的正是它们；而靠人去改装配文件一行来撞哈希是不可靠的（`vp fmt` 会把多余空行收掉）。**症状是整套 web 用例红，而错误信息指向「找不到文案」，与「刚加的资源文件」毫无关系**——排查时先想到这一条。

#### 一期边界

英文界面已不会印中文（`errorTextPlan` 最后一支按状态码给通用句）；中文界面无 code / code 未登记的 400/422 仍直接用后端那句——在定稿判据下这不是欠账，是被频次逐步收拢的面。参数缺失（后端漏发）时退回按 locale 的兜底并被 `notify.fromError` 上报，那是契约破口的信号。

## 10. 门禁与验收

### 10.1 门禁的四条判据

判据是这四条，**同时成立**才算一道门禁：

1. **覆盖完整**——清单上的每条资源都被检查，清单外的资源不允许存在（§5.5 契约 1）
2. **判定准确**——按目标格式的真实语法判，不按正则近似判
3. **自动执行**——在 `pnpm` 脚本、`lefthook.yml` 的某个 job、`ci.yml` 的某个步骤里能指认出它跑在哪一步
4. **失败阻断交付**——红了 typecheck/build/push 就过不去

**codegen（§5.5）按这四条成立**：判据 1 = `MANIFEST` + `--list`；判据 2 = 用运行时那个 `IntlMessageFormat` 的 AST 判，不写正则近似；判据 3 = `i18n:gen` / `i18n:drift` 两个 script、lefthook 作业 `i18n-drift`、CI 步骤 `i18n`；判据 4 = 失败即退 1 且不写盘，drift 模式专门用来拦「资源改了、生成物没跟着改」。§5.5 末那 11 类变异是逐条验过的，不是推的。

两条要点：

- **判据 3 是接上去的，不是本来就有的。** 文档曾长期声称 lefthook 里有 `i18n-drift` 作业，实际 drift 只在 CI 跑——「有门禁」和「门禁接在了执行点上」是两件事。**写完判据要当场验证它在执行点上真的存在**，别信自己的文档。
- **别用「它是脚本 / 它是类型」代替这四条判据来论证可靠性。** codegen 本身就是脚本，它同样可能漏扫、可能没接进 CI、可能红了却照样写出半截生成物。它之所以算门禁，是因为 §5.5 那四条契约把这四条判据逐条钉住了，而不是因为它长得像生成器。用官方 parser 精确解析各语言的**独立校验脚本**也完全可以满足这四条——本仓库选 codegen 是因为它顺手把类型产出了，不是因为脚本这条路被证明不成立。（取代 `scripts/i18n-check.mjs`：它在 §5.5 契约接线之前四条一条都不成立，见下表。）

`i18n-check.mjs` 按这四条判下来的账（它已删除，这张表只作对照，不要照它读现在的仓库）：

| 判据     | 旧脚本的事实                                                                                                                     |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 覆盖完整 | 扫描面是 `apps/*` 那三份 `src/locales/`，看不见 app-kit 那份内联字典——而全仓库真在用的两条插值消息恰好全在那儿。漏掉全部，命中零 |
| 判定准确 | 花括号只配平不解析 ICU 规则；占位符靠正则 `\{(\w+)\}` 数，`{count, plural, …}` 里的嵌套参数抓不到                                |
| 自动执行 | `lefthook.yml` 的 pre-commit / pre-push 与 `.github/workflows/` 都没有它。只能靠人记得                                           |
| 失败阻断 | 跟着上一条：不进任何流水线，红了也不拦任何东西                                                                                   |

它查的三件事现在都由 codegen 承担：两侧 key 集合相等 → codegen 比 key 集合（§5.5 表第 1、2 行）；花括号配对 → 用 parser 逐条解析（第 3 行）；两侧 `{placeholder}` 一致 → 解析**全部语言**后比对（第 4 行）。「对新增强制」也成立，但承担者是 codegen 的 namespace/key 比对（`--check` 与 pre-push 都会红），不是类型——装配走 glob 之后，`Record<MessageKey, …>` 那种赋值检查不存在了。结论没变（不需要白名单机制），理由换了。

**未使用 key 的 scanner 只判一件极窄的事**：catalog 里的每条 key，在 `.ts`/`.tsx` 源码（跳过 `.d.ts`、`*.gen.ts`、`locales/`）里能不能找到 `"<key>"` 这个带引号的整串。它不扫调用点形状、不判 key 拼在哪，只问「有没有人引用」：

- 导航表里的 `labelKey: "seller.nav.order"`、组件里的 `t("web.nav.home")` 都算引用——**所以「把动态 key 改成字面量」这条改造不需要白名单，也不需要常量表**；
- 用模板串拼出来的 key（``t(`seller.nav.${key}`)``）不算引用，于是拼出来的每条 key 会被逐条报成「没人用」，那正是改造的信号——门禁自己会推着代码变成可搜的字面量；
- 漏报方向单一：key 只在注释或字符串里被提到也算「用过了」（宁可漏报不误伤），所以它不是完备性证明，只是一条不会误伤人的提醒线。

（另一个形状——让引用变成真标识符以复用 fallow 的可达性分析——被探针否掉了：`unused-exports` 只管到导出符号本身，对象属性与 enum 成员一次都没报。「复用已有门禁」是推测不是事实。）

**「加了码可能忘加文案」这条口子也有机器了**：`ErrorCodeVocabularyTest` 的第四边（§7.3 代价 1）+ TS 侧 `error-keys.ts` 的 `satisfies`。查不到的是另一侧——用户可见的 `detail` 没有对应 code；那一侧按 §7.3 的定稿判据不设门禁，收拢靠 `error_fallback` 上报的真实频次。

### 10.2 测试

测试文件按域就近放着，这里只记**读文件名看不出来的**几条判据：

- **断言格式化结果，不断言 parser 内部**。`message.test.ts` 要证明的是「locale 真的驱动复数选择」「坏 ICU 不抛错」，不是 `intl-messageformat` 自己的解析对不对。
- **时钟/时区一律让环境变，不把环境钉住**。`format.test.ts` / `timezone.test.ts` 让 `TZ` 在 UTC / America/New_York / Pacific_Kiritimati 之间切换并断言输出不变。反过来（`vi.stubEnv("TZ", …)` 再断言字面量）等于把实现的环境依赖钉死、恰好绕过要防的那件事——这两条用例去掉 `TZDate` 就当场变红，是它们的判据。
- **每个用例里让后端 detail 与 catalog 句子故意不同**，否则 `notify.test.tsx` 的断言会空过。
- **「key 写得对」不写运行时用例**：那是源表那行类型标注在管，写错即 `TS2820`；运行时再断言一遍等于断言 `true`。菜单测试只钉行为（逐层翻译、`to` 不动、外链不被当 key 翻、权限裁剪）。
- **组件测试要传本端 resources**：`renderWithProviders` 默认只挂 app-kit 那份，所以渲染用了本端 catalog key 的组件必须 `{ resources: webMessages }`。漏传的症状是「按中文句子找不到元素」——`t()` 取不到模板时回落成 key 本身（不抛、不空），而断言还在找那句中文。

**已覆盖的集成契约：**web/app/i18n-router.test.tsx 验证正文、路由标题、即时 SDK 请求头、下一条 Toast 和未保存输入；app-kit/i18n/ssr.test.tsx 验证独立请求实例与 hydration；common/i18n/message.test.ts 验证统一降级。

### 10.3 验收标准

验收看这几条，前四条是行为、后面是门禁：

- 中英切换可用、刷新后保持；新改的用户可见文案不再硬编码
- en-US 缺失时回退 zh-CN 不白屏；**消息解析失败同样返回 key、不抛错**（§5.1）
- 出站头的 locale 来自请求/装配作用域而非模块全局（§3.5）
- 时间格式化吃显式平台时区，不依赖运行环境默认（§5.6）
- 资源门禁满足 §10.1 四条判据且**能被指认跑在哪一步**——验收的是它靠不靠得住，不是它存不存在
- 金额没有第二条格式化路径（§4.4，codegen 的 AST 检查执行）
- `pnpm lint / pnpm typecheck / pnpm test` 全绿

错误文案那条的验收口径在 §7.3（中文界面按判据保留 `detail` 兜底，不算违约）；缓存维度的缺口在 §2。

## 11. 反模式与项目选择

这一节分成两半，因为它们常被混在一起写——**把项目偏好当成普遍规律论证，会让人以为别处也该照抄**，而真正的原因是「我们选了这个并且它能被验证」。

### 11.1 真反模式（做了就会出错，与项目偏好无关）

- 用中文/英文原句当 key
- 字符串拼接生成句子
- 组件内写死用户可见文案
- 跨请求共享的可变 locale（模块级 `let`，SSR 下串语言）——注意这禁的范围很窄：请求/应用各自独立的 i18next 实例不是跨请求共享状态（§3.5）
- 资源不进 §5.5 那份统一清单：藏在组件旁边的字典、组件默认 props 里的中文。真正的判据是「清单覆盖不到」，**不是「它是 TS 而不是 JSON」**——TS 对象同样能被类型约束
- 把 `detail` 当**非中文界面**的 UI 文案（§7.3：中文界面那一格是判据明写的兜底，其它语种拿它就是漏中文）；前后端各维护一份错误码文案且无门禁
- 缺翻译时静默吞掉或回退为空串
- 用 ICU 的 `{n, number, currency: CNY}` 格式化金额（§4.4）：开出 `formatMoney` 之外的第二条金额路径，撞 AGENTS.md 的 Money 硬规则
- 直接改 `formatMoney` 的 CNY 假设来做多币种
- 动态内容未翻译却宣称国际化完成
- **让 `contextHeaders` 读模块级 locale**（§7.1）：后端接了 LocaleFilter 也白接，头本身就是错的
- **让 codegen 产出生成物却没人消费它**：`typecheck`/`build` 不引用 `.gen.ts`，等于门禁不存在（§5.5 契约 3）
- **用「它是脚本 / 它是类型」代替 §10.1 那四条判据来论证可靠性**：生成器也是脚本，也会漏扫、也会不跑

### 11.2 项目选择（合理但不是普遍规律，换项目可能反向）

- **UI 错误文案在前端、不在 Java properties**（§7.3）。反过来的情形是真实存在的：公开 API、多客户端、邮件短信都必须服务端本地化——本仓库那两类也已经划给 LocaleContext 了。所以「服务端建 MessageSource」**不是**普遍反模式。
- **资源用 JSON**。选它是因为翻译工具直接读写、glob 清单好定义；不是因为非 JSON 就失控。
- **语言标签内部统一用地区级**（`zh-CN` / `en-US`）。`en` 是合法标签，`normalizeLocale` 的职责本来就是收层级（用 Intl.Locale 解析基础语言，再从支持清单选择 en-US）。真正要避免的是**同一链路里混用不同层级**，语言级、脚本级、地区级哪一层是「内部口径」由产品要不要区分 `pt-BR`/`pt-PT` 决定。
- **非组件上下文用参数/注入实例传递 locale，`AsyncLocalStorage` 只是兜底**（§3.5 约束 3）。上一条版本把它写成必选，那是不必要的隐式机制。
- **按 namespace 拆资源文件**（§4.2）。这是可维护性与 ownership 的选择，不解决联合类型体量——那是另一个决定。
- **一期不做 URL 前缀、走 `Vary`**（§5.6）。SEO 要求高的产品会反过来选路径前缀，那是 P4 的正常改道，不是纠错。
