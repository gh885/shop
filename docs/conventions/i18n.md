# 国际化（i18n）约定与落地架构

> 当前只启用 zh-CN + en-US，但所有模型按「未来支持 N 个语言」设计。
> 本文是 i18n 的唯一入口；改用户可见文案、错误文案、日期/数字格式前先读。
> 相关文档：前端规范 [frontend.md](frontend.md)、错误码 [../error-codes.md](../error-codes.md)、架构总览 [../architecture.md](../architecture.md)。

## 1. 结论

| 项                        | 决定                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------- |
| 源语言 sourceLocale       | zh-CN                                                                                    |
| 支持语言 supportedLocales | zh-CN、en-US                                                                             |
| 默认语言 defaultLocale    | zh-CN                                                                                    |
| 回退链 fallback           | en-US -> zh-CN                                                                           |
| 一期范围                  | 三端 UI 文案、错误码文案、日期/数字格式、Locale 请求头透传                               |
| 一期不做                  | RTL、多币种结算、动态内容翻译、TMS 深度集成、按地区数据驻留                              |
| 包边界                    | 纯逻辑进 @shop/common；React Provider/hook 进 @shop/app-kit；业务文案按 app ownership 拆 |
| Web URL 策略              | 一期先用 cookie + Accept-Language；正式出海前再升级为路径前缀 /en-US/...                 |

**一句话：架构上支持多语言，一期只交付中英；文案资源可替换，核心代码不感知当前支持几种语言。**

## 3. Locale 模型

### 3.1 类型与常量

放在 packages/common/src/i18n/locale.ts（纯逻辑，不依赖 React）：

    export const SUPPORTED_LOCALES = ['zh-CN', 'en-US'] as const
    export type AppLocale = (typeof SUPPORTED_LOCALES)[number]

    export const DEFAULT_LOCALE: AppLocale = 'zh-CN'
    export const SOURCE_LOCALE: AppLocale = 'zh-CN'

    export const FALLBACKS: Record<AppLocale, AppLocale | null> = {
        'zh-CN': null,
        'en-US': 'zh-CN',
    }

### 3.2 归一化

外部输入可能来自：

- Cookie：locale=zh-CN
- Accept-Language：en-US,en;q=0.9,zh-CN;q=0.8
- 用户资料
- 未来 URL 前缀

统一入口：

    export function normalizeLocale(input: string | null | undefined): AppLocale | null
    export function resolveLocale(candidates: Array<string | null | undefined>): AppLocale

一期可把 zh、zh-Hans、en 分别归一到 zh-CN、en-US；以后加语言时只扩映射表。

### 3.3 解析优先级

| 场景               | 优先级                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 三端（今天的实现） | locale cookie（「用户显式设置」就落在这条 cookie 里）> navigator.language > DEFAULT_LOCALE |
| web SSR 首屏       | 同上，但挂载前恒为 DEFAULT_LOCALE：服务端还没参与解析（缺口记在 §5.3 与 §9 P3）            |
| web 正式出海后     | URL 前缀 > locale cookie > Accept-Language > 默认                                          |

三行都交给同一个 `resolveLocale()`：归一（`zh_CN` / `zh-Hans-CN` → `zh-CN`）与「不支持就往下走一级」只在它那里判一遍，装配侧不各判一次。

### 3.4 回退

任何取文案的地方都遵守：

    请求 locale -> 当前 locale 资源 -> fallback locale 资源 -> key 本身

key 本身作为最后兜底，同时上报缺失监控。不允许回退成空字符串，也不允许因缺翻译白屏。

## 4. 资源 ownership 与格式

### 4.1 放哪

| 层                      | 职责                                                        | 不做什么                             |
| ----------------------- | ----------------------------------------------------------- | ------------------------------------ |
| @shop/common            | Locale 解析、回退、格式化纯函数、错误码文案字典             | 不依赖 React、不承载页面业务文案     |
| @shop/app-kit           | I18nProvider、useT、跨三端共享的登录/通用文案、日期展示适配 | 不承载 web/seller/admin 各自业务文案 |
| @shop/ui-web            | 纯 UI；组件文案通过 labels / i18n / locale prop 注入        | 不在组件内部写死中文或英文业务文案   |
| apps/web/src/locales    | 买家端业务文案                                              | 不复制 app-kit/ui-web 已有文案       |
| apps/seller/src/locales | 卖家端业务文案                                              | 同上                                 |
| apps/admin/src/locales  | 管理端业务文案                                              | 同上                                 |

### 4.2 命名空间

    apps/web/src/locales/
      zh-CN/
        common.json
        home.json
        product.json
        order.json
      en-US/
        common.json
        home.json
        product.json
        order.json

共享组件文案走 appKit namespace，例如：

    appKit.login.submit
    appKit.error.network

### 4.3 key 规范

使用语义 key，禁止用中文/英文原句当 key：

    home.header.searchPlaceholder
    product.detail.addToCart
    order.status.pendingPayment
    common.action.confirm

命名建议：

    {domain}.{area}.{element}

### 4.4 文案写法

必须使用 ICU 风格参数，禁止拼接：

    order.items: {count, plural, =0 {No items} =1 {1 item} other {# items}}
    order.greeting: Hello, {name}

一期可以先实现最常用子集：变量插值 + plural；select、selectordinal、日期/数字参数后续补。

## 5. 运行时设计

### 5.1 纯核心

packages/common/src/i18n/ 提供：

    lookupMessage(catalog, key, locale): string | undefined
    formatMessage(template, params, locale): string
    formatNumber(value, locale, options?): string
    formatDateTime(value, locale, options?): string

日期格式不要在三端各写一套 yyyy-MM-dd，由 core 统一暴露应用层格式：

    formatDate(iso, locale)      // 中文：2025-06-01；英文：Jun 1, 2025
    formatDateTime(iso, locale)  // 两端的业务展示口径各写一条，不散落

### 5.2 React 胶水

packages/app-kit/src/i18n/ 提供：

    <I18nProvider locale={locale} messages={messages}>
        {children}
    </I18nProvider>

    const { locale, setLocale, t, formatDate } = useI18n()
    const t = useT()

各 app 传入自己的资源包：

    <I18nProvider initialLocale={initialLocale} resources={{ zh-CN: webZhCN, en-US: webEnUS }}>

seller/admin 是 SPA，在 mountSpa 外层包 Provider；web 是 SSR，在 RootDocument 的 shell 层包 Provider。

**web 今天没传 initialLocale**（`__root.tsx` 只传 `resources`）：Provider 首屏保持 `DEFAULT_LOCALE`，挂载后再读 cookie/浏览器语言切换——这样 SSR 与 hydration 的 HTML 一致，代价是海外用户首帧拿到中文。真正的解是服务端解析 locale 再传下来（见 §9 P3），不是把 Provider 挪到客户端。

### 5.3 SSR

web 的 __root.tsx：

- lang 使用当前 Locale
- title、description 从 t() 取
- 不稳定/随机值不要参与 SSR 文案，避免 hydration 不一致
- 一期不用 URL 前缀，但 Locale 仍应由服务端确定后下发，不能客户端渲染后才切 —— **这一条今天不成立**：后端没有 LocaleFilter（§9 P3），web 也没把服务端 locale 传进 Provider，首帧恒为 `DEFAULT_LOCALE`，挂载后才按 cookie/浏览器语言换。换的后果只有一帧文案，不产生 hydration 报错（Provider 刻意这么设计），所以先记成缺口不拦提交；真出海要 SEO 时必须补上

### 5.4 语言切换

新增统一 LocaleSwitcher，行为：

1. 写 cookie
2. 更新 React context
3. 触发页面用新 Locale 重渲染
4. document.documentElement.lang 同步
5. 后续可同步用户资料 / URL

## 7. 请求头与后端

### 7.1 前端请求头

configureSdkClient 已有 contextHeaders 钩子，各 app 直接注入：

    configureSdkClient('', tokenStore, {
        contextHeaders: () => ({
            'Accept-Language': locale,
            'X-Locale': locale,
            'X-Timezone': timezone,
        }),
    })

一期 X-Timezone 可以先不启用；但 Header 名和上下文形状先定好。

今天的实际装配（三端 `configureSdkClient` 各一处）：三端都只发 `Accept-Language` + `X-Locale`，`X-Timezone` 一处都没发；seller 用同一个钩子多带 `X-Shop-Id`。这两个头目前**后端没人读**（§7.2 未落地），发出去只进访问日志，不改变响应语言。

### 7.2 后端 LocaleContext

**整节未落地**（§9 P3）：`infra/web` 下没有 LocaleContext / LocaleFilter，后端不知道请求要什么语言，错误 detail 恒为中文——这正是 §7.3 的 Step 1 先在前端补映射的原因。

在 apps/server/src/main/java/com/shop/platform/infra/web 增加：

- LocaleContext / LocaleContextHolder
- LocaleFilter：解析 X-Locale > Accept-Language > 默认 zh-CN
- WebMvcConfig 注册 Filter
- 请求结束后清理 ThreadLocal
- HttpRequestLoggingInterceptor 的 http.request 事件带 locale

### 7.3 错误文案

一期分两步：

Step 1（推荐先做）：错误码文案前端映射

- docs/error-codes.md 增加 zh-CN 文案、en-US 文案两列 —— **未做**：那张表今天的列是 `Code / HTTP / 谁在读 / 前端行为 / 后端触发场景`，文案只在 TS 侧有一份
- packages/common/src/i18n/error-messages.ts 持有映射 —— **已做**（含单测）
- ApiError 处理时：有 code 且映射存在 -> 用映射；否则回退后端 detail —— **未接**：错误提示今天走 `packages/app-kit/src/notify.ts` 的「detail 优先」，`getErrorMessage` 除单测外没有任何生产调用方，所以英文界面看到的仍是中文 detail。接进错误路径是这一节剩下的一半，做之前别把它算成已完成
- 无 code 的 400/422 先接受中文 detail，但列成已知缺口

Step 2（完整形态）：后端 MessageSource

- apps/server/src/main/resources/i18n/messages.properties / messages_en_US.properties
- GlobalExceptionHandler 使用 MessageSource + LocaleContextHolder
- BusinessException 逐步从 detail 字符串改为 messageKey + args
- 校验消息也走 key
- 这一步完成前，英文界面里的兜底错误仍可能显示中文；一期必须在已知边界中显式记录

错误码不进 OpenAPI 契约，因此补中英文文案不需要 pnpm gen:sdk。

## 8. 动态内容

一期明确不翻译：

- 商品标题、店铺名、公告、UGC、地址等用户数据
- 英文界面仍可能显示中文动态数据

数据模型预留：

    entity_translation(entity_type, entity_id, field, locale, value, status, version)

或 JSONB：name_i18n = {zh-CN: ..., en-US: ...}。

不要新增 name_zh / name_en 这种列；第三种语言会逼迫全表迁移。动态内容翻译是后续独立项目，不阻塞 UI i18n 一期。

## 10. 门禁与验收

### 10.1 校验脚本（今天查什么、跑在哪）

`pnpm i18n:check`（`scripts/i18n-check.mjs`）逐 app 把 `src/locales/{zh-CN,en-US}/*.json` 成对比较，今天查三样：

- 两侧 key 集合相等（缺哪边都报；这一条同时就是「en-US 覆盖率」，没有独立指标）
- 文案里花括号配对——ICU 语法只校到这一层，不解析规则
- 同一个 key 两侧的 `{placeholder}` 集合一致

**没查的**：未使用 key（要扫 `t()` 调用点，脚本没做）、以及「只对新增/改动强制、存量白名单清零」的分级（现在全站一刀切，红了就改）。

**它目前不在 CI 里跑**：`.github/workflows/ci.yml` 没有这一步，所以这道门禁只约束手动执行。挂进 CI 属于新增门禁，等中英资源按 §9 铺到有成衣文件可查时再定——今天只有 `common.json` 一格，CI 上跑与不跑看不出差别。

### 10.2 测试

已覆盖：

- `packages/common/src/i18n/{locale,message}.test.ts`：归一化（`zh_CN` / `zh-Hans-CN` / Accept-Language 权重序）、回退链（en-US → zh-CN → 源语言）、插值、plural 与 select
- `packages/app-kit/src/i18n/locale.test.ts`：cookie 读写（含 `locale` 不被 `locale_backup` 混淆、残缺转义的现状、属性串长什么样）、`navigator.language` 参与回落
- `packages/app-kit/src/i18n/provider.test.tsx`：Provider 首屏按装配侧给的 locale 渲染、切语言、缺 key 回退
- `packages/common/src/i18n/error-messages.test.ts`：错误码 → 中英文文案映射

没覆盖，等相应能力落地再补：

- Provider 的两个副作用（`document.documentElement.lang` 跟着 locale 走、一改 locale 就写 cookie）只在 `locale.test.ts` 单元层各自钉住，没有一条测「渲染后 lang/cookie 确实变了」的断言
- web SSR 的 lang / title / 文案一致性——服务端还没参与 locale 解析（§5.3）
- list/detail 中英文各一条 E2E（`e2e/` 今天只跑下单主路径与发货物流链路）

### 10.3 验收标准

- 中英切换可用，刷新后保持
- 所有新改用户可见文案不再硬编码
- en-US 缺失时回退 zh-CN，不白屏
- API 请求带 Accept-Language / X-Locale
- 已知无 code 的后端错误文案仍可能中文，并在文档中明确
- pnpm lint / pnpm typecheck / pnpm test 全绿

## 11. 反模式

- 用中文/英文原句当 key
- 字符串拼接生成句子
- 组件内写死中文或英文
- 前后端各维护一份错误码文案且无门禁
- 用 zh/en 代替 zh-CN/en-US
- 为两种语言加 name_zh / name_en 列
- 动态内容未翻译却宣称国际化完成
- 缺翻译时静默吞掉或回退为空串
- 直接改 formatMoney 的 CNY 假设来做多币种
