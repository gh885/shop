# 时间事件：过期在哪一刻为真

- **状态**：已落地
- **记录日期**：2026-10-11
- **出现在哪**：订单超时两条规则（待付款关单、发货后自动收货）、售后三条超时窗口（卖家响应 / 买家回寄 / 卖家收货）、账号注销冷静期、优惠券过期（券包展示与收敛任务）；「卖家未发货自动取消」本来也在这条线上，已按「只提醒不代决」拍板移出（见「选了哪个」）

## 背景

「到期」是时间上的事实，状态是库里的行。`pay_expire_at` 过了，库里那行还是「待付款」——这个事实在哪一刻、被谁判为真？是读的每条路径各自比时间，还是后台某个时刻把它写进库？行业里这组选择叫**惰性过期与主动过期**（Redis 文档里是「惰性删除 + 定期删除」）。

它的特征是：**过期的「事实」只有一个，但能读它的地方有很多**——付款闸门、券包列表、对账统计、后台扫描，每个地方都站在不同的时刻读它。判定点不写清楚，同一行就会有两个答案。

本仓库两个域选了相反的答案，而且都是刻意的：**订单信状态列**（付款闸门只看订单状态，不看时间），**券信时间**（`CouponEvaluator` 注释：「可用性以绝对时间为准，直接比 effective_at / expire_at，不看状态列，状态列只是展示投影」）。这条记录把这套不对称讲清楚。

## 方案比较

| 族                           | 方案                                                                                    | 适用                                       | 代价                                                                       |
| ---------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------- |
| **一、读时判（惰性）**       | 1. 消费点各自现算：每次读或动作把 `now ≥ deadline` 折进谓词                             | 无副作用、纯资格（JWT 的 `exp`）           | 每个读点都要记得判，漏一处就有过期实体被当有效；含时间谓词的查询索引不友好 |
|                              | 2. 动作点当闸门现算：变更入口的 `WHERE` 里现场比时间                                    | 状态滞后会让这个动作产出错误结果           | 展示与闸门各判一次，两处口径要同源                                         |
|                              | 3. 判定收进共享 evaluator：全部消费方调同一个方法                                       | 多读点必须同答案                           | 口径收了一处，仍靠调用方记得调                                             |
|                              | 4. 展示态折进 SQL 谓词：列表筛选按「未使用 / 已过期」折算                               | 惰性状态要进分页筛选                       | 每个查询各折一份，折法本身就是口径                                         |
|                              | 5. 交给存储引擎 TTL：Redis 惰性删除 + 定期删除，读不到即过期                            | 验证码、会话这类没有状态列的场景           | 引擎的语义是「键没了」不是「转了状态」；要状态、要通知的消费方接不住       |
| **二、写时判（主动收敛）**   | 6. 到期扫描 + 条件更新：扫描的 `WHERE expire_col <= now()` 就是判定，落点一条语句改状态 | 到期有副作用；状态列要被后续判断与统计消费 | 判定时刻滞后于事实，滞后等于扫描间隔；要调度与逐笔隔离的基建               |
|                              | 7. 逐笔到点定时器：排定时刻即判定时刻                                                   | 要求精确到点                               | 持久化、错过触发、多实例都归调度器（机制见 0004），本仓库零处              |
| **三、两段式（两个都用）**   | 8. 收敛保状态列 + 读路径对未收敛行现算                                                  | 状态列进展示、又要按状态统计               | 同一行两个答案并存，口径必须写死在一处并声明谁管哪段                       |
|                              | 9. 读时顺手收敛：读到过期就刷或删（惰性删除形状）                                       | 容忍只覆盖被访问到的行                     | 读路径带写、并发重复触发；Redis 内部即此形状，本仓库零处                   |
| **四、改口径，让判定点消失** | 10. 到点只提醒不代决：系统不发动作，决定权留给人                                        | 自动动作会误伤（对方其实还想要）           | 提醒要有人接住，无系统动作兜底                                             |
|                              | 11. 状态不落列：读时由事件流加时钟推导（极端惰性）                                      | 状态没有独立消费方、真相全在事件流         | 读要折叠事件，查询与索引全重做；本仓库零处                                 |

## 选了哪个，为什么

**状态流转与副作用走族二的 6；「券能不能用」走族一的 3；券包展示是 8 的两段式；订单里有一处动作点现算的孤例（2）；「卖家未发货」是族四 10 的孤例。**

判据两问，依次问「到期有没有副作用」与「结论的消费方是谁」。

- **有副作用 → 6。** 到期要放库存、要退款、要删号，就必须有一个可重试、可逐笔隔离、可观测的写入来承接，读路径没有地方安放副作用。全仓七条到期线（订单两条规则、售后三条窗口、注销一条、券一条）全落在扫描上：扫描的 `WHERE expire_col < now()` 即判定，落点全是条件更新。
- **结论只被动作消费、且状态滞后会产出错误结果 → 2。** 订单状态动作里唯一的现算闸门是延长确认收货（ORD-63）：service 预检 `deadline.isAfter(now)`，mapper 第四条闸门 `.gt(receive_expire_at, now)`。给一个已过期的截止再加 7 天不是「滞后」而是「救回一个已终结的窗口」，这种点必须现场判；展示侧的 `canExtendReceive` 用同一口径派生。
- **结论被付款、退款、售后消费 → 状态列为唯一答案，读点不许各自现算。** 付款闸门只信订单状态：**刻意接受**「到点后到扫描跑过前（一个扫描周期，30 秒档）超期单仍可支付」这个窗口——让闸门现算时间等于引入第二口径，而窗口内支付的单没有受害者。这个窗口是选的，不是漏的。
- **结论是「此刻能不能用」→ 3，权威只能在读时。** 只有读那一刻知道现在几点。券的可用性判定一律读时比时间，口径收在 CPN-21 一处：结算评估与券包展示共用一个 `timeReason` 方法，注释写死不看状态列。
- **状态列还要进展示与统计 → 8 两段式。** 券包页签按展示态折 SQL（CPN-51）：UNUSED 页签额外排掉 `expire_at <= now` 的行、EXPIRED 页签把「已收敛的」与「还没被刷到的」都收进来；`MyCoupon.displayStatus` 给同一口径的徽章。收敛任务（CPN-41）注释写死「不承担正确性」，它只为状态列可信（对账、统计、索引）服务。
- **族四 10 的孤例是拍板，不是遗漏**：「付款起 3 天未发货自动取消」曾真实存在于订单超时表里（原 SHIP 行），误杀的是买家还想要的单（预售、定制、沟通中缺货），而买家对已付款单本来就有取消退款权（ORD-20）。现在 `ship_expire_at` 只作两侧提醒（买家卡片红字、卖家徽章），不再由系统代做决定（ORD-60）。
- **纯资格、无副作用 → 1 / 2，零扫描。** 售后申请窗口 `apply_expire_at` 是仓内样本：没有扫描方、没有状态列要收敛，申请点经 `OrderAfterSaleView.afterSaleOpenAt` 谓词现算（AFS-01），完成后截止列不再变，判定与动作之间没有竞态。会话与验证码则是 5：键没了就是过期。
- 4 只有券包查询一处；11 零处——状态由事件推要知道「现在几点」才有答案，折叠与索引重做的代价换不来什么，本仓库的账本（流水、轨迹）是补充不是替代。

## 代价

1. 订单 / 售后 / 注销域接受「事实已过期、状态未落」的窗口，最长一个扫描间隔（30 秒 / 30 秒 / 1 小时）。付款闸门不现算时间，窗口内超期单照付。
2. 券域两个答案并存：时间口径（CPN-21）与展示口径（CPN-51）各一处，再开一个读点或再写一份折法，就是第二份口径开始漂移。
3. 收敛任务停摆的含义分域：券停摆只伤状态列（注释写死「不承担正确性」）；订单 / 售后 / 注销停摆是事故——超期单占着冻结库存、售后卡在双方赔付、注销宣泄不了。运维上这三条是时间闸门。
4. 惰性谓词折不进简单查询时必须显式折 SQL（CPN-51 的形态），含时间的条件对索引不友好。
5. 「到点只提醒」意味着有界面、有人要接住提醒，系统不再兜底（全站没有消息通道，前端连「提醒发货」占位按钮都删掉了，ORD-60）。

## 什么时候重新评估

- 窗口被业务嫌长（用户看见倒计时归零而支付仍成功）：把「动作点现算」加回支付闸门，口径就落进券的形状（两个答案并存），要同步建 CPN-21 式的唯一出处。
- 「到点只提醒不代决」出现第三处：把这条口径写进规则文档，别让每处各自解释。
- 券的两段式被抄到第三个域：把「展示态折 SQL」做成共享形状（现在是一处查询加一处 `displayStatus`）。
- 出现大流量、无副作用的到期（临时权益一类）：评估共享 evaluator 或视图统一惰性口径，别让每个读点各判。
