# 前端遥测：多条采集链怎么装配与卸载

- **状态**：已落地
- **记录日期**：2026-10-15
- **出现在哪**：`packages/monitoring/src/{monitor,types,errors,vitals,blank-screen,state}.ts`；三端装配点 `apps/{seller,admin}/src/main.tsx`、`apps/web/src/shared/lib/monitoring.ts`

## 背景

`@shop/monitoring` 里长出了三条并列的采集链：全局错误（未捕获异常 / Promise 拒绝 / 资源加载失败）、Web Vitals、SPA 白屏。它们各自用一个模块级 `let bound = false` 保证「只装一次」，装配则散在三处：web 手动调两次 bind，seller/admin 走 `startSpaMonitoring` 内部替你调，PV 又在 `packages/app-kit/src/shell/spa-entry.tsx` 里单独接一次。

症状是加一条采集链要改三个地方，而且**装了就拆不掉**：`configureMonitoring` 被调第二次时会新建一个 `Transport`、再挂一遍 window 监听与一个 30 秒 `setInterval`，旧的那套连同它的队列一起被孤立，没有任何句柄能取消。web 的装配挂在 `useEffect` 里，dev 下 StrictMode 会把「装两次」变成常态而不是意外。

## 方案比较

| 方案                                           | 适用                                                           | 代价                                                                          |
| ---------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 1. 每端手写装配调用                            | 采集项只有两三个，且各端形态一致                               | 加一项改 N 处；装配顺序与「只装一次」靠每处自己守，漏一处是静默的             |
| 2. 带依赖声明与优先级的插件注册表              | 插件之间有真实的先后依赖，或插件来自包外                       | 要先设计一套依赖解析与拓扑排序；错序的症状同样是静默的，得额外加校验          |
| 3. `Integration[]` + `setup(ctx)` 返回卸载函数 | 采集项彼此并列、产出同一种事件、装配是「一个入口 + 一份列表」  | 插件之间不能互相依赖；跨插件时序只能写进各自的 `setup` 里，靠注释而非类型保住 |
| 4. 构造器注入 / DI 容器                        | 宿主本来就有容器，采集项需要按生命周期作用域（请求级、会话级） | 为一个遥测包引入一套容器与其生命周期概念，收益与它的大小不成比例              |
| 5. 事件总线订阅                                | 宿主已有一条总线，采集项要订阅业务事件而非浏览器事件           | 上报口退化成「谁都能往里塞」，单一出口失效；事件的形状不再由本包定义          |

## 选了哪个，为什么

**3。** 判据一句话：**插件必须能被一个不知道它存在的默认列表装起来，也必须能被调用方按实例摘掉。**

按这条判据，方案 1 直接出局——它没法被默认列表装起来。方案 2 与 5 是「将来真出现依赖或总线时才付得起」的解法，今天付的是纯成本。方案 4 在别处对，但本包的装配是「一个页面一次」，没有作用域可依附。

两处刻意的例外：

1. **传输器（`Transport`）不做插件。** 它只有一个实现、只干一件事：把队列送出去。做成插件就要回答「多个 transport 并存时一个成功一个失败算不算成功」，而今天没有这个需求。它仍由宿主 `monitor.ts` 直接管，但**同样要能卸**——`bindLifecycle` / `startHeartbeat` 因此返回卸载函数（见代价 4）。
2. **PV / 路由事件不做插件。** 它的监听属于 router 的持有者（`packages/app-kit/src/shell/route-tracking.ts` 与三端入口），包内伸手去订阅 router 是错的层。它保持成一个普通导出 `trackRoute`。

默认策略是**全开再裁**：`integrations` 收到默认列表、返回你要的那批。三端差别只在这个 filter 里（web 是 SSR，摘掉白屏）。

## 代价

1. **裁剪键是实例同一性**，不是名字字符串：`(d) => d.filter((i) => i !== blankScreenIntegration)`。所以插件必须导出为**稳定实例**，不能是每次调用新建的工厂，否则 filter 永远不匹配、且不报错。换来的是改名不会让某端的裁剪静默失效。
2. **`web-vitals` 没有退订接口**，库订阅只能「每页一次」，卸载不复位。能卸的只有我们自己挂的那个 `visibilitychange` 监听。所以「重复装配只注册一次」这条语义落在库订阅的标志上，而「卸载干净」只覆盖我们自己的监听。
3. **`dispose()` 只卸载，不 flush，也不重置单例状态。** 不 flush 是因为那会凭空多一条发送路径；不重置是因为 StrictMode 卸载重挂之后，`captureError` / `setMonitoringUser` 这些出口还得继续可用——它们在业务代码里被独立调用，不该随装配的存亡而失效。后果：卸载而未重装时，游离的 `captureError` / `track` 仍按最后一次配置上报。
4. **「transport 不是插件」不代表它没被碰到。** 为了让 teardown 成立，`bindLifecycle` / `startHeartbeat` 的返回类型从 `void` 变成了 `() => void`，并且要在卸载时复位 `listenerBound`。
5. **`setup` 是同步的，没有依赖或优先级声明。** 今天三个插件彼此独立所以够用；代价是将来真出现「B 必须等 A 装完」时，顺序只能靠各自的 `setup` 内部自己保证，类型上表达不出来。

## 什么时候重新评估

- 出现一条真实的**插件间依赖**（不是今天这种「谁先谁后都行」），或需要按顺序保证某条时序时。
- 有**第三方要在本包外发插件**：默认列表今天写死在 `monitor.ts`，那时才需要注册入口。
- 需要**在类型上**强制某端不许装某个插件（而不是靠运行时 filter 摘）：说明三端差异已经大到列表本身不该共用。
- 默认列表超过约八个插件：按实例 filter 的写法会开始难读，届时先考虑按域分几个预设列表，而不是引入优先级系统。
