# adr — 技术决策记录

> 回答「这个问题有几条路、我们走了哪条、为什么、付了什么代价」。一条记录一个**通用技术问题**（并发控制、超时驱动、跨模块读数这类横跨多个业务域的），不是某个业务里的单点取舍。
>
> 边界：**业务规则**（规则是什么）在 [docs/business-rules/](../business-rules/)；**工程约定**（代码怎么写）在 [AGENTS.md](../../AGENTS.md) 与 [docs/conventions/](../conventions/)；**外部调研**在 [docs/reference/](../reference/)。这里只放岔路口：换一条路也能跑，但我们选了这一条，并且说得出为什么。
>
> 命名：目录叫 `adr`（Architecture Decision Record，这类文档的通用叫法）。没沿用 `decisions`——那个名字 2026-09 用过一次，装的是业务规则的论证，已并入 business-rules，同名会撞语义。

## 一条记录怎么写

标题写**问题**，不写技术名（「怎么防止丢失更新」，不是「不用悲观锁」）。五个小节，缺哪个就说明哪件事没想清楚：

| 小节             | 回答什么                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| 背景             | 遇到的是什么现象？特征是什么？不堆术语，要让人认得出自己撞上的是不是它                                     |
| 方案比较         | 这类问题**全部**已知解法，按族分组，每条写适用场景与代价。表里不写我们选了什么，让它保持是一张通用的参考表 |
| 选了哪个，为什么 | 一句判据，再按判据把方案分到采用 / 例外 / 不用；例外要写明条件与处数                                       |
| 代价             | 为这个选择接受了什么。诚实写，别写成优点；已知未守的也写在这里                                             |
| 什么时候重新评估 | 什么信号出现时回来重看。要可核证（「第三个计数型不变式出现」），不写「以后再说」                           |

大结论（比如「为什么没有消息队列」）**不单独成条**——它是多条小记录的共同结论，读者把相关条目摆在一起自己能看出来。
