# 可观测性采集栈：托管还是自建

- **状态**：已落地（本机联调验证；主机上线时启用规则）
- **记录日期**：2026-10-12
- **出现在哪**：`deploy/observability/`（Alloy 配置、看板、告警规则、`.env.example`）、`scripts/obs-cloud-sync.mjs`、production-readiness 监控清单

## 背景

[observability.md](../conventions/observability.md) 把「采集栈」定为上线前置：指标能抓、日志进集中检索、告警能到人。本机最小栈（`pnpm obs:up`）已把指标名、PromQL、告警表达式在真实数据上验过，但它跑在开发机上，不是生产形态。部署目标是一台阿里云 2C / 1.6G 主机，已经承载 PG 与 Redis 容器，再塞 Prometheus + Alertmanager + Grafana + Loki 放不下；告警通知这最后一公里也从未接通过。

## 方案比较

| 方案                                           | 适用                                                                | 代价                                                                                                    |
| ---------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| 1. 自建全家桶上主机                            | 主机有富余、数据要留在自己手里                                      | 1.6G 内存放不下；四个组件各要升级与自我监控                                                             |
| 2. 自建放第二台主机                            | 同上，且愿意多养一台                                                | 多一台机器的钱与运维；监控自己也要被监控                                                                |
| 3. 托管：Grafana Cloud 免费档 + 主机一个 Alloy | 资源受限；现有资产已是 Grafana 形状（PromQL 看板、Prometheus 规则） | 数据出境到托管方（日志 PII 已按契约脱敏）；免费档保留 14 天、指标 1 万活跃序列；告警邮件只能发 org 成员 |
| 4. 国内云托管（阿里云 SLS + ARMS）             | 数据须留境内，或 Grafana Cloud 直连不稳                             | 看板与规则要换一套查询语言重写；两个产品拼接                                                            |

## 选了哪个，为什么

**3：Grafana Cloud 承接指标、日志、告警、看板，主机只跑一个 Alloy。** 判据：现有资产一行不改就能搬过去——5 块看板 JSON 只换数据源 uid，`shop-alerts.yml` 原文经 convert API 导成 Grafana-managed 规则，采集端配置全走环境变量。主机到 Grafana Cloud 的连通性实测可用（东京 region，延迟约 2 秒）。4 留作直连不稳或数据须留境内时的退路。

两条实测约束已写进脚本注释，这里留档：

- **convert API 别传 `X-Grafana-Alerting-Folder-UID`**：它被当父目录，再用 YAML 里的命名空间建子目录，规则落到 `Shop/Shop`。只用命名空间（= 文件夹标题）即可。
- **一条规则里别混异构标签集**：`increase(...) == 0 or absent(...)` 两支同时为真时，`absent` 支的标签是其它序列的子集；导入后补的表达式链用 `||` 按标签连接，子集会和每条序列都配上，产出重复标签集，告警实例创建失败（Normal (Error)）。拆成两条规则各自齐整。Prometheus 原生告警没有这个问题，所以本机栈此前从未暴露。

工程口径：云端是仓库的只读副本（规则 provisioned、UI 不可编辑），改仓库、重跑 `pnpm obs:cloud:sync`；主机上线前规则保持 `--pause`，否则本机采集一停，`absent()` 类规则会按设计空叫。

## 代价

1. 数据在托管方：日志 PII 边界靠 [frontend-monitoring.md](../conventions/frontend-monitoring.md) 契约 5 与 `maskPhone` 守，不靠网络隔离。
2. 免费档上限是硬边界：14 天保留、1 万活跃序列。「指标标签只许有界枚举」的契约因此更不能破。
3. 告警只能发给 org 成员邮箱：换收件人要先邀请进 org。

## 什么时候重新评估

- 出现第二个服务进程或 MQ：要链路追踪时先看 Grafana Cloud 的 Tempo（也在免费档内），不是回头自建。
- 数据必须留境内，或主机到 Grafana Cloud 直连持续不稳（本机联调验证时延迟约 2 秒，可用）：走方案 4。
- 指标活跃序列逼近 1 万或日志逼近 50GB/月：先查标签基数是否破了契约，再谈升档。
