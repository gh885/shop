# 并发控制：怎么防止写偏斜

- **状态**：已落地
- **记录日期**：2026-10-11
- **出现在哪**：末位超管保护、下单恶拍闸门、收藏 / 加购 / 库存行 / 轨迹节点 / 类目属性值的幂等插入、物流异常单去重；三个软上限（买家地址 / 商家地址 / 购物车条数）刻意不守

## 背景

写偏斜是两个事务各读一个**共享前提**，各改**不同的行**，各自提交后前提被破坏。「还有两个在岗超管」→ 两个事务各禁用一个不同的 → 零个在岗。「查无同款收藏」→ 两个请求各插一条 → 两条。

它和丢失更新的本质区别：**碰的不是同一行**，所以条件更新、行锁这些行级手段全部失效。更麻烦的是它常涉及**还不存在的行**（幻影）——「查无同款」那个「无」没有行可锁。

## 方案比较

| 族                                   | 方案                                                                   | 适用                                   | 代价                                                           |
| ------------------------------------ | ---------------------------------------------------------------------- | -------------------------------------- | -------------------------------------------------------------- |
| **一、让数据库声明式地守不变式**     | 1. 唯一约束 + `ON CONFLICT`（`DO NOTHING` 或 `DO UPDATE … RETURNING`） | 唯一性、互斥                           | 守卫住在索引里，入口校验必须与之等价否则 500                   |
|                                      | 2. `CHECK` 约束                                                        | 单行内不变式                           | 守不了跨行，不是写偏斜的解法                                   |
|                                      | 3. 排他约束 `EXCLUDE`（gist）                                          | 时间段不重叠、区间互斥                 | 要 gist 索引                                                   |
|                                      | 4. 触发器里数聚合                                                      | 想把计数放进库                         | **陷阱**：触发器看的是同一快照，不加锁它自己也写偏斜           |
| **二、把跨行不变式折成一个可锁的点** | 5. 咨询锁：按逻辑键串行化这段                                          | 计数 ≥ N 这类聚合                      | 整段串行；必须在事务内调；键全局唯一                           |
|                                      | 6. 物化冲突：建一行代表这个不变式，`FOR UPDATE` 锁它                   | 同 5                                   | 多一张表只为锁                                                 |
|                                      | 7. 把聚合反范式成一行计数，`WHERE count > 1` 做 CAS                    | 同 5                                   | 计数要同事务维护；它把写偏斜转成丢失更新                       |
| **三、数据库侦测**                   | 8. `SERIALIZABLE`（PG SSI）侦测读写依赖环，中止一方                    | 任意写偏斜                             | 中止落在哪方是随机的，必须有重试基建；热路径 500；全局开代价大 |
| **四、悲观锁所读的行**               | 9. `SELECT … FOR UPDATE` 锁住决策所读的全部行                          | 行都已存在                             | 互相锁对方的行凑成死锁；**幻影锁不住**，唯一性场景根本用不了   |
| **五、架构 / 业务**                  | 10. 按键串行化（单执行者）                                             | 治理类低频动作                         | 要路由基建                                                     |
|                                      | 11. 提交后校验 + 补偿                                                  | 能容忍短暂破坏                         | 窗口期不变式已破，最终一致味                                   |
|                                      | 12. 改业务规则消灭不变式（如固定一个不可禁用的 root 超管）             | 不变式本身可商量                       | 改产品规则                                                     |
|                                      | 13. 插入后 catch `DuplicateKeyException`                               | 冲突即整体回滚、**不需在同一事务回读** | PG 一报唯一冲突整个事务 aborted（25P02），catch 后回读执行不到 |

## 选了哪个，为什么

**族一的 1 是主力；5 守两个硬的计数型不变式（末位超管、下单恶拍闸门）；三个软上限先查后插、接受并发超一两条；13 只放行一处。**

判据：**不变式能不能用数据库约束声明出来。**

- 能（唯一性 / 互斥）→ 1。全仓 34 条唯一索引，`ON CONFLICT` 5 处（cart / favorite / sku_stock / tracking_node / 类目属性值）。守卫住在索引里，零应用代码，并发由数据库在行锁下合并。要不要回读决定分支：`DO NOTHING` 不回读（sku_stock 建行、轨迹去重），`DO UPDATE … RETURNING` 要回读（收藏、加购、属性值）。
- 不能且是**硬**不变式 → 5。两处：末位超管（`StaffMapper.lockSuperAdminGovernance`，全局一把锁，人点的低频动作）；下单恶拍闸门（`OrderMapper.lockCheckoutGate`，按 userId 取锁只串本人的结算——它是防刷闸门，而写偏斜恰好只在有人并发刷时出现，不锁它就在该起作用时失效）。否决 8：无重试基建、热路径 500、为两处开全局不值。否决 6：多一张表只为锁。否决 7：一个计数要同事务维护，为两处不值。否决 9：死锁 + 幻影。
- 不能且是**软**上限 → 先 count 后 insert，接受。买家地址 20、商家地址、购物车 99 三处：并发下会超出一两条，后果是多存一条地址，不值一把锁。软硬的分界是「超出去会不会伤到别人、或被当成攻击面」。
- 13 只在「冲突即回滚、不回读」的形状下放行一处（`ShipmentIssueService`，实体插入要 id 自动填充用不了 `ON CONFLICT`，而异常逃出方法即整体回滚、下一单不受影响）。其余地方一律 1，原因是 25P02。
- 2 用在单行不变式上（`min_price <= max_price`），3、4、10、11、12 零处。

## 代价

1. 唯一索引是**第二道闸**，入口校验必须与它等价，入口更松的那几个字符是 500。
2. `DO UPDATE` 分支要写幂等的 `SET`，有时是空操作只为拿 `RETURNING`（favorite 的 `SET product_id = EXCLUDED.product_id`），读起来别扭。
3. 咨询锁与计数必须成对出现在同一个私有出口里，否则新增调用点会忘记取锁。
4. **刻意不守**：一单可能有多条 PENDING 支付流水（并发发起各插一条）。资金不变式是「一单一 SUCCESS」，由部分唯一索引 `uk_payments_order_success` 守着，第二条去 confirm 时条件转移过不了闸、整单回滚；多出的 PENDING 只是账面噪音。要收拾它得加 `WHERE status = 'PENDING'` 的部分唯一索引 + `ON CONFLICT DO NOTHING`。
5. **三个软上限不守**：买家地址、商家地址、购物车条数都是先 count 后 insert，并发会超一两条，接受。
6. 撞唯一索引必须包 `DuplicateKeys.conflictOnDuplicate` 折成 409：`GlobalExceptionHandler` 不映射 `DuplicateKeyException`，漏包就是 500（`AddressService.setDefault` 曾漏，审视时补上）。

## 什么时候重新评估

- 硬的计数型不变式到第三个（现在两个）：重新比较 5、7、8。咨询锁抄到第三份时，SERIALIZABLE + 一套重试可能反而便宜。
- 某个软上限变硬（地址条数成了收费档位、购物车上限成了反爬口径）：那一条从「接受」改成 5。
- 出现「时间段不重叠」类不变式：上 3。
- 支付 PENDING 唯一性要真守：按代价第 4 条补索引。
- 出现第二处想 catch `DuplicateKeyException`：先回答「冲突后要不要在同一事务里继续」，要就必须用 1。
