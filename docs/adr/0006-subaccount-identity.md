# 卖家子账号：身份怎么承载

- **状态**：已落地（阶段一；阶段二「操作日志」未做）
- **记录日期**：2026-10-13
- **出现在哪**：`account.shop_subaccounts`（V75）、`account/service/SubaccountService`、`infra/security/SubaccountAuthFilter`、`shop/service/ShopSubaccountService`、`apps/seller/src/shared/lib/session-kind.ts`
- **相关**：业务规则 [ACC-10 ~ ACC-14](../business-rules/account.md)、授权矩阵 [§二/§七](../conventions/authorization-matrix.md)、路线图 [subaccount-rework-plan.md](../subaccount-rework-plan.md)

## 背景

卖家侧要给店员开账号干活（看订单、发货、改商品），但**不能给他店主的能力**，也不该把他私人的买家账号卷进工作关系里。原先的形态是「子账号 = 一个普通买家账号（手机号即身份）+ 一条 `shop_members` 关系」：店主按手机号邀请 → 对方用自己的账号登录后确认。它跑得通，但暴露出三件事：

1. **身份粘连**：店员的工作身份就是他私人的买家账号。店主移除他之后，他仍持有那个账号的一切；反过来，他被平台封号、注销、换手机号，工作侧全部受影响。企业客户的真实诉求是「员工离职就交回工作身份」，而不是「从我的店里摘掉一个私人账号」。
2. **建号必须双方在场**：邀请得等对方登录确认。店主想批量开号、或者员工还没注册过任何账号时，这条路走不通（未注册手机号直接被拒）。
3. **留痕落不到人**：订单流水上只有「卖家」这个角色，没有「哪个店员」。而这恰恰是店主最需要的（谁把价改错了）。

## 方案比较

| 方案                               | 适用                                                | 代价                                                                                                                               |
| ---------------------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 1. 统一账号 + 成员关系（原形态）   | 开放平台 / 一个自然人跨多个商户；身份本来就属于个人 | 工作身份与私人身份不可分离；建号要双方在场；留痕只到角色粒度；权限模型只能挂在关系行上                                             |
| 2. 独立子账号凭证（商店自己发号）  | 企业内部用工；工作身份由雇主开设与收回              | 需要一套独立的凭证/激活/找回体系；同一自然人可能在平台上有两个互不相认的身份；店主成了员工手机号的持有者（要按个保法最小必要处理） |
| 3. 复用平台员工体系（staff）       | 平台自营 / 代运营                                   | 平台员工的权限是平台级的，按店隔离要另造一层；员工体系的口径（工号、岗位）与店员的「岗位由店主定义」根本不是一回事                 |
| 4. 单点登录到企业 IdP（SAML/OIDC） | 有 IT 部门的中大型商户                              | 要接外部身份提供方、要处理 IdP 下线/换供应商；中小商户没有 IdP                                                                     |

## 选了哪个，为什么

**2：独立子账号凭证**（拍板 2026-10-13）。判据是「工作身份必须能被雇主单方面开设与收回，且留痕到人」——方案 1 三条症状是同一件事的三个面，都源自身份属于个人。具体形状：

- **凭证行自带店铺**：`account.shop_subaccounts` 有 `shop_id`，登录后工作店铺就确定了，不需要也不允许客户端用 `X-Shop-Id` 指定（带了别家店的直接 403）。
- **第三种认证主体**：JWT `kind=subaccount` 与 `user` / `staff` 并列，只在 `/seller/**` 与 `/auth/subaccount/**` 生效（ACC-25）。这样「店员登不进买家端」不是靠配置，而是身份模型本身的性质。
- **激活锚点是手机号**：店主建号时填员工手机号，员工首次登录用**本人**手机号收码验证（同店一号一账号）。手机号是平台既有的身份锚点（与买家同一套信任模型），**不发也不存身份证号**。
- **停用与移除分开**：停用 = 保留凭证、下一请求即失效、可解冻（离职交接期）；移除 = 删行、登录名与号占位释放。
- **登录名不拼店名**：淘宝那个 `店铺名:子账号名` 的形状在这里是坑——店名在 ACC-74 的重提流程里可改，登录名跟着漂等于员工下次登不上。

方案 1 留作将来开放平台（一个自然人服务多个商户）的形态：那时「身份属于个人」重新成立，这条决策就该重看。

## 代价

- **同一个自然人有两份互不相认的身份**：他是某店的店员，同时可能是买家。两边手机号相同、主体不同，平台不打通（打通就意味着工作行为能关联到私人购买记录）。
- **店主持有员工手机号**：这是个保法意义上的个人信息处理，按最小必要做——列表恒掩码、明文逐条索取并留痕（ACC-79）。
- **一套新的凭证生命周期**：登录名唯一性、口令策略、激活状态机、refresh 会话第三只 cookie（ACC-21）都要自己维护；子账号没有短信自助找回，忘了口令只能店主重置——把找回这件事的权威留在雇主侧是刻意的，代价是店主成了单点。
- **成员表被掏空**：`shop_members` 只剩 OWNER 行，`MemberStatus.PENDING` / `MemberRole.MEMBER` 成了历史档（表不物理删、历史行读得出，但没有生产者）。权限码从关系行搬到了凭证行，跨模块读它要走 `account::api`。
- **前端多一个会话语义**：同一浏览器可以有「买家/店主」与「子账号」两份会话并存，前端必须知道自己当前是哪一种（`session-kind` 标记）才能选对 refresh 端点与是否注入 `X-Shop-Id`。
- **未做**：操作日志（阶段二，店主查「谁干了啥」）。今天留痕仍只在少数显式动作上（取号码明文、评价回复带 operator）。订单状态流水 `orders.order_status_log` 只有 `actor_type`（BUYER/SELLER/SYSTEM）、**没有操作人 id**，所以阶段二不是「加个查询出口」，要加列或另起表。

## 什么时候重新评估

- 出现**开放平台**诉求（一个自然人需要服务多家商户、且身份由他自己持有）时——那正是方案 1 重新成立的条件。
- 出现**企业 IdP** 诉求（商户要求用自家账号体系登录、员工离职在 IdP 侧统一处理）时——方案 4 会变成更省事的那条路。
- 子账号数量级跨过一个量级（几十人/店）时重看两件事：登录名是否需要命名空间、以及店主手工建号是否还够用（可能要批量导入）。
