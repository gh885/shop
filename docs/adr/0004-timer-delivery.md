# 时间事件：到点的转移由谁驱动

- **状态**：已落地
- **记录日期**：2026-10-11
- **出现在哪**：全部八个 `@Scheduled` 作业——三条 30 秒时间闸门（订单超时、售后超时、outbox 重投）、注销冷静期 1 小时、券过期收敛 10 分钟、轨迹轮询 5 分钟（轮预算 60 秒）、物流异常扫描 1 小时、对账探针（每日 03:15）

## 背景

0003 定了「到点由后台收敛」。但「到点」还要让一段代码在那个时刻被叫醒。行业里的时钟有几个来源：业务库（轮询扫描）、消息系统（延时消息、延迟队列）、进程内（定时器、时间轮）、工作流引擎（持久化定时器）。失效模式各有名字：**错过触发（misfire）、重复触发、重启丢失、第二个真相源**。

选哪边，取决于把「到点」当成什么：一次投递（丢了要专门处理），还是一次对账（这轮没成，下一轮自然再来）。

## 方案比较

| 族                              | 方案                                                                 | 适用                             | 代价                                                                                                 |
| ------------------------------- | -------------------------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **一、业务库当时钟**            | 1. 到期扫描：到期列部分索引 + 按同一列升序 LIMIT + 落点条件更新      | 状态在库里、要幂等、多实例无所谓 | 收敛延迟上界等于扫描间隔；空扫成本随表增长                                                           |
|                                 | 2. 扫描加定点唤醒：`pg_cron` 定点拉起 / `LISTEN/NOTIFY` 即时叫一轮   | 想压延迟又不想引第二个真相源     | 通知掉线即丢、扫描兜底照留；多一个依赖                                                               |
| **二、消息系统当时钟**          | 3. 延时消息：RocketMQ 定时消息 / RabbitMQ TTL 加死信（Kafka 无原生） | 到点动作与库不同机、量大削峰     | 第二个真相源：行提前消失（取消、已支付）消息仍在途，消费点照样回库做条件更新让位；丢消息仍要扫描兜底 |
|                                 | 4. 延迟队列：Redis ZSET 按到期时刻做 score                           | 轻量、已有 Redis                 | 正确性不押 Redis（闸门与账本不进缓存，ACC-43 口径）；重建丢到期索引；失败重投自建                    |
| **三、进程内定时器**            | 5. `DelayQueue` / 时间轮 / `ScheduledExecutor`                       | 丢了也无所谓的缓存式到期         | 重启全丢；多实例各排一份；正确性不能押内存                                                           |
| **四、持久化定时器 / 外部调度** | 6. 工作流引擎 durable timer（Temporal / Camunda）                    | 定时器是流程第一公民的长流程     | 为几条超时线引一整套引擎与运维；状态机在库里，引擎只管一半就是第二个真相源                           |
|                                 | 7. 外部调度器拉起同一条扫描（k8s CronJob / XXL-Job / systemd timer） | 调度要集中治理、要选主           | 多一层部署依赖；扫描本身仍要幂等，正确性工作一分没省                                                 |

## 选了哪个，为什么

**族一的到期扫描，八条线共用一个形状：扫描全集靠部分索引、落点全是条件更新、逐笔隔离走 `Sweep`；不加分布式锁，不引入延时消息与引擎。**

判据一句话：**递送机制的正确性需求，能不能被「重扫即重试」吸收。** 三个结构性理由全是从「扫描是幂等的对账」长出来的：

- **重扫即重试，所以「错过触发」不存在**：某轮抛异常（`Sweep` 逐笔隔离只丢那一笔）、进程重启、整轮被慢任务挤掉，都不会把哪一行弄丢——下一轮同批继续扫，卡住的行天然还在队首。没有 misfire 处理、没有死信队列、没有重试计数。售后让位后的自愈就是这个形状：订单的到期条件一直在，售后落到终态后同一轮扫描把它补上（AFS-43）。
- **单一真相源**：「何时到期」只有一处事实，业务行上的 `expire_*` 列加部分索引；没有第二份到期索引需要和取消、支付、发货同步。
- **多实例免锁**：落点全是条件更新，谁抢到算谁的，抢不到返回 false 让位；正确性不依赖锁，`OrderTimeoutService` 注释里连升级路都写好了（等空扫真影响负载再上 `pg_try_advisory_xact_lock`）。

其余不选：

- 3、4 替不掉扫描。行会提前消失（买家取消、支付成功、卖家提前处理），消息到点时消费方还是得回库做条件更新让位，它买到的只是「延迟从 30 秒压到秒级」，而业务窗口是分钟（支付）到天级（售后、券），这个精度用不上；代价却是第二个真相源加丢消息时照样留扫描兜底。等出现秒级窗口诉求再评估（0003 的重新评估第一条同时生效）。
- 5：重启全丢、多实例重复，正确性不能押内存；本仓库唯一的进程内时间用法是调度器本身。
- 6、7：状态机在库里，引擎与外部调度器打理不到它，引进来正确性一分不省（落点还是条件更新），多出来的是部署与运维。等到点动作出进程（外呼、跨服务编排）时再比较。

工程口径：全部作业共用一个 4 线程调度池（`CallerRunsPolicy`、`MdcTaskDecorator` 给链路起点）；扫描间隔与业务窗口配对——30 秒对分钟级时间闸门、10 分钟对天级券窗口、1 小时对注销与异常扫描、每日对账探针。两个刻意例外：`TrackingPollJob`（外呼非幂等，自带 60 秒轮预算，与扫描的钩子不同形）、`ShipmentIssueService`（要把 `DuplicateKeyException` 折成「已登记」的正常路径，通用 catch 会把它误判成失败）。

## 代价

1. 收敛延迟上界等于扫描间隔，间隔是语义参数不是性能旋钮：它等于「事实与状态之间允许的最大滞后」。改业务窗口要重新配对（与 0003 代价 1 是同一条约束的两面）。
2. 空扫成本随表增长：靠部分索引压小扫描全集、批上限防长事务（订单与售后同为 100，由 `SweepTest` 核对；注销 20 笔刻意更小——毁灭性动作宁可分批慢做）；表大了要监控扫批耗时。
3. 没有「到点精确触发」这回事：一切动作最早发生在下一轮，且积压时容差按批线性拉长——一条线每轮只处理一批，到期行超过批上限就排到后面几轮，真实滞后是「间隔 × 积压批数」。拍卖式秒级语义不适用这套形状。
4. 八条线挤一个 4 线程池：外呼型慢任务一轮能占几分钟，新增此类任务必须自带预算闸门（`TrackingPollJob` 的 `ROUND_BUDGET` 是先例）。
5. 多实例部署时重复空扫（正确性无碍、负载翻倍）——今天单实例，写下来当已知。
6. 逐笔隔离必须走 `Sweep`，两条例外各有理由；新增扫描线先判是否属于例外类，否则一律走它。

## 什么时候重新评估

- 出现秒级窗口诉求（倒计时精确关单）：延时消息或延迟队列上桌，扫描降为兜底；正确性仍押条件更新。
- 空扫真影响库负载：按代码注释的既定升级路上 `pg_try_advisory_xact_lock`，或按线分池。
- 作业数与慢任务把共享池挤爆：分池，或上外部调度（此时重评 7）。
- 到点动作出进程（外呼、跨服务）：按 `TrackingPollJob` 形状扩展，或重评 6。
