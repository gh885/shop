# 物流 / 运费

> 代码入口：apps/server/.../logistics、shop（运费模板）；apps/seller/shipping、apps/web/logistics。规则以代码为准沉淀，改代码请同步本文件。

## 一、发货与订单联动

- **[LOG-01]** 卖家发货入口为 `POST /seller/shipments`（授权 ORDER_FULFILL），一次提交「字典承运商 code + 运单号」，同事务落一个包裹并推进订单；shopId 取自店铺上下文（X-Shop-Id），前端不传店 ID。
- **[LOG-02]** 可发货的订单状态只有 PAID（首次发货）与 SHIPPED（追加包裹），已取消/已完成发货被拒；归属校验先于状态校验——非本店订单一律 404「订单不存在」（不泄露存在性），状态不可发给 409「订单当前状态不可发货」。发货与订单推进同事务、原子：包裹落不下则订单不推进，订单推不进（并发抢不到状态）则包裹回滚，绝不出现「有包裹但订单还是待发货」；并发抢不到状态时同样给 409「订单状态已变更，当前不可发货」。
- **[LOG-03]** 首次发货经 `markShipped` 在同一事务内推进订单并回填 `shipped_at` 与 `receive_expire_at`（= 发货时刻 + 7 天），同时落一条审计流水（动作 SHIP、操作者 SELLER）；追加包裹不产生状态转移、不落流水。
- **[LOG-04]** 订单上的发货时刻与收货窗口属于首次发货：`shipped_at` / `receive_expire_at` 用 COALESCE 只回填一次，追加包裹不得把它们往后推；但订单的物流摘要投影 `logistics_company` / `tracking_no` 每次发货都刷新为最新包裹。
- **[LOG-06]** 发货硬要求店铺已配置「默认发货地址」（未删且 ACTIVE）：没有就 400「请先设置默认发货地址」，不猜地址；发货时把寄件人（联系人/电话/省市区/详址/公司名）作为快照定格在包裹上（`ship_from_*` 七列），不再写回订单。
- **[LOG-07]** 卖家路径承运商必须给字典 code，没有名字兜底：code 不存在给 400「快递公司不存在」，存在但已停用给 400「该快递公司已停用」；入参层 code 与运单号均必填（运单号 ≤64 字符）。
- **[LOG-73]** 付款后卖家发货窗口为 3 天：订单 `ship_expire_at` = 支付时刻 + 3 天，到期仍未发货由订单侧自动取消并退款（超时关单归订单，发货入口只受此时限约束）。

## 二、包裹模型与轨迹状态投影

- **[LOG-09]** 包裹（shipment）= 一次发货一行，方向只有 FORWARD（卖家发买家）/ RETURN（买家退货回寄）两值；一单可多包裹（拆包/分批发），正向与逆向共用同一张表、同一查询与展示路径，靠 direction 列区分。
- **[LOG-10]** 运单号全局唯一：一个运单号只属于一个订单/包裹（`uk_shipments_tracking_no`）。卖家发货撞号报「该运单号已录入，请核对后重试」，买家回寄撞号报「该运单号已被使用，请核对后重填」。
- **[LOG-11]** 包裹状态机七态：PENDING_PICKUP(10) → PICKED_UP(20) → IN_TRANSIT(30) → DELIVERING(40) → DELIVERED(50)，另有 RETURNED(60) 与 EXCEPTION(rank 0)。状态是轨迹节点的投影，没有任何直接 setStatus 入口。
- **[LOG-12]** 状态只单调前进：推进用 `sourcesOf(target)` 反推合法前态做条件更新（WHERE status IN (…)），乱序/迟到/重推的旧节点只落库不改状态；已签收不会被后来的「运输中」覆盖。
- **[LOG-13]** EXCEPTION 是过程态不是分支：它既是任意前向状态的合法前态（异常处理完可继续派送），也接受任意非终态进入；两个终态 DELIVERED / RETURNED 不可回退（无更大目标态可达）。
- **[LOG-14]** 节点码 → 状态的映射是唯一推导入口（`TrackingNodeCode.status()`）：PICKED_UP→已揽收；ARRIVED_HUB / DEPARTED_HUB→运输中；OUT_FOR_DELIVERY→派送中；DELIVERED→已签收；RETURNED→已退回；EXCEPTION→异常。多码对一态刻意为之——「轨迹要细、状态要粗」。承运商原始状态码在接入边界翻译后即丢弃，不进领域。
- **[LOG-15]** 轨迹节点 append-only（只插不改、无 updated_at）；同一包裹 + 同一节点码 + 同一时刻 + 同一地点 = 同一条事实，由 `dedupe_key` 唯一索引 + ON CONFLICT DO NOTHING 去重，重复录入幂等返回（不报错、不增行、状态不动）。去重不依赖推送方 message id（重推会换 id）。
- **[LOG-16]** 轨迹排序与状态推进以承运商事件发生时刻 `occurred_at` 为准，不取落库时间；查询返回按事件时刻正序（id 兜同刻），迟到补推的旧节点按自己的时刻归位。

## 三、签收与确认收货联动

- **[LOG-17]** 签收（DELIVERED）是唯一牵动订单的节点：包裹推进到 DELIVERED 时同事务回填 `shipments.delivered_at`，并经 `OrderCommand.markDelivered` 把订单确认收货窗口从签收时刻重算（`receive_expire_at = 签收时刻 + 7 天`）。
- **[LOG-18]** 签收对订单的写回只认「状态 SHIPPED 且 delivered_at 为空」：重复签收、已取消/已完成的单是无副作用的幂等返回，迟到节点不会二次重算收货窗口。
- **[LOG-19]** 确认收货窗口 7 天双起算：发货时按发货时刻先铺兜底（物流迟迟不签收单不悬着），签收后改从签收时刻起算——用户看到「签收后还有 7 天」，到期自动确认收货。

## 四、轨迹接入（推送 / 轮询 / 人工补录）

- **[LOG-20]** 轨迹归一化优先级：细粒度描述文本关键词 > 粗状态码兜底；两者都判不出则跳过该节点不猜（宁少一条轨迹，不猜错状态——单调推进后不可回退）。关键词表顺序即优先级，「派送/派件」必须排在「签收」之前（否则「派送中，预计今日签收」被误判为签收）。
- **[LOG-21]** 文本关键词 → 节点码：派送/派件→OUT_FOR_DELIVERY；退回→RETURNED；拒收/问题件/滞留→EXCEPTION；签收→DELIVERED；揽收/已收件→PICKED_UP；到达→ARRIVED_HUB；离开/发出→DEPARTED_HUB。粗状态兜底（快递鸟 State 口径）：1→揽收、2/5/6→到达分拨、3→签收、4→异常、7→退回。
- **[LOG-22]** 承运商推送入口 `POST /logistics/webhooks/{carrierCode}` 匿名可达，安全完全靠验签（requestData+appKey 摘要、对原文做摘要、`MessageDigest.isEqual` 比较）；未配置密钥时一律 403（fail-close，没验签不落库）。
- **[LOG-23]** 推送按运单号匹配包裹（不看方向）；找不到包裹静默成功（记日志返回 200）——报错只会让对方反复重推一个永远处理不了的报文。
- **[LOG-24]** 轮询兜底任务每 5 分钟扫一轮：候选 = 未到终态（含 RETURN）且最后一条节点（无节点则发货时刻）早于 6 小时的包裹，单轮上限 50 个；网关未配置密钥时任务直接空转返回。包裹无承运商 code（老数据手填未归一成功）时跳过不拉。
- **[LOG-25]** 推送与轮询共用同一条落库路径（`TrackingSyncService.record` → `TrackingService.recordNode`），去重与单调推进只有一份规则；单条节点失败不影响其余，整批拉取失败只记日志等下一轮。
- **[LOG-26]** 平台运营可经 `POST /admin/logistics/shipments/{id}/tracking-nodes`（权限 LOGISTICS_MANAGE）人工补录轨迹节点，与 webhook 落同一个 service 入口；补录重复节点同样幂等跳过。这是长期能力（承运商漏扫、推送丢失、纠错），不是临时通道。

## 五、承运商字典

- **[LOG-27]** 承运商字典 8 家种子（迁移注释误写「七家」）：SF 顺丰速运 / ZTO 中通快递 / YTO 圆通速递 / STO 申通快递 / YD 韵达快递 / JD 京东物流 / JT 极兔速递 / EMS 邮政EMS；code 全局唯一，是稳定标识（对接物流商用），name 是展示名。
- **[LOG-28]** 承运商停用只影响「以后可选」：发货下拉只给 enabled=TRUE、按 sort_no 升序；历史包裹不受影响（包裹上 code 指身份、name 是发货时刻展示快照，承运商改名不改写历史单据）。
- **[LOG-29]** 承运商名归一口径全入口统一：能对上字典就用字典名，对不上保留原文（卖家发货只传 code；买家回寄可手填名字，按 name 反查字典、命中归一、未命中留原文且 code 为空）。字典名反查按 sort_no 取第一条、LIMIT 1。

## 六、物流异常治理

- **[LOG-30]** 异常判定只看时间、不依赖承运商推「异常」：以最后一条轨迹节点时刻（无节点则发货时刻）距今是否超阈为准，可离线复算、可调阈值重扫。
- **[LOG-31]** 三类异常与阈值：PICKUP_TIMEOUT = 停在 PENDING_PICKUP 超 24 小时未揽收；TRANSIT_STALLED = 停在 PICKED_UP/IN_TRANSIT 超 48 小时无中转动态；DELIVERY_STALLED = 停在 DELIVERING 超 24 小时未派送成功。
- **[LOG-32]** 异常扫描每 1 小时一轮，单类单轮上限 200 单；只扫正向包裹（RETURN 卡住由售后流程自己跟进，混进来会淹没物流异常列表）。
- **[LOG-33]** 同一包裹同一类异常同时至多一张未结单（部分唯一索引，重复扫描静默跳过）；未结单是客服待办，按发现时间倒序列出。
- **[LOG-34]** 包裹到终态（DELIVERED/RETURNED）时其全部未结异常单同事务自动结单；客服手动结单：单不存在 404、已结 409「异常单已处理，无需重复操作」——不静默成功；系统不提供「手动触发重扫」入口（该改的是阈值不是加按钮）。
- **[LOG-35]** 异常单 detail 是人话（类型描述 + 最后动态时刻 + 已停滞小时数），客服可直接念给买家听。

## 七、买家物流轨迹查询与展示

- **[LOG-36]** 买家查轨迹走 `GET /orders/{id}/tracking`（需登录），按包裹自身 user_id 过归属闸：未发货、无包裹、越权访问同为 404「暂无物流信息」，同一话术。
- **[LOG-37]** 出参是订单级包裹列表（一单多包裹常态）：排序 = direction 升序（正向在前、逆向在后）再按发货先后；首个正向包裹即订单物流摘要口径。出参不含包裹主键、userId/shopId、去重键等治理字段；状态/节点只给标准词表枚举，中文名由前端词表投影。
- **[LOG-38]** 每个轨迹节点同时吐后端推导的粗粒度 `status`（节点码→状态映射的唯一真相在后端），避免前端复制一份会漂移的映射表。
- **[LOG-39]** 买家侧时间轴按「相邻同状态分段」（到达/离开分拨同属运输中段），节点新→旧排列；同一状态被打断会再分段，段 key 带下标。订单侧事件（已下单=createdAt、已发货=shippedAt）只并进首个正向包裹的轴尾，无数据源的环节（如「仓库处理中」）不造假节点。
- **[LOG-40]** 买家展示词表：PENDING_PICKUP=等待揽收 / PICKED_UP=已揽件 / IN_TRANSIT=运输中 / DELIVERING=派送中 / DELIVERED=已签收 / RETURNED=已退回 / EXCEPTION=物流异常；节点无描述时兜底文案（如「快件已到达」）。EXCEPTION 与 RETURNED 按异常红色分级。
- **[LOG-41]** 折叠规则：收起态按轴序保留最新 2 条节点（跨段计），段结构保留；全局仅轴顶一条高亮。节点时间文案「MM-dd HH:mm」，跨年补年份。摘要卡收件人脱敏：手机号 195\*\*\*\*1956（前 3 后 4），姓名保留首字（张三→张\*\*），位数不足原样不伪造掩码。
- **[LOG-42]** 逆向包裹在买家轴上标题改称「退货物流」；承运商条不提供联系电话与 logo（契约里没有的数据源，不编造），运单号可一键复制。
- **[LOG-43]** 前端把「未发货 404」视为业务事实而非错误：查询层归零为 null，页面只剩「有轨迹/没有轨迹」两态，其余错误不重试即时暴露。

## 八、运费模板与配置（卖家）

- **[LOG-44]** 运费模板是店铺对外的计费合同：每店至多一份生效模板（`uk_shipping_templates_shop`，软删后可重建）；端点只有 GET/PUT `/seller/shipping-template`（权限 SHIPPING_MANAGE），保存为覆盖式整份提交——模板+规则+区域+不配送一次事务全重建，没有多模板/逐条 CRUD。
- **[LOG-45]** 计费方式只有按件一维（首件价+续件价），不做按重量/体积、不做多运送方式（对齐淘宝但砍掉其渠道定价包袱）；列名把单位写进名字（first_quantity），要加按重时新增 valuation 列。运费计价口径是「同店合计件数」，不是按行。
- **[LOG-46]** 一档运费 = 首件标准 firstQuantity 件收 firstFee，超出部分每满 addQuantity 件加一个 addFee，不足一档按一档（向上取整）；firstQuantity/addQuantity ≥ 1，firstFee/addFee ≥ 0，全链路 Money、一期币种恒 CNY（DB CHECK 钉死）。
- **[LOG-47]** 模板必须恰有一条默认规则（is_default 唯一索引兜底，区域未命中任何指定地区规则时用它）；默认规则缺失即数据损坏，装配时响亮失败而非静默按包邮算。
- **[LOG-48]** 区域规则：指定地区规则 = 一档运费 + 若干国标区划码前缀（省 2 位/市 4 位/区县 6 位，入参正则 `\d{2}|\d{4}|\d{6}`）；指定地区模板规则至多 50 条、不配送地区至多 100 个前缀。
- **[LOG-49]** 保存校验：前缀必须落在国标区划码空间（RegionRegistry），无效即拒；同一前缀不得配两条计费规则（否则「最长前缀胜」变掷骰子）；同一前缀已配收费规则不得再设为不配送，但更细粒度的不配送合法（如广东省计费、深圳市不配送）。
- **[LOG-50]** 整店包邮（freeShipping=TRUE，对齐淘宝 assumer=1）开启时，满件/满额门槛被服务端抹掉为 NULL（死配置不落库）；默认规则与指定地区规则数据仍保留在库中，关闭包邮后可继续使用。
- **[LOG-51]** 未设的包邮门槛存 NULL 而不是 0（0 元门槛=「满 0 元包邮」，语义不同）；模板与每档规则自带币种列，报价用自己的币种，不借订单的。
- **[LOG-52]** 卖家侧表单校验（先于后端）：首件/续件必须 ≥1 整数、费用 ≥0 金额、指定地区规则必须先选地区、同一区划码不得配两条规则或兼设不配送；满件/满额门槛仅在不包邮时提交。

## 九、运费计费与不配送

- **[LOG-53]** 计费判定次序固定：不配送优先于一切（包邮条件救不了送不到）→ 模板级包邮优先于逐地区定价 → 指定地区规则按「最长前缀胜」取（6 位区县 > 4 位市 > 2 位省，同时命中广东省与深圳市取深圳市）→ 都不命中回落默认规则。
- **[LOG-54]** 不配送命中时运费报 0 且 deliverable=false——「送不到」与「送得到但贵（偏远加价）」是两个问题，不许用极大运费哨兵值混在一起。
- **[LOG-55]** 店铺从未配置模板 → 恒包邮（报价 templateId=null、运费 0）：模板是后上线能力，拒绝下单等于锁死存量店铺；订单落库时模板快照列留 NULL，语义=没走计费。
- **[LOG-56]** 报价入参的收货区码取收货地址快照的国标区划码，缺失即 400「收货地区不能为空」；商品额币种与模板币种不一致即 400。
- **[LOG-57]** 计费是纯函数口径（模板+规则+区域装配成 ShippingPricing 后只吃区码/件数/金额），运费错误代价高于多一个 record；ShippingPricing 内嵌实体不得越过 HTTP 边界，出参经 ShippingTemplateResponse 逐层转换。

## 十、包邮门槛

- **[LOG-58]** 三条包邮判定（任一命中即运费 0，币种跟模板）：整店包邮；满件包邮——同店合计件数 ≥ freeOverQuantity；满额包邮——同店商品总额 ≥ freeOverAmount（Money.atLeast，恰好等于门槛算够）。
- **[LOG-59]** 满额包邮的基数是「优惠前、运费外的同店商品总额」：运费是待求结果不能拿它判条件（循环）；券后也不丢包邮——运费先按优惠前金额算、券在运费之后才减。满件基数为同店合计件数。

## 十一、结算时运费入单

- **[LOG-60]** 结算按店铺分组即拆单预告：一个店铺一份模板一份运费，随分组一起定格；预览与下单共用同一次计算（防「预览一个价、下单另一个价」）。
- **[LOG-62]** 下单硬闸：任一店铺分组 deliverable=false 即整单拒绝「部分商品不支持配送到所选地区，请更换收货地址」——预览页拦不住脚本直接下单。
- **[LOG-63]** 下单把计费证据快照进订单：`shipping_template_id`（按哪份模板收的）+ `receiver_region_code`（计费依据的区划码，名字匹配不可靠、国标码才是比对的键）；事后改模板不影响历史订单追溯，两列是运费争议翻证材料。
- **[LOG-64]** 结算预览允许未选地址：此时运费预告为 0、不判配送（地区未知算不出运费），该预告不可当成交口径；真实下单必须走带地址的路径。

## 十二、退货回寄（逆向）

- **[LOG-65]** 买家回寄仅存在于「退货退款」售后单处于 RETURNING 时：填写承运商 + 运单号，经 `ReturnShipmentCommand.replace` 同事务落一条 direction=RETURN 的包裹（首次提交等同 `record`，重复提交覆盖更新——见 LOG-72）；售后单上的 return_logistics_company / return_tracking_no 两列降级为投影（写回归一后的字典名），轨迹真相在 logistics。
- **[LOG-66]** 回寄包裹起步状态是 PICKED_UP（不是 PENDING_PICKUP）：买家填单号时货已交承运商；它不填面单寄件人（回寄面单是买家线下填的，平台没有也不该有这份数据；买家收货地址在订单快照里，不再复制）。
- **[LOG-67]** 回寄入口承运商口径：字典 code 可空（买家可能只知道名字），但手填公司名与运单号必填（≤50 / ≤64 字符）；给了 code 必须命中字典且启用（400），没给则按名字回查字典归一、匹配不上原样记录。归一后「同一家顺丰」只有一种写法。
- **[LOG-68]** 逆向复用正向的一切接入：承运商推送按运单号匹配（不看方向）、轮询扫描会扫它（未到终态即可）、买家「查看物流」两个方向一起返回；但异常停滞扫描不扫它（只看 FORWARD）。
- **[LOG-72]** 买家重复提交回寄（改运单号、换快递）是**覆盖更新**（C10）：`ReturnShipmentCommand.replace` 同事务删除本订单旧的 RETURN 包裹**及其轨迹节点**后再 `record` 新建，一单同一时刻至多一张有效回寄包裹——售后卡与物流页只见最新一条，旧单号的迟到推送不会串挂到新包裹上；重交同一运单号也不撞唯一索引（先删后插同事务）。删除重建而不是原地改号/作废标记：作废要动状态 CHECK 迁移；原地改号会让旧单号已落的轨迹节点挂在换了身份的包裹上、状态投影无法单调重算。与「一单可多包裹」不冲突：多条语义只属于正向拆包，逆向是「当前在途的这一张」。本条取代旧口径「每次提交新增一条、不覆盖，历史多条展示/对账口径未定」（未定即无既有消费方，历史遗留多条不迁移，下一次覆盖提交自然收敛）。

## 十三、卖家发货弹窗（前端）

- **[LOG-70]** 发货弹窗 = 承运商字典下拉 + 运单号输入，只传 code 不传名字（展示名后端按字典归一）；承运商下拉加载失败可就地重试，字典为空提示「暂无可选快递公司，请联系平台维护字典」。
- **[LOG-71]** 弹窗提交前校验：未选承运商「请选择快递公司」、运单号空「请填写运单号」；运单号提交前 trim；弹窗每次打开重置表单（组件实例复用）。发货成功走 createShipment（201 无返回体）。
