# 店铺 / 账号 / 权限

> 代码入口：apps/server/.../shop、account、infra/security；apps/web（auth/address）、apps/admin。规则以代码为准沉淀，改代码请同步本文件。

## 一、店铺（开店 / 状态 / 资料）

- **[ACC-01]** 任何已登录的统一账号用户（account.users，手机号即身份）都可开店，无需额外资格；开店即建店并自动进入待审核态 `PENDING_REVIEW`，平台审核通过才 `ACTIVE`。**一人一店**（拍板）：开店时该用户在 `shop_members` 已持有 ≥1 条 OWNER 记录即拒（400 + code `SHOP_LIMIT_EXCEEDED`）；判定口径取 OWNER 行数（与授权同源，不看 `shops.owner_id` 冗余列），被拒/被封的店仍占名额（店铺不物理删除、无释放通道）；**子账号不占名额**——它是 `account.shop_subaccounts` 里的凭证行、不是成员行，「一人一店」只数 OWNER 行（子账号见 §三）。
- **[ACC-02]** 店名必填、trim 后最长 50 字符（DB `VARCHAR(50)`）；**店名全平台唯一**：被任一既有店铺（含待审/被拒/被封——不看状态）占用即拒（400 + code `SHOP_NAME_TAKEN`），并发由唯一索引 `uk_shops_name`（V61）兜底成同一 400；logoKey 可选、最长 255。
- **[ACC-03]** 开店是同事务三写：建店（PENDING_REVIEW）+ 店主自动成为本店 `OWNER` 角色、`ACTIVE` 状态的成员 + 入队一条 `PENDING` 审核记录；授权判断以 `shop_members` 为准，`shops.owner_id` 只是冗余并存。这张表只写得出 OWNER 行——子账号的绑定与授权码住在 `account.shop_subaccounts`（§三），不在这里。
- **[ACC-04]** 店铺状态机：`PENDING_REVIEW → ACTIVE / REJECTED`；`REJECTED →（卖家补材料原地重提）PENDING_REVIEW`（ACC-74）；`ACTIVE ⇄ DISABLED`（枚举含 4 态：PENDING_REVIEW / ACTIVE / REJECTED / DISABLED）；唯一可营业态是 ACTIVE（谓词 `ShopStatus.isActive()`），不做物理删除。状态一旦进入不可营业（驳回/禁用），推进与「全店在架商品级联下架」同事务发生，见 ACC-72。
- **[ACC-05]** 买家侧公开查看店铺（`GET /api/shops/{id}`，匿名可达）只对 `ACTIVE` 店铺返回；待审核/被拒/封禁的店一律 404「店铺不存在」，不泄露"存在但不可用"。公开出参仅 id/店名/logoKey/createdAt。这份读进 Redis 缓存（`shop:public`，按店铺 id）：只有 ACTIVE 行会入缓存——404 是抛异常而异常不入缓存，所以「审核通过」不需要失效；反向离开 ACTIVE 的两条路径（店主注销的连带停营业 ACC-76、平台封店 ACC-60）都显式 evict（不清就等于封了店还能被买家读到一整个 TTL；缓存口径见 apps/server/AGENTS.md「读缓存」）。
- **[ACC-06]** 卖家侧接口（`/seller/**`）必须携带 `X-Shop-Id` 头，缺失或非法（非 UUID）→ 403「缺少店铺上下文」；店铺必须存在且状态为 `PENDING_REVIEW` 或 `ACTIVE` 才放行（REJECTED/DISABLED 不可经营，403「店铺不存在或不可用」）；当前用户必须是该店 `ACTIVE` 成员，否则 403「你不是该店铺成员」。产物接口的 shopId 一律取过滤器装载的上下文，不信任请求体/参数里的 shopId。**放行经营 ≠ 放行成交**：待审店能备货建商品，但买家侧交易只认 ACTIVE（ACC-05 店页 404 + ACC-72 交易闸），商品上架了也卖不出去。
- **[ACC-07]** 「是卖家」= 在 `shop.shop_members` 有 ACTIVE 的 OWNER 记录（本表在子账号改造后只剩店主行，不再有 MEMBER 行）。一人一店下「我的店铺列表」至多一家，新店在前；**子账号不在这个列表里**——它有自己的登录入口与自述端点（`GET /auth/subaccount/me` 返回自带店铺，见 §三），`/shops/mine` 对子账号令牌直接 401。
- **[ACC-72]** 店铺停止营业的级联与交易闸（拍板）：
    - **级联下架**：审核驳回（及将来任何进入不可营业态）在店铺状态推进的**同一事务**发布 `shop::events` 的 `ShopTradingSuspendedEvent(shopId, reason)`，product 侧同步 `@EventListener` 一条条件 UPDATE 把该店全部 `PUBLISHED` 商品置 `WAREHOUSE`——店都不能营业了，架上留着只让买家点得进买不下。只动在架：草稿与「仓库中」的商品原样不动；不逐个走 `ProductService#off`（那条路径带 X-Shop-Id 归属校验与读-改-写，卖家语境专用）。**反向不自动回上架**：恢复 ACTIVE 不发布事件也不补逻辑——恢复营业 ≠ 平台背书这批历史商品仍满足上架门槛，卖家自己在后台重上、重上时复检（`off` 已收为包内方法，级联不借用）。
    - **交易闸**：买家侧成交路径逐店校验营业态——加购（按商品所属店）与下单（本单任一家店）在其余闸门之后过 `ShopReadQuery.isActive`，非 ACTIVE 一律 **409「店铺已停止营业」（不带 code）**：不是入参非法（400），是资源当前状态不允许这笔操作，前端只需按 status 分支。结算预览**不查**（预览不是成交，见 ORD 侧口径）。加购这道闸兜的是「车里已有条目 + 店刚好停了」的并发窗口——级联下架已让第 1 步「商品已下架」先挡下多数情况。
    - **依赖口径**：`ShopReadQuery.isActive` 是 shop :: api 里唯一「按状态过滤」的读出口，只吐 boolean、`ShopStatus` 词表不外泄给 cart/order；给布尔而不是抛异常，是因为它同时服务「拒绝成交」与「列表灰显」两种消费。`DISABLED` 的写入方目前只有一个：店主注销时的连带停营业（ACC-76，走同一个事件）。立约不变：**将来任何让店进入不可营业态的入口必须发布同一个事件**，否则级联漏一处即静默失守。
- **[ACC-74]** 被驳回的店铺可以**原地重新提交审核**（卖家自助，对标「资质补齐再来」）：`POST /shops/{shopId}/resubmit`，入参与开店同形状（复用 `CreateShopRequest`，不另立 DTO）。
    - **谁能提**：只有该店 `OWNER`（复用 ACC-12 的 `requireOwner`，外人 403）；**能提的只有当前态 = REJECTED 这一格**——待审的店已经在队列里、ACTIVE 店无需重审、被封的店要等平台解封（ACC-60，卖家侧无自助路），三者一律 409「只有审核未通过的店铺可以重新提交」。
    - **改什么**：店名与 logoKey 按提交值整体覆盖，改名重新过全局唯一闸（本店自己那行不算冲突：`existsOtherNamed` 带 `id <> ?`；并发撞 `uk_shops_name` 兜成同一个 400 `SHOP_NAME_TAKEN`）。
    - **怎么落**：条件更新（`WHERE status = REJECTED`）是并发真相——预检与写之间被并发的重提/审核抢先则影响 0 行 → 409「店铺状态已变化，请刷新后重试」；成功后同事务再入队一条 `PENDING` 审核记录，**上一轮那条 REJECTED 留痕不动**（一店多条 review 是常态，审核员看到的仍是完整历史链）。
    - **为什么不释放名额再开一家**：一人一店数的是 OWNER 身份（ACC-01），被拒的店仍占名额；只放开名额等于让卖家丢掉店名占位与已上传 logo，也让平台丢掉上一轮审核记录。原地重提把「补材料」留在同一行店铺上，代价只是队列多一条 PENDING。
    - **重提不复活营业**：驳回时全店在架商品已级联下架（ACC-72），这次重提只把店推回 `PENDING_REVIEW`；即便日后审核通过也只到 ACTIVE，商品仍要卖家自己重新上架（ACC-72 反向刻意不回上架）。
    - **驳回理由下发**：`ShopResponse.rejectReason`（可空）= 该店 REJECTED 行里 `decidedAt` 最新那条的 reason，**只在店铺当前状态为 REJECTED 时装配**（已通过/已封禁的店不挂历史批注）；`reason` 为空则不下发，前端不显示空标题。这只出现在卖家侧 `/shops`，买家侧 `PublicShopResponse`（ACC-05）字段另有一只，不受影响。
- **[ACC-60]** 平台侧店铺治理 = 封店 / 解封（`POST /admin/shops/{id}/suspend` 与 `/resume`，两端同 `SHOP_GOVERNANCE`，均 204 空体），与入驻审核（ACC-08/ACC-09 的 `/admin/reviews`）**分端分职**：审核判「这店能不能开张」，治理判「已经开张的店要不要继续营业」——后果不同、入口不同，不并进同一个队列页。列表 `GET /admin/shops` 同码授权，状态档位 + 关键字（店名或店主 ID，非 UUID 当没匹配上而不是 400）可组合筛选，固定「最新在前」。
    - **封店与驳回共用同一条下架出口**：`ShopMapper.suspend` 是只推 ACTIVE 行的条件更新（`WHERE status = ACTIVE`），成功后在**同一事务**发布 `ShopTradingSuspendedEvent(shopId, "PLATFORM_SUSPEND")` 触发全店在架商品级联下架（ACC-72 的立约：判据是「店不营业了」，不是「谁让它不营业的」）——因此级联下架不可能只被一条路径实现；原因串区分得开（店主注销那条是 `OWNER_DELETED`，审计里看得出是哪条路封的）。同事务再 evict `shop:public`（ACC-05），否则封完店买家侧还能读到缓存里的营业态。
    - **状态码口径**：先判存在性（查无此店 404「店铺不存在」），再判档位——缺席与「不是营业中」是两件事，混成一句话就没法回答「这家店到底存不存在」。封店的档位判据**只有**条件更新（`WHERE status = ACTIVE` 影响 0 行即非营业中），一律 **409**「只有营业中的店铺才能封店，请刷新后重试」，不静默成功：「我封了但其实没封」是治理事故。解封先显式判档位（当前态不是 `DISABLED` → **400**「只有已封停的店铺才能解封」，因为这里要说的不是「你抢输了」而是「这一档压根不该解」），随后条件更新 0 行才给 409「店铺状态已变化，请刷新后重试」。
    - **解封只解 `DISABLED` 一档且带两道闸**：① `REJECTED` 是审核驳回，解它等于替审核员翻案；② **店主账号必须仍可用**（`UserReadQuery.isActive`）——`DISABLED` 也由店主注销连带产生（ACC-76），给一个已注销的人的店解封等于平台替他复活一个他已放弃的店，这一条回 400「店主账号已注销或被禁用，无法解封该店铺」，注销与禁用共用同一句话（调用方只需知道「这店不该被恢复」，不需要知道为什么）。
    - **解封不自动重上架**：下架期间商品可能改了价、换了图，「恢复营业」与「恢复在架」是两件事，平台只做前者，卖家自己重新上架并复检（ACC-72 同一取舍）。审计 detail 里明写 `products_relisted=否`，免得事后查账以为商品跟着回来了。
    - **留痕**：封店/解封各落一行操作审计账本（动作 `SHOP_TRADING_SUSPENDED` / `SHOP_TRADING_RESUMED`，带店名与店主 id，GEN-65），与状态推进同事务。被封的店**没有卖家自助路**：ACC-74 的重提只认 REJECTED 那一格，封停只能由平台自己解。
    - **前端**：admin「商家 → 店铺治理」页（侧栏入口按 `SHOP_GOVERNANCE` 裁剪，ACC-58）行内按钮按档位给——`ACTIVE` 才出「封店」（destructive 二次确认，文案点名「在架商品一并下架、解封不会自动重上架」），`DISABLED` 才出「解封」，其余档位显示「不可封店 / 不可解封」灰字而不是一个注定 409 的按钮；成功后失效本页列表缓存。

## 二、店铺审核（平台侧）

- **[ACC-08]** 审核队列 `GET /admin/reviews` 需 `SHOP_REVIEW` 权限（岗位 REVIEWER / SUPER_ADMIN）；列表按 status 筛选分页，PENDING 优先、新店在前；出参拼装店名与店主手机号（跨 schema 按 ID 两步查，禁止 JOIN）。
- **[ACC-09]** 仅 `PENDING` 的审核记录可被处置，重复审核报错「该店铺已审核，请刷新列表」；通过 → 店铺转 `ACTIVE`，拒绝 → 转 `REJECTED` 且理由必填（≤255 字符）；审批留痕（审批员工 ID、理由、decidedAt）与店铺状态推进同事务原子生效。**驳回的副作用链不止改状态**：同事务发布 `ShopTradingSuspendedEvent` 触发全店在架商品级联下架（ACC-72），且这家店继续占着店主的「一人一店」名额（ACC-01）——卖家自助「重开一家店」无路，自助路是原地重提（ACC-74）。已处置的审核记录本身不翻案（不做二次开放、不改写历史行），但被驳回的店可由卖家补材料重新入队一条 PENDING（ACC-74）。处置落一条业务事件 `shop_review.decided`（GEN-50）。

## 三、店铺子账号（独立凭证）

> 子账号**不是**买家账号的变体：它是第三种认证主体（JWT `kind=subaccount`），凭证行在 `account.shop_subaccounts`，
> 有登录名、口令与绑定手机号，与 `account.users` 的手机号账号体系互不相认。店主那条「邀请 → 对方确认」的
> 成员关系已整体退场（2026-10-13 拍板）：店与子账号的绑定写在凭证行上，`shop.shop_members` 只剩开店写入的
> OWNER 行（一人一店的名额与店铺归属）。

- **[ACC-10]** 子账号是两段式：店主建号（登录名 + 初始口令 + 员工手机号，落 `PENDING_ACTIVATION`）→ 员工在卖家登录页用**本人手机号**收码验证（`POST /auth/subaccount/activate`）→ 置 `ACTIVE` 并当场签发会话（激活即登录）。未激活的账登不进：口令登录返回 403 + code `SUBACCOUNT_NOT_ACTIVATED`（这一档必须让前端能分辨，否则员工不知道自己该去激活）。**建号不发短信**：发码入口 `POST /auth/subaccount/sms-code` 由员工自己触发，要求「登录名 + 手机号 + 待激活态」三者同时命中，任一不匹配回同一句 400——这个入口匿名可达，分话术就成了登录名枚举器；它还要先过图形验证码（与买家发码共用 `GET /auth/captcha`）。**身份证不入库**（拍板）：平台的身份锚点本来就是手机号（与买家同一套信任模型），存身份证号是敏感个人信息、合规成本远大于收益；激活时记 `verified_at` 作追责锚点，实名认证留到「追责到自然人」成为硬需求时再接三方认证。
- **[ACC-11]** 建号规则：登录名**全局唯一**（`uk_shop_subaccounts_login_name`）且**不拼店名**——淘宝那个 `店铺名:子账号名` 的形状在这里是坑，店名可改（ACC-74），登录名跟着店名漂等于员工下次就登不上；形状 `^[A-Za-z0-9_-]+$`、4~50 字（粘贴错一个空格就是「登录名明明对却登不上」）。手机号必须是大陆号（要收得到激活码）且**同店一个号至多一个子账号**（`uk_shop_subaccounts_shop_phone`，含未激活与已停用）。初始口令过与买家/员工同一套 `PasswordPolicy`。并发撞唯一索引时 service 回读判定撞的是哪一格，给与预检同一句话（400）。
- **[ACC-12]** 店主专属操作（均需 `isActiveOwner`，否则 403「只有店主可以执行该操作」）：建号、列表、调整权限（全量替换）、停用/启用、重置口令、移除、取号码明文。列表手机号**一律掩码**（店主不是子账号本人，没有「自己那行」），明文走 `POST /shops/{shopId}/subaccounts/{subaccountId}/phone` 逐条索取并留痕（`shop_subaccount.phone_revealed`）；别店的子账号与不存在的行同为 404「子账号不存在」。**子账号自己进不了这组端点**：`/shops/**` 只吃用户令牌（店主），子账号令牌在那里是「类型错误」401——管理面与工作面是两套身份。
- **[ACC-13]** 停用 / 启用 / 移除三分（拍板）：**停用**（`PATCH /shops/{shopId}/subaccounts/{id}/status {enabled:false}`）= 保留凭证、下一请求即失效（判权每请求查库、不吃缓存，refresh 链同样重查状态）、可解冻；**启用**把没验过号的行放回 `PENDING_ACTIVATION`（不能让「启用」变成绕过手机验证的后门），验过号的回 `ACTIVE`；**移除** = 删行，凭证不复存在、登录名与手机号占位一并释放。三者都是条件更新，影响 0 行即 409「子账号状态已变化，请刷新后重试」。停用刻意**不吊销 refresh token**：员工禁用要同步吊销是因为员工 access 活 8 小时，而子账号 access 只活 10 分钟、且每个请求都重查状态，停用下一请求就生效。**子账号没有短信自助找回**：忘了口令只能店主重置（重置与自助改密都会吊销该子账号全部设备会话，与 ACC-24 同一后果）。
- **[ACC-14]** 子账号可授予的权限码白名单只有 5 个：`PRODUCT_MANAGE / ORDER_FULFILL / ADDRESS_MANAGE / SHIPPING_MANAGE / COUPON_MANAGE`；`MEMBER_MANAGE / SHOP_MANAGE` 为 OWNER 固有、不入可授予集合（防子账号自我提权）。归口 `common.SellerGrants`（两个实施点共一份：店铺侧的管理端点与账号侧的建号/改权命令）。入参经 sanitize：null/空 → 空集（最小权限默认值）、去重保序、白名单外或 null 元素 → 400「包含不可授予的权限码」。权限码以 jsonb 数组存 `account.shop_subaccounts.permissions`，默认 `[]`；店主通配不落此列。
- **[ACC-79]** 「卖家自己的号」同样按 ORD-62 的口径处理，批量出参一律掩码、明文逐条索取且取用留痕（个保法最小必要不因「这是自己人」而豁免；号码掩码的唯一后端出口仍是 `PhoneNumber.mask()`，GEN-51）：
    - **平台审核队列**：`GET /admin/reviews` 的 `ownerPhone` 恒为掩码（前 3 后 4，查不到号时是 `****` 而不是 null——契约上不留「有时是明文」的缝）。要打电话核实资质走 `POST /admin/reviews/{id}/owner-phone`，落业务事件 `shop_review.owner_phone_revealed`（`review_id/shop_id/staff_id`，号码本身不入日志，GEN-50）。审核记录/店铺/店主账号任一缺席同为 404，不给「存在但拿不到号」的中间态。做成独立动作端点而不是把明文塞回队列，是为了让「看号码」在契约上就是一个动作。
    - **店铺子账号列表**：`GET /shops/{shopId}/subaccounts` 里号码一律掩码（店主不是子账号本人，没有「自己那行」）；要拨号走 `POST /shops/{shopId}/subaccounts/{subaccountId}/phone`，落 `shop_subaccount.phone_revealed`（`shop_id/subaccount_id/operator_id`）。闸门是店主专属，别店的子账号与不存在的行同为 404「子账号不存在」——不泄露「这个 id 是不是别家店的」。
    - **前端只有一个索取入口**：三处掩码列（卖家订单列表的买家号、店铺子账号列表的号、平台审核队列的店主号）共用 `@shop/ui-web` 的 `MaskedValueCell`，`****` 这道「还能不能索取」的判断因此只有一份。它管三件事：明文行不再给入口、**索取中那个按钮必须禁用**（一次索取 = 后端一条取用记录，连点就是凭空多几条审计记录）、给了 `subject`（收件人 / 店名）时可访问名要说得出是谁的号，没给（子账号列表那种只有号码的行）时靠这一格显示的号码本身分——一屏十个都叫「查看」的按钮读屏分不出来，而每一次索取都在后端留一条取用记录，认错行不是「多看一眼」。写回明文这件事仍在各页自己的 mutation 里（就地改列表缓存那一行、不失效列表，ORD-62 ②），组件只管显示与按住。
    - 已知边界同 ORD-62：索取没有频次闸门，脚本刷全量号码今天仍然可行，只是每一笔都留得下痕；闸门随消息/客服体系或隐私面单一起补。

## 四、认证与令牌（买家）

- **[ACC-15]** 买家账号 = 手机号（全局唯一，唯一索引 `idx_users_phone` 兜底），无角色字段；短信验证码登录即注册：首次登录自动建号，状态固定 `ACTIVE`、密码为 NULL（可后补）。并发撞唯一索引时回读对方插入的账号幂等。
- **[ACC-16]** 登录/刷新/下单统一账号闸门：`UserStatus` 只有 ACTIVE/DISABLED 两态，非 ACTIVE 一律 403 + code `USER_DISABLED`；禁用账号不能借短信通道绕过（短信登录同样校验）。刷新链路同样校验账号状态：禁用账号的旧 refresh 已被消费、新码不签发——「封号」自动等效「吊销全部会话」（买家与员工同规则）。账号不做物理删除：**「不删行」不等于「不注销」**——注销是另一个轴（`deleted_at` + 匿名化，见 ACC-75），封号与注销共用「非 ACTIVE 即失去全部资格」这一道闸门，但只有注销会把个人信息清掉。登录族被这道闸门拦下时先记 `auth.login.failed reason=disabled`（带 `user_id` + `client_ip`）再抛 403——封号之后还在试登录，是要能查到的事；刷新链路的闸门不回记，那里没有"有人在试"这个主体动作。
- **[ACC-17]** 密码登录防枚举：对外失败文案恒为「手机号或密码错误」（无此用户/未设密码/密码错误三分支只进 `auth.login.failed` 事件，`reason` ∈ user_not_found / no_password / wrong_password，GEN-49）；用户不存在或未设密码时对合法 dummy BCrypt 哈希白算一次补齐耗时；被限流时同样跑 dummy hash 且返回与登录失败一模一样的响应（不告知"被限流"）——响应不区分，事件区分（`reason=rate_limited`）。已移除 `PASSWORD_NOT_SET` 错误码。
- **[ACC-18]** 密码登录限流双维度：IP 10 次/60 秒、手机号 5 次/600 秒（Redis 固定窗口 INCR，超限任一即拒）；登录成功清除两侧计数。
- **[ACC-19]** 双 token：access = ES256 JWT，含 `type=access`、`kind=user|staff|subaccount`、jti/iss(`shop-platform`)/aud(`shop-api`) claim；买家 access 寿命 10 分钟（600_000ms），平台员工 access 寿命独立 8 小时（28_800_000ms），**子账号沿用 C 端那一档 10 分钟**（它「停用即时生效」靠判权每请求查库，不靠令牌短命，短命只是顺带把离职后旧 access 还能用多久压到最小）。refresh = 不透明随机串（前缀 `rt:` + 32 字节随机 hex），寿命 7 天；有效期权威是 Redis TTL，cookie maxAge 只是展示层。
- **[ACC-20]** refresh token 只在服务端存 HMAC-SHA256(pepper, token) 摘要不落明文；pepper 配置于 `shop.security.pepper`，生产必须 ≥32 字符（过短启动失败），未配置降级为临时值并告警（重启即在途凭证失效，为何这样降级见 ACC-73）。响应体刻意不序列化 refreshToken（TokenPair `@JsonIgnore`），只经 httpOnly cookie 下发。
- **[ACC-21]** refresh cookie 属性：httpOnly + Secure + SameSite=Lax，`name=refresh_token`、path 收窄到 `/auth/refresh`、maxAge 7 天；管理端独立 `name=staff_refresh_token`、path=`/admin/auth/refresh`、不设 domain；**子账号再独立一只** `name=subaccount_refresh_token`、path=`/auth/subaccount/refresh`（第三套会话不能与前两只互相覆盖）。买家 refresh 端点入站双来源（Cookie 优先、Body 兜底），两者皆无 → 401 `INVALID_TOKEN`；admin 端只认 cookie。入参 deviceId 缺省（无 body 或未带）归入 `"default"` 桶——注意它只是**提交值**，最终生效的设备身份以 token 绑定为准（ACC-63），`"default"` 只在反查不到绑定时才真正落账。
- **[ACC-22]** refresh 一次一换（rotation，Redis GETDEL 原子消费）+ 重放裁决：已消费过的 refresh 再现，15 秒宽限期内按多标签页并发竞争处理（401 无 code，detail「登录状态正在其他页面刷新，请稍后重试」，不吊销）；超宽限期判定盗用 → 吊销该主体全部设备会话，410 + code `REFRESH_TOKEN_REUSED`。消费痕迹 TTL 30 分钟。轮换成功记 `auth.token.refreshed`（`user_id`）而不是复用 `auth.login.succeeded`：续期与登录是两件事，合成一条就把「续期」计成「登录」，登录量与注册漏斗一起失真（签发令牌的 `issueTokens` 是两条路径的汇合点，事件因此打在各自入口，不打在汇合点）。
- **[ACC-24]** 改密（setPassword）与重置密码（resetPassword）成功后一律吊销该用户全部设备的 refresh token（全端下线），并记 `auth.password.changed`（`via` ∈ self / reset_code——同一个事件名区分两条路径，GEN-49）；**子账号同理**（店主重置与自助改密都吊销该子账号全部设备会话）。重置密码对不存在的手机号静默成功（不暴露账号存在性），**也因此不记这条事件**：没有账号被改，凭空记一次换密等于在审计里造一个不存在的人。普通登出只吊销当前 deviceId；提供登出单设备与 logout-all。
- **[ACC-25]** 双 token 域隔离（三套主体各一条链）：`kind=staff` 的 token 只能在 `/admin/**` 链路生效（StaffAuthFilter），`kind=subaccount` 的只能在 `/seller/**` 与 `/auth/subaccount/**` 生效（SubaccountAuthFilter），买家链路（JwtAuthFilter）两者都拒——子账号令牌打 `/orders`、`/cart` 一律 401「Token 类型错误」；反之用户令牌进不了管理端，员工令牌也进不了卖家链。**子账号在 `/seller/**` 上与店主令牌共存**：子账号链先跑，命中就在请求上打标记让用户链让位，两种身份不会同时装载。kinds 校验失败统一 401 `INVALID_TOKEN`。校验顺序：Bearer 头 → 验签 → type=access → kind → audience → 过期（`TOKEN_EXPIRED`）。access 无黑名单：改密后旧 access 最多再存活其剩余寿命（≤10 分钟），为已接受的取舍。
- **[ACC-26]** 匿名可达面（skipPaths 前缀匹配）：商品/Feed/类目/店铺/.cms 浏览、`/auth/captcha|sms-code|login/*|refresh|forgot-password|reset-password`、**`/auth/subaccount`（子账号的登录/刷新/激活/发码四格；me、登出、改密不在此列，它们吃子账号令牌）**、`/admin`（走员工链）、物流 webhook（靠报文签名，未配密钥一律 403 不 fail-open）、actuator 与 OpenAPI 文档。购物车/下单等买家写接口不豁免，需登录。非法（非规范）路径统一 400「非法请求路径」，不给绕过前缀判断留缝。
- **[ACC-27]** 买家/卖家共享会话（轻量单点登录）：web 与 seller 共用同一账号与同一 `refresh_token` cookie，生产配 `shop.auth.refresh-cookie-domain`（如 `.example.com`）后登录一处另一处自动登录；本地留空不共享。admin 不纳入共享。共享只解决身份不解决权限——卖家侧能操作什么完全由 X-Shop-Id + 成员关系在服务端裁决。**子账号是这条的刻意例外**：它的 refresh 走独立 cookie（ACC-21），登进工作台不顶掉同浏览器里的买家会话，也不被买家登出带走——共享解决的是「店主一处登录两处可用」，子账号是工作身份、没有这个诉求；代价是同一浏览器可以有「买家/店主」与「子账号」两份会话并存，前端按 localStorage 里的会话种类标记决定刷新打哪个端点与是否注入 `X-Shop-Id`（ACC-80）。共享 cookie 带来一个副作用必须处理：两端 localStorage 各持一份 deviceId，同一个 token 会被两个值交替提交，设备身份因此**不跟提交值走**（ACC-63）。

## 五、员工（Staff）账号

- **[ACC-29]** 平台员工是独立于买/卖家的第二套账号体系（`account.staff`）：登录凭证 = 工号 + 密码，不走手机验证码；员工不能自助注册，只能由超管建号（建号与调岗见 ACC-57，禁用/启用见 ACC-71，列表见 ACC-84——四个入口全在 `STAFF_MANAGE` 之下，员工侧没有自助写路径）。工号全局唯一（varchar(50)，唯一索引 `uk_staff_employee_no`），密码 BCrypt 必填。
- **[ACC-30]** 员工登录失败对外统一「工号或密码错误」（工号不存在与密码错误不区分）；对内精确原因只进 `staff.login.failed` 事件（`reason` ∈ staff_not_found / wrong_password / disabled / rate_limited，GEN-49）——被封员工还在试工号口令、或某个 IP 正在撞限流，过去在日志里完全隐身，现在一条可检索。工号是半标识符，只有查无此号那支带掩码工号。`StaffStatus` 非 ACTIVE → 403 + code `STAFF_DISABLED`。员工登录入口 `/admin/auth/login`，refresh 与 C 端复用同一套轮换/重放检测机制（RefreshTokenStore），但员工侧不采集 UA/IP 设备元数据，设备名固定「管理端」。
- **[ACC-31]** 员工 `me` 出参含岗位与有效权限码列表：禁用员工或未知/为空岗位一律给空权限集（如实呈现，拦截由判权层负责）；SUPER_ADMIN 展示时把通配符展开为全量具体码。
- **[ACC-71]** 封号端点（C12 产品化）：admin 侧 `PATCH /admin/users/{id}/status`（买家）与 `PATCH /admin/staff/{id}/status`（员工），body `{status: ACTIVE|DISABLED}`，授权统一 `STAFF_MANAGE`（仅 SUPER_ADMIN）。禁用后的闭合链路两侧不同：买家侧**不**同步吊销 refresh——在途 access 无黑名单最长剩 10 分钟（ACC-19/25 取舍），随后刷新撞 `refresh` 状态闸门（旧码已被 rotate 消费、新码不签发）+ 重登被 `USER_DISABLED` 拦，封号在 10 分钟窗口后自然等效全端下线；员工 access 寿命 8 小时，禁用在落状态之外同步 `RefreshTokenStore.revokeAll` 吊销全端会话，即时收场。启用＝状态回 ACTIVE，闸门实时查库，恢复登录/刷新（判权下一请求即生效）。两侧各记一条审计事件（`account.status.changed` / `staff.status.changed`，必带被禁主体 id + 新状态 + 操作人 `staff_id`，GEN-51「谁动了谁的数据」）——端点入参不带操作人，它由 `AdminAccountController` 从 `StaffContext` 取出后透传给 service，controller 不替 service 决定审计内容。目标不存在时 404 冒泡**不留事件**，否则审计里多出一条「封了一个不存在的账号」。不做物理删除（ACC-16）。
- **[ACC-84]** 管理端账号治理列表：`GET /admin/users` 与 `GET /admin/staff` 均要求 `STAFF_MANAGE`，服务端分页并支持状态筛选；买家关键字同时命中手机号/昵称，员工关键字同时命中工号/姓名，非法状态值 400。列表按创建时间倒序，买家手机号恒为 `138****8000` 形状的掩码且不提供批量明文出口，密码哈希、头像 key、注销内部字段不进 HTTP 契约；员工岗位只出 `SUPER_ADMIN/REVIEWER/OPS` 稳定枚举名，库中未知/null role 折为 null，不因单行脏值阻断整页。admin 的「用户管理/员工管理」消费 `me.permissions`，无 `STAFF_MANAGE` 时侧栏不展示（整套按码裁剪的口径见 ACC-58）；两页的禁用/启用动作接 ACC-71 端点并经二次确认，成功后只失效对应账号列表缓存。
- **[ACC-57]** 员工建号与调岗在管理端闭合（`POST /admin/staff` 建号返回 201、`PUT /admin/staff/{id}/role` 调岗），与 ACC-71 的禁用/启用、ACC-84 的列表同挂 `STAFF_MANAGE`（只有 SUPER_ADMIN 通配可达，ACC-44）；给 201 而不给 Location：建完就回列表，没有「去新资源页」这个动作。员工侧没有自助写路径——不自助注册、不改密（口令由超管建号时一次性告知，`/admin/auth/**` 只有登录/刷新/me/登出）、不物理删除（ACC-16）。
    - **建号闸门按「能不能事后补救」排**：① 工号唯一先预检（挡误操作）再由唯一索引 `uk_staff_employee_no` 兜并发，**两条路同一句 400**「工号已被使用，请换一个」——并发撞索引不交 500（PG 报唯一错即把事务标 aborted，「catch 后回读对方那行」这条路走不到）；② 口令走 `PasswordPolicy`，与买家建密**同一份判定**（≥8 位、UTF-8 字节 ≤72、不在 14 条常见口令黑名单；「不与手机号相同」那一档员工没有对照物，跳过），只落 BCrypt 哈希；③ 岗位是必选入参而非默认值——创建时就想清楚「这个人要干什么」比事后调岗安全（调岗有自指与末位两道禁令），选错只是多招一个人。工号形状 `^[A-Za-z0-9-]+$`、≤50 字（登录账号不许带空格：粘错一个空格就是「工号明明对却登不上」），展示名可空 ≤50。新建即 `ACTIVE`，落一行审计账本（动作 `ACCOUNT_STAFF_CREATED`，detail 带掩码工号与岗位，GEN-65）。
    - **调岗闸门顺序即口径**：① 查无此人 → 404「员工不存在」；② **自指禁令** `staffId == operatorId` → 400「不能修改自己的岗位」（调低自己的岗位等于当场自削权限且事后无痕，把「误操作」变成既成事实）；③ **同岗位是空动作** → 直接返回，不写库也不记审计（账本里一行「没发生过的变更」是噪音）；④ 末位超管保护（下条）；⑤ 条件更新 `WHERE role <> 目标岗位`，0 行 → 409「员工状态已变化，请刷新后重试」——这一句同时挡并发的第二次调岗与重复下发，后到者不会多记一条账（此前只按 id 更新，任何后到者都算改成功）。审计动作 `ACCOUNT_STAFF_ROLE_CHANGED` 带 from/to 与掩码工号。**只改岗位不改状态**：状态是另一条动作（ACC-71）。
    - **末位超管保护（禁用与降级共用这一个判据）**：目标若是**在岗**超管（role = SUPER_ADMIN 且 status = ACTIVE；非超管或未在岗直接返回、不进锁——普通员工的治理动作没有聚合约束，不该被这把锁串起来），**先**取一把事务级咨询锁（`pg_advisory_xact_lock`，键 `"SHOP_SAL"`，提交即释放）**再**数在岗超管，`countActiveSuperAdmins() <= 1` 即 409（禁用给「不能禁用最后一个在岗的超管」、降级给「不能降级最后一个在岗的超管」）。被禁的超管不算在岗，所以「最后一个在岗」不等于「最后一个」。
    - **锁为什么排在计数之前（拍板，不是排列偏好）**：这条判据是**聚合**，行级条件更新只挡「同一行被改两次」，挡不住「两个最后超管在同一刻被分别处置」——两边的写各不碰对方的行、各自的计数都还看见对方在岗，判完双双放行，平台就此永久失去建员工/调岗/封店的能力（`STAFF_MANAGE` 只有通配可达，而通配挂在超管岗位上）。选咨询锁而不是行锁：要在读计数前锁住「其他在岗超管」那几行，两个事务会各拿共享锁再抢主写锁凑成环（PG 直接 `deadlock_detected`，治理动作变 500）；这类动作一天没有几次、全是人在管理端点的，串行化代价可忽略。锁必须在事务里调用（`_xact_` 语义，语句结束即释放 = 等于没锁）。判据收在一个私有方法里，是为了不给「新调用点只写了计数没写锁」留口子。
    - **禁用那半边**沿用 ACC-71 的链路，末位保护插在「存在性之后、写之前」，与降级同一口径；落状态是一句只推 status 的条件更新（禁用 `WHERE status = ACTIVE`、启用 `WHERE status = DISABLED`，各带 updated_at），0 行即 409——于是既不重复吊销全端会话、也不往账本里补第二行同样的处置；对已启用的员工再启用是空动作，交回 409 而不是静默「成功」。
    - **前端**：员工列表页头给「新建员工」，行内「调岗」与「禁用/启用」并列；**改自己那一行不出按钮**（灰字「不可改自己」，与后端那句 400 同一口径的第一次拦截——人不该去点一个注定失败的按钮，闸门仍在后端，前端裁剪是体验不是安全边界）；库里/出参的岗位名不在契约词表内（脏值）按「无岗位」处理、不出调岗按钮。岗位下拉三项各带一句后果描述（「内容、类目、物流轨迹、优惠券运营」这类人话，不是权限码清单），词表取契约 `StaffRole` 不另抄一份。

## 六、验证码规则（短信 OTP）

- **[ACC-32]** 短信验证码为 6 位数字（SecureRandom），有效期 5 分钟；Redis 只存 HMAC-SHA256(pepper, "phone:code") 摘要。**四套用途**共用这一套机制，只有 key 前缀与短信文案不同：登录码（登录/注册）、重置密码码（带「重置密码验证码: 」前缀）、注销码、**子账号激活码（`activation:*`，带「子账号激活验证码: 」前缀，见 ACC-10）**。
- **[ACC-33]** 发送频控四层：单 IP 10 条/分钟（429 `SMS_RATE_LIMIT`）→ 单 IP 每日不同手机号数上限默认 30（可配 `shop.auth.sms-ip-distinct-phones-max`，只限"新号码"，已见号码复发不受影响）→ 单手机号 60 秒重发冷却（429 `SMS_RATE_LIMIT`）→ 单手机号每日 20 条上限（429 `SMS_DAILY_LIMIT`）。短信发送被限流时明示 429（与密码登录被限流的静默策略相反，因该信息无枚举价值）。
- **[ACC-34]** 校验规则：同一验证码至多尝试 5 次，错满 5 次即烧码（后续输入走 `SMS_CODE_EXPIRED`）；前 4 次错误不烧码只计数（手滑友好），重发即重置尝试计数；校验成功立即消费（一次性）；无哈希（未发/过期）报 400 `SMS_CODE_EXPIRED`，码不符报 400 `SMS_CODE_INVALID`。校验接口不另设限流（猜测空间数学封顶 10⁶×5 次）。
- **[ACC-35]** 匿名发码入口前置人机验证：`POST /auth/sms-code` 与 `POST /auth/forgot-password` 都必须先通过图形验证码——两个端点同为「匿名 + 按自报手机号发真短信」的入口，只有 IP/号码频控（ACC-33）时挡不住一个 IP 换号横扫的轰炸。防线顺序：入参格式（`@Valid`，在方法体之前）→ 人机验证 → 频控 → OTP，这条顺序闭合在 `AuthService.sendSmsCode` / `AuthService.forgotPassword` 这一个用例里，controller 只调一次（编排散进入口就没有复用，也没有顺序保证）。图形验证码 4 位字符（字符集剔除 0/O/1/I/L 等混淆字符），答案 SHA-256 摘要存 Redis 5 分钟；校验无论成败都消费该 captchaId（防重放），故被频控拒掉时那一枚图形码也已经用掉、用户要重做一次验证——「廉价凭证先失败」的刻意代价。两枚入参必填，缺失/空白 → 422 字段级拦截；`captchaId` 指向的答案不存在 → 400 `CAPTCHA_REQUIRED`（服务端兜底空白串）/ `CAPTCHA_EXPIRED`，码不符 → 400 `CAPTCHA_INVALID`（大小写不敏感，前端据此刷新重输）。**dev profile 例外**：配了 `shop.auth.captcha-channel=dev` 时固定码 `DEV4` 直通比对那一步（`DevCaptchaChannel`，与短信固定码 666666 同一模式，理由只有一个——E2E 每轮要注册新账号，认 PNG 不是自动化能稳定做的事）。豁免只免「比对」不免「提交过人机验证」：缺 `captchaId` 或空码照旧 400，`generate()` 照旧出图，前端流程与生产一致；生产 profile 把该属性写死成非 dev 值，bean 不装配 = 那条分支恒假，不是运行时可切的开关。
- **[ACC-36]** 开发环境固定短信码 `666666`：仅当显式配置 `shop.auth.sms-channel=dev` 才装配 DevSmsChannel（matchIfMissing=false），生产漏配真实通道直接启动失败，不会静默留后门。dev 固定码同样清尝试计数并放行。

## 七、密码与资料

- **[ACC-85]** 账号语言偏好：买家与卖家共用 `account.users.preferred_locale`，员工使用 `account.staff.preferred_locale`；初始为 NULL，不把设备语言自动写入账号。只允许本人更新，`expectedAccountId` 必须等于认证主体，用于拒绝账号切换后的旧请求（409）；不支持的 Locale 返回 400。更新只写偏好与 `updated_at`，禁用或已注销账号不能修改，用户注销时清空偏好。

- **[ACC-37]** 密码策略：至少 8 位、UTF-8 字节数 ≤72（BCrypt 硬限制）、不能与手机号相同、不在硬编码常见弱密码黑名单（14 条，小写比较）；BCrypt cost 12。错误码不带独立 code，统一 400 文案。
- **[ACC-38]** 设置/修改密码：首次设置（passwordHash 为 NULL）不要求旧密码；已有密码必须提供正确的 currentPassword（401「当前密码错误」）；改密后全端吊销（见 ACC-24）。重置密码走短信码体系（非长 token）：先本地校验强度再消费一次性验证码。
- **[ACC-39]** 个人资料：昵称 trim 后非空且 ≤30 字（400）；avatarKey 为对象存储 key ≤255，null=不改、空串=清空；手机号在 `me`/资料出参一律脱敏为 `138****8000` 形态。头像上传走一次性 ticket 直传对象存储。
- **[ACC-40]** 手机号值对象：三档口径按「这个入口能不能猜」分——**触发真实发短信的入站端点**（`POST /auth/sms-code`、`POST /auth/forgot-password`）在 DTO 上强校验大陆手机号 `@Pattern(PhoneNumber.CHINA_MOBILE_PATTERN)`（`^1[3-9]\d{9}$`），格式错走 **422 + `errors[]`、不带 code**（GEN-19 第①条线；被 Zod 拦在前端时根本到不了这里）；**登录族**（短信/密码登录、改密）维持 7–20 字符 trim 宽松直存，与「对外失败文案恒为手机号或密码错误」的防枚举姿态配套（ACC-17），校验过严反而把格式判据泄露给脚本；地址联系人电话允许 `PhoneNumber.CONTACT_PATTERN`（`^[0-9+\-]{5,20}$`，可代收/座机）。三档正则都是 `PhoneNumber` 的编译期常量、DTO 只引用（GEN-52），「常量逐字节等于本条写的形状」由 `ValidationVocabularyTest` 钉（GEN-53），且三档放行的号 `of()` 必归一化得掉。业务强校验处（建子账号时校验员工手机号）在 service 层用大陆号正则（ACC-11）。归一化去空格/连字符/括号/点号（但联系人档的形状门本身不收空格与括号——粘贴「138 0000 0000」在 DTO 就被挡，放宽它属接口变更，GEN-54）。日志一律脱敏（GEN-51）。

## 八、权限判定（RBAC / 判权拦截器）

- **[ACC-41]** 判权入口 = `@RequirePermission` 注解（方法级覆盖类级），value 为 ANY 语义（持有任一码即通过）；通配码 `*` 恒通过，只出现在解析层，注解上永远写具体码。权限码契约 SCREAMING_SNAKE_CASE，只增不改名不删除。
- **[ACC-42]** 受保护命名空间 `/admin/**` 与 `/seller/**` 默认拒绝：handler 缺 `@RequirePermission` → 403 `PERMISSION_DENIED`「接口未配置权限」；唯一豁免是 `/admin/auth/**` 自服务端点（登录/刷新/me/登出，只吃认证）。另有启动自检 AdminEndpointGuardTest 把漏标炸在开发期（双保险）。非法路径不进判权。
- **[ACC-43]** 判权按主体域解析：PermissionResolver 链取第一个非 null 结果——员工域（StaffContext 有值）实时查库解析岗位权限集；卖家域（ShopMemberContext 有值，由 ShopMembershipFilter 装载）分两种身份：**店主**（用户令牌 + `X-Shop-Id`）→ 通配 `*` 全通过，**子账号**（`kind=subaccount` 令牌，店自带在凭证上）→ 该行被授予的码集（null 当空集）。上下文不属于任何受保护域（无人认领）→ 空集 fail-close。判权每请求实时查库不做缓存：禁用/收权下一请求即生效。
- **[ACC-44]** 平台岗位 → 权限映射（枚举硬编码，改映射=改代码发版；那张对照表由门禁按 `StaffRole.permissions()` 求值核对，不是抄表，见 [permission-codes.md](../conventions/permission-codes.md)）：`SUPER_ADMIN` → 通配全通过；`REVIEWER` → `SHOP_REVIEW + AUDIT_VIEW + SHOP_GOVERNANCE`；`OPS` → `CMS_MANAGE + CATEGORY_MANAGE + LOGISTICS_MANAGE + COUPON_OPS + AUDIT_VIEW + SHOP_GOVERNANCE`。库中未知/null role 一律空权限（fail-close）。`SHOP_GOVERNANCE` 同时发给审核与运营两岗是拍板而非疏忽：封店/解封（ACC-60）与审核驳回（ACC-09）的后果同源（都把店推成不可营业并级联下架），手里的人多一个不多；`STAFF_MANAGE` 与 `AUDIT_VIEW` 的分工才是硬边界——**建人与改人能自我扩权，看账不能改账**，所以只有 `STAFF_MANAGE` 是「通配独占」（除 SUPER_ADMIN 外无岗位持有）。
- **[ACC-45]** 全量权限码 13 个（`Permissions.all()` 即这份清单，顺序不参与核对）：admin 域 8（`SHOP_REVIEW` / `CMS_MANAGE` / `CATEGORY_MANAGE` / `LOGISTICS_MANAGE` / `COUPON_OPS` / `AUDIT_VIEW` / `SHOP_GOVERNANCE` / `STAFF_MANAGE`）+ seller 域 5（`PRODUCT_MANAGE` / `ORDER_FULFILL` / `ADDRESS_MANAGE` / `SHIPPING_MANAGE` / `COUPON_MANAGE`，即 ACC-14 的可授予白名单）。全部是 MANAGE 型合并码（读随写权），拆分读写的触发器=第一个「能看不能改」岗位出现。**每个码都真的有挂点**（无挂点的码只有通配能命中，那是死码，门禁逐码核对）：卖家侧实际注解——订单 / 售后 / 物流发货 / **卖家评价回复** → `ORDER_FULFILL`，商品 → `PRODUCT_MANAGE`，商家地址 → `ADDRESS_MANAGE`，运费模板 → `SHIPPING_MANAGE`，优惠券 → `COUPON_MANAGE`；平台侧——入驻审核 → `SHOP_REVIEW`，CMS → `CMS_MANAGE`，类目 → `CATEGORY_MANAGE`（两个控制器），物流轨迹 → `LOGISTICS_MANAGE`（列表 + 异常处置两个控制器），券运营 → `COUPON_OPS`，审计查询与导出 → `AUDIT_VIEW`，店铺治理 → `SHOP_GOVERNANCE`，账号治理 → `STAFF_MANAGE`。`MEMBER_MANAGE` / `SHOP_MANAGE` 是只有文档登记的占位码（ACC-46）。
- **[ACC-46]** 子账号管理（建号/改权/停启用/重置口令/移除/列表/取号码明文）不走权限码，按「店主角色」裁决（`/shops/**` 不在判权命名空间内，service 层 `isActiveOwner` 否则 403）；文档口径：`MEMBER_MANAGE`/`SHOP_MANAGE` 为 OWNER 固有，刻意不建权限码常量。
- **[ACC-58]** 管理端侧栏按**权限码**裁剪（不是按岗位名、也不是前端自己再造一套角色判断）：入口登记 `key → 所需码` 一张表，可见性 = `me.permissions` 是否含该码，缺省（表里没登记 key）= 任何岗位可见。今天登记了六格：`用户管理`/`员工管理` → `STAFF_MANAGE`（ACC-71/84/57）、`店铺治理` → `SHOP_GOVERNANCE`（ACC-60）、`优惠券运营` → `COUPON_OPS`（CPN-62）、`物流异常` → `LOGISTICS_MANAGE`、`操作审计` → `AUDIT_VIEW`（GEN-65）。裁剪是**两层**的：组内单叶（同一组里各叶所需码可以不同，「商家」组的 `店铺治理` 与 `入驻审核` 就不是一拨人管的页）与整组（组内只剩一个入口时，整组随那一叶走）；一叶被裁掉后它的 section 与 group 逐级变空即整体不出现——不留空壳分组。码值不在 app 里写字面量，一律取 `packages/common` 的 `PermissionCodes.*` 唯一 owner（与后端 `Permissions` 的等式由门禁双向核对，GEN-63）。
    - **它不是安全边界**：真正的闸是后端 `@RequirePermission`（ACC-41/42），侧栏裁剪只回答「不该看见的人不必看见」。直敲 URL 仍会进页面，数据由后端 403 挡（GEN 的错误口径），因此前端不为「无权限」另立一套拦截。
    - **漏登记静默偏向「看得见」**：新增带权限的页面时必须在登记表里加一行，漏了就是「所有岗位都看得见 + 点进去后端 403」，不崩、只是脏。今天未登记的是 `入驻审核`（`SHOP_REVIEW`）、`类目管理`（`CATEGORY_MANAGE`）与 CMS 三格（`CMS_MANAGE`）——于是运营看得到审核队列、审核员看得到类目与内容，都进不去（拿到 403 而不是「不存在」，因为判权按主体缺码说话，ACC-66）。这条偏向是刻意的：漏登记红在「多看见一个入口」，错登记红在「治理人看不到自己要处理的页」，后者更坏。

## 九、地址簿（买家收货地址）

- **[ACC-47]** 买家地址全部需登录（`/user/addresses`），仅本人可见——不存在或不属于当前用户一律 404「地址不存在」，不泄露他人数据存在性。列表排序：默认地址置顶，其余按创建时间倒序。
- **[ACC-48]** 每个买家至多一个默认地址：设默认（新增/编辑/设默认端点）先清本人其他默认，部分唯一索引 `uk_addresses_default`（is_default=TRUE 且未删）兜底并发；允许「无默认地址」状态——删除默认地址不自动顶替，另有显式取消默认端点（DELETE /{id}/default）。
- **[ACC-49]** 地址删除是软删（deletedAt 逻辑删除，查询自动过滤，且不把 deletedAt 序列化出 HTTP 边界）。地址独立于订单：下单结算时按 ID 跨 schema 只读（快照归 order）。
- **[ACC-50]** 地址字段校验：收件人 ≤30、电话 `PhoneNumber.CONTACT_PATTERN`（可代收≠账号手机号）、行政区划码 6 位数字（`RegionRegistry.CODE_PATTERN`）且必须是合法国标码——存在性由 `RegionRegistry.requireValidCode` 判，「行政区划代码无效」这句话术全局只有它一处（service 不再各写 `validateRegion`）。形状门与权威判定同为 400，但落点不同：形状错走 Bean Validation 那条线，区划不存在走 service 自判（GEN-19/GEN-54）。省/市/区各 ≤30 必填、详址 ≤120、标签 ≤20。前端 zod 镜像同样规则，但只镜像**用户填的那几项**：口径写在 `packages/common/src/domain/address.ts`（买家/商家两端一份，长度上限与 `ADDRESS_NAME_MAX`/`ADDRESS_DETAIL_MAX` 一起，后端同名 owner 是 `common/AddressFieldRules`，两边是否还相等由 `FieldRuleVocabularyTest` 逐条核对而不是靠这句散文），省市区名不进表单（ACC-81）；不复刻默认唯一性等业务规则。
- **[ACC-51]** 地址标签：内置枚举 HOME/WORK/SCHOOL/PARENTS/FRIEND（未指定默认 HOME），其余非空字符串视为用户自定义文案原样入库（前端自定义标签限 4 字）；前端按已知 code 渲染图标，未知值按纯文本展示。
- **[ACC-52]** 智能粘贴：一段非结构化收货文本可解析为结构化字段（第三方分词库 + RegionRegistry 区划名→国标码映射），解析不入库；收件人清洗尾部标点杂讯；收件人/手机号可能解析失败，由前端回填让用户确认。前端只取回包里的 regionCode，不取它那份省市区名——名字的权威出口是区划库反查（ACC-81），查不出三级的码就当没识别出来，提示手动选择。
- **[ACC-53]** 买家地址条数上限 20 条：新增（create）时未删地址已达 20 条即拒（400 + code `ADDRESS_LIMIT_EXCEEDED`，「最多保存 20 条收货地址」）；软删不占名额（计数只算未删行）。

## 十、地址簿（商家发货/退货地址）

- **[ACC-54]** 商家地址归 shop 模块（`shop.merchant_addresses`，表迁自 merchant_address schema），授权 = `ADDRESS_MANAGE` 权限码 + 成员身份（X-Shop-Id 上下文），shopId 前端不传；越店访问一律 404。单表模型：一条地址 = 地址本体 + 「默认发货」「默认退货」两个布尔，一条地址可同时承担两者；面单寄件人 = companyName（公司名称）。
- **[ACC-55]** 每店默认发货/默认退货各至多一个：设默认先清本店同类默认，部分唯一索引（未删且为默认的行）兜底并发；列表排序默认发货/默认退货置顶、其余按更新时间倒序；删除/取消默认不静默顶替，允许该店暂时无默认。
- **[ACC-56]** 商家地址字段：联系人 ≤30、电话 `PhoneNumber.CONTACT_PATTERN`、区划码 `RegionRegistry.CODE_PATTERN` + `requireValidCode`（与买家侧同一处定义、同一句话术）、省/市必填、区/县可空（直辖市/直筒子市）、详址 ≤120、邮编可空 6 位数字、公司名 ≤60、备注 ≤200；默认标记 null 时新增视为 false、编辑保持原值。邮编的形状与区划码撞车（同为 6 位数字）但**刻意不共用常量**——它是另一个概念，合并会让一处放宽静默改掉另一处（GEN-54）。地址有 ACTIVE/DISABLED 状态维度（停用不参与快照解析，软删归 deletedAt）；api 快照解析只认「未删 + ACTIVE」。区/县名同为派生值，不在表单里（ACC-81）。
- **[ACC-70]** 商家地址条数上限每店 200 条：新增（create）时本店未删地址已达 200 条即拒（400 + code `MERCHANT_ADDRESS_LIMIT_EXCEEDED`，「最多添加 200 条地址」，与卖家工作台文案同口径）；软删不占名额。
- **[ACC-81]** （两端共用）地址表单不存省市区名，只存那一个 6 位区划码：三级名是提交时按区划库（国标 `regions.json`）反查出来的派生值，落库仍是冗余的三列（ACC-50/ACC-56 的必填口径不变）。反查用的路径与级联选择器显示的是同一条，故「看到的三级」与「存下来的三级」不会分家；直筒子市用区划库合成的 6 位码（`市码+00`），一样出三级。派生出口 `regionNamesByCode` 与字段口径同在 `packages/common/src/domain/address.ts`，买家/商家两端各调一次（`apps/web/src/address/queries.ts`、`apps/seller/src/shop/address/queries.ts`）。后果要说清：编辑一条老地址并保存，三级名会按当前区划库刷新（直辖市那一级本就是「市辖区」，选择器显示的也是它）——名字跟着码走，不跟着上一次落库的写法走；已下单的收货信息不受影响（快照归 order，ACC-49）。

## 十一、账号注销（买家自助，个保法第 47 条）

- **[ACC-75]** 注销是两段式（申请 → 生效），不是一键删除：
    - **申请只落一个时刻**：`account.users.deletion_requested_at`（冷静期起点）。期内账号一切照常——能登录、能下单、能撤销，数据一行不动。
    - **冷静期 15 天**（`AccountDeletionTimeouts.COOLING_OFF`），期满由 `AccountDeletionJob`（每小时扫一轮，每批至多 20 笔）执行。两段的理由：删除不可逆，而「误操作 / 验证码被他人拿到后恶意注销」唯一的补救窗口就是这段时间；它同时是**反劫持**门槛——只握有一枚一次性码的人 15 天内也拿不到账号，真机主有 15 天发现并撤销。批量上限不是性能考虑：注销是毁灭性动作，宁可分批慢做，也不要一轮锁住大批账号行。
    - **冷静期不是审核期，也不暂停任何东西**：平台不审批注销（无人工闸、无客服介入），期内不冻结交易能力，订单/退款/售后照常流转。
    - **撤销 = 清空申请时刻**，无限次。因为申请什么都没动，撤销即完全复原，不存在「已部分清理不可恢复」的中间态。
- **[ACC-76]** 三档数据处置（个保法「删除」在电商语境下的实际形状）：
    - **匿名化（清掉个人信息，行保留）**：phone → 占位串（见 ACC-77）、`password_hash` / `avatar_key` → null、nickname → 「已注销用户」、status → DISABLED、`deleted_at` = 生效时刻。行不删（电商法第 31 条交易信息留存，且历史订单/评价/售后要有主语可挂）；刻意**不**加 `@TableLogic`——`deleted_at` 是「注销生效时刻」这个业务事实，与地址/商品的软删标志语义不同，不混用同一列（ACC-16「不删行 ≠ 不注销」）。昵称/占位号码是系统生成、全员同一形状，不属于个人信息，留给仍在引用这个 id 的地方一句能读的说明，而不是空白或裸 uuid。
    - **清掉（意愿数据）**：购物车条目与收藏 `deleteByUser` 物理删——人不在，「我喜欢/我想要」既无人消费，又是一份可关联到具体某人的兴趣画像，正是删除权要带走的那类信息；收货地址走它自己的软删（与 ACC-49 同一套删除词汇，不立第二套）；未使用券置 `VOID` 而非删行（核销流水与「这张券曾发给谁」的发放统计要靠这行对账，VOID 是券自己的终态，运营作废走同一个态）。
    - **保留（平台治理凭据，一律不动）**：订单、退款/售后、支付与资金流水、评价、店铺本体与店主归属、审核历史。
    - **卖家身份**：店主名下 ACTIVE 店 → 条件更新 `suspend`（ACTIVE→DISABLED）+ 同事务按 ACC-72 的立约发布 `ShopTradingSuspendedEvent(shopId, "OWNER_DELETED")`，product 据此级联下架在架商品；本人名下的 `shop_members` OWNER 行删掉（一人一店的名额随人消失，不连带清理等于给已注销的人留一个占位）。**子账号凭证不受影响**：那些是别人的工作身份，追责锚点不该跟着店主的账号消失；店已经不可营业，子账号登进来也做不了任何事（`ShopMembershipFilter` 的店铺可用闸门会挡）。**店不删、不改店主、不释放店名**——「这家店曾属于谁」是治理凭据，已售出的单还要有人对货。这里与平台主动封店（ACC-60）走的是**同一个** `suspend` + 发事件出口，只有原因串不同（`OWNER_DELETED` / `PLATFORM_SUSPEND`），因此两家店的下架后果一模一样，而审计里仍然分得清是哪条路封的；要恢复也只能走 ACC-60 的解封，而那条闸门会因「店主账号已不可用」拒绝把已注销者的店放回来。
    - **依赖方向**：清理散在 cart / favorite / coupon / shop 四个模块。account 谁都不依赖，只发布 `account::events` 的 `UserDeletedEvent`（不携带任何个人信息），四个消费方各自 `@EventListener` 同步处理；反向（account 调它们的 api）会与既有的 `shop → account::api` 凑成模块环。同步监听 = 同一个事务，任一处失败整体回滚，不会出现「号已注销、购物车还挂在那个手机号上」这种半截状态。顺带的好处：清理规则长在使用那张表的模块里。
    - **不做在途资格闸门**（拍板）：注销不检查「有没有未完成订单/售后」——那要读 order/aftersale，而 account 依赖它们同样成环；何况人在 15 天里始终能正常处理在途事务，期满仍在途的单由 ORD/AFS 自己的超时链跑到终态。注销删的是**将来**的资格，不是别人的在途工作。
    - **会话**：`RefreshTokenStore.revokeAll` 排在事务内最后一步——Redis 不在事务里、回滚也退不回来，宁可多踢一次也不要「注销失败却把人留着」。在途 access 无黑名单，最长 10 分钟后自然失效（ACC-19/25 同一取舍）。并发与幂等不靠锁：全部资格判定合成**一笔**条件 UPDATE（未注销 + ACTIVE + 申请时刻非空且已过 cutoff），影响 0 行即本轮不执行——多实例并发扫描同一行只有一个赢，期内被撤销或被平台禁用天然不落地。
- **[ACC-77]** 号码释放与新主体：注销后 phone 列填 `dz` + uuid **尾** 16 位十六进制。取尾不取头：头部是毫秒时间戳，同一毫秒注销的两行会撞全局唯一索引 `idx_users_phone`，尾段是 uuidv7 的随机段（约 62 位熵）；`dz` 前缀让它不再是任何合法号码形状，登录族按号码查不到这行，长度 18 ≤ 列宽 20。原号码就此交还——电信循环放号后的下一个人可把它注册成**全新主体**（新 user id，与注销者无任何关联，历史不继承）。已知边界：号码占位使 ORD-59 那类「按手机号的计数」自然归零，新主体因此拿到满额额度，与「买家滥用侧无计数」同档，属已接受。
- **[ACC-78]** 端点与前端入口：4 条口子全在 `/auth/deletion`（`GET` 状态出 `{requested, effectiveAt}`、`POST /code` 发验证码、`POST` 提交申请、`DELETE` 撤销），均要求已登录——不在 ACC-26 的匿名豁免清单里。
    - **发码不收手机号、也不要图形验证码**：号码取 token 背后的账号，不让前端自报，因此不存在「拿别人的号收码」这条通道（这正是它与注册/登录发码的差别）。
    - **申请只带 code**（`ConfirmDeletionRequest`，6 位数字），不再输密码：能登录 + 能收本机短信已是两因子。验证码在写库**之前**消费：写库失败（并发/已申请）只浪费一枚码，是重发一次的烦；反过来等于「没过验证就能注销」，是漏洞。
    - **前端入口在「账号安全」页**：注销条目 → 数据处置清单（哪些清掉 / 哪些保留 / 哪些匿名，让用户在知情前提下决定）→ 发码 + 输码 → destructive 二次确认 → 提交即进冷静期；已在冷静期时该条目改显「预计 X 生效」并给撤销按钮。OTP 错误/限流的前端行为沿用 ACC-67，不另立一套。
    - **禁用中的账号不给自助注销**：`requireActive` 对 `deleted_at != null` 回 404「用户不存在」（注销后没有账号可看，也不泄露"曾经存在"），非 ACTIVE 回 403 `USER_DISABLED`——封号是平台在追的事，注销不能成为「把追踪线索自我销毁」的出口；要注销先由平台解禁（ACC-71）。

## 全局会话与鉴权行为（横切）

- **[ACC-61]** 前端会话（三端共用 auth-kit）：access token 只存内存（auth-kit 闭包变量），不落 localStorage；refresh token 走 httpOnly cookie——cookie 安全属性见 ACC-21，买家/卖家共享会话见 ACC-27。启动时 `bootstrapAuth()` 用 refresh cookie 静默刷新一次裁决登录态：单例 Promise（多处 await 只发一次请求——第二次轮换会把第一次签发的 token 判成重放），refresh cookie 有效 → 换 accessToken 并裁决 authed，失败 → clear 裁决 guest；登录态三值 unknown/authed/guest 经 `useSyncExternalStore` 订阅广播，tokenStore 写入即 authed、清除即 guest。**两个例外让结论不会卡死**：已 authed 时 `bootstrapAuth()` 直接放行不再刷（登录成功不该再等一轮）；`clear()` 作废那枚单例 Promise，登出后同一页面仍能用 cookie 静默重登，而不是必须整页重载（cookie 没过期就登不回来是 bug，不是语义）。
- **[ACC-62]** 401 自动续期重发：SDK 响应拦截器收到 401 且非 refresh 端点自身时，用原生 fetch POST 各自前缀下的 refresh 端点（C 端默认 `auth/refresh`，admin 装配时传自己的），成功则写入 tokenStore 并重建重发原请求（用户无感）；refresh 失败/响应无 accessToken → 原始 401 正常冒泡。刷新失败不弹提示、不清态由消费方按 401 自行处理。**刷新是单飞的**：同一时刻多个请求各自 401（首屏并发是常态）只发一笔 refresh，兄弟请求 await 同一枚 Promise，成功写 tokenStore 也只做一次——各刷各的等于自己制造 ACC-22 的重放。刷完仍失败按 ACC-22 分两档：落在 15 秒宽限期内后端判「多标签页竞争」给 401 不吊销，本请求冒泡原始 401（此时兄弟请求早已换到新 token，用户看到的是句假的「登录已过期」，重试即恢复）；超出宽限期判成盗用 → 410。**410 例外（C14 已实现）**：refresh 返回 410 且 code `REFRESH_TOKEN_REUSED`（后端已全端吊销，ACC-22）时，拦截器就地 `tokenStore.clear()` 清登录态（`clear` 在 TokenStore 上是必给字段：可选就意味着某个装配漏实现时清态静默变成 no-op，人被吊销了前端还显示已登录），并把该 410 冒泡——detail（「全部设备已下线」语义）经错误拦截器归一成 ApiError，toast 由消费方全局错误通道呈现，拦截器不直造 UI。响应的 body 只能消费一次，所以吊销时每个 await 到结果的调用点各自拿一份同体的新 410，不是共享同一个 Response。重发原请求要重建 `Request`（原 body 已消费，从序列化结果取）；重建失败则原始 401 冒泡。
- **[ACC-63]** 设备 ID：首次 `crypto.randomUUID()` 生成并持久化 localStorage（默认键 `shop_device_id`，各端可换键隔离会话——admin 用独立键隔离），随 refresh 上报支撑多端设备列表与按设备吊销。**设备身份以 refresh token 首次绑定为准，不信任本次提交的 deviceId**（拍板，方案①）：`RefreshTokenStore.rotate` 先在设备集合里反查「当前索引指向本 token 摘要」的 deviceId（消费旧码删的是权威键 `refresh:<hmac>`，设备索引 `refresh:user:<subject>:<deviceId>` 此时仍在，其值即旧摘要；扫本主体个位数成员、不碰 KEYS），命中则清索引与重签发都沿用那一条，只有反查不到（历史数据/绑定丢失）才回退用提交值登记。这不加 Redis 往返，也不引入新状态。**语义变化：吊销粒度 = 浏览器**——同一浏览器上 web/seller 两端（各持一份 deviceId、共用一个 cookie，ACC-27）从此合并成一条设备条目，不再每换一端刷新就迁移出一个假活跃条目；代价是「按设备吊销」再也无法只踢卖家工作台而留住买家端，跨标签页/跨端「单独下线其中一个」属已接受的边界。员工侧不采集设备元数据、恒 `"default"` 单桶（ACC-30）。
- **[ACC-64]** 未登录访问受保护路由：客户端导航 `beforeLoad: requireAuth()` 先 await bootstrap 裁决，未登录拉起全局登录 Dialog 并 redirect 首页（web）；SSR 首屏不裁决登录态（cookie 只在浏览器端刷），由客户端守卫（`_protected` 布局 gate）兜底。
- **[ACC-80]** 卖家登出的清态范围 = access token **+ 当前店铺上下文**（`X-Shop-Id` 的来源，ACC-06）**+ 会话种类标记**：前两者持久在 localStorage 并由 SDK 拦截器注入每一个请求，只清 token 就是让下一个用同一浏览器登录的账号替上一个人发 `/seller/**` 请求（不在那家店 → 403「你不是该店铺成员」；恰好是成员 → 未经选择就开在别人店里经营）；种类标记留着则是让下一个店主的静默刷新去打子账号的刷新端点，用店主浏览器里那份子账号 cookie 换出一个子账号令牌。清态放在 `finally`：登出接口失败也要清，本地状态不该因为一次远端调用失败而留着。**子账号的店不从 `X-Shop-Id` 来**：它自带在凭证上，前端在子账号会话下不注入这个头，后端对「带了别家店 X-Shop-Id」的请求直接 403。已知边界：410 吊销裁决走 ACC-62 的 `tokenStore.clear()`，不经 `logout()`，店铺上下文因此残留——`/shops/mine` 不在 `ShopMembershipFilter` 的 `/seller` 命名空间内，`useCurrentShop` 的「落到第一家 ACTIVE 店」兜底仍能把它修回来，所以残留的代价是首个 `/seller/**` 请求可能带错店铺头，不是永久卡死。

## 错误码 → 前端行为

- **[ACC-65]** Token 类错误：`TOKEN_EXPIRED`（401，access token 过期——买家 10 分钟 / 员工 8 小时）→ 前端静默 refresh 续期，用户无感；`INVALID_TOKEN`（401，未携带/格式错/类型错/受众错/签名失败）→ 清用户状态回未登录；`REFRESH_TOKEN_REUSED`（410，重放超宽限期）→ 后端同步吊销该主体所有设备会话，前端呈现「所有设备已下线」。
- **[ACC-66]** `USER_DISABLED` / `STAFF_DISABLED`（403）：登录与鉴权时账号状态非 ACTIVE 即抛，前端展示后端 detail「账号已被禁用」；**`SUBACCOUNT_NOT_ACTIVATED`（403）：子账号还没验过本人手机号就来登口令，前端据此把卖家登录页切到激活步骤**（其余两档子账号失败不分码：口令错与登录名不存在同为 401「登录名或密码错误」，停用为无码 403）；`PERMISSION_DENIED`（403）：已认证主体缺权限码（PermissionInterceptor 判权失败），前端按 403/无权限呈现，不引导重新登录。
- **[ACC-67]** 短信码错误的前端行为：`SMS_CODE_INVALID`/`SMS_CODE_EXPIRED` 使验证码输入框标红（invalid 态），用户重新输入即清错；发码按钮成功后本地起 60s 倒计时（「Ns 后重发」），倒计时/手机号合法/图形码 4 位三者齐备才可发码。429 `SMS_RATE_LIMIT` 命中时同样起 60s 倒计时（C14 已实现：服务端窗口就是 60s，连点只会再撞限流；`SMS_DAILY_LIMIT` 等其余失败不起）。
- **[ACC-68]** 图形验证码错误的前端行为：前端（共享 LoginForm）对三类图形验证码错误（`CAPTCHA_REQUIRED`/`CAPTCHA_EXPIRED`/`CAPTCHA_INVALID`，后端规则见 ACC-35）统一处理：标红输入框、刷新验证码图、清空重输；重输时只清除验证码类错误。
- **[ACC-73]** 安全配置缺失的统一姿态是「按能不能安全降级分档」，不是一刀切 fail-fast：**降级会留后门**的（短信通道 `shop.auth.sms-channel` 漏配真实通道、物流验签密钥）→ 启动失败或请求侧一律拒绝（LOG-22 webhook 未配密钥 403，不 fail-open）；**降级只伤在途凭证**的（pepper、JWT ES256 密钥对）→ 生成临时值并告警，重启即在途凭证全部失效，等于「开发环境免配置可跑」的代价显式转嫁给会话。两处临时值告警级别刻意不同：pepper 影响 refresh 与验证码（`log.warn`），JWT 只影响 access（`log.info`，且无长度闸门）——这是不对称，不是遗漏。是否要给 JWT 补长度/存在性闸门尚未拍板，列为留白。
