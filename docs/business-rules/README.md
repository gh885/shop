## 编号约定

- 编号只标**首次收录**，跨域联动条款归「动作的发起方」文件（例：退券细则归 coupon.md，aftersale.md 只留一句联动）；引用时可跨文件直接写编号。
- 条目缺号（如 LOG 缺 05/08、PAY 缺 16~~21/29~~31/35/39/40）表示该条已合并进其他条款、移交到归属域文件，或整条属实现细节而非业务规则，不回收号、不重排——保持历史引用稳定。
- `Xxx-N`（CPN-N1…）与文件末「已定案未实现」节：已拍板但代码未落的规则，落地时转正、废弃时删除。

## 已知留白（不是遗漏）

- 券的自动促销半边引擎、叠加字段、事件发券幂等均未落（coupon.md 未实现节）。
- 封号管理端点与用户/员工列表已落（ACC-71、ACC-84）；优惠券查询与作废运营入口已落（CPN-62），admin 页面由 `COUPON_OPS` 授权。
- 店铺停营业**不级联券**：店被驳回/禁用时，该店券模板与其下用户券保持原状（ACC-72 只管商品与成交闸门，下单侧的营业闸会让券用不出去）。要不要随店停发/作废未拍板。
- 平台封店/解封已落（ACC-60，`AdminShopController` + `ShopAdminService`）：封店走 `ShopMapper.suspend` 并发布
  `ShopTradingSuspendedEvent` 级联下架（与审核驳回同一出口），解封不自动重上架；解封额外挡一道「店主账号已注销/禁用」。
- 注销只是**交还手机号**：号码维度的历史计数（如 ORD-59 那类按号码的额度）随匿名化归零，重新注册的同号码是新主体、拿满额（ACC-77），与「买家滥用侧无计数」同档，属已接受。
- JWT 密钥是否补长度/存在性闸门未拍板（ACC-73 记的不对称现状）。
- 号码明文索取只有留痕、**没有频次闸门**：卖家逐单取买家电话（ORD-62）、平台逐条取店主号、成员逐条取他人号（ACC-79）三个出口都是脚本刷全量在今天仍然可行，只是每一笔都留得下痕——相对改前「一屏列表全是明文」是净改善，闸门与到期回落等接消息/客服体系或隐私面单时一起补。
- **两个 401 码说的是同一件前端动作，只记账不合并**（GEN-62）：`TOKEN_EXPIRED` 与 `INVALID_TOKEN` 按 GEN-17 第一条（「前端能用 status 区分的不加 code」）该只剩一个——`sdk-client` 的 401 拦截只看状态，两个码走同一条路（续期一次，失败即未登录）。留着是因为诊断上有用：日志与 ProblemDetail 里分得清「过期」与「签名错 / 类型错 / 受众错」，而合并成一个是把可检索的事实抹平。**代价写在这里**：谁哪天要让前端按码分叉，得先回答「另一个码归谁」，而不是就地新增第三个。等式由 `ErrorCodeVocabularyTest` 的另一半守着——两个码各有真实抛出点、文档「谁在读」都是 `—`，写进一个不存在的读者会红。
- **同一概念的两档列宽并存，只记账不合并**（GEN-61）：入驻审核备注 255 而「一段人写的说明」在其余七个入参都是 200（`ShopFieldRules.REVIEW_REASON_MAX` vs `NoteFieldRules.FREE_TEXT_MAX`）；类目属性值配图 512 而商品主图 / 轮播 / 详情 / SKU 图与各类对象存储 key 都是 255（`CategoryFieldRules.ATTR_VALUE_IMAGE_MAX` vs `ProductFieldRules.IMAGE_KEY_MAX`）。合并任意一侧都要动入站上限或动库，两者都属于契约/库变更，不在收口这一批里做；等值关系由 `FieldRuleVocabularyTest` 逐条核对，改窄那一条会红。
