# 订单 / 购物车 / 收藏

> 代码入口：apps/server/.../order、cart、favorite；apps/web（cart/checkout/order）、apps/seller/order。规则以代码为准沉淀，改代码请同步本文件。

---

## 一、订单创建与结算预览

- **[ORD-01]** 下单与预览都必须登录（`/orders/preview`、`/orders/create` 不在 JWT skipPaths 内，未登录 401）；订单归属校验一律「不存在与不属于本人同一句话」——404「订单不存在」，不泄露单据存在性；卖家侧越店访问同样 404。
- **[ORD-02]** 结算行来源不归后端管：购物车勾选与立即购买在前端归约成同一形状 `lines = [{skuId, quantity}]` 提交，order 不回查购物车、不区分来源；预览与创建都按 product/inventory 重算价格与库存。
- **[ORD-03]** 单行数量 1~999（`@Min(1) @Max(999)`，DB 列 `CHECK quantity BETWEEN 1 AND 999` 同值兜底）；请求里同 SKU 多行先合并件数，合并后仍封顶 999；**结算行数 1..99**（预览与创建同一对约束：`@NotNull` 管必填 + `@Size(min=1, max=99)` 管区间 → 422「结算条目需 1 到 99 行」；空列表另有 service 层兜底 400「结算条目不能为空」）——上限刻意与购物车坑位上限 CART-02 同源：全选整车恰好等于上限，超出即不经购物车、直接刷结算接口的脚本（恶拍防线之一，并发待付款单数闸门仍未落）。不写成 `@NotEmpty` + `@Size`：springdoc 的 `required` 只由 `@NotEmpty`/`@NotNull` 推，而 `@NotEmpty` 与 `@Size` 并存时 `minItems` 会被 `@Size` 默认的 `min=0` 盖掉——生成的 SDK 会同时丢掉非空与必填。
- **[ORD-04]** 结算行可售性三道判定：SKU 存在且在售、其 SPU 已上架、可用库存 ≥ 件数。前两道不过 → 失效行 cause=`UNAVAILABLE`；仅库存不足 → cause=`STOCK_SHORTAGE`。预览产出「有效行 + 失效行平铺」；**创建订单要求全量有效**，任一行失效/缺货直接拒绝（400「部分商品已下架或库存不足，请重新确认结算」）。
- **[ORD-05]** 一次结算按店铺拆成 N 笔订单（一店一单），**全成全败**（同一事务）；分组顺序按 shopId 升序（非用户勾选顺序），预览与成单同序——这是多店并发下单的锁序，防互等死锁。
- **[ORD-06]** 下单幂等键 `checkoutKey`（UUID，必填）：同一 `(user_id, checkout_key, shop_id)` 唯一（部分唯一索引 `uk_orders_user_checkout_shop`），重复提交在主表 insert 撞键后**回读原单返回**，不会第二次冻结库存；首次尝试因缺货回滚时什么都没落库，同一 key 可再用。前端进入结算页时生成一次（双击与超时重试同键），重新进入结算页 = 新一次结算 = 新键。
- **[ORD-07]** 收货地址：下单必填 `addressId`（预览可缺省），必须归属本人且未软删，否则一律 404「收货地址不存在」；下单瞬间把地址展开成订单上的收货快照列（收件人/电话/区划码/省市区/详址），之后改/删地址不影响本单。快照列**存明文**，脱敏只发生在出参（卖家侧看买家号码是掩码，ORD-62）。
- **[ORD-08]** 买家留言 `buyerMessage` 最长 200 字，可空；落库前 trim，全空白按 null 存。订单详情原样透出，空显示「—」。
- **[ORD-09]** 业务单号 `orderNo`（对外展示/客服对账用，与 UUID 主键分离）= 17 位毫秒时间戳(yyyyMMddHHmmssSSS) + 6 位主键随机段派生十进制，共 23 字符，全局唯一（`uk_orders_order_no`）；不做撞号重试，靠构造不撞。
- **[ORD-10]** 新单初始态 `PENDING_PAYMENT`，`afterSaleStatus=NONE`，`payExpireAt = 下单时刻 + 15 分钟`；落一行审计流水（无前态 → PENDING_PAYMENT，动作 CREATE，发起方 BUYER）。
- **[ORD-11]** 下单在事务内同步冻结库存（`stockCommand.freeze`，inventory::api）：库存不足抛 409 → 整笔下单（含全部拆单）回滚；同时逐单占用选中的券（`couponCommand.lock`，UNUSED→LOCKED），抢不到同样回滚。
- **[ORD-12]** 下单成功在事务内发布 `OrderPlacedEvent(userId, skuIds)`，cart 同步监听删已购 SKU 条目（见 CART-09）；**立即购买同样发布**——买家已买下该 SKU，车里同款条目一并清掉。
- **[ORD-13]** 结算预览是只读幂等接口，与创建走**同一条计费路径同一个方法**（同源同口径）；地址可缺省——无地址时运费只能预告 0，且这份预告不能当成交口径（创建必须带真实地址）。预览出参：按店分组（每组=一笔待创建订单）+ 失效行平铺 + 地址回显（可 null）+ 应付总额。
- **[ORD-14]** 一次结算（预览与创建皆然）最多选 20 张券（`@Size(max=20)`，语义=一店至多一张）；同店传同一张券两次去重后只用一次。买家选中的券随请求提交，后端逐张判定：**选了却不可用、或不属于本单任何一家店，一律 400 并说明原因，绝不静默忽略**（不可用时把券名和不可用原因码翻成话术返回）。
- **[ORD-15]** 券的候选顺序由后端定（可用优先 → 减免额大 → 先过期 → id），预览回传整份候选（含不可用者及原因码）供结算页渲染；**后端不自动替用户选券**，`appliedCouponId` 只回显请求里传来的 id，「默认选中第一张可用券」是前端行为（见 ORD-41）。
- **[ORD-16]** 店铺不配送到收货地区（运费模板命中不配送名单）时预览给 `deliverable=false`，结算页拦截提示；脚本绕过预览直接下单在创建处硬拒（400「部分商品不支持配送到所选地区，请更换收货地址」）。不配送优先于一切——包邮条件也救不了它。
- **[ORD-54]** 下单入口三道状态闸门（顺序即代码顺序）：① 账号闸门——经 account::api 的 `UserReadQuery.isActive` 校验买家状态，非 ACTIVE（含用户缺失）一律 403 + code `USER_DISABLED`「账号已被禁用」，与登录闸门同一份语义——token 未过期不等于账号还能交易；② 恶拍闸门——两条计数（细则 ORD-59），命中一律 429「待付款订单过多…」/「近期取消的未付款订单过多…」（无 code）；③ 营业闸门——本单涉及的**每一家店**（按有效行的 shopId 去重）过 `ShopReadQuery.isActive`，非 ACTIVE 一律 409「店铺已停止营业」（无 code，前端只按 status 分支），细则见 ACC-72。恶拍闸紧跟账号闸、排在地址快照之前（它是这道门口最便宜的检查，先把脚本挡在重活之外）；营业闸排在地址快照与有效行校验之后、拆单冻结之前，被拦时不触达任何数据动作。409 而不是 400：不是入参非法，是资源当前状态不允许这笔操作，与「商品已下架/售罄」同一口径。结算预览是只读接口，三道闸都不设（预览不是成交）。
- **[ORD-59]** 恶拍防护两道计数闸（拍下即冻结库存 ORD-11 的反制；一次多店结算本身就产出 N 单，故两条都按「单」计、不按「次」计）：**① 在途待付款 ≤ 10 单**——`count(user_id, status=PENDING_PAYMENT) ≥ 10` 即拒；**② 24 小时内拍下不付 ≤ 10 单**——`count(user_id, status=CANCELLED, paid_at IS NULL, cancelled_at ≥ now−24h) ≥ 10` 即拒，判据取 `paid_at` 为空：已付款后取消（含卖家超发货时限后买家自己取消 ORD-27）不算恶意。命中一律 **429**（无 code，`BusinessException.rateLimited`），语义是「你还能拥有这些单，只是不能再开新单」——**不释库存、不关在途单**，那几单照常按 ORD-26 自行超时关闭；阈值远高于正常买家量级。两条计数走 `idx_orders_user_created` 的 user_id 前缀，不为此加新索引。

## 二、状态机与可执行动作

- **[ORD-17]** 履约主状态机五态单路径：`PENDING_PAYMENT（待付款）→ PAID（待发货）→ SHIPPED（已发货）→ COMPLETED（已完成）`；`PENDING_PAYMENT` 与 `PAID` 均可 → `CANCELLED`；`COMPLETED` / `CANCELLED` 是终态无出边（**已完成不可取消**——终态没有到 `CANCELLED` 的边）。完成之后的交易纠葛走售后线（AfterSaleStatus），不再改主状态。转移合法性唯一真相是 `OrderStatus.TRANSITIONS` 表。
- **[ORD-18]** 一切状态变更走条件更新（`WHERE status IN (sourcesOf(目标态))`），影响行数即并发闸门：买家/卖家入口抢不到转移报 **409**（如「订单状态已变更，当前不可取消」），系统超时入口返回 false 让位——正确性不依赖锁。每次变更落一行审计流水（`orders.order_status_log`：前态/后态/动作/发起方 BUYER|SELLER|SYSTEM/原因）。
- **[ORD-19]** 可执行动作（按钮组唯一真相）由后端算：动作集 = 当前态出边 ∩ 角色允许的目标态。买家：PENDING_PAYMENT → `PAY, CANCEL`；PAID → `CANCEL`；SHIPPED → `RECEIVE`；终态 → 空。卖家：PAID → `SHIP`；**SHIPPED → `SHIP`（追加包裹，转移表带 SHIPPED 自环，见 ORD-55）**；其余为空。输出按枚举声明序（PAY, CANCEL, SHIP, RECEIVE）保证 JSON 稳定。买家列表/详情与卖家列表/详情**四个契约都下发 `availableActions`**，前端只定文案、顺序、主次，不再按状态另推一张按钮表。
- **[ORD-20]** **待发货（PAID）的买家可以取消**（`PAID → CANCELLED` 是合法转移，且回补库存 + 退款）——这是产品口径，不是漏洞；历史上前端只给「提醒发货」造成漂移，已收敛为消费后端动作集。
- **[ORD-55]** 多包裹动作暴露：转移表给 SHIPPED 加**自环**（SHIPPED → SHIPPED），与 `OrderMapper.markShippedReturningPrevious` 条件更新的 `status IN ('PAID','SHIPPED')` 是同一份事实的两个投影——追加包裹本就是合法转移，此前只是没进动作推导。效果：SHIPPED 态的 `sellerActions()` 继续派生 `SHIP`（按钮语义 = 追加包裹，目标状态不变），卖家列表/详情都能看到再发货入口；买家侧不受影响（SHIP 不在买家目标态集）。SHIP 动作语义随之扩展：同一动作两次落点不同（首发货落流水，追加只刷物流摘要，见 ORD-37）。
- **[ORD-56]** 卖家列表行契约（`SellerOrderListItemResponse`）下发 `availableActions`（复用 `Order::sellerActions`，与买家列表同一先例同口径）；卖家列表行内「发货」按钮改为消费该动作集，不再按 `status === PAID` 硬推（收敛原则同 ORD-19：前端只定「怎么画」，不定「有没有」）。

## 三、金额构成与计费口径

- **[ORD-21]** 订单金额四件套恒等式：`pay_amount = item_amount + shipping_fee − discount_amount`（单位分），由 DB 约束 `ck_orders_pay_amount`（V57）与 service 计费双钉；另 `0 ≤ discount_amount ≤ item_amount + shipping_fee`（不得减穿为负）、各金额列 `≥ 0`。行项目小计 `amount = price × quantity`（`ck_order_items_amount`）。
- **[ORD-22]** 商品额 = Σ(成交单价 × 件数)，价格取**下单瞬间 SKU 快照**（现价 + 划线价原样定格）；图片在解析时定格（SKU 图空回落 SPU 主图），读端零逻辑。
- **[ORD-61]** 行项快照再加一项服务声明：`orders.items.seven_day_return`（NOT NULL DEFAULT TRUE，V63）在下单瞬间从 `product.products.seven_day_return` 定格（`ValidLine` 的最后一个分量 → 落库），与 name/price/image 同族「成交即定格」。**售后判定读它而不读商品现值**（AFS-45）：买家那份七天无理由在下单那一刻定终身，卖家后来改勾选抹不掉已成交的单。整单售后取「**每个行项都为 true** 才算这单支持无理由」——拼单里有一件不支持，就不把强制加到卖家头上（宁可少强制，不可错强制）；行项为空同样按不成立处理。列不给 NULL 第三种语义：不支持是显式声明，缺省即支持，历史行回填 TRUE 与法定默认一致。
- **[ORD-23]** 运费由 shop::api 运费模板报价得出，订单侧按**同店合计**整单取一份、不是按行累加；店铺未配运费模板 → 运费恒 0。落库同时定格计费快照：模板 id + 收货区划码。（运费门槛/包邮判定/报价细则归 logistics.md，券门槛基数归 coupon.md）
- **[ORD-24]** 用券快照三列随订单定格：`user_coupon_id`、`coupon_bearer`（承担方 SELLER/PLATFORM）、`discount_amount`——前两者**同空同非空**（DB CHECK `ck_orders_coupon_snapshot_complete`），`discount_amount` 恒非空、不用券为 0；`coupon_bearer` 取值限 SELLER/PLATFORM。券规则事后被改、券被删除都不影响本单自证「减了多少、凭哪张券」，承担方是将来结算拆账依据。
- **[ORD-25]** 金额与预览同源：订单落库的金额四件套直接吃分组计费结果，**不重算**（重算必漂移）；「预览一个价、下单另一个价」被当作最经典客诉来源专门防。币种成对落库：订单 `currency` 取 `item_amount` 的币种（一单恒单币种），行项币种跟成交价，全链路 Money。

## 四、生命周期时限（超时）

- **[ORD-26]** 待付款窗口：**下单起 15 分钟**未支付自动关单（`pay_expire_at`），动作 AUTO_CANCEL、发起方 SYSTEM、原因固定「超时未支付，自动关闭」；只认 PENDING_PAYMENT，到期释放冻结库存（未付款，不发退款事件、不涉及退款）。
- **[ORD-27]** 发货窗口：**付款起 3 天**记在 `ship_expire_at`（付款时回填）——**只作提醒依据，不驱动任何自动转移**（超时扫描表里没有 PAID 这条线，见 ORD-60）。到期不关单、不退款：卖家的发货违约成本不由系统代买家处置。该列随三个出参下发（买家列表项 / 买家详情 / 卖家列表项，`nullable`），其发货时效判定与物流轨迹口径归 logistics.md。
- **[ORD-28]** 确认收货窗口：默认 **发货起 7 天**（`receive_expire_at` 发货时回填兜底）；物流轨迹推进到**签收**时由 logistics 经 `order::api markDelivered` 从签收时刻**重算 7 天**——用户看到的是「签收后还有 7 天」。到期自动确认收货（AUTO_RECEIVE，无库存/退款动作）；**该单有进行中的售后单时让位**，等售后落到终态后同一轮扫描再完成（AFS-43）。`shipped_at` 与 `receive_expire_at` 只由首次发货回填，追加包裹不后推；包裹退回（RETURNED）时同样从退回时刻重算（LOG-17）。
- **[ORD-29]** 售后申请窗口：**完成（确认收货）起 15 天**（`apply_expire_at` 完成时回填），过期不再受理售后申请。
- **[ORD-53]** 两条时限的衔接：确认收货有「发货起 7 天（签收后重算 7 天）」的超时自动确认（ORD-28），到期系统 `AUTO_RECEIVE` 转完成并同步开通售后申请窗口（ORD-38 完成时回填 `apply_expire_at = +15 天`）——**自动确认后买家仍完整享有 15 天售后申请窗口**，超时自动确认不缩短、不吞掉买家的售后权；两条时限独立成立（一个决定何时转完成，一个从转完成那一刻起算）。
- **[ORD-30]** 超时扫描：每 **30 秒**一轮（fixedDelay），两条线（待付款 / 待收货）各按「状态 + 到期列」扫，单批上限 **100 笔**，逐笔独立事务；多实例并发扫靠条件更新让位，不加分布式锁。

## 五、支付与订单推进

- **[ORD-31]** 支付入口在 payment 模块，只有 PENDING_PAYMENT 单可发起支付（409「订单不是待付款状态」），一单至多一条成功流水。两段式流程等支付单细则见 payment.md。
- **[ORD-32]** 支付确认同事务推进订单 `markPaid`：条件转移 PENDING_PAYMENT→PAID（抢不到抛 409 令支付事务整体回滚，资金与订单两侧原子）→ 扣实冻结库存（capture）→ 核销本单券（LOCKED→USED，**自此不可逆**，退款走补发新券）→ 回填 `paid_at` 与 `ship_expire_at`。

## 六、取消与退款触发来源

- **[ORD-33]** 取消唯一落点按**真实前态**分流（条件更新 RETURNING OLD 取回，不靠 CAS 前的陈旧读）：付款前（PENDING_PAYMENT）取消 = 只释放冻结库存 + 券 LOCKED→UNUSED 回买家手上可再用；付款后（PAID）取消 = 回补总库存（`stockCommand.restock`，流水类型 RETURN）+ 退券补偿（原券已 USED，**另发新券**）+ 发 `OrderCancelledEvent` 委托 payment 同事务落退款单（该单唯一 SUCCESS 流水原地转 REFUNDED，不新建行）。两条路径的失败姿态刻意不同：**取消是买家既得权利，退款写不成不阻塞取消**——无成功流水或渠道拒退时取消照成、退款留缺口走人工对账（对账兜底见 PAY-13），只有售后路径才是「退款失败连带回滚」（PAY-24）。取消本身失败则什么都不落。
- **[ORD-34]** 退款（资金置 REFUNDED）只有两个触发来源：① 已付款订单被取消（买家手点——含卖家超发货时限后买家自己选取消，ORD-27）→ `OrderCancelledEvent`；② 售后退款成立 → `AfterSaleRefundedEvent`。未付款单取消不发退款事件。payment 侧对两类事件的监听处置取舍见 payment.md。
- **[ORD-35]** 买家取消原因可选、最长 200 字（`@Size(max=200)`），trim 后落 `cancel_reason`；超时关单/自动取消由系统写固定文案，不走该入参。买家端取消弹层收集原因并透传（见 ORD-57），不再固定传「用户取消」。
- **[ORD-57]** 买家取消原因弹层（列表/详情共用，`useOrderActions` 持有状态、页面渲染 `cancelDialog`）：快捷原因**不想买了 / 信息填错 / 其他**（单选、可跳过）+ 备注（选填，封顶 180 字），提交时拼成一句自由文本（`原因：备注`）透传 PUT `/orders/{id}/cancel` 的 `reason`——后端本就是自由文本，**不造枚举 code**；一个都没填则 `reason` 缺席（不硬造「用户取消」占位）。换单重挂载弹窗，已填内容不跨单残留。

## 七、发货与收货（跨 logistics）

- **[ORD-36]** 发货入口在 logistics（`POST /seller/shipments`；老路径 `PUT /seller/orders/{id}/ship` 兼容承接），需 ORDER_FULFILL 权限，店 ID 取 X-Shop-Id 上下文，前端不传；越店与不存在同为 404。发货必须给启用字典内的承运商 code + 非空运单号（自由文本名已废），且店铺已设默认发货地址（否则 400「请先设置默认发货地址」），寄件人快照定格进包裹。
- **[ORD-37]** 一单可多次发货（多包裹）：首次 PAID→SHIPPED 落审计流水并回填 `shipped_at/receive_expire_at`；追加包裹 SHIPPED→SHIPPED 无状态转移、不落流水（自环见 ORD-55，`sellerActions` 因此继续下发 `SHIP`），只把订单上的物流摘要（公司/单号）刷成**最新包裹**口径。包裹落不下则订单不推进（同事务），反之亦然。一个运单号只能属于一个订单（唯一索引，撞键报「该运单号已录入」）。可发货状态 = PAID 或 SHIPPED，其余（已取消/已完成）409「订单当前状态不可发货」。
- **[ORD-38]** 确认收货：仅 SHIPPED→COMPLETED（买家 RECEIVE 或系统 AUTO_RECEIVE 共用落点），转完成时回填 `completed_at` 并开通售后申请窗口（`apply_expire_at = +15 天`），同事务经 product::api 累加销量投影（行项按 productId 合并）。抢不到转移 409。

## 八、售后投影

- **[ORD-39]** 订单持有售后投影列：`afterSaleStatus`（NONE/APPLYING/RETURNING/REFUNDED/REJECTED/CLOSED，NONE=从未申请）与 `refund_amount`（仅退款完成时写回，须与本单同币种否则 WHERE 挡掉），由 aftersale 每次转移经 `order::api syncAfterSale` 同事务写回；售后单真相在 aftersale.tickets，order 不反向读。售后线与履约主状态**正交**（完成单可同时展示主状态 + 售后徽章）。
- **[ORD-40]** 售后申请门槛（四项同时成立）：订单已发货或已完成（SHIPPED / COMPLETED，待收货阶段的出口细则见 AFS-43）、申请窗口未过（待收货不设截止，完成后按 `apply_expire_at`，AFS-02；申请时的条件更新即闸门）、无进行中的售后单（`uk_tickets_open_per_order` 并发下也只容一张）、最新一张售后单非 `REFUNDED`（已退款禁止再次申请，409 + code `AFTER_SALE_ALREADY_REFUNDED`，见 AFS-05）。退款口径 V1 = 整单实付（`refund_amount = 订单 pay_amount`），不支持部分退。买家撤销仅 APPLYING 可做；卖家同意仅退款=一步退成，同意退货退款=转 RETURNING，确认收到退货才退款+回补库存；被拒/撤销后窗口内可重新申请。

## 九、买家/卖家侧前端规则（web / seller）

- **[ORD-41]** 结算页地址默认勾选：用户手动选过的保留 → 否则取默认地址 → 否则第一条；一个地址都没有时不能提交（按钮禁用 + 引导去添加）。结算行经 URL search 传递（skuId+正整数件数，脏值兜底成空数组走「无可结算条目」）；结算页需登录。提交成功后统一跳**第一单**的收银台（多单经 search.orderIds 携带，V1 按单逐单支付）。
- **[ORD-42]** 换券/换地址/换行项都触发重新预览（queryKey 含三者），换券必须重算——这正是「预览价≠实付价」的防法；默认选券只补「未表态」的店，用户已表态（含明确选「不使用」）不被后来的预览覆盖，已不在本单的店自动剔除。提交前把每店选择归约成 `userCouponIds`（过滤未选/不用，排序保证 key 稳定）。
- **[ORD-43]** 结算页选券口径：一店一张（Record shopId→userCouponId，null=明确不用）；后端判不可用的券置灰并把原因码翻成人话；后端不选券、前端默认选第一张可用券（见 ORD-15）；一家店无候选时不开展开入口，显示「本店暂无可用优惠券」。
- **[ORD-44]** 结算页金额展示恒按「商品总价 + 运费 − 优惠 = 应付总额」口径，优惠为 0 不渲染该行；应付以预览净额为准，预览未回来显示占位「—」而不是 ¥0.00。行小计前端本地算（单价×件数）仅展示用，成交以服务端为准。
- **[ORD-45]** 前端状态投影：后端 PAID → 领域「待发货」、SHIPPED →「待收货」、COMPLETED → 展示文案「交易成功」；无「待评价/退款中」主状态阶段；未知 wire 值兜底显示为待付款。列表筛选传回后端大写枚举。
- **[ORD-46]** 待付款订单在列表卡片与详情页展示「付款剩余 mm:ss」倒计时（取契约的 `payExpireAt`，其余状态不显示）。
- **[ORD-47]** 订单按钮排 = 后端动作（PAY/CANCEL/RECEIVE → pay/cancel/confirm，SHIP 买家侧丢弃）∪ 前端附加动作：待收货追加「查看物流」；终态卡片追加「再买一单」，详情页 completed 额外给「加入购物车」并把「再买一单」升为主操作。主操作每屏唯一：待付款=去付款、待收货=确认收货。顺序固定（pay→cancel→logistics→confirm→rebuy→add_cart→ship）。取消走取消原因弹窗（ORD-57），确认收货带全局二次确认；进行中按钮禁用防重复提交。
- **[ORD-60]** 卖家超发货时限的展示口径：**只提醒，不代关单，不给死按钮**（拍板，不是遗漏）。三处落地：① 超时扫描表里没有 PAID 这条线（`OrderTimeout` 只有待付款 / 待收货两条，ORD-30），系统永不自动取消已付款单——买家的出口本就是 ORD-20 的待发货手点取消 + ORD-33 的付款后回补退款，无需系统代劳；② 买家列表卡片按 `shipExpireAt` 改文案：未到点灰字「商家需在 yyyy-MM-dd HH:mm 前发货」，过点红字「商家已超过发货时限（…），可取消订单并退款」，倒计时只在这张卡上呈现，详情页不加（同一句文案不两处维护）；③ 卖家工作台列表在 PAID 且过点时挂「超时未发货」徽章。前端**删除**了历史上那个「提醒发货」按钮：全站没有消息通道，它点了什么都不发生（占位按钮不算功能）。
- **[ORD-48]** 买家订单列表页签：全部/待付款/待发货/待收货/已完成，**「已取消」不设页签**；列表分页按下单时间倒序，非法状态筛选值 400（`status` 以字符串收，service 层 `valueOf` 失败即 `badRequest`，不走 Spring 类型转换的 400 兜底，见 GEN-19）。店铺已注销时店名为 null，UI 显示「店铺已关闭」。
- **[ORD-49]** 列表契约只有净额 `payAmount`（商品额/运费/优惠拆分只在详情），金额三行必须在详情页用详情契约覆盖才加得起来；列表卡片内嵌行项目免二次请求。
- **[ORD-50]** 售后入口（订单行上「申请售后」）前端门槛与 ORD-40 对齐：待收货或已完成 + 申请窗口未过（待收货阶段 `applyExpireAt` 还没回填，缺列即视为开着，AFS-02）+ 无进行中单；**已退款（REFUNDED）不再提供入口**（后端同拦二次申请，409 `AFTER_SALE_ALREADY_REFUNDED`，见 AFS-05）。类型二选一：仅退款（不寄回，同意即退）在前、退货退款（寄回，卖家收货后退）在后。买家售后动作按单状态直读：APPLYING→撤销；RETURNING→填/改退货物流（已填再多一个「查看」）；终态→无。
- **[ORD-51]** 卖家工作台订单列表：五个主状态页签（含已取消）+ 售后状态第二徽章线；行内「发货」消费契约下发的 `availableActions`（含 SHIP 即给，PAID 首发货与 SHIPPED 追加包裹同按钮，见 ORD-55/56），**不再按 status 硬推**；售后按钮同口径吃契约下发：动作集由 aftersale 按本页订单批查（`GET /seller/after-sales/actions?orderIds=…` → `SellerOrderTicketActions`，与售后工作台同一份 `TicketAvailableAction`），前端**不按订单上的 `afterSaleStatus` 投影另推一张按钮表**（订单行那条投影只用于徽章）。为什么不并进订单行：动作由售后状态机算出，而依赖方向是 aftersale → order :: api，反向带字段会成环。批查失败只意味着「这一行暂时不给售后按钮」（`throwOnError: false` 降级，不炸整页），卖家仍可从售后工作台处理。动作与售后条件都不满足显示「—」。售后工作台默认停在「待处理(APPLYING)」页签。
- **[ORD-62]** 买家手机号对卖家默认脱敏（个保法最小必要，与 ACC-75～78 同一族的「交还对个人信息的控制」）。卖家侧**任何**出参里的收件人电话都是掩码（唯一出口 `PhoneNumber.mask()`，前 3 后 4 → `138****1234`），落两处：列表行 `SellerOrderListItemResponse.receiverPhone`、详情 `OrderDetailResponse.sellerView(...)`。详情契约与买家侧共用一个 record，所以掩码挂在**视角工厂**上而不是 `from` 里——买家看自己的号仍是明文，同一字段两侧语义不同是这条规则定的例外，别当重复实现合并掉。明文唯一出口 `POST /seller/orders/{id}/receiver-phone`（权限随类级 `ORDER_FULFILL`，读随写权；越店与不存在同为 404，复用 `requireShopOwned` 那道门），取用即打 `order.receiver_phone_revealed` 事件（`shop_id` / `order_id` / `operator_id`，**号码本身不进日志**），叠加 `http.request` 的天然逐请求留痕。
  ① 为什么不掩姓名与详址：卖家发货必需，而我们没有隐私面单 / 虚拟号那一层（快递渠道只查轨迹，从不下发收件信息），掩了就是不给发货；淘宝用虚拟号解的那一半，我们对应的产物是「默认掩码 + 逐单显式索取 + 取用留痕」。
  ② 前端（工作台列表「买家」列）显示掩码并给「查看」入口，取到的明文**就地写回列表缓存那一行**（不另立组件状态），且这个动作**不失效列表查询**——失效会立刻重拉、后端回的还是掩码，等于刚点开就抹回去；已取明文的行不再给「查看」。
- **[ORD-58]** 结算页买家留言：左栏「买家留言」输入框（Textarea，选填、封顶 200 字对齐 `@Size(max=200)`），随下单 mutation 透传 `buyerMessage`（trim 后空串按未填处理，不传占位）；整次结算一份，按店拆单时逐单落同一句快照（契约与落库口径见 ORD-08）。
- **[ORD-52]** 收银台金额取自订单详情（loader 强制读最新，「不能拿一份可能过期的金额去收钱」），前端不报价；「确认支付」一次点按串联两段（发起→确认）。

## 十、购物车

- **[CART-01]** 加购门槛按序三道：SKU 存在且在售（否则 400「商品规格不存在或已停售」）、其 SPU 已上架（否则 400「商品已下架」）、**商品所属店铺在营业**（`ShopReadQuery.isActive`，非 ACTIVE 一律 409「店铺已停止营业」，与下单同一口径，见 ACC-72）；**库存不足不拦加购**（闸门后移到下单）。第三道挡的是「车里已有条目 + 店刚好停了」的并发窗口——店被驳回/禁用时其上架商品已被事件级联下架，第二道就先挡下了。
- **[CART-02]** 单用户购物车最多 **99 种不同 SKU**（条目坑位上限，防刷）；车里已有该 SKU 时只累加数量、不占新坑、不计入该闸门。
- **[CART-03]** 同 SKU 重复加购**幂等合并为数量累加**（不是新增行），累加封顶 999（upsert `LEAST(旧+新, 999)` 在行锁下由 DB 完成；DB 列 CHECK 1..999 兜底）；单行入参数量 1..999。
- **[CART-04]** 新条目默认勾选（`selected DEFAULT TRUE`，落库保证跨设备一致）；列表按加入时间倒序（新加的在前）。
- **[CART-05]** 条目可改数量（1..999）与勾选位，null 字段保持原值；批量勾选 itemIds 省略=作用于整车（全选/全不选共用），所有操作 SQL 带 user_id 归属条件，越权条目一律 404 不泄露存在性。
- **[CART-06]** 失效条目（SKU 被删/停售、SPU 下架）**原样保留置灰**（`available=false`），供买家清理；SKU/商品已被删除时连快照都不返回（product/sku 为 null），下架则快照仍在。批量删除（清除失效/删除选中共用）要求非空 id 列表。
- **[CART-07]** 角标计数分开给：总条目数 + 已勾选条目数，免拉整车。
- **[CART-08]** 购物车条目展示实时价与实时可用库存（现价/划线价 + availableStock，加购到下单之间保留比价窗口），但都是只读投影，成交以下单重算为准。
- **[CART-09]** 下单即清车：cart 同步监听 `OrderPlacedEvent`，在**下单事务内**按 userId+skuId 删除被买下的条目（不依赖条目 id，order 不认识购物车）——不变式：订单在，条目必不在。事件发布口径（含立即购买同样清车）见 ORD-12。
- **[CART-10]** 前端结算只认「已勾选且可售（available 且快照齐全）」的条目；失效条目不参与全选语义，全选框只有「未选/全选」两态（部分勾选显示未选）；整车按店铺分组展示、保持服务端顺序，商品已删除的条目聚到末尾「失效商品」组；单条数量前端预判上限 999 与库存（以后端裁决为准）；下单成功后购物车列表与角标缓存一并失效。

## 十一、收藏

- **[FAV-01]** 收藏是 **SPU 级**（收藏商品不收藏规格），只对「存在且已上架」的商品开放，否则「商品不存在或已下架」；数量无上限（无坑位闸门）。
- **[FAV-02]** 收藏是幂等开关：重复收藏不报错、不产生第二行（upsert 撞 `(user_id, product_id)` 唯一索引返回既有行）；取消收藏 = DELETE，不存在也返回成功。非行管理——没有「改收藏」一说。
- **[FAV-03]** 收藏列表按收藏时间倒序（新收藏在前）分页；商品被删/下架时条目保留置灰（`available=false`），卡片数据读取时拼装并带收藏人数（本模块自有指标 count 聚合）。
- **[FAV-04]** 「是否已收藏」是独立批量查询接口（入参商品 id 集，返回已收藏子集），商品详情不内嵌该状态——product 模块不反向依赖 favorite。
