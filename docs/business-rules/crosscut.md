# 横切全局行为

> 代码入口：packages/client（sdk-client）、packages/common（error-codes）、app-kit（QueryBoundary/notify/confirm）、createAppQueryClient、infra RequestIdFilter/GlobalExceptionHandler；入站校验词表在各领域类型（PhoneNumber、RegionRegistry、Quantities、AddressFieldRules、NoteFieldRules、TrackingFieldRules、AccountFieldRules、cms.dto.LinkTarget、cms.dto.CmsFieldRules、coupon.dto.CouponFieldRules、UserCouponStatus、ProductSort、ProductFieldRules），门禁是 ValidationVocabularyTest 与 FieldRuleVocabularyTest；业务事件唯一出口是 infra.observability 的 BizEvent（`MdcScope` 只管信封），目录门禁是 BusinessEventCatalogTest。规则以代码为准沉淀，改代码请同步本文件。

## 错误码体系

- **[GEN-17]** 错误码定义原则（判据改过两版，第二版是 2026-09-30 被普查逼出来的）：**用户看到的句子由前端 catalog 或状态码通道给；`detail` 只在中文界面当文案，其它语种它是日志字段。** 第一版写的是「这句话用户可见 → 就要有 code」，不再问「前端要不要分支」——它字面执行要新建 **204** 个码（报错出口 304 处 / 带 code 37 处 / 不带 code 那 267 处的内联中文句子去重 204 句，口径与复数方式在 `docs/error-codes.md` 头部），而那一百多句绝大多数前端从不按句子分叉（404 的 78 处全是「XX 不存在」）。所以 code 的准入换回两条：**前端要按它分支**，或**这句话被兜底接住的真实频次证明它值得单独翻译**。用户看到的句子归前端 catalog——`packages/app-kit/src/locales/{zh-Hans-CN,en-US}/error.json` 的 `error.<CODE>`，两份语言每个码恰有一条；拿不到 code 时非中文界面按状态码取 `appKit.error.*`（九条两份语言齐），中文界面取 `detail`。两个上限码（`ADDRESS_LIMIT_EXCEEDED` / `MERCHANT_ADDRESS_LIMIT_EXCEEDED`）**曾**在 detail 优先的例外清单上，2026-10 改走 `params` 通道后退出（上限数字作为数据出一次，catalog 用 `{limit}` 槽位接，后端改数字前端零改动）——**例外清单已空，且不再是机制而是历史**。句子装不下关键值时**不再靠 detail 兜**，走字段级参数通道：ProblemDetail 扩展属性 `errors` = `[{ field, message, value? }]`，`field` 是消费方表单/DTO 的机器字段名、`value` 是那条规则作用到的数据，前端 `packages/common` 的 `ApiFieldError` 是对边——第一个用它的是 `FORBIDDEN_WORD_HIT`（COM-01 命中词，2026-09-30 退出例外清单）。不复述状态码那一档仍然保留（404/403 那句由前端自己的通道出，给它们加 code 只会多一条没人读的键），表单校验错误由 `errors[]` 列表承载同理。逐条码的唯一真相源是注册表 `contracts/error-codes.mjs`（2026-10 起；此前是 `docs/error-codes.md` 里那张表），Java 侧 `common.ErrorCodes` 与 TS 侧 `error-codes.ts` 是 `pnpm errors:gen` 的生成物、文案同步至两份 `error.json`（**四边**相等由 [GEN-62] 的 `ErrorCodeVocabularyTest` 核对，TS 侧另有 `error-keys.ts` 的 `satisfies` 在编译期拦「加了码忘配文案」；条数不在本条写死，以文件为准）。`behavior` 那一栏允许是**无专属分支**那一档（如 `SHOP_NAME_TAKEN`/`USER_DISABLED`/`INSUFFICIENT_STOCK` 只是如实 toast 一句 catalog 文案）——这类 code 的价值在让文案可预期、可 grep、可测，不因「不驱动 if 分支」就违反定义原则；但该栏必须写实际行为，不写承诺，且必须以「按码分支：」或「不按码分支：」开头，这一句是不是事实由生产源码里真实的 `ErrorCodes.X` 引用反查，而不是由人声明。门禁查的是 code→文案，**不是** detail→code，而这一侧按新判据**不设全量门禁**（补齐即 204 个码）：收拢它的是 `notify.fromError` 在走过 detail / 状态码那两支时发的 `error_fallback source=… status=… code=…` 上报，升级名单从真实频次来，不从那 204 句里猜。

- **[GEN-62]** 错误码是这座仓库里唯一没有类型承载的对外词汇，所以三边（注册表 `contracts/error-codes.mjs` → 生成的 Java `common.ErrorCodes` ⇄ 生成的 `packages/common/src/contract/error-codes.ts`）与注册表自己宣称的前端动作，全部改由 **`ErrorCodeVocabularyTest`**（无库、不起 Spring，反射 + 纯文本）核对（GEN-17 那句「无一致性测试兜底」从今天起不成立）。§7.3 落地之后**又长出第四边**——每个 code 在 `packages/app-kit/src/locales/{zh-Hans-CN,en-US}/error.json` 恰有一条非空、不重复的 `error.<CODE>`，两份语言的键集合都与注册表 ∪ 客户端那份词表相等；这道核对过去没有，它守的是「加了码忘了配文案」，那是新判据（GEN-17）下唯一会静默伤到用户的一种漏。收成一份的依据与 GEN-56 同一条：code 拼错是**无声**的——状态码照旧、detail 照旧、只断状态码的接口测试照旧绿，唯一变的是前端那条按码分支静静地永不命中；而 41 处抛出点散在 19 个文件里各抄字面量，同一个码最多抄了 6 遍（`INVALID_TOKEN`）。现在字面量的 owner 是 `common.ErrorCodes`（24 个码，与注册表那 24 张卡逐一对应、顺序相同，由 `pnpm errors:gen` 生成；前端独有的四个住 `client-failure.ts`，**不进注册表**），抛出点只许写 `ErrorCodes.X`：注册表里的每个值在 `src/main/java` 除 owner 外零出现，且每个出口的码位实参只许是 `ErrorCodes.X`、`null`（那一发刻意不带码）或三处**登记在案的导管**（`Validate.isTrue` 的形参、两个鉴权过滤器手里的 `verification.code()`）——白名单是等式，新起一条「码从变量里来」的导管当场红，因为那种站点静态扫不到就等于不存在。**状态码不在测试里抄表**：`badRequest/forbidden/conflict` 各自给哪个状态，由测试从 `BusinessException` 的工厂签名与函数体读出来（工厂改状态，文档那一列就红），并且要求每个静态工厂要么属于「带码」那族、要么属于「只给人话」那族（`notFound`/`unauthorized`/`rateLimited` 与两个 1 参重载），长出第三种形状会让出口枚举不再完整——这一条是**分全性**而不是抽查。**`behavior` 那句分支声明由扫描验真**：门禁拿生产前端（三端 `src` + 三包 `src`，排除 `*.test.*`/`*.gen.*`/生成物）里真实出现的 `ErrorCodes.X` 反查出「有没有读点」，与声明两向都必须相等——新增了按码分支的地方不回写注册表会红，注册表写着「按码分支」却已扫不到读点也红。**具体文件名不落在任何需要人回写的格子里**（2026-10 起：旧文档表那一列同时是声明和扫描结果，两份真相源靠一条门禁焊住，正是那五条愿望的成因）。起这道闸门前该列并不存在，而「前端行为」那一列有五行写着码驱动的动作用于全仓零引用（`TOKEN_EXPIRED`/`INVALID_TOKEN` 宣称续期与跳登录，实际 401 路径只看状态；`PERMISSION_DENIED` 宣称渲染无权限页，全仓没有那句话；`SHOP_NAME_TAKEN` 宣称字段标红，而后端那一发不带 `errors`、标红来自提交前的 zod；`BANNER_TIME_RANGE_INVALID` 同因）——五行的文案已按实际行为改写，动作本身是产品决定，不在本轮顺手实现。**与 GEN-56 那一族数字的关键差别**：code 由 `GlobalExceptionHandler` 挂成 ProblemDetail 扩展属性，**不进** `openapi/api-docs.json`，所以改码不需要 `pnpm sdk:gen`（今天六个码在契约文件里出现次数全为 0，实测）；本轮所有替换逐字节同值。TS 侧同批把 `ErrorCodes` 与 `RESPONSE_VALIDATION_FAILED` 两个出口登记进 `shared-vocabulary.test.ts` 的「owner 不是孤儿」清单——前端只许有一份错误码表。**它挡不住的**：`detail` 文案与日志里的码（不是契约，随便改）；码值本身被换掉而三边同步改齐（那是接口变更，得人判）；以及同一码在两个出口给出不同状态之外的「多重状态」情形——那种情况测试直接报「同一个码在不同出口给出多种状态」，今天零例。

- **[GEN-63]** 判权码与错误码同罪，代价更贵一档（GEN-62 的同类，第二份没有类型承载的对外词汇）。owner 是 `common.Permissions`（十三个码：admin 域 8 个 + seller 域 5 个，`all()` 是全量清单），`docs/conventions/permission-codes.md` 那张表是它的**镜像**，三边核对由 **`PermissionVocabularyTest`**（无库、不起 Spring，反射调用生产代码 + 源码扫描）承担。收成一份的依据比错误码更硬：`@RequirePermission` 里少写一个字母不会报错，只会让那道判权**静默换成另一个名字**——错误码拼错断的是一条前端分支，判权码拼错断的是一次越权。禁令与等式：码值字面量除 owner 外在 `src/main/java` 零出现、注解码位只许是 `Permissions.X`（写 `null`、写局部变量、写别的常量都当场红）、每个码都真的有挂点（无挂点的码只有通配能命中，那是死码）、文档表 ⇄ 常量 ⇄ `all()` 同一集合且每行一个码。**文档那两列是推出来的，不是抄的**：「授予」由 `StaffRole.permissions()` 与 `SellerGrants.GRANTABLE` 求值生成（岗位改映射而表不跟着改就红），「消费端点」由注解扫描生成——于是「运营作废券暂借 `CMS_MANAGE`」这件事第一次从注释搬进表里看得见；只有 SUPER_ADMIN 通配可达的码与「文档有、代码无」的占位码各自钉成 `containsExactlyInAnyOrder` 的等式（今天分别是 `{STAFF_MANAGE}` 与 `{MEMBER_MANAGE, SHOP_MANAGE}`），加一行必须同时进登记集合，不然红。
  同轮修掉的真 bug：`AdminEndpointGuardTest`（文档宣称与运行时默认拒绝构成「双保险」）自己抄了一份 `List.of("/admin", "/seller")` 并**内联重写**了命名空间判定，而 `StaffAuthFilter` 的注释正写着「两处共用 `RequestPaths.inNamespace`」——判权清单加第三项时运行时会拒绝、自检查不到，双保险当场是空话。现在清单（`GUARDED_NAMESPACES`）、判定（`inNamespace` / `inGuardedNamespace`）与自服务豁免（`ADMIN_SELF_SERVICE_PREFIX` / `isAdminSelfService`）全部住在 `infra/web/RequestPaths`，拦截器、两个过滤器、启动自检、本门禁五处共用同一份；`JwtProperties.skipPaths` 里的 `"/admin"` 与 `StaffAuthFilter` 那两条 login/refresh 前缀一并由常量拼出（逐字节同值），并由结构禁令钉住：命名空间字面量只许出现在 owner 与 `@RequestMapping` 的路由值里（放行侧留了样本断言，防禁令扫过头）。
  顺带立一条此前没人在意的安全等式：**匿名白名单按 `startsWith` 匹配、判权按命名空间匹配**，两者的缝（如假想的 `/administrators`）意味着该路由既不过买家认证也不要求权限码 = 匿名且无判权。`匿名白名单与命名空间守卫在真实路由上不分歧` 从源码把每条真实路由拼出来（类级 `@RequestMapping` + 方法级映射）逐条核对，今天零分歧；反证已做——把员工端点基路径改成 `/adminauth` 当场红。另留 `受保护命名空间的每条路由都声明了权限注解` 作为启动自检的**静态版**：那道 Spring 测试要起上下文（无库跑不了），静态版核对同一条不变量、路由清单换成源码解析，因此没有库也仍在跑。本轮 11 道反证全部命中各自的断言（常量名与值分家 / 新增常量漏进 `all()` / 注解码位写字面量 / 文档少一格消费端点 / 文档改一个岗位 / 文档多一行代码没有的码 / 第二份命名空间字面量 / 路由落进前缀缝 / 删掉判权注解 / 自服务前缀被改写 / 前端抄一份码）；前端零消费点这一句也从声明改成扫描（三端三包 `src` 里出现权限码字面量即红，真要按码隐藏入口时会红着提示先建 owner）。**它挡不住的**：岗位该不该管券这类语义（映射本身是产品决定）、`skipPaths` 被 yaml 覆盖后的分歧（本门禁读的是 `JwtProperties` 默认值，覆盖时要有带上下文的测试来判）、以及路由从别处拼接而来的一切形状（本仓库目前为零）。迁移脚本 V23/V24 的头注释仍写着搬家前的 `docs/permission-implementation.md`、`admin/service/StaffRole` 和只有两码的旧白名单——那是事实发生过的地方，按 GEN-61 的判据不改。

## 错误信封

- **[GEN-18]** 后端错误统一 RFC 9457 ProblemDetail 信封：`{ title, status, detail, instance, requestId, code?, params?, errors? }`，`requestId` 取链路 trace_id、`instance` 由 Spring MVC 从请求 URI 补；所有错误响应带 `Cache-Control: no-store`。**形状的唯一书面来源是 OpenAPI 契约**（`ApiProblem`，每个端点挂一条 `default` 响应；2026-10 的 N3 落地，见 `docs/error-codes.md` §错误响应契约），运行时与它是否相等由 `ErrorBodyVocabularyTest`（源码键 ⇄ 契约声明）与 `ErrorResponseContractTest`（真实响应 ⇄ 契约声明）两向核对。前端 SDK 错误拦截器先用生成的 `zApiProblem` 校验，再把任意失败归一化为 `ApiError { status, detail, code?, requestId?, errors?, params? }`——它**没有 `title`**（那是英文 reason phrase，对用户无用；此前在 schema 里声明着却从没人填，N3 一并删掉）；校验没过时保留原始状态码、退回逐格宽松解读，响应体无 `detail` 时兜底「请求失败，请稍后重试」；拿不到响应的失败为 `status: 0` 并按 `error.name` **分族**（`packages/common/src/contract/client-failure.ts` 的 `NETWORK_ERROR` / `REQUEST_TIMEOUT` / `REQUEST_ABORTED`，取消那一族不计进接口错误率）——三族此前共用同一句通用文案，而它们的用户动作互斥（检查连接 / 重试 / 什么都不说）。
- **[GEN-19]** 入参错误分四条线，形状各不相同：① **Bean Validation 失败 → 422 + `errors[{field,message}]`，不带 code**——`@RequestBody`（`MethodArgumentNotValidException`）与 `@RequestParam`/`@Validated` 约束（`ConstraintViolationException`）走同一个 `unprocessable` 组装，两处字段口径一致；② **请求根本解析不成参数 → 400，只有 detail 没有 errors**——缺必填查询参数、请求体不可解析（`HttpMessageNotReadableException`）、参数类型/枚举转换失败（`MethodArgumentTypeMismatchException`，回显值超 `ECHOED_VALUE_MAX`=100 字符截断；判越界与下刀必须引用同一个常量，写成两个字面量时改其一会让 `substring` 越界、这个 handler 自己落进兜底 500，由 `回显截断的阈值与下刀位置是同一个数` 从常量算期望值钉住），三者同形状；③ **业务代码自判的非法筛选值 → service 层 400 带人话 detail**（订单 status、售后 tab 等，见 ORD-48 / AFS-28），不经 Spring 类型转换；④ **路由不存在 → 404，不带 code 也不回显路径**——匿名白名单按 `startsWith` 放行（GEN-63 那条同一枚硬币的另一面），所以 `/api/cms/typo` 过得了认证又没有 handler，最终由静态资源处理器抛 `NoResourceFoundException`；它此前进 `Exception` 兜底 = 客户端打错一个 URL 换来 500 加一条「未捕获异常」的 ERROR 堆栈（启库实测 `/api/cms/home-nav` 撞出来的，测试全绿因为它从不打这个 URL）。落点由 `ProductControllerTest.非法排序_422带字段名` 实测钉住，不是从注释推的（该注释曾错写 400）；④ 的落点由 `UnmappedRouteTest` 走真过滤器链钉住（删掉那个 handler 会红成 500，反证已做），只测 handler 本身不算数——路由到 handler 的交接也要有人钉。前端表单被 Zod 拦下的不产生后端 code。**同一个「值不在合法表里」落哪条线，取决于门装在哪一层**：查询 DTO 上挂了 `@Pattern` 的（券包 status、商品 sort）走①＝422，字符串直收、service 用 `Validate.enumFilter` 自判的（订单/售后/审核）走③＝400。
- **[GEN-28]** 客户端本地失败自成一族，住 `packages/common/src/contract/client-failure.ts` 的 `ClientFailureCodes`（**不在** `error-codes.ts` 里——那份词表的每个码都对得上一个 Java 常量与一处抛出点，掺进前端独有的码就要靠豁免清单让核对通过）。四个成员：`RESPONSE_VALIDATION_FAILED`（后端 2xx 但 payload 不符合 OpenAPI 契约，zod responseValidator 抛出；dev 完整打印 issues 到 console.warn，生产 console.error 打可 grep 上报锚点；归一化 ApiError 的 status 取响应状态；读路径按查询错误交给渲染层降级，写路径强抛）、`NETWORK_ERROR`（fetch 直接失败，认不出的无响应失败一律归它）、`REQUEST_TIMEOUT`（ky 的 10s timeout）、`REQUEST_ABORTED`（TanStack Query 的 signal 透传进 SDK 后取消在途请求；**不计进接口错误率**）。分族的原因是三者用户动作互斥（检查连接 / 重试 / 什么都不说），此前它们共用一个 `status === 0` 分支，用户看到的是同一句通用文案。两者在取文案这一步不分家（`errorTextPlan` 只看有没有 catalog 条目）。

- **[GEN-72]** 撞唯一索引（值已被占用）的写接口，一律从 `infra.db.DuplicateKeys` 出，两个方法按**用户手里有没有可改的输入框**分：有框可标红的走 `fieldDuplicated(action, field, detail)`——409 + `errors[{field,message}]`，前端把这句话落到那个输入框上（`serverFieldErrors` 只读 `errors[]`、与状态码无关）；点了按钮 / 拨了开关、没有框可标的走 `conflictOnDuplicate(action, detail)`——409 + 一句 toast。**两者的状态码都是 409**（撞唯一索引是资源状态冲突，RFC 9110），分岔落在带不带 `errors`、不落在状态码上——400 说的是「请求本身非法」，而这请求完全合法（只是那个值被别人占了）。`field` 是消费方表单/DTO 的机器字段名（如 `name` / `value`），不是中文标签。落点：类目名 / 属性名 / 属性值已带 `errors[field]`（`categoryService` / `categoryAttrService`），评价已从手工 catch 收进 `conflictOnDuplicate`；进行中售后单、默认地址、默认推荐词条、运单号、SKU 编码是按钮 / 批量类，不带。**未收编的两处**：券领取与店名 / 工号仍各写 catch——它们的码写死在抛出点（`ErrorCodes.X`），转手会让码从参数来、成为新导管（`ErrorCodeVocabularyTest` 的白名单是等式），要收编得先登记理由。**与人工幂等键不是一回事**：`DuplicateKeys` 只答「这个键已存在」，不回放「上次的结果」——要无感返回原单的（下单）走 `OrderPlacementService` 的撞键回读，不能用这里的 409。

## 传输与链路

- **[GEN-35]** 传输层全局策略：请求超时 10s；仅幂等 GET 在 408/429/502/503/504 自动重试 2 次（ky 原生）；所有请求自动注入 `Authorization: Bearer`（有 token 时）、`x-request-id`（值为 UUID 去横线的 32 位 hex，业务未显式传入时——与 GEN-36 后端 `RequestIdFilter` 的校验规则对齐，不合规格式会被后端丢弃重生成）、动态上下文头（如 seller `X-Shop-Id`，业务同名头优先）；请求一律 `credentials: "include"`。
- **[GEN-36]** 后端链路 ID：`RequestIdFilter` 读入站 `x-request-id`（须为 32 位 hex，不合法则自生成 UUID 去横线），回写同名响应头并注入 MDC `trace_id`（进错误信封 `requestId` 与全部日志）；`@Async/@Scheduled` 经 `MdcTaskDecorator` 延续或新起 trace_id。

## 写操作反馈

- **[GEN-38]** 写操作一律用库 `useMutation`，反馈与后果走官方 `meta` 通道（`MutationMeta` 只有 4 个字段，经 `Register` 类型增强，拼错字段编译不过），由 `createAppQueryClient()` 里的全局 `MutationCache` 一次执行，不包 hook 工厂：`meta.success` 有值即 `notify.success` toast；`meta.invalidates` 逐个 `invalidateQueries`；失败且非 `meta.silentError` 时 `notify.fromError(error, meta.error)`。
- **[GEN-39]** 提示语义：`success` 不填即不提示（高频操作如购物车勾选/改数量刻意静默；无 `silentSuccess` 开关，「要不要提示」由字段有/无承载）；`error` 只是**网络层错误的兜底**——`notify.fromError` 的取文案链是 code 优先（命中登记码 → catalog 那句，见 GEN-17 与 i18n.md），`status === 0` **且没有码**才用 `meta.error`（没给则退 `error.network`；断网 / 超时 / 取消三族现在有码，走 catalog），既没 code 命中又不是网络错误时回退后端 `detail`（迁移期兜底，两个 detail 优先码与漏网的那些走这条）。
- **[GEN-40]** `invalidates` 必须传真实 query key（前缀匹配命中整棵子树），不发明 tag 表；「由变量算出的 key」失效用库自己的 `onSuccess`（第 2 参 variables、第 4 参带 client）。不传 `invalidates` = 显式声明不改变任何缓存，不是漏写。
- **[GEN-41]** 全局回调先于逐点回调执行（TanStack 官方顺序），因此：失效发生在调用方 onSuccess 善后之前；想在失败时「先拦住」全局 toast 只能通过 `meta.silentError` 显式声明（逐点 onError 抑制不了），且只有「错误已在别处被用户看见」（表单内联报错、登出后已在登录页）才允许用它。
- **[GEN-42]** 乐观更新固定 `optimisticListMutationOptions` 一次实现官方三步（onMutate 取消在途→快照→patch；onError 回滚；onSettled 失效），领域只供「怎么 patch」，反馈仍归全局。
- **[GEN-43]** 危险操作二次确认走全局 `confirm({ title, description, confirmText, action })`（与 notify 同级收口，根布局只挂一份 `<ConfirmDialogHost />`）：`action` 传 `mutation.mutateAsync(...)`——promise 期间按钮转圈、成功关面、失败保持打开等重试（错误提示已由全局弹过不重复）；只在客户端事件回调里调。

## 错误呈现

- **[GEN-44]** `throwOnError: throwWhenNoData` 是全局默认（`createAppQueryClient`）：只有「一条数据都没有」时才把查询错误抛给边界；有旧数据的后台重取失败不炸页。判据逐字等同官方 suspense 内部默认，`useSuspenseQuery` 用自己的同名判据覆盖、不受客户端默认影响。
- **[GEN-45]** 退出默认的唯一判据是「头上有没有可接的边界」：页面主体→路由 `errorComponent`（`RouteErrorFallback`）；区块/弹窗内部件→`QueryBoundary`（`@shop/app-kit`）；角标/收藏心形等无边界附属件必须显式 `throwOnError: false` 就地渲染 isError + 官方 `refetch()` 重试。`useSuspenseQuery` 要退出默认只能在调用点内联写（写进共享 options 静默失效）。
- **[GEN-46]** 查询默认兜底：`staleTime: 10s`（挡 mount 即重拉；结算预览类显式 `staleTime: 0`）、`retry` 保持库默认 3 次指数退避（404 有业务含义的查询显式 `retry: false`）。
- **[GEN-47]** 错误重试与刷新分道：`invalidateQueries` 只用于 mutation 之后刷数据；查询失败态的「重试」由边界的官方 reset 完成（Router `reset()` + `QueryErrorResetBoundary.reset()`，三端 Provider 树已挂、`QueryBoundary` 自带一层）。

## 业务事件日志

- **[GEN-48]** 业务事件日志的唯一出口是 `BizEvent`（`infra.observability`）：`BizEvent.of("领域.事件").put("k", v)…emit()/warn()/error(cause)` 一次调用写完字段并打出那行。值为 null 即跳过该键，UUID/数值/枚举直接传，调用点不转字符串；`message` 由同一批字段生成（事件名 + 按写入顺序的 `k=v`），**调用点不写文案**——分成两份写就一定会漂（`shop_review.decided` 曾字段写 `decision=APPROVED`、文案打 `status=TRADING`，读文案的人拿到的是店铺营业状态）。信封字段（trace_id/version/env）仍由 RequestIdFilter 经 `MdcScope` 写，`MdcScope` 不再拿来手写 event：把「埋字段」和「打那行」拆成两步之后，忘了第二步就是一个静默丢失的事件（MDC 里写过了、日志里根本没有）。输出 ECS JSON，`event` 是检索/聚合/告警的唯一依据。
- **[GEN-49]** 事件命名：`领域实体.动词过去式`（成功/中性）与 `领域实体.动词.failed`（失败）；点分小写短标识、非中文非函数名，段内允许多词蛇形（`order.receiver_phone_revealed`），但段首段尾不能是下划线——这条形状由 `BusinessEventCatalogTest` 的正则判，不靠读注释。失败事件必带枚举化 `reason`；因渠道或异常而失败的那些再补 `error.type`/`error.message`。成功事件必带实体 ID。同一件事的多条路径共用一个事件名，用 `via`/`reason` 区分，不另起名字（另起会让聚合要先知道有几条路径）。
- **[GEN-50]** 事件目录只有一份：[business-event-logging.md](../conventions/business-event-logging.md) 的「已有事件目录」表，业务规则文档**不再抄第二份字段表**（这一条曾把十个事件连字段抄进 crosscut，代码改了它不会红）。规则文档讲到后果时指名单个事件是可以的——它是那条规则的凭据，不是一份目录。表与代码由 `BusinessEventCatalogTest`（无库、纯文本扫描）逐条核对：事件名双向相等、表里列为必带的字段每个埋点都写、埋点写出的字段表里都列着、列为可选的至少有一个埋点真写、一个事件名在表里只能有一行、规则文档反引号点名的事件目录里都得有（末段词表取自目录本身，故库路径 `account.users.deletion_requested_at` 这类同名形状不会被误判）。这里只记判据：值得立事件的是钱（`payment.refunded` / `payment.refund.failed`）、不可逆（`user.deleted`）、以及「谁动了谁的数据」（三条 `*_revealed`、`shop_review.decided`、两条 `*.status.changed`）；新增公共出站依赖必须先补埋点再上线。
- **[GEN-51]** 日志红线：不往 MDC 放密码/token/身份证号等敏感信息。手机号后 4 位掩码的唯一后端出口是 `PhoneNumber.mask()`，现行 9 个调用点（`/me` 出参、开发态短信日志、重置密码发送、登录失败与登录限流两条事件出口、卖家订单列表行、卖家订单详情的卖家视角、平台审核队列出参、店铺子账号列表的掩码行）；口径只有一条：**任何批量出参都不带别人或买家的手机号明文**，明文只能逐条显式索取且取用留痕（买家侧 ORD-62，卖家侧 ACC-79）。子账号列表里没有「操作者自己那行」可留明文——店主不是子账号本人，所以那一列整体掩码。前端掩码同样只有一个出口：`@shop/common` 的 `maskPhone` / `MASK_SEGMENT`（位数不足原样返回，不伪造掩码——与后端相反的那条兜底是各自的取舍，不是漂移）。`ui-web` 的 `MaskedValue` 因刻意零内部依赖另持一份 `MASK_SEGMENT`，由 `shared-vocabulary.test.ts` 钉「与 common 逐字节相等」。全局敏感字段审计仍列为延后项。

## 操作审计（audit）

- **[GEN-65]** 治理动作（封号、员工创建/调权/禁用、券作废、店铺审核决定、平台封店/解封、物流异常处置、轨迹补录）必须落一行 **append-only 审计账本**：写入只经 `audit :: api` 的 `RecordAuditCommand`，**与动作同事务**（`Propagation.MANDATORY`）——动作回滚则账本一起回滚，「动作没发生却留下一行账」比缺一行更坏（查出来是假账）。为此不走事件：事件的语义是 at-least-once 的异步投递，两头都可能偏（动作成了但监听没跑 / 动作回滚了账本里有行）。
- **[GEN-66]** 动作名与目标类型是同一格，词表是 `audit.api.AuditAction`（每项自带 `AuditTargetType`）：调用点**不能自己传 targetType**，它由 action 决定（一个动作不可能既动买家又动店铺）。两份写法就是两组查不到的账，审计查询按 `action` 归组。
- **[GEN-67]** 账本**只读**：`AuditRecordMapper` 不暴露任何 update/delete，`review.reviews` 之外没有第二个真相；追加只指追评/回复那类 append（本模块只写 insert）。绕过它去改就等于没有审计。
- **[GEN-68]** 敏感字段在**写入侧**就只落掩码：`detail` 是自由文本，调用点必须先掩（手机号 `PhoneNumber.mask()`、工号掩码）再传；审计模块不解析、不还原，只忠实存。`operator_name` 是**展示名快照**（员工改名/删除后账本仍要能读懂「谁做的」），查无此人时为 null，前台显「未知操作人」——宁可少一个名字，也不因为查不到名字就让整个动作回滚。
- **[GEN-69]** 审计**不等于**业务事件日志（GEN-48~51）：事件回答「系统发生了什么」，可检索但随日志保留期滚失；账本回答「谁对谁做了什么」，要能按操作人/对象/时间反查与导出。两者不合并。同理评价（REV-17）不进账本：买家与卖家之间的内容往来不是平台治理动作，混进去会让审计查询被无关行淹没。
- **[GEN-70]** 审计查询入口只读本模块 schema：行里的 `target_id` 是不带语义的主键文本（跨模块对象），**不回查各模块表**（那会让审计入口欠每个模块一份依赖）；需要上下文时按动作去对应页面看。筛选（操作人/目标/动作/时间窗）与排序的组装收在 mapper（`selectPageAdmin`），service 只做枚举解析与出参形状；时间窗取闭开区间 `[from, to)`（前端时间选择器给的是精确时刻，不按分钟截断）。
- **[GEN-71]** 导出在管理端，且**导出前二次确认**：审计是追责材料，导出意味着这批记录离开系统被复制走，而「我导了筛选条件之外的东西」只有一次显式确认能挡；确认框里写清范围与条数上限（单次上限 `EXPORT_ROW_LIMIT`，超限提示收窄筛选而不是静默截断）。CSV 拼接在前端（`apps/admin/src/audit/export.ts`，RFC 4180 转义 + BOM），真要导十万行应改走后端导出任务而不是让浏览器拼。

## 入站校验词表

- **[GEN-52]** 一条形状规则只有一处定义，且定义住在**持有该概念的领域类型**里：DTO 的 `@Pattern`/`@Size` 引用常量、不抄字面量。现行词表出口——`PhoneNumber.CHINA_MOBILE_PATTERN` / `PhoneNumber.CONTACT_PATTERN`（ACC-40）、`RegionRegistry.CODE_PATTERN` / `PREFIX_PATTERN`（LOG-48）、`cms.dto.LinkTarget.PATTERN`（CMS-05）、`UserCouponStatus.PATTERN`（CPN-52）、`ProductSort.PATTERN`（PRD-63）、`ProductAdminSort.PATTERN`（PRD-79）、`ProductFieldRules.{NAME_MAX,NAME_MESSAGE,SELL_POINT_PATTERN,SELL_POINT_MESSAGE}`（PRD-20/42）。`LinkTarget`、`ProductSort` 是为持词表新建的类型，但**字段类型仍是 String**——换成枚举会改 OpenAPI 形状；它们另提供 `fromWire` 把词表解析收成一处（`ProductSort` 顺带替掉 switch 里散落的字符串字面量）。
- **[GEN-53]** 注解元素值必须是编译期常量表达式（`String.join`、stream 推导都非法），所以「常量逐字节等于枚举名 / wire 值 / 真实区划码」这条等式编译期查不了，改由 `ValidationVocabularyTest`（无库、反射+扫源码）在测试期钉：词表与枚举名逐字对齐、买家/卖家两份排序词表与 product 模块里的 switch 分支标签一一对应（排序 SQL 现住 `ProductMapper`，库存那半边的内存定序住 `ProductQueryService`；门禁扫整个模块、不点名文件——分支从一个文件搬进另一个是常事，点名的那两条会空转还照样绿。Java 对 switch **语句**不做穷尽检查，加了枚举值忘了加分支只有这里能红）、手机号三档放行的号 `PhoneNumber.of()` 必接得住、区划码形状与 `regions.json` 真值同形。该测试自带反空转断言（常量引用数为 0 就红），并规定「同一个字面量不许出现在两个文件里」。**它与契约无重叠**：形状对不对由 `ApiDocsContractTest` 判，本条只判定义在哪。
- **[GEN-54]** 改词表 = 改接口：`@Pattern`/`@Size` 的值会导出进 `openapi/api-docs.json` 和生成的 zod（`packages/api/src/sdk/zod.gen.ts`），动一个字符就得先起后端跑 `pnpm sdk:gen`，否则 `ApiDocsContractTest` 把不一致判红。因此「内部收口」级别的改动，替换值必须与被替换字面量**逐字节相同**（含 message 文案）。形似而概念不同的规则**不许合并**：商家地址邮编与区划码同为 6 位数字，各留一份，合并会让一处放宽静默改掉另一处。声明式形状门与权威判定按概念分层而不是各写一遍——区划码「形对但不存在」（`RegionRegistry.requireValidCode`/`requirePrefix`，400 话术唯一出口，service 不再各写 `validateRegion`）、联系电话「形松但归一化后不是号」（`PhoneNumber.of()`）都由领域类型补第二道门；空格/括号不在联系人档门内是**现行契约**而非疏漏，放宽属接口变更。
- **[GEN-55]** 一条业务事实只打一行：同一事实的第二份拷贝要逐处删掉。登录失败曾先按分支打一句人读 warn、再打一条同因事件（两份 `reason`，改一处另一处静默过期），现在只剩事件；下单曾打「单数 + 总应付」的汇总行，而每单的 `order.created` 已各自带 `pay_amount`，单数与总额由检索侧按 `checkout_key` 聚合，汇总行删。判据：如果第二行只是第一行的另一种措辞或它的计数/求和，它就不是新信息。留在普通 `log` 里的必须是另一类东西（诊断、流程叙述，见 GEN-50 的「什么才立一条事件」），不是同一事实的第二次抄写。

## 数字词表与定时扫描

- **[GEN-56]** 长度、数量与金额之外的数值边界各有具名 Java owner，DTO 注解只引用它。`FieldRuleVocabularyTest` 检查 Java 常量＝注解值＝已发布契约，并确认入口上限不超过迁移中的列宽；数据库本身参与裁剪的件数 CHECK 必须与入口相等。前端的结构化数值由 OpenAPI 生成，不再手写第五份；例外见 GEN-64。同值不代表同义，只有业务明确要求相等的规则才建立跨概念检查，例如购物车条目数与下单行数。
    - **形似而概念不同的数字不许合并**（同 GEN-54）：昵称 30 与人名 30、邮编 6 位与区划码 6 位各留一份，合并会让一处放宽静默改掉另一处。
    - **入站门比落库列宽更松是一类真 bug**，且没有任何测试会红：买家回寄的快递公司名门是 50（`ReturnGoodsRequest.logisticsCompany`），归一后的名字除了进 `logistics.shipments.carrier_name VARCHAR(50)`，还冗余投影一份进 `aftersale.tickets.return_logistics_company`，而后者建表时从旧列照搬成 `VARCHAR(32)`——33~50 字的公司名过得了校验、撞在列上，买家照抄面单全名就拿到一个 500。V66 把投影列加宽到 50 对齐（迁移只增不改，本机库待下次起 Flyway 才执行；加宽 varchar 是元数据操作，不重写行），这条等式自此由本条的门禁守着（把 V66 撤掉，`FieldRuleVocabularyTest` 立即红在这一格）。
    - 数字属于接口：改一个数就要先起后端跑 `pnpm sdk:gen`（否则 `ApiDocsContractTest` 红），所以内部收口级别的改动替换值必须与被替换字面量逐字节相同。
- **[GEN-57]** 定时扫描**逐笔隔离**：一批里有一笔抛异常只丢那一笔，不丢整批——三条售后超时线、订单超时、到期注销都走唯一出口 `common.Sweep.each(log, 线名, rows, 行标识, 落点)`，它 catch `RuntimeException`、单笔一行 error 带行标识、批末补一行 warn 交代「多少笔里失败了几笔」，返回值仍只算真正落成的笔数。判据来自查询形状：扫描一律按到期时刻升序加 `LIMIT` 取头部，所以没有隔离时一笔稳定失败的行**每轮都排在队首**，后面的行永远轮不到——作业照跑、照打日志，整条线却已停摆。注销侧尤其要命：卡住的正是冷静期早已满期的那批（`AccountDeletionService.sweep` 的注释长期写着「第 3 笔失败不牵连前 2 笔」，而循环里没有 try/catch）。隔离不等于吞异常，也**不引入死信或重试计数**：下一轮同批重扫就是重试通道。刻意不走这条的有两处——`TrackingPollJob`（外呼可用性与截止时刻的钩子不同形，套模板要配的开关比省下的代码长）与 `ShipmentIssueService`（它要把 `DuplicateKeyException` 折成「已登记」，通用 catch 会把这条正常路径变成失败）。
