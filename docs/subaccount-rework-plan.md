# 卖家子账号体系改造计划

> 按「淘宝式」对齐卖家子账号体系（2026-10-13 拍板）：独立子账号凭证 + 建号/手机验证激活 + 独立登录 + 停用/密码重置 + 操作日志，另有两个带触发器的后置阶段。
>
> **进度（2026-10-13）**：阶段一 + 阶段三**已落地**（取舍与代价记在 [ADR-0006](adr/0006-subaccount-identity.md)，规则条目见 [account.md ACC-10 ~ ACC-14](business-rules/account.md)、授权矩阵 [§二/§七](conventions/authorization-matrix.md)）；阶段二、四、五仍待触发。
>
> 本文是**路线图**，不是规范：每阶段开工前立 ADR / 改业务规则条目，落地后同步
> [authorization-matrix.md](conventions/authorization-matrix.md)（§二 主体与角色、§三 卖家表、§七 `/shops` 登记、§八 留白）。
> 阶段顺序与触发条件以本文为准；实现细节在各阶段自己的 ADR 与改动里。

## 现状与目标

|          | 现状（改造前）                                          | 目标（淘宝式）                                          | 状态               |
| -------- | ------------------------------------------------------- | ------------------------------------------------------- | ------------------ |
| 凭证     | 一套账号（手机号 = 身份），子账号 = 普通账号 + 成员关系 | 独立子账号凭证（登录名 + 密码），工作身份与私人身份分离 | 已落地             |
| 建号     | 店主邀请 → 对方确认                                     | 店主创建 → 员工手机验证激活                             | 已落地             |
| 登录     | 普通登录 + `X-Shop-Id` 选店                             | 独立登录入口（子账号凭证登录工作台，店自带在凭证上）    | 已落地             |
| 停用     | 只有移除（删关系）                                      | 停用/启用中间态 + 店主重置密码                          | 已落地             |
| 留痕     | 订单有库内流水但无出口；其余动作无流水                  | 店主可查的子账号操作日志                                | **未做**（阶段二） |
| 数据范围 | 成员看全店                                              | （触发器）「全部 / 仅分配给我」档位                     | 待触发             |
| 角色     | 5 个功能码直接勾                                        | （触发器）角色/岗位模板                                 | 待触发             |

已对齐、不动：授权开关模型、全量替换、收权下一请求生效、越权隔离（双锁）、离职回收。

## 阶段一：独立凭证（地基）—— 已落地

**验收口径**（全部有端到端用例，`ShopSubaccountIT`）：店主创建子账号（设登录名 + 密码）→ 员工首次登录激活（短信验证本人手机号）→ 用子账号凭证登录卖家工作台 → 子账号不能登录买家端（纯工作身份）→ 店主可停用/启用、重置密码。

**激活口径**：短信验证本人手机号，复用现有短信通道（含限流）与图形验证码；**身份证不入库**——平台的身份锚点本来就是手机号（与买家账号同一套信任模型），没有实名设施也不自建（存身份证号 = 敏感个人信息，合规成本远大于收益）；同店一个手机号只能激活一个子账号。激活时记录 `verified_at` 作为追责锚点；实名认证留到「追责到自然人」成为硬需求时再立（届时接三方认证，不自存号）。

**实际落成的形状**（计划里待定的两处已定）：

- **登录名全局唯一、不拼店名**。淘宝那个 `店铺名:子账号名` 在原方案里是「待 ADR 定」；结论是不采用——店名在 ACC-74 的重提流程里可改，登录名跟着漂等于员工下次登不上。
- **过滤器链不是「替换」而是加第三条**：店主仍走「用户 JWT + `X-Shop-Id` + `shop_members` 的 OWNER 行」，子账号走「凭证自带店铺」；`SubaccountAuthFilter` 在 `/seller/**` 上先跑，命中就打标记让 `JwtAuthFilter` 让位，两条身份链不会同时装载。
- **认证端点落在 `/auth/subaccount/**`**（不是 `/seller/auth/**`）：子账号只吃认证不吃授权，进受判权保护的命名空间就得给每个自助端点写权限码或再造一份自服务豁免清单；`/auth` 本来就不在受保护命名空间里。

**改造面清单（已全部落地）**：

- **auth 域**：第三种凭证（`kind=subaccount`）与登录接口 `/auth/subaccount/{login,activate,sms-code,refresh,logout,me,password}`；子账号不走短信自助找回，走店主重置；
- **过滤器链**：`SubaccountAuthFilter`（新）+ `JwtAuthFilter` 让位 + `ShopMembershipFilter` 双身份装载（店主 / 子账号自带店铺，带别家店 `X-Shop-Id` 403）；
- **权限解析**：`SellerPermissionResolver` 从子账号凭证行读码；**判权每请求实时求值的口径保持不变**（收权/停用下一请求生效）；
- **店铺模块**：邀请端点（`/shops/invites/**`）退场，新增 `/shops/{shopId}/subaccounts/**`（建号/列表/改权/停启用/重置口令/取号码明文/移除）；`shop_members` 只剩 OWNER 行；
- **前端**：卖家端登录页（店主 / 子账号两个顶层 Tab，子账号撞 `SUBACCOUNT_NOT_ACTIVATED` 就地切激活步骤）+ 子账号管理页（创建/停用/重置密码/勾权限/移除/取号码明文），会话种类标记决定 refresh 端点与是否注入 `X-Shop-Id`；
- **门禁联动**：`PermissionVocabularyTest`、`AdminEndpointGuardTest`、`SellerSubaccountPermissionIT`（收权与停用即时生效）、`ShopSubaccountIT`（端到端）、`authorization-matrix.md` 四节同步。

**ADR**：[0006 卖家子账号：身份怎么承载](adr/0006-subaccount-identity.md)（统一账号 + 成员关系 vs 独立凭证 vs 复用员工体系 vs 企业 IdP）。

**明确不做**：双轨与迁移脚本——按项目规则（无需向后兼容、无需数据迁移），旧成员关系直接替换。

## 阶段二：操作日志（店主可查「谁干了啥」）

- **记什么**：卖家工作台全部写操作——商品改价/上下架/规格、发货、售后裁决、券操作、地址与运费模板、子账号与权限变更（含权限调整前后值）；
- **放哪**：新表（店铺维度、append-only）+ 查询端点；**不进治理账本**（`audit.audit_records` 的边界见 GEN-65/69：账本只记平台治理动作）；
- **与既有流水的关系**：`orders.order_status_log` 已有逐笔（前态/后态/动作/发起方），但**只有 `actor_type`（BUYER/SELLER/SYSTEM）、没有操作人 id**——所以它不是「加一个查询出口即可」，要加列或另起表（阶段一施工时核实过）；售后协商的 `ticket_events` 不动；
- **可见性**：店主可见全部；成员是否可见「自己的操作」随实现定；
- **前端**：卖家端「操作日志」页。

## 阶段三：停用中间态 —— 已并入阶段一

原计划单列，实际与阶段一同批落地（同一张表、同一套状态机，拆开做等于同一格动两次）：

- 子账号状态 `PENDING_ACTIVATION` / `ACTIVE` / `DISABLED`：停用 = 保留凭证、立即失效（判权每请求查库）、可解冻；与「移除」（删凭证行）区分；
- 启用是**有条件**的：没验过号的行回 `PENDING_ACTIVATION`（不让「启用」成为绕过手机验证的后门），验过号的回 `ACTIVE`；
- 停用刻意**不吊销 refresh token**：子账号 access 只活 10 分钟且每请求重查状态，停用下一请求即生效（员工禁用要同步吊销是因为员工 access 活 8 小时）。

## 阶段四：数据范围档位（触发器：跟单业务出现）

- **前置业务**：「订单分配给谁」——先立客服跟单需求（分配/接待/绩效），权限档位跟着它走；没有分配，「仅自己的单」不存在，单独做权限开关是空开关；
- **做成什么样**：订单模块增加「全部 / 仅分配给我」档位；mapper 过滤从「店铺」扩展到「店铺 × 分配」；
- **触发器**：第一个多客服店铺出现，或跟单需求进入 TODO。

## 阶段五：角色模板（触发器：权限码拆细）

- 角色 = 功能码（× 数据范围）的打包，预设岗位（客服/运营/仓储/财务）+ 自定义；
- **触发器**：权限码从 5 个合并码拆细之后才有意义（拆码触发器见 [permission-codes.md](conventions/permission-codes.md)：第一个「能看不能改」岗位出现）。

## 不做

- **部门树**：不做（几十人店铺才有意义）；
- **多店/主体层**：另行讨论，触发器 = 第一个多店商户（见 [authorization-matrix.md](conventions/authorization-matrix.md) §八 同族留白）。
